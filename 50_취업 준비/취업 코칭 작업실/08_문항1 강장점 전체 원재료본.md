# 문항 1 강·장점 전체 원재료본

> [!warning] 이 문서는 제출용 자기소개서가 아니다
> 분량, 문장 완성도, 중복을 제한하지 않고 장운호의 강점·사례·약점·사실 경계를 모두 펼쳐 놓은 삭제 전 원재료다.  
> 여기서 억지로 하나의 사례에 사람 전체를 끼워 맞추지 않는다. 이후 지원 직무와 글자 수가 정해지면 문단을 하나씩 지운다.

## 문항

> **해당 분야에 지원한 본인만의 강/장점에 대해 작성해 주세요.**

## 이 문서에서 지킬 경계

- 현재 가장 직접적으로 연결되는 직무는 **기술 취약점 진단·정보보호 컨설팅**이다.
- 취약점 관리·보안 자동화·AppSec는 인접 관심 분야이자 성장 방향이다.
- 순수 모의해킹 전문가, Red Team, SOC 분석가, 클라우드 아키텍트, DevSecOps 실무자로 이미 검증됐다고 쓰지 않는다.
- 팀 결과, 개인 행동, AI가 만든 부분, 설계만 한 부분, 실제로 실행·검증한 부분을 분리한다.
- 3차 프로젝트는 진행 중이다. 이미 확인된 행동 근거는 쓸 수 있지만 최종 성과로 포장하지 않는다.
- 장점만 나열하지 않고, 같은 성향이 과해졌을 때 생기는 약점과 이를 관리하는 방법도 함께 남긴다.

## 1. 장운호에게는 적어도 이런 면들이 같이 있다

장운호는 하나의 키워드나 사례로 설명하기 어려운 사람이다. 적어도 다음과 같은 면들이 함께 있다.

1. **모르는 것을 아는 척하기보다, 무엇을 모르는지 드러내려고 한다.**  
   처음 보는 기술을 바로 구현하기보다 그것이 무엇이고 왜 필요한지 묻는다. 설명을 듣고도 납득되지 않으면 다시 묻고, 비슷해 보이는 개념의 차이를 확인한다.

2. **결과보다 판정 근거를 확인한다.**  
   “동작했다”, “취약하다”, “해결됐다”는 말만으로는 잘 믿지 않는다. 어떤 입력, 응답, 로그, 코드, 상태가 그 결론을 지지하는지 확인하려 한다.

3. **문제를 한 점이 아니라 흐름으로 본다.**  
   웹 요청에서 DB까지, 패킷의 왕복 경로, GitHub의 변경이 ECR과 GitOps를 거쳐 EKS에 배포되는 과정처럼 여러 구성요소 사이의 흐름을 따라가며 원인을 좁힌다.

4. **복잡한 것을 구조로 나눈다.**  
   항목, 증거, 상태, 다음 행동을 문서와 파일로 분리해 다시 찾을 수 있게 만든다. 이는 문서를 예쁘게 꾸미기 위한 취향이라기보다 누락, 과장, 중복 작업을 줄이기 위한 방식에 가깝다.

5. **처음 세운 목표가 틀렸다고 판단하면 방향을 바꾼다.**  
   자동 판정률을 높이는 것이 목표였던 웹 진단 스크립트를, 오탐과 판정 한계를 확인한 뒤 증거 수집기로 낮췄다. 많은 기능을 구현하는 것보다 구현하지 않는 편이 정직한 경우도 인정한다.

6. **AI를 많이 활용하지만, AI의 답을 그대로 자기 실력으로 삼고 싶어 하지 않는다.**  
   AI에게 설명, 코드 초안, 비교안, 문서 정리를 요청하면서도 실제 구조와 비슷한지, 하드코딩된 시연에 불과한지, 다른 해결책은 무엇인지 되묻는다. 본인이 설명하고 재현할 수 있는 범위와 AI가 대신 만든 범위를 구분하려 한다.

7. **실패나 중단을 숨기기보다 그 안에서 판정 기준을 뽑아낸다.**  
   멘토에게 SQL Injection 과정을 제대로 설명하지 못한 일, 웹 진단 자동화가 중단된 일, GNS 통신 장애를 최종 성공까지 닫지 못한 일을 완성된 성과처럼 포장하지 않는다. 대신 왜 막혔고 다음에는 무엇을 확인해야 하는지 남긴다.

8. **한 문제를 깊게 파는 만큼 범위를 크게 잡는 위험도 있다.**  
   정확성을 높이려다 계획과 문서가 커지고, 모든 불확실성을 없애려다 결정이 늦어질 수 있다. 이 성향은 분명 약점이지만, 최근에는 완료 기준, 증거 수준, 보류 항목을 나눠 관리하는 방향으로 바꾸고 있다.

9. **공격 자체보다 공격이 성립하는 이유와 그 증거에 더 관심이 있다.**  
   단순히 Payload를 성공시키는 것보다 입력이 어느 해석기로 넘어갔는지, 참·거짓 응답이 어떻게 달라졌는지, 로그에 무엇이 남았는지, 조치 후 같은 공격이 왜 막혔는지를 알고 싶어 한다.

10. **아직 희망 직무를 과장해서 확정하지 않았지만, 반복해서 에너지가 생기는 문제 유형은 분명하다.**  
    애매한 진단 결과를 검증하고, 취약점이나 장애의 흐름을 추적하고, 자동화 결과의 신뢰성을 높이는 일에 오래 머문다.

## 2. 문항 1 무제한 통합 초안

저의 강점은 책임감, 끈기, 분석력처럼 하나의 단어로만 설명하기 어렵습니다. 하나의 사례가 저를 온전히 설명하지도 못합니다. 대신 여러 프로젝트에서 반복된 문제 접근 방식은 비교적 분명합니다. 저는 결과를 빨리 만드는 것보다 그 결과가 왜 나왔는지, 무엇으로 증명할 수 있는지, 어디까지를 사실이라고 말할 수 있는지를 확인하려는 사람입니다. 모르는 기술을 만났을 때 사용법부터 외우기보다 먼저 그 기술이 어떤 문제를 해결하며 내부에서 어떤 흐름으로 움직이는지를 이해하려고 합니다. 결과가 예상과 다르면 정답을 맞히는 데 그치지 않고 입력과 출력, 권한과 상태, 요청과 응답 사이의 관계를 따라가며 원인을 좁힙니다. 이 성향은 때로 진행 속도를 늦추지만, 진단 결과의 오탐을 줄이고 제가 한 일을 과장하지 않게 만드는 기반이 되었습니다.

저는 원래 건축학과 학생이었고 2026년 2월 말부터 보안 위협 대응을 위한 보안 엔지니어 교육을 받기 시작했습니다. 처음에는 클라우드 보안이나 DevSecOps라는 직무명에 관심이 있었지만, 무엇을 실제로 좋아하는지는 알지 못했습니다. 교육과 프로젝트를 진행하면서 제가 반복해서 붙잡는 문제는 특정 제품이나 직무명이 아니라는 것을 알게 되었습니다. 저는 “이 설정이 맞는가”, “이 응답만으로 정말 취약하다고 할 수 있는가”, “공격이 성공했다면 어느 지점에 어떤 흔적이 남아야 하는가”, “조치됐다고 말하려면 무엇을 다시 확인해야 하는가” 같은 질문에 오래 머물렀습니다. 제가 보안 분야에서 가진 첫 번째 강점은 이미 많은 것을 안다는 것이 아니라, 모르는 상태를 숨기지 않고 질문을 더 구체적인 검증 문제로 바꾸려는 태도입니다.

교육 초기에 저는 JSP 환경의 `application.properties`에 저장된 DB 애플리케이션 계정을 어떻게 보호할지 생각한 적이 있습니다. 처음에는 웹 서버의 다른 디렉터리나 웹 서버와 통신 가능한 별도 서버에 정보를 두는 방법을 떠올렸습니다. 그러나 곧 `application.properties`를 읽을 정도로 서버가 침해됐다면 같은 서버의 다른 위치나 연결된 서버도 안전하다고 단정할 수 없다고 생각했습니다. 정답을 떠올리지 못해 포기했지만, 이후 환경 변수와 별도의 Secret 관리 방식을 알게 됐습니다. 여기서도 저는 환경 변수로 옮기면 완전히 보호된다고 이해하지 않았습니다. 애플리케이션 프로세스나 서버 권한이 탈취되면 환경 변수 역시 읽힐 수 있으므로, 실제 보호는 코드와 Secret의 분리뿐 아니라 접근 권한 최소화, DB 계정의 권한 제한, 조회 기록, Secret 회전과 재배포 절차가 함께 있어야 한다고 보게 됐습니다. 첫 번째 프로젝트에서는 이 생각을 바탕으로 DB·메일 설정을 애플리케이션 코드에서 분리하고, Tomcat 설치, Git 저장소 Build, WAR 배포, NFS와 로그 설정, 최종 확인을 하나의 Bash Script로 묶었습니다. 현재 확인된 것은 Script의 구조와 문법이며 모든 환경에서 완전한 무인 배포를 보장하는 것은 아닙니다. 그러나 반복 작업을 한 번의 실행 흐름으로 만들고, 인터넷 연결이 필요한 단계와 내부망 전환 후 단계를 구분한 경험은 문제를 재현 가능한 절차로 바꾸는 제 성향을 보여줍니다.

서버가 망가지거나 침해됐을 때 어떻게 대응할 것인지 묻는 문제에는, 클라우드나 가용성을 제대로 배우기 전이었는데도 “고쳐 쓰기보다 부수고 새로 만든다”고 답했습니다. 당시에는 단순한 직감이었지만 이후 Immutable Infrastructure, 격리, 증적 보존, 안전한 Image와 IaC를 통한 재배포, Secret 회전이라는 개념을 배우면서 직감을 더 정확한 절차로 보정했습니다. 지금은 침해 서버를 바로 삭제하는 것 또한 옳지 않다는 것을 압니다. 먼저 격리하고 로그와 스냅샷 등 증거를 보존한 뒤 원인을 확인하고, 취약점을 제거한 기준 Image나 코드로 새 환경을 만들고, 노출 가능성이 있는 자격 증명을 회전한 뒤 같은 공격을 다시 검증해야 합니다. 저는 처음 떠올린 답을 정답으로 고집하기보다, 뒤에 배운 지식으로 어느 부분이 맞고 무엇이 빠졌는지를 다시 정리하는 편입니다.

두 번째 프로젝트에서는 KISA 기준으로 온프레미스와 AWS 환경의 보안 진단, 조치, 보고서화를 수행했고, 저는 CARE 웹 애플리케이션의 웹 취약점 점검을 깊게 맡았습니다. 웹 애플리케이션에 특정 취약점을 유발할 기능이 없으면 해당 항목을 점검 불가로 넘길 수도 있었지만, 저는 일부 항목에 검증용 기능을 의도적으로 추가해 취약한 상태와 조치된 상태를 비교하고 싶었습니다. 이때 AI에게 단순히 취약 코드를 만들어 달라고만 하지 않았습니다. 만들어진 기능이 결과를 보여주기 위해 하드코딩된 시연인지, 실제 웹 애플리케이션에서 존재할 법한 구조인지, 적용한 조치가 여러 대응 방법 중 어느 유형인지, 다른 대응 방법은 무엇인지 계속 물었습니다. 제가 중요하게 본 것은 취약점을 많이 만들었다는 사실보다, 입력이 실제 해석기까지 도달해 취약한 동작이 발생하고 조치 후 같은 입력의 의미가 달라지는 구조였습니다.

이 과정에서 LDAP Injection은 오히려 구현하지 않았습니다. 구현 전에 AI에게 LDAP와 LDAP Injection을 설명해 달라고 요청했고, 사용자 입력이 LDAP Filter에 결합되어 조회 의미를 바꾼다는 구조가 SQL Injection과 닮았다고 느꼈습니다. 그러나 CARE 환경에는 실제 LDAP Server와 Filter Parser가 없었습니다. 단지 특정 문자열을 만나면 성공한 것처럼 응답하는 Mock을 만들면 취약점을 재현한 것이 아니라 정답을 하드코딩한 시연에 가까워질 수 있다고 판단했습니다. 그래서 LDAP Injection은 실제 구현에서 제외하고 SQL Injection과의 공통점과 차이를 비교하는 학습으로 남겼습니다. 이것은 제가 모든 항목을 구현했다는 사례가 아니라, 새로운 기술을 이해한 뒤 현재 환경에서 진짜 검증이 가능한지 판단하고, 학습 가치가 낮은 가짜 구현은 하지 않기로 결정한 사례입니다.

반대로 OS Command Injection은 구현할 가치가 있다고 판단했습니다. CARE는 PHP와 Linux에서 실행되고 있었고, 서버 상태 확인을 위해 사용자가 입력한 대상에 `ping`을 실행하는 기능은 실제 애플리케이션에서도 있을 법한 맥락이었습니다. 취약한 상태에서는 `target` 입력이 Shell Command에 문자열로 결합되도록 구성하고 `127.0.0.1;id`와 같은 입력으로 명령이 이어서 실행되는지 확인했습니다. 조치 상태에서는 입력 Allowlist와 Shell Argument 처리를 적용했습니다. 이 사례는 LDAP와 달리 실제 Shell이라는 해석기와 실행 결과를 확인할 수 있었으며, SQL Injection과도 영향과 조치 위치가 달랐습니다. 같은 “Injection”이라는 이름 아래에 있어도 실제 해석기, 공격 결과, 방어 방식이 다르다는 것을 비교할 수 있었습니다. 저의 장점은 항목 수를 채우는 것이 아니라, 구현 전에는 환경과 학습 가치를 따지고 구현 후에는 그 구조가 현실적인지를 다시 의심하는 데 있습니다.

SQL Injection 점검에서는 로그인 입력과 게시글 검색 기능을 대상으로 참 조건과 거짓 조건에 따른 응답 차이, 오류 노출, 인증 우회 가능성을 구분했습니다. 단순히 따옴표나 `OR 1=1`을 넣고 화면이 바뀌었다는 사실만 적기보다 정상 입력과 공격 입력을 비교하고, 검색 결과가 어떻게 달라지는지와 로그인 우회가 어떤 의미인지 분리하려 했습니다. 원인은 사용자 입력이 Query 문자열에 직접 결합되는 구조로 보았고, 조치는 Prepared Statement와 Parameter Binding을 중심으로 정리하되 입력 제한, 오류 정보 노출 방지, DB 애플리케이션 계정 최소 권한 같은 추가 통제도 함께 살펴봤습니다. 다만 이 프로젝트를 설명하는 자리에서 멘토가 “어떤 방식의 SQL Injection을 했느냐”고 물었을 때는 제가 수행한 과정을 짧고 정확하게 설명하지 못했습니다. 이 경험은 공격을 한 것과 그것을 이해하고 설명할 수 있는 것은 다르다는 점을 깨닫게 했습니다. 이후에는 error-based, boolean-based, 인증 우회, UNION 기반 접근을 구분하고, 실제로 수행한 범위와 시도하지 않은 범위를 나누어 설명하려고 했습니다.

두 번째 프로젝트에서 저는 21개 웹 점검 항목을 하나의 긴 보고서로만 관리하지 않고 전체 Router와 항목별 노트로 분리했습니다. 각 항목에서 화면, Request·Response, Log, DB, Source Code, 조치 후 재검증 중 어떤 증거가 필요한지 나누고, 현재 확인된 것과 아직 확인하지 못한 것을 표시했습니다. 이 구조를 만든 이유는 문서의 양을 늘리기 위해서가 아니었습니다. “HTTP 200이므로 취약”, “오류가 없으므로 양호”처럼 단일 신호를 결론으로 오해하지 않기 위해서였습니다. 진단자가 바뀌어도 같은 요청을 다시 보내고 같은 증거를 찾아볼 수 있어야 판정의 신뢰성을 설명할 수 있다고 생각했습니다. 선택한 항목은 원인과 조치까지 더 깊게 설명할 수 있게 됐지만, 21개 전체를 동일한 깊이로 완료한 것은 아닙니다. 저는 완료하지 않은 범위까지 제 성과로 넓히는 대신, 실제로 증거를 닫은 항목과 남아 있는 항목을 구분하고 싶습니다.

이 관심은 KISA 웹 애플리케이션 진단 스크립트 개인 확장으로 이어졌습니다. 처음 목표는 결과에 `Manual`로 남는 항목을 줄이고 자동 판정 비율을 높이는 것이었습니다. 그러나 외부의 웹 진단 도구나 실제 점검에서 수동 확인이 남는 이유를 살펴보면서, `Manual`이 단순히 자동화 기술이 부족해서 생기는 쓰레기 상태가 아니라는 점을 알게 됐습니다. 로그인 세션과 사용자 권한, 여러 요청의 순서, DB 상태, 업무 규칙, 상태 변경의 부작용, 테스트 후 원상 복구, 고객이 허용한 공격 범위, 오탐 제거처럼 기계가 단일 요청·응답만 보고 확정하기 어려운 조건이 많았습니다. 같은 HTTP 200도 파일을 받은 것인지, 로그인 화면으로 이동한 것인지, 오류 안내를 정상 페이지 안에 출력한 것인지에 따라 의미가 달랐습니다. 파괴적이거나 업무 영향을 줄 수 있는 검사는 기술적으로 자동화할 수 있어도 승인과 안전 문제 때문에 사람이 확인해야 합니다.

저는 처음에 이 사람의 확인을 AI가 대신할 수 있지 않을까 생각해 개인 프로젝트를 시작했습니다. 고정 Rule보다 AI가 Source, Request·Response, Log, DB 정보와 업무 맥락을 함께 읽는다면 `Manual`을 줄일 수 있다고 봤습니다. 그러나 개발 중 파일 다운로드 항목에서 HTTP 200만으로 취약하다고 판정하는 오탐을 발견했습니다. 정상적인 차단 안내나 로그인 이동도 200으로 올 수 있기 때문에 Status Code만으로는 실제 파일 노출을 증명할 수 없었습니다. Header, Body, Redirect, 로그인 상태, Source Code, DB 상태 같은 추가 증거가 필요했습니다. 이 경험을 통해 “AI를 붙이면 Manual이 사라진다”는 가설 자체도 다시 보게 됐습니다. 증거가 부족하면 AI 역시 그럴듯한 오판을 만들 수 있고, AI가 최종 책임을 질 수도 없습니다.

그래서 프로젝트의 방향을 완전 자동 판정기에서 재현 가능한 증거 수집기로 바꿨습니다. `profile → check → request → evidence → report` 흐름을 분리하고, 실행 Mode 제한, 테스트 Fixture 기록, Cleanup 실패 기록, Secret Redaction, Workflow 회귀 테스트를 추가했습니다. Rule은 반복 가능한 요청과 객관적 증거를 수집하고, AI는 여러 증거를 종합해 오탐 가능성과 후속 검증 절차를 제안하며, 사람은 업무 맥락과 위험을 고려해 최종 판정하는 역할로 나눴습니다. 다만 AI Reviewer Layer는 설계에 머물렀고 실제 완성품으로 구현하지 못했습니다. 이 프로젝트는 중단됐지만, 자동화율을 높이는 것보다 자동화 결과가 무엇을 증명하는지 제한하는 것이 더 중요하다는 판단을 얻었습니다. 저는 계획한 결과를 만들지 못했을 때 실패를 감추기보다, 처음 목표가 왜 부적절했는지 찾아 역할을 다시 정의하는 편입니다.

이 방식은 웹 진단 외의 트러블슈팅에서도 반복됐습니다. GNS 환경에서 상대 Router까지 Request가 도착하고 Reply도 제 Router까지 돌아오는데 Ping이 실패한 문제가 있었습니다. 처음에는 Route 누락처럼 보일 수 있었지만 Packet의 Source와 Destination이 왕복 과정에서 어떻게 바뀌는지 추적하고 양쪽 NAT ACL을 비교했습니다. 그 결과 팀 간 통신 대역까지 양쪽에서 중복 PAT가 적용되어 Reply가 원래 통신과 일치하지 않는 방향으로 변환되는 문제로 좁혔고, 상호 통신 대역을 NAT 대상에서 제외하는 방향을 제시했습니다. 수정 후 성공 Ping까지 확보하지 못했기 때문에 해결 완료 사례라고 할 수는 없습니다. 그러나 보이는 증상만으로 원인을 정하지 않고 Packet Flow와 정책을 대조해 가설을 좁힌 과정은 제 문제 해결 방식을 보여줍니다.

Terraform과 AWS를 학습할 때도 완성 코드를 받는 것보다 Module을 왜 나누는지, Root Module과 Child Module의 책임이 무엇인지, Input과 Output이 어떤 경계를 연결하는지 이해하려 했습니다. AI가 작성한 코드의 비중이 큰 환경도 있었기 때문에 전체 Architecture와 코드를 혼자 작성했다고 말할 수는 없습니다. 대신 `plan`, `apply`, Runtime 확인, `No changes`, `destroy`, 잔존 자원 확인을 통해 코드가 실제 환경에서 만든 결과를 검증하고, 비용과 보안 경계를 직접 승인하는 경험을 쌓았습니다. Kubernetes에서도 명령어 목록보다 Pod, ReplicaSet, Deployment의 관계와 Rolling Update·Rollback, Service와 EndpointSlice, Namespace DNS를 실제 Runtime 상태와 HTTP 응답으로 연결해 이해하려 했습니다. 저에게 학습은 코드를 한 번 실행하는 것이 아니라, 구조를 제 말로 설명하고 상태가 바뀌는 과정을 확인하는 일에 가깝습니다.

현재 진행 중인 3차 프로젝트에서도 같은 성향이 나타나고 있습니다. 이 프로젝트는 아직 완료되지 않았고 최종 성과로 쓸 수 없습니다. 다만 개인 AWS 계정에서 팀원의 Terraform을 선행 통합 검증하면서 Foundation과 매일 생성·삭제할 Runtime을 분리하고, Source Push가 GitHub Actions, ECR, GitOps, Argo CD를 거쳐 EKS에 반영되는 흐름을 확인했습니다. PR을 병합한 뒤 새 Image와 GitOps Revision, Argo CD 상태, Pod Rolling Update, 외부 응답을 연결해 추적했습니다. 이 과정에서 Windows Secret ACL, MariaDB TLS 요구, Argo CRD가 지원하지 않는 필드, ALB에서 Kubernetes Node로 가는 Security Group Rule 누락을 각각 다른 원인으로 구분했습니다. 특히 CloudFront 504를 CloudFront 자체 문제로 단정하지 않고 ALB Target Timeout과 ALB→Node 80/TCP 경로까지 따라가 SG Rule 누락을 찾았습니다.

또한 Versioning이 적용된 S3가 `BucketNotEmpty`로 삭제되지 않았을 때 Source의 `force_destroy = true`와 기존 State의 `false`가 다르다는 점을 확인하고 복구 Plan을 적용한 뒤 잔존 자원을 다시 검사했습니다. 반대로 아직 수집하지 못한 EKS Control Plane, Pod·Application, WAF, ALB·CloudFront, VPC Flow, S3 Data Event Log는 구현된 것처럼 적지 않고 미구현 범위로 분리했습니다. 현재 확인된 것은 진행 중인 실험환경과 일부 Runtime·배포·CloudTrail Evidence이며, 팀 계정과 다른 노트북에서 같은 결과가 재현되는지는 아직 검증하지 못했습니다. 이 사례에서 제가 주장할 수 있는 강점은 대규모 클라우드 환경을 혼자 설계했다는 것이 아니라, 실행 중 나타난 서로 다른 장애를 흐름과 증거로 나누고, 완료·미완료·팀 이식성의 경계를 기록했다는 점입니다.

저는 AI를 적극적으로 사용합니다. 낯선 개념 설명, 구현 초안, 비교표, 대량 문서 정리, 테스트 후보 생성에는 AI가 사람보다 빠를 때가 많습니다. 그러나 빠른 답과 믿을 수 있는 답은 같지 않다고 생각합니다. LDAP 기능을 만들기 전에는 실제 Directory Service 없이 구현하는 것이 하드코딩된 시연이 되지 않는지 확인했고, 취약 코드가 만들어진 뒤에는 실제 웹 기능과 비슷한지, 적용한 조치가 무엇이며 다른 방안은 어떤 것이 있는지 되물었습니다. Terraform이나 문서도 AI가 만든 부분과 제가 선택·승인·실행·검증한 부분을 나눠야 한다고 생각합니다. AI를 사용하지 않은 사람처럼 보이려 하기보다, AI가 빠르게 만든 결과를 어떤 기준으로 검토하고 어디까지 책임질지를 설명하는 것이 앞으로의 실무 역량에 더 가깝다고 봅니다.

복잡한 작업을 문서와 경로로 나누는 것도 저의 강점입니다. 저는 한 번 해결한 문제를 대화 속에만 남겨두기보다 다시 찾을 수 있는 증거, 현재 상태, 다음 행동으로 구조화합니다. 웹 21개 항목을 Router와 개별 노트로 분리했고, 자동화 프로젝트에서는 Profile, Check, Payload, Evidence, Report의 역할을 나눴으며, 수업과 프로젝트 기록에서도 MOC, RAW, 일일 로그, Source Digest의 목적을 구분했습니다. 이 성향은 겉으로는 문서화 능력처럼 보이지만, 제가 실제로 얻고 싶은 효과는 추적성과 재현성입니다. 누가 무엇을 했는지, 어떤 판단이 실제 실행으로 검증됐는지, 중단 뒤 어디서 다시 시작해야 하는지를 잃지 않게 하려는 것입니다.

다만 같은 성향에는 분명한 약점이 있습니다. 하나의 문제를 파고들다 범위가 커지고, 구조를 잘 만들려다 실행보다 문서가 앞설 수 있습니다. 21개 항목 전수 자동화, AI Reviewer, Cloud와 Container와 CI/CD를 한 번에 다루려 했던 계획이 그 예입니다. 모든 불확실성을 제거하고 결정하려 하면 팀 프로젝트의 속도와 충돌할 수도 있습니다. 표현이 급해지면 문제 제기가 짧고 거칠어질 때도 있습니다. 따라서 지금은 모든 것을 완벽하게 해결한 뒤 끝내려 하기보다, 현재 증거로 결정 가능한 범위, 추가 검증이 필요한 범위, 이번 시간 안에는 하지 않을 범위를 나누고 있습니다. 실제 팀이나 고객과 대화할 때는 문제, 근거, 영향, 요청 순서로 표현하는 습관도 더 필요합니다.

저는 아직 실제 고객사를 대상으로 진단하거나 침해사고를 대응한 경험이 없습니다. 상용 Scanner를 운영 규모로 다루거나, 대규모 자산의 조치 담당자와 SLA를 관리하거나, 버그바운티·CTF·CVE 분석으로 공격 역량을 검증한 경험도 없습니다. 그렇기 때문에 저의 장점을 “이미 완성된 보안 전문가”라고 표현하고 싶지 않습니다. 현재 근거로 가장 자신 있게 말할 수 있는 것은, 애매한 기술 결과를 여러 증거로 분해하고, 요청·권한·패킷·배포 흐름을 따라 원인을 좁히며, 자동화와 AI가 내린 결론의 책임 범위를 다시 설정하는 학습 방식입니다.

기술 취약점 진단과 정보보호 컨설팅은 단순히 도구 결과를 전달하는 일이 아니라, 왜 취약한지, 어떤 영향이 있는지, 무엇을 조치해야 하는지, 조치가 실제로 이행됐는지를 증거로 설명해야 하는 일이라고 이해하고 있습니다. 이 직무에서 저의 강점은 가장 많은 취약점을 빨리 찾는다는 주장이 아닙니다. 취약하다는 결론이 어떤 증거 위에 서 있는지 확인하고, 오탐 가능성과 미검증 범위를 숨기지 않으며, 같은 조건을 다시 재현할 수 있게 정리하는 태도입니다. 향후에는 이 강점을 실제 고객 환경의 범위 관리, 개발자·운영자와의 조치 협의, 취약점 우선순위와 이행점검 경험으로 확장하고 싶습니다.

결국 저를 설명하는 것은 CARE 하나, SQL Injection 하나, 진단 스크립트 하나가 아닙니다. 웹 취약점 점검에서는 존재하지 않는 기능을 무작정 꾸미지 않고 실제 해석기와 증거를 따졌고, 자동화에서는 높은 자동 판정률보다 판정 신뢰성을 택했으며, 네트워크 장애에서는 Packet의 왕복 흐름을 따라갔고, 인프라에서는 코드 작성자라는 주장보다 Runtime과 수명주기를 검증하려 했습니다. 서로 다른 사례에서 같은 방식이 반복됐습니다. 저는 모르는 것을 구조화된 질문으로 바꾸고, 애매한 결과를 증거로 나누고, 근거가 달라지면 처음 계획도 수정하는 사람입니다. 지금까지의 프로젝트가 모두 완성된 성공은 아니지만, 바로 그 불완전한 과정에서 무엇을 사실이라고 말할 수 있는지 구분하는 능력이 저만의 가장 분명한 강점이라고 생각합니다.

## 3. 강점별 독립 원재료

### A. 모르는 것을 질문으로 바꾸는 태도

저는 모르는 것을 빨리 감추는 것보다 정확히 무엇을 모르는지 찾는 편입니다. LDAP를 구현하기 전에는 먼저 LDAP가 무엇인지 설명을 요청했고, SQL DB와 닮아 보이는 부분과 다른 부분을 비교했습니다. Terraform Module을 배울 때도 작성법보다 왜 Module을 나누며 Output이 왜 필요한지를 먼저 물었습니다. 이 방식은 처음에는 느려 보이지만, 낯선 기술을 단순한 명령어 목록이 아니라 기존 지식과 연결된 구조로 이해하게 합니다.

- 근거 사례: LDAP 구현 전 조사와 제외 판단
- 근거 사례: Terraform Root·Child Module, Input·Output 경계 학습
- 근거 사례: 멘토에게 SQLi 설명을 못한 뒤 공격 유형과 과정 재정리
- 위험: 질문이 계속 늘어나 실행 시점을 놓칠 수 있음
- 보완: “이번 작업에서 반드시 알아야 할 것”과 “나중에 확인할 것” 분리

### B. 판정 근거를 나누는 습관

저는 하나의 신호가 전체 결론을 대표하지 않는다고 생각합니다. HTTP 200, 화면 변화, 오류 문구, Scanner Finding은 모두 중요한 단서지만 그 자체가 취약성의 확정 증거는 아닐 수 있습니다. 화면, Request·Response, Header, Redirect, Log, DB, Source Code와 재검증 결과를 분리해 확인하려는 습관은 오탐과 과장을 줄이는 데 도움이 됩니다.

- 근거 사례: 파일 다운로드 HTTP 200 오탐 발견
- 근거 사례: SQLi 정상·참·거짓 입력 비교
- 근거 사례: 21개 항목별 Evidence 기준
- 근거 사례: 3차 프로젝트에서 구현된 Log와 미구현 Log 분리
- 위험: 증거를 너무 많이 요구하면 결론을 내리지 못할 수 있음
- 보완: 확정, 의심, 미확인, 제외처럼 판정 수준 분리

### C. 흐름을 따라 원인을 좁히는 방식

저는 장애가 나타난 지점이 원인이라고 바로 단정하지 않습니다. 웹 요청이 어디서 해석되는지, 패킷이 왕복하며 주소가 어떻게 바뀌는지, Source Commit이 어떤 배포 단계를 지나 Runtime에 반영되는지를 따라갑니다. 이 방식은 서로 다른 계층의 문제를 구분하는 데 도움이 됩니다.

- 근거 사례: GNS 이중 PAT의 Request·Reply·ACL 대조
- 근거 사례: CloudFront 504에서 ALB Target Timeout과 ALB→Node SG 누락 추적
- 근거 사례: `PR Merge → GitHub Actions → ECR → GitOps → Argo CD → Rolling Update`
- 위험: 전체 흐름을 모두 보려다 조사 범위가 넓어질 수 있음
- 보완: 증상 발생 지점, 직전 정상 지점, 변경된 경계부터 좁혀 확인

### D. 복잡성을 재현 가능한 구조로 바꾸는 능력

저는 반복되는 작업이나 많은 점검 항목을 머릿속에만 두지 않고 입력, 처리, 증거, 결과, 다음 행동으로 나눕니다. 이 구조는 다른 사람이 다시 실행하거나 중단 후 재개할 때 유용합니다.

- 근거 사례: CARE 21개 항목 Router와 개별 노트
- 근거 사례: `profile → check → request → evidence → report`
- 근거 사례: WEB 통합 구축 Script의 단계 분리
- 근거 사례: RAW·일일 로그·MOC·Source Digest 역할 분리
- 위험: 구조 자체가 목적이 되어 구현보다 커질 수 있음
- 보완: 각 문서와 자동화가 실제로 줄인 누락·재작업·오탐을 설명

### E. 근거가 바뀌면 목표를 수정하는 유연성

저는 처음 계획을 끝까지 지키는 것보다 계획의 전제가 틀렸다면 수정하는 것이 책임 있는 태도라고 생각합니다. 자동 판정률을 높이려던 목표는 오탐과 Manual의 정당한 이유를 확인한 뒤 증거 수집과 사람의 최종 승인 구조로 바뀌었습니다. LDAP는 환경에 실제 Parser가 없어 구현하지 않았습니다. 3차 프로젝트에서는 모든 Log를 이미 수집한다고 가정하지 않고 실제 지속 저장이 확인된 CloudTrail과 아직 미구현인 Log를 분리했습니다.

- 근거 사례: 자동 판정기 → Evidence Collector
- 근거 사례: LDAP Mock 구현 제외
- 근거 사례: 로그 수집 계층과 제품 계층 재분류
- 위험: 방향 전환이 잦으면 마무리가 약해 보일 수 있음
- 보완: 전환 이유, 버린 범위, 새 완료 기준을 명시

### F. AI를 빠른 작업자이자 검토 대상으로 사용하는 능력

저는 AI가 만든 결과를 숨기지 않습니다. 대신 AI를 사용한 사실이 곧 제 역량을 부정한다고도 생각하지 않습니다. 제가 중요하게 보는 것은 어떤 문제를 AI에 맡겼고, 어떤 기준으로 결과를 검토했으며, 어디서 거절하거나 방향을 바꿨는지입니다.

- AI에 맡긴 것: 낯선 개념 설명, 코드 초안, 비교안, 대량 정리, 테스트 후보
- 직접 판단한 것: 실제 환경과 유사한지, 하드코딩된 시연인지, 비용·보안 경계, 실행 승인, 증거 수준
- 직접 검증한 것: Runtime 상태, 요청·응답, Test, `plan/apply/destroy`, Log와 잔존 자원
- 말하면 안 되는 것: AI가 작성한 전체 코드를 혼자 독립 설계·구현했다는 주장
- 위험: AI 없이 설명하거나 재현할 수 없는 범위가 커질 수 있음
- 보완: 면접 전에 사례별로 “10분 설명 가능”, “다시 실행 가능”, “코드 한 줄씩 방어 가능” 범위를 점검

### G. 구현하지 않은 이유도 설명하는 판단력

기술 프로젝트에서는 많은 기능을 넣는 것이 항상 좋은 결과는 아닙니다. 실제 Service나 Parser가 없는 상태에서 취약점을 흉내 내면 학습한 것처럼 보이지만, 입력과 실제 취약 동작 사이의 인과관계가 없습니다. 저는 LDAP를 제외한 이유, AI Reviewer를 구현하지 못한 사실, GNS가 최종 성공 검증까지 닫히지 않은 사실을 구분해 남기려고 했습니다.

- 근거 사례: LDAP Injection은 비교 학습으로만 남김
- 근거 사례: AI Reviewer는 설계, 미구현
- 근거 사례: GNS PAT는 원인과 수정 방향, 성공 증거 없음
- 근거 사례: 3차 팀 환경 이식성 미검증
- 장점의 의미: 과장을 막고 다음 검증 지점을 분명히 함

### H. 공격과 조치를 한 쌍으로 보는 관점

저는 취약한 화면을 만드는 데서 끝내기보다 같은 입력을 조치 전후에 다시 적용해 차이를 보고 싶어 합니다. SQLi에서는 Query 결합과 Parameter Binding, Command Injection에서는 Shell 문자열 결합과 입력 검증·Argument 처리, Secret에서는 코드 분리와 권한·회전, 침해 서버에서는 격리·증거 보존·재배포를 함께 봤습니다.

- 근거 사례: 취약 모드와 조치 모드 비교
- 근거 사례: 원인·조치·재검증 Evidence 구조
- 근거 사례: Versioned S3 삭제 실패 후 복구 Plan과 잔존 검사
- 성장 방향: 실제 고객 환경의 이행점검과 위험 수용 추적

### I. 소유권과 사실 경계를 구분하려는 정직성

팀이 함께 만든 IAM 구조나 AWS 환경 전체를 개인 성과로 가져오지 않으려 합니다. AI가 작성한 코드, 팀원이 설계한 Terraform, 제가 실행하고 보정한 부분, 아직 계획인 부분을 나누려 합니다. 이 태도는 자소서 문장을 약하게 만들 수 있지만, 꼬리질문에서 무너지지 않는 설명을 만드는 데 필요합니다.

- 팀 결과: 온프레미스·AWS 진단, IAM 세분화, 인프라 전체
- 개인 근거가 강한 부분: CARE 웹 진단 구조화, Code Injection 판단, Checker 방향 전환과 일부 구현, WEB Script, Runtime 검증·트러블슈팅
- 미완성: AI Reviewer, GNS 성공 재검증, 3차 최종 성과

### J. 약점을 숨기지 않고 작업 방식으로 관리하려는 태도

저는 한 문제를 깊게 파는 만큼 범위를 크게 잡고 결정을 늦출 수 있습니다. 문서화와 구조화가 실행을 앞설 때도 있고, 문제 상황에서 표현이 짧고 거칠어질 수 있습니다. 이런 점은 장점으로 미화할 수 없는 실제 약점입니다. 다만 최근에는 시간 제한, 완료 조건, 증거 수준, 미검증 목록을 별도로 두고, 팀이나 외부에 설명할 때 문제·근거·영향·요청 순서로 바꾸려 하고 있습니다.

| Terraform·AWS Lifecycle 검증 | Runtime 검증, 비용·보안 승인, State와 실제 자원 대조 | 실행 근거 있음, AI 코드 비중 큼 | 전체 코드 독립 작성 |
| Kubernetes Runtime 학습 | 객체 관계와 상태 변화 이해 | Rolling Update·Service·DNS 등 실습 근거 | Production 운영 경험 |
| 진행 중 3차 프로젝트 | CI/CD·GitOps·EKS 흐름 추적, 다계층 장애 보정, 완료 경계 관리 | 개인 계정 선행 검증과 최신 일일 로그, 프로젝트 진행 중 | 팀 계정 재현, 최종 보안 시나리오·전체 Log |
| Vault·Evidence 문서 구조 | 추적성, 재시작 가능성, AI 협업 경계 | 실제 문서 구조 존재 | 보안 기술 자체의 깊이 |

## 5. 장운호의 강점을 이루는 긴장 관계

### 깊이 있게 파고든다 ↔ 범위를 키운다

- 장점: 남들이 지나칠 수 있는 전제와 오탐을 찾는다.
- 약점: 한 항목이 프로젝트 전체보다 커질 수 있다.
- 실제 사례: 웹 21개 항목 전수 자동화와 AI Reviewer까지 계획.
- 현재 보완: 대표 항목, 완료 기준, 미구현 범위 분리.

### 정확하게 말하려 한다 ↔ 결론이 늦어진다

- 장점: 근거 없는 완성·성공 주장을 피한다.
- 약점: 모든 증거를 모으기 전까지 결정을 미룰 수 있다.
- 실제 사례: 증거 유형을 계속 늘리고 보고서 범위가 커짐.
- 현재 보완: 현재 증거로 가능한 잠정 판정과 추가 검증을 분리.

### AI를 적극 활용한다 ↔ 자기 역량 경계가 흐려질 수 있다

- 장점: 낯선 영역을 빠르게 탐색하고 반복 작업을 확장한다.
- 약점: 산출물 규모가 본인의 독립 구현 능력보다 커질 수 있다.
- 실제 사례: Terraform 대형 코드와 대량 문서.
- 현재 보완: AI 생성, 개인 판단, 직접 실행, Runtime 검증을 구분.

### 구조화를 잘한다 ↔ 문서가 실행보다 커질 수 있다

- 장점: 재현·추적·인수인계가 쉬워진다.
- 약점: MOC와 분류 체계를 만드는 데 시간이 많이 든다.
- 현재 보완: 각 문서가 줄이는 누락과 재작업이 없으면 만들지 않는 기준 필요.

### 문제를 정면으로 지적한다 ↔ 표현이 거칠어질 수 있다

- 장점: 잘못된 전제나 AI의 억지 답을 그냥 넘기지 않는다.
- 약점: 팀·고객 상황에서는 상대가 공격받는다고 느낄 수 있다.
- 현재 보완: “문제 → 근거 → 영향 → 확인 요청” 순서로 번역.

## 6. 지원 직무와 연결할 수 있는 부분

### 기술 취약점 진단·정보보호 컨설팅

가장 직접적으로 연결된다.

- 도구 결과를 그대로 옮기지 않고 오탐과 판정 근거를 확인하려는 태도
- 화면, Request·Response, Log, DB, Source Code, 재검증을 분리한 경험
- 취약 원인, 조치 방법, 조치 후 검증을 한 흐름으로 본 경험
- 보고서에서 완료·미완료·팀·개인 범위를 구분하려는 태도
- 부족한 것: 실제 고객 범위 협의, 위험도·우선순위 합의, 상용 Scanner와 대규모 자산, 고객 보고

### 취약점 관리·보안 자동화

인접 성장 방향으로 연결된다.

- `Manual`이 생기는 이유를 분류하고 자동화 가능한 부분과 사람 판단을 분리
- Evidence Collector, Mode Gate, Cleanup, Redaction, Regression Test
- 조치와 이행점검을 반복 가능한 Workflow로 보고 있음
- 부족한 것: 운영 규모 SLA, 자산 소유자, 예외 승인, 재점검 Orchestration

### AppSec·DevSecOps

관심과 기반 경험은 있으나 실무 경험으로 부르면 안 된다.

- 코드에서 취약 원인과 안전한 구현 비교
- Secret 외부화, CI/CD·GitOps, PR 보안 검토 경험
- Source부터 Image·Manifest·Runtime까지 흐름에 관심
- 부족한 것: 실제 개발 조직 SDLC, 개발자 설득, SAST·DAST 정책 운영, Release Gate 운영

### 순수 모의해킹·Red Team

현재 강점과 일부 맞지만 검증이 부족하다.

- 공격 시나리오, 취약점 재현, 공격과 조치 전후 비교를 좋아함
- 부족한 것: CTF, 버그바운티, CVE 분석, Exploit 개발, 리버싱, 정식 침투 테스트 방법론
- 따라서 “모의해킹 전문가”가 아니라 “취약점을 증거로 검증하는 공격자 관점에 관심이 있다”가 현재 수준에 맞다.

### 보안관제·CERT

로그와 원인 분석에 관심은 있지만 현재 직접 근거가 상대적으로 약하다.

- CloudTrail, WAF, ALB, EKS, Application Log의 역할과 관측 지점에 관심
- 부족한 것: 실제 경보 Triage, SIEM Rule Tuning, 교대 관제, Incident Handling

## 7. 면접에서 방어 가능한 주장과 금지할 주장

### 현재 방어 가능한 주장

- 웹 취약점 진단에서 단일 신호보다 여러 Evidence를 대조하려 했다.
- CARE 웹 항목을 구조화하고 일부 항목을 원인·조치·재검증까지 깊게 다뤘다.
- SQLi에서 정상·참·거짓 응답과 인증 우회를 구분했다.
- 실제 LDAP 환경이 없어 하드코딩된 Mock의 가치가 낮다고 판단해 구현하지 않았다.
- 실제 Shell 실행 맥락을 가진 OS Command Injection 실험을 조치 전후로 비교했다.
- `Manual`의 원인을 분석하고 자동 판정기 목표를 Evidence Collector로 변경했다.
- 파일 다운로드에서 HTTP 200만으로 취약 판정하는 오탐을 발견했다.
- Checker에 Mode Gate, Fixture·Cleanup Ledger, Secret Redaction, Regression Test를 일부 구현했다.
- WEB 구축·설정 과정을 Bash Script로 묶었고 Secret을 코드에서 분리했다.
- GNS 이중 PAT 문제에서 Packet Flow와 NAT ACL을 대조해 원인을 좁혔다.
- AI가 작성한 코드도 Runtime과 Lifecycle을 직접 검증하고 미검증 범위를 분리하려 했다.
- 진행 중인 3차 프로젝트에서 여러 계층의 Runtime 장애를 원인별로 보정했다.

### 현재 금지할 주장

- KISA 웹 21개 항목을 모두 동일한 깊이로 완료했다.
- CARE에서 LDAP Injection 취약점을 실제로 구현·검증했다.
- CARE에 원래 있던 모든 취약점을 스스로 발견했다.
- AI 기반 웹 취약점 최종 판정 시스템을 완성했다.
- GNS 장애를 최종 통신 성공까지 해결했다.
- WEB Script가 어떤 서버에서도 완전 무인 배포를 보장한다.
- 환경 변수로 Secret을 옮겼기 때문에 서버가 침해돼도 안전하다.
- Terraform 전체 Architecture와 코드를 독립적으로 작성했다.
- 팀 IAM 구조 전체를 본인이 설계·구현했다.
- 실제 침해사고 대응 경험이 있다.
- Production EKS, DevSecOps, AppSec, SOC 운영 경험이 있다.
- 3차 프로젝트의 최종 보안 성과가 이미 확정됐다.

## 8. 나중에 줄일 때 쓸 수 있는 중심 문장 후보

아래 문장들은 서로 경쟁하는 최종안이 아니라, 어떤 축을 남길지 선택하기 위한 후보들이다.

### 후보 1 — 증거 기반 판정

> 저의 강점은 애매한 기술 결과를 하나의 신호로 단정하지 않고, 요청·응답·로그·코드·상태를 대조해 판정 가능한 범위를 좁히는 것입니다.

### 후보 2 — 이해 후 구현

> 저는 기능을 많이 만드는 것보다 실제 환경에서 어떤 구조로 동작하는지 이해한 뒤, 가짜 재현은 제외하고 검증 가능한 범위만 구현하려 합니다.

### 후보 3 — 흐름 기반 문제 해결

> 저는 장애가 보이는 지점을 원인으로 단정하지 않고, 요청·권한·패킷·배포의 흐름을 따라 직전 정상 지점과 깨진 경계를 찾습니다.

### 후보 4 — 방향 전환

> 저는 처음 세운 목표를 방어하기보다, 오탐이나 미검증 전제를 발견하면 목표와 도구의 역할 자체를 다시 설계합니다.

### 후보 5 — AI 협업

> 저는 AI를 빠른 구현 도구로 활용하되, 결과가 실제 구조와 같은지와 제가 책임질 수 있는 범위를 직접 검토합니다.

### 후보 6 — 재현성과 문서화

> 저는 한 번 해결한 문제를 개인의 기억에 남기지 않고, 다른 사람이 다시 확인할 수 있는 입력·증거·상태·재검증 절차로 구조화합니다.

### 후보 7 — 전체를 묶는 문장

> 저는 모르는 것을 구조화된 질문으로 바꾸고, 애매한 결과를 증거로 나누며, 근거가 달라지면 처음 계획도 수정하는 사람입니다.

## 9. 삭제 순서

최종 글자 수가 정해지면 아래 순서로 지운다.

1. **지원 직무와 거리가 먼 기술 나열부터 삭제한다.**
   - Kubernetes 객체 이름, AWS Resource 수, 세부 Tool 목록
2. **같은 강점을 반복하는 보조 사례를 삭제한다.**
   - Evidence 판정 축을 택하면 PAT나 Secret 사례는 보조 한 문장만 유지
3. **현재 미완성인 3차 프로젝트를 우선 축소한다.**
   - 최신 사례라는 이유만으로 대표 사례로 올리지 않음
4. **직무 요구와 직접 이어지지 않는 개인사·학습사 부분을 줄인다.**
   - 건축학과 출신과 교육 시작 시점은 필요한 경우에만 유지
5. **약점은 하나만 남기되 실제 관리 행동을 붙인다.**
6. **AI 사용 경계는 삭제하지 않는다.**
   - 사례에서 AI 비중이 크다면 한 문장이라도 반드시 남김
7. **완료·미완료 경계는 삭제하지 않는다.**
   - 문장을 짧게 하더라도 범위를 넓혀 쓰지 않음
8. **마지막에는 중심 강점 1개, 대표 사례 1개, 보조 근거 1개, 직무 연결 1개만 남긴다.**
