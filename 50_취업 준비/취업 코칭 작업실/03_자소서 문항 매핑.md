# 자기소개서 문항 매핑

## 작성 원칙

- 희망 직무가 하는 일, 요구 기술, 선호하는 성격·기술 인재상을 먼저 조사한다.
- 직무 설명과 인재상을 답변에 직접 나열할 필요는 없다. 조사 결과는 경험과 강점 선택의 기준으로 사용한다.
- 관심 분야의 유행을 나열하지 않고 실제 프로젝트 판단과 연결한다.
- 배운 기술 목록보다 역할, 문제, 행동, 검증, 변화가 드러나게 쓴다.
- 각 경험은 `상황 → 역할 수행 → 결과` 순서로 준비한다.
- 같은 사례를 여러 문항에 재사용할 때는 강조점을 달리한다.
- 면접에서 설명할 수 없는 문장은 넣지 않는다.
- 최신 사례라도 증거 gate가 닫히지 않았으면 검증 완료된 이전 사례를 대안으로 유지한다.

## 현재 기준

- 현재 지원서 상태와 문항별 최신 소재는 [[50_취업 준비/취업 코칭 작업실/09_입사지원서 마무리 작업판|입사지원서 마무리 작업판]]을 우선한다.
- 3차 프로젝트의 구축 범위와 미완료 증거 gate는 [[50_취업 준비/취업 코칭 작업실/10_입사지원서 준비 현황과 3차 프로젝트 정리|입사지원서 준비 현황과 3차 프로젝트 정리]]에서 확인한다.
- 사례의 사실성은 [[50_취업 준비/취업 코칭 작업실/01_증거 장부|증거 장부]], 사례 단위 구조는 [[50_취업 준비/취업 코칭 작업실/02_실제 사례 후보|실제 사례 후보]]를 기준으로 한다.
- 이 문서는 완성 문장을 쓰는 곳이 아니라 `문항 ↔ 사례 ↔ 증거 ↔ 남은 gate`를 연결하는 매핑 문서다.

## 공통 사전 조사

- 희망 직무: 미확정
- 직무가 하는 일: 2026년 신입·현재 공고 기반 1차 조사 완료
- 직무가 요구하는 기술: 직무군별 1차 비교 완료
- 직무가 선호하는 성격·인재상: 일부 공고에서 확인, 희망 직무 확정 후 추가 조사 필요
- 조사 노트: [[50_취업 준비/취업 코칭 작업실/04_직무 시장 조사|직무 시장 조사]]
- 회사·공고가 정해지기 전에는 공통 마스터본의 경험 선택만 관리하고 회사별 지원동기는 확정하지 않는다.

## 문항 1. 본인만의 강·장점

- 강점 키워드 가안: 결과를 그대로 믿지 않고 `무엇이 무엇을 증명하는지` 대조군과 Runtime evidence로 확인하는 태도
- 최신 우선 사례: A-14 Capital One 공격·정상 대조 실험
- 상황: 공격 Alert가 발생했다는 사실만으로 Rule의 정확성이나 공격 성공 범위를 충분히 설명하기 어려웠다.
- 역할 수행: 공격과 정상 사용자 동작을 같은 조건·Object·탐지 기준으로 비교하고, Source Event·Alert·정상 대조군을 같은 TAKE에서 연결하는 검증 기준을 잡았다.
- 결과로 쓸 수 있는 범위: 검증 방식과 대조 실험 설계는 현재 지원서의 최신 소재다.
- 근거 ID: E-027
- 증거 gate: 공격·정상 대조군의 동일 조건·Object·TAKE Runtime evidence가 아직 장부에서 `보강 필요`다.
- 검증 완료 대안: A-01 CARE 웹 애플리케이션 취약점 집중 진단. E-001~E-005.

## 문항 2. 관심 분야와 적용·발전 과정

- 관심 흐름: 웹 취약점의 원인·오탐 분석 → 증거 중심 자동화 → IAM·IMDS·워크로드 권한 → 제한된 보안 자동 대응
- 기반 사례: A-02 `Manual`에서 evidence collector로 방향 전환
- 최신 확장 사례: A-13 제한된 자동 대응과 안전 경계
- 상황: 웹 진단에서는 고정 규칙의 오탐과 manual 한계를 경험했고, 3차 프로젝트에서는 한 Alert의 값을 그대로 자동 실행할 때 오조치 범위가 커질 수 있었다.
- 역할 수행: 2차에서는 checker를 evidence collector로 낮추고 사람 승인 경계를 뒀다. 3차에서는 Rule 단계의 증거 의미를 분리하고 Shuffle에서 Rule·Schema·신선도·Hash·고정 대상을 재검증한 뒤 사전 정의된 Workflow만 허용했다.
- 발전 과정: 자동 판정 지향 → 오탐·manual 발견 → 증거 수집과 승인 경계 → Cloud/EKS의 권한·Telemetry·SOAR 안전 경계로 확장
- 근거 ID: E-006~E-010, E-023~E-025
- 증거 gate: A-13의 동일 TAKE Alert→Shuffle→GitHub Run→Argo→Pod/보안 수준 연결이 닫히기 전에는 E2E 자동 대응 완료로 표현하지 않는다.

## 문항 3. 습득 기술·역할·문제 해결

- 최신 우선 사례: A-11 Karpenter State 밖 자원 종료 트러블슈팅
- 배경 사례: A-10 Foundation / Daily Runtime 수명주기 분리
- 상황: 비용 절감을 위해 Daily Runtime을 반복 삭제해야 했지만, Karpenter가 Terraform State 밖에서 만든 NodeClaim·EC2가 남아 Destroy를 방해했다.
- 역할 수행: Foundation과 Daily Runtime의 Root·State·수명주기를 먼저 분리했고, 종료 시 NodePool·NodeClaim 정리와 프로젝트 Tag가 일치하는 EC2의 제한된 종료 확인 절차를 추가했다.
- 판단: Terraform 선언 상태만 보는 대신 Controller가 만든 Runtime 자원의 실제 소유권과 삭제 범위를 별도로 확인했다.
- 근거 ID: E-020, E-021
- 증거 gate: 잔여 Runtime 0과 Foundation 보호가 같은 종료 실행에서 확인된 근거를 연결한다.
- Runtime 검증이 이미 닫힌 대안: A-12 10분 Poll → DVWA 저지연 Route 보정. E-022, E-026.
- 이전 대안: A-05 GNS 이중 PAT 트러블슈팅, A-03 WEB 통합 자동화.

## 문항 4. 지원동기·포부

- 공통 방향: 원인을 분석하고, 조치 범위를 제한하며, 실행 뒤 다시 검증하는 보안 엔지니어링 흐름을 지향한다.
- 연결 가능한 경험: A-02의 오탐 보정, A-12의 Source별 지연 분리, A-13의 제한된 자동 대응.
- 근거 ID: E-006~E-010, E-022~E-026.
- 현재 상태: 공통 마스터본의 방향만 유지한다. 회사·직무가 정해진 뒤 실제 공고 요구와 연결하며, 회사별 사실을 이 문서에서 미리 만들어내지 않는다.

## 남은 결정

- 문항 1은 E-027 Runtime evidence가 닫히면 A-14를 유지하고, 닫히지 않으면 A-01로 되돌린다.
- 문항 2는 지원 직무가 Cloud Security / SOC / DevSecOps에 가까울수록 A-13의 비중을 높이고, 웹 진단·보안 자동화 쪽이면 A-02를 중심으로 둔다.
- 문항 3은 E-021 종료 실행 증거가 닫히면 A-11을 유지하고, 제출 시점까지 닫히지 않으면 A-12를 우선한다.
- 문항 4는 회사·공고가 정해진 뒤에만 회사별 지원동기로 변환한다.
