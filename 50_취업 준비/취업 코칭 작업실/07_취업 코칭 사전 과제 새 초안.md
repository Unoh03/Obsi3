## 실제 사례 3가지

| 사례 | 내가 실제로 한 일 | 보여줄 수 있는 점 |
|---|---|---|
| CARE 웹 애플리케이션 취약점 점검 | 21개 점검 항목의 문서와 증거 기준을 나누고, SQL Injection 등 우선 항목을 깊게 점검했다. | 한 분야를 맡아 근거를 정리하며 파고드는 태도 |

## 1. 본인의 강점과 이를 보여주는 경험

### 강점

**한번 맡은 문제는 표면적인 결과만 확인하고 끝내지 않고, 판단 근거를 정리하면서 깊게 파고드는 편이다.**

### 상황

2차 프로젝트에서 KISA 기준으로 온프레미스와 AWS 환경을 진단했고, 나는 CARE 웹 애플리케이션 취약점 점검을 맡았다. 웹 점검은 같은 공격을 하더라도 로그인 상태나 입력값, 응답 내용에 따라 결과의 의미가 달라질 수 있어 단순히 성공 화면만 모으는 것으로는 부족하다고 생각했다.

### 역할 수행

21개 점검 항목을 한 문서에 계속 쌓는 대신 전체 진행 상황을 보는 문서와 항목별 점검 문서를 나눴다. 각 항목에서 확인할 증거도 화면, 요청·응답, 서버 로그, DB 결과, 관련 코드, 조치 후 재검증으로 구분했다.

SQL Injection을 점검할 때는 게시판 검색에 참·거짓 조건을 넣어 결과 차이를 비교한 경우와 로그인 인증 우회를 시도한 경우를 나누어 정리했다. 공격이 동작했다는 결과뿐 아니라 문자열 결합이 원인이 될 수 있다는 점과 Prepared Statement 등 조치 방법도 함께 기록했다.

### 결과

웹 진단의 진행 상태와 판정 근거를 다시 찾아볼 수 있는 구조를 만들었고, SQL Injection은 테스트 과정부터 원인과 조치안까지 한 흐름으로 설명할 수 있게 됐다. 모든 항목을 얕게 끝내기보다 우선순위를 정해 일부 항목을 깊게 확인한 경험을 통해, 내가 한 분야를 맡으면 근거를 정리하며 파고드는 편이라는 점을 알게 됐다.

## 2. 관심 분야와 관련 이슈, 프로젝트 적용과 발전 과정

### 관심 분야와 이슈

관심 분야는 **웹 취약점 진단 자동화와 AI를 이용한 판정 보조**다.

CARE 점검 경험을 바탕으로 KISA Web Application 21개 항목을 자동으로 진단하는 개인 확장 프로젝트를 시작했다. 처음 목표는 `Manual` 항목을 줄여 자동 판정 비율을 높이는 것이었다. 하지만 인증 상태, 사용자 권한, 업무 흐름과 상태 변경이 필요한 항목은 정해진 요청과 문자열 비교만으로 판단하기 어려워 `manual_required`로 남는 경우가 많았다.

파일 다운로드 항목에서는 HTTP 200 응답을 취약하다는 증거로 판단했지만, 실제 응답이 파일이 아니라 로그인 화면이나 차단 안내일 수도 있다는 오탐도 발견했다.

### 역할 수행과 프로젝트 적용

먼저 `Manual`이 발생하는 이유를 테스트 환경이나 사전 데이터가 부족한 경우, 조건에 따라 자동·수동 판정이 달라지는 경우, 사람의 업무 흐름 해석이 필요한 경우로 나눴다. HTTP status만 확인하던 방식도 header, body, redirect, 로그인 상태, source와 DB 상태를 함께 보도록 판정 근거를 넓혔다.

이후 checker를 바로 취약·양호를 결정하는 도구가 아니라 `profile → check → request → evidence → report` 순서로 증거를 남기는 도구로 다시 설계하고 구현했다. 상태를 바꾸는 테스트에는 실행 mode 확인, fixture와 cleanup 기록, secret 가림 처리와 회귀 테스트도 추가했다.

이 과정에서 사람이 하던 확인 중 일부를 AI가 대신할 수 있지 않을까 생각했다. 다만 AI도 판단에 필요한 상태와 증거를 받지 못하면 같은 오탐을 낼 수 있기 때문에, 스크립트가 증거를 수집하고 AI가 비교·검토한 뒤 사람이 최종 판단하는 구조로 방향을 바꿨다.

### 결과와 관심 분야의 발전

checker의 증거 수집 구조와 workflow 회귀 테스트까지는 구현했지만, AI review 기능은 설계 단계에서 멈췄다. 그래도 이 경험을 통해 관심이 단순히 자동 판정 비율을 높이는 것에서, **고정 규칙·AI·사람이 각각 어디까지 판단해야 결과를 신뢰할 수 있는지**를 고민하는 방향으로 발전했다.

## 3. 학원에서 배운 것과 수행한 역할, 인상 깊었던 트러블슈팅

### 배운 것과 수행한 역할

학원에서 Linux와 웹 서버, 네트워크와 NAT, 웹 취약점, AWS와 IAM, KISA 기준 취약점 진단을 배웠다. 프로젝트에서는 웹 서버·LB·NFS가 있는 구간과 CARE 웹 애플리케이션 점검을 맡았다.

### 상황

2차 프로젝트에서 GNS 네트워크를 구성하던 중 내 R2에서 상대 팀 R2로 보낸 ping이 모두 실패했다. 처음에는 라우팅 경로가 빠졌다고 생각했지만, 패킷을 확인해 보니 요청은 상대편까지 도착했고 응답도 내 R1까지 돌아오고 있었다.

### 역할 수행

Wireshark에서 요청과 응답의 출발지·목적지 주소가 구간마다 어떻게 바뀌는지 따라갔다. 그리고 양쪽 R1의 NAT ACL을 비교했다. 그 결과 팀 간 통신 패킷에도 양쪽에서 각각 PAT가 적용되면서, 돌아오는 응답의 주소가 처음 요청과 정상적으로 연결되지 않는 흐름을 확인했다.

명령을 하나씩 바꿔보는 대신, 패킷이 어디까지 갔고 어느 지점부터 주소가 달라졌는지를 기준으로 원인을 좁혔다.

### 결과

단순한 라우팅 누락이 아니라 팀 간 통신 대역까지 다시 PAT한 정책이 원인이라고 판단했다. 팀 간 대역은 NAT 대상에서 제외하고 라우팅만 하도록 해야 한다는 수정 방향도 정리했다.

당시 기록에는 수정 설정을 적용한 뒤 ping이 성공한 증거까지 남아 있지는 않다. 그러나 이 경험을 통해 네트워크 문제를 볼 때 처음 떠오른 원인에 머무르지 않고, 실제 패킷 흐름을 따라가며 가설을 좁히는 방법을 배웠다.
