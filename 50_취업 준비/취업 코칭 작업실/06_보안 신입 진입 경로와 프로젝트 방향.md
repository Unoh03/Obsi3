# 보안 신입 진입 경로와 프로젝트 방향

> [!warning]
> 이 문서는 현재 채용시장과 장운호의 기존 경험을 대조한 **내부 의사결정 초안**이다. 3차 프로젝트 방향은 강사 요구사항, 멘토 조언, 팀원 역량과 합의가 확인되기 전까지 `조건부 1순위 가설`이며 확정안이 아니다.

## 현재 결론

- 신입 채용문이 상대적으로 넓은 분야는 `보안관제·SOC`와 `보안솔루션 기술지원·운영`이다.
- 장운호의 현재 경험과 문제 해결 방식을 가장 직접적으로 사용할 수 있는 분야는 `기술 취약점 진단·보안컨설팅`이다.
- 이후 확장 방향으로는 `취약점 관리·보안 자동화`, 더 나아가 `AppSec`이 연결된다.
- 3차 프로젝트의 조건부 1순위 가설은 **웹·컨테이너 공격 시나리오 기반 취약점 검증–조치–재점검 자동화**다.

## 1. 시장 근거

세부 공고와 직무군별 근거는 [[50_취업 준비/취업 코칭 작업실/04_직무 시장 조사|직무 시장 조사]]에서 관리한다.

### 신입 진입 폭

| 진입 폭 | 직무군 | 판단 근거와 주의점 |
|---|---|---|
| 넓음 | 보안관제·SOC | 신입·경력 혼합 및 상시 공고가 확인된다. 이벤트 모니터링, 초동대응, 보고, 교대근무가 포함될 수 있다. |
| 넓음 | 보안솔루션 기술지원·운영 | 서버·네트워크 기초와 트러블슈팅을 바탕으로 시작할 수 있다. 제품 정책·배포·장애처리와 고객 대응 비중이 크다. |
| 중간 | 기술 취약점 진단·보안컨설팅 | 신입 공고가 존재하지만 취약점 재현, 증적, 개선안, 보고서와 고객 프로젝트 수행 능력을 보여줘야 한다. |
| 중간~좁음 | SIEM·클라우드 보안점검·취약점 관리 | 별도 신입 모집분야가 실제로 존재한다. 다만 독립 공고 수가 상대적으로 적고 대기업 공채 경쟁과 학력 조건을 따로 봐야 한다. |
| 좁음 | AppSec·DevSecOps 전문 역할 | 애플리케이션 구조, 개발, SDLC, CI/CD와 보안 자동화를 함께 요구하는 경우가 많다. |
| 매우 좁음 | CERT·침해사고 분석·순수 모의해킹·공격 연구 | CTF, 버그바운티, CVE, 리버싱, 포렌식 등 별도의 깊은 증거를 요구하거나 우대하는 경우가 많다. |

## 2. 장운호 경험 대입

개별 사례의 기여·AI 활용·완성 경계는 [[50_취업 준비/취업 코칭 작업실/02_실제 사례 후보|실제 사례 후보]]와 [[50_취업 준비/취업 코칭 작업실/01_증거 장부|증거 장부]]를 기준으로 한다.

| 반복해서 확인된 행동 | 연결되는 사례 | 직무에서의 의미 |
|---|---|---|
| 애매한 결과를 그냥 넘기지 않고 증거를 나눠 확인 | CARE 웹 진단, SQLi 참·거짓 비교 | 기술 취약점 진단, AppSec |
| 자동 판정의 오탐과 `manual_required` 원인을 분석 | evidence collector 방향 전환 | 취약점 검증, 보안 자동화 |
| 화면·요청/응답·로그·DB·코드를 연결해 판정 범위를 제한 | 파일 다운로드 오탐 분석 | 오탐 제거, 증적 작성, 재점검 |
| 반복 작업과 검증 지점을 실행 흐름으로 구조화 | WEB 통합 구축·재구축 스크립트 | 취약점 관리 자동화, DevSecOps 인접 역량 |
| 패킷과 상태 흐름을 따라 원인을 좁힘 | GNS 이중 PAT 트러블슈팅 | 인프라 진단, 기술지원, 문제 해결 |

### 현재 강점

장운호의 현재 강점은 단순히 `공격을 좋아한다`거나 `자동화를 해봤다`는 데 있지 않다.

> **애매한 진단 결과를 재현하고, 서로 다른 증거를 대조해 판정 범위를 좁힌 뒤, 조치와 재점검으로 연결하려는 방식**

이 방식은 기술 취약점 진단·보안컨설팅에 가장 직접적으로 연결되고, 취약점 관리·보안 자동화와 AppSec으로 확장할 수 있다.

### 아직 부족한 증거

- 실제 고객·개발자와 조치안을 협의하고 위험을 설명한 경험
- 운영 환경에서 다수 자산의 취약점 담당자·기한·예외를 추적한 경험
- 상용 보안제품 정책·배포·장애 대응 경험
- 실제 보안 이벤트 triage, 탐지 룰 작성, 사고 대응 경험
- CTF·버그바운티·CVE·리버싱 등 순수 공격 연구 직무의 선행 증거

## 3. 진입 경로 판정

### 현재 1순위

**기술 취약점 진단·보안컨설팅**

- CARE 웹 진단, KISA 기준 적용, SQLi 재현, 증거 구조화, 보고서 경험을 가장 적게 버리고 활용할 수 있다.
- 순수 공격 연구보다 현재 증거와의 간극이 작다.
- 웹뿐 아니라 서버·네트워크·DB·클라우드 진단으로 확장할 수 있다.

### 인접 성장 방향

**취약점 관리·보안 자동화**

- `manual_required` 분석, 오탐 검증, evidence collector, Bash 자동화 경험과 연결된다.
- 향후에는 CVE·CCE, 자산·담당자·SLA·예외·재점검 추적, API 연동과 운영 적용 증거가 필요하다.

**AppSec**

- 애플리케이션 취약점 재현, 코드와 업무 문맥 분석, 개발자와 조치안을 협의하고 재검증하는 역할과 연결된다.
- 현재는 개발·SDLC·CI/CD 경험을 더 보강해야 하므로 첫 직무명보다는 성장 방향에 가깝다.

### 현재 주력으로 단정하지 않을 분야

- `보안관제`: 신입 입구는 넓지만 현재 대표 사례가 로그 triage·초동대응보다 취약점 재현과 증거 판정에 치우쳐 있다.
- `보안솔루션 기술지원·운영`: Linux·네트워크·트러블슈팅은 연결되지만 제품 운영과 고객 대응에 대한 선호·경험이 확인되지 않았다.
- `순수 모의해킹·공격 연구`: 관심은 강하지만 독립 취약점 발견과 공격 연구 증거가 부족하다.
- `DevSecOps`: 하나의 명확한 신입 직무라기보다 개발·보안·운영이 SDLC 안에서 보안을 함께 적용하는 방식에 가깝다. 현재 경험 중 자동화 부분은 연결되지만 전체 역할을 수행했다고 표현하지 않는다.

## 4. 3차 프로젝트 조건부 1순위 가설

### 주제

> **웹·컨테이너 공격 시나리오 기반 취약점 검증 및 조치 이행점검 자동화**

### 핵심 질문

> 자동 스캐너가 발견한 결과가 실제 취약점인지 어떻게 증명하고, 조치됐다는 사실을 동일 조건의 재공격과 증적으로 어떻게 확인할 것인가?

### 최소 흐름

```text
자동 스캔 결과 수집
→ 사람이 실제 재현
→ 확인 / 오탐 / 추가검증 필요 구분
→ 영향도·증거·조치안 기록
→ 코드·설정 조치
→ 동일 조건 재공격
→ 종료 / 예외 / 미조치 판정
```

### 4주 프로젝트 최소 범위

- 취약 웹 서비스 1개
- Docker 또는 Kubernetes 기반 재현 환경
- 서로 성격이 다른 공격 시나리오 3개 안팎
  - 자동 탐지가 비교적 쉬운 SQL Injection 또는 XSS
  - 사용자 역할·업무 흐름 해석이 필요한 인증·인가 우회 또는 IDOR
  - 컨테이너 이미지 취약점, secret 노출, 과도한 권한 중 하나
- ZAP·Trivy 등 자동 도구 결과와 수동 검증 결과 비교
- 조치 전후의 요청·응답·로그·코드·설정 증적
- 결과 상태와 재점검 이력을 추적하는 장부 또는 자동 보고

### 직무별 어필 지점

| 직무 | 프로젝트에서 보여줄 증거 |
|---|---|
| 기술 취약점 진단·보안컨설팅 | 재현 절차, 오탐 검증, 증적, 영향도, 개선안, 재점검 |
| 취약점 관리 | finding 상태, 담당·기한·예외, 조치 이력, 종료 기준 |
| 보안 자동화 | 스캔 결과 수집, 증거 저장, 회귀 테스트, 보고 자동화 |
| AppSec | 코드·업무 문맥 분석, 조치안 협의, 수정 후 재검증 |
| 클라우드·컨테이너 보안 | 이미지·secret·권한·배포 설정 점검 |

### AI 적용 경계

AI는 프로젝트의 필수 본체가 아니라 선택 기능으로 둔다.

- 가능 역할: `Manual` 결과의 추가 증거와 후속 검증 절차 제안, 증거 요약, 보고서 초안
- 금지할 과장: AI가 취약 여부를 완전히 자동 판정했다는 주장
- 최종 판정: 사람이 증거를 확인하고 승인

### 피해야 할 방향

- Juice Shop 문제를 많이 푼 기록만 남기는 구성
- Kubernetes와 보안도구를 여러 개 설치한 뒤 보안 프로젝트라고 부르는 구성
- 공격 수를 과도하게 늘려 조치와 재점검이 비는 구성
- AI Agent를 제목으로 내세우고 실제 검증 흐름은 미완성으로 남기는 구성
- `Red Team`, `완전 자동 진단`, `AI 최종 판정` 등 현재 증거보다 큰 표현

## 5. 멘토·강사·팀 확인 전 남은 결정

1. 신입 기술 진단·취약점 관리 지원자에게 공격 개수보다 오탐 검증과 조치·재점검의 깊이가 더 강한 증거가 되는가?
2. 실무에서는 이 흐름이 `기술 취약점 진단`, `취약점 관리`, `AppSec` 중 어떤 직무명으로 채용되는가?
3. 4주·3~4명 기준으로 웹과 컨테이너를 함께 다루는 범위가 적절한가, 아니면 웹에 집중해야 하는가?
4. 교육과정의 최종 프로젝트 요구사항과 조원들의 실제 구현 가능 범위는 어디까지인가?

## 최종 판단

장운호에게는 가장 넓은 신입 입구에 맞춰 보안관제를 선택하는 것보다, 현재의 증거 판정·재현·문서화 역량을 살려 `기술 취약점 진단·보안컨설팅`으로 진입하고 `취약점 관리·보안 자동화·AppSec`으로 확장하는 경로가 더 자연스럽다.

3차 프로젝트 역시 모의해킹의 난도를 과장하거나 클라우드 기술을 전시하기보다, **공격 결과가 실제 취약점인지 검증하고 조치 완료까지 증명하는 닫힌 루프**를 만드는 것이 현재 강점을 가장 선명하게 보여주는 조건부 1순위 가설이다.
