## 2. 점검 중에는 실제로 어떤 일을 할까

다음은 **4번류 지식에 기반한 일반적인 운영 설명 모델**이다. 메이플의 내부 Runbook을 재현한 것이 아니며, 모든 점검이 모든 단계를 수행하는 것도 아니다. Runbook은 작업 순서·확인 조건·실패 시 조치를 적은 운영 절차서다.

```text
사전 준비: 배포물·변경 범위·복구 방법 준비
    ↓
신규 이용 제한 → 진행 중 작업 정리
    ↓
변경 전 상태·복구 가능 여부 확인
    ↓
코드·설정 반영 + 필요한 데이터 변환
    ↓
서비스 기동·연결·준비 상태 확인
    ↓
핵심 이용 경로·데이터 검증
    ↓
개방 판단 → 이용 재개 → 오류·지연 관찰
```

### 2.1 새 작업을 막고 진행 중 작업을 정리한다

옥션 거래를 예로 들면 구매자의 재화 차감, 아이템 이전, 판매자의 정산 기록이 서로 맞아야 한다. 변경 도중 일부 단계만 처리된 상태가 남지 않도록 신규 요청을 제한하고, 처리 중인 작업의 완료·취소·재시도 방식을 관리해야 한다.

- **Connection draining:** 새로운 연결·요청 유입을 줄이고 기존 작업이 정리될 시간을 준다.
- **Graceful shutdown:** 종료 신호를 받은 애플리케이션이 연결·저장 작업을 정리한 뒤 종료한다.
- **Quiescing:** 변경 대상의 활동을 안정된 상태로 가라앉힌다.

이들은 관련된 개념이지만 같은 기능은 아니다. 연결을 끊는 것만으로 거래의 원자성이나 데이터 일관성이 보장되지는 않는다. 여러 서비스에 걸친 거래라면 실패·재시도·중복 처리까지 애플리케이션이 설계해야 한다.

### 2.2 운영 환경에 코드·설정·데이터를 반영한다

일반적인 패치에서는 사전에 개발·시험한 배포물과 설정을 운영 환경에 반영한다. 점검 중 문제가 드러나면 추가 수정과 재배포가 생길 수 있다.

여기서 구분해야 하는 것이 **코드 교체와 데이터 변환**이다.

```text
코드 교체: 앞으로 잔여 시간을 계산하는 프로그램 변경
데이터 변환: 이미 저장된 이용자별 잔여 시간을 새 기준으로 조정
```

MVP 개편 안내는 두 번째 문제를 떠올리게 한다. 다만 공지의 “잔여 시간 조정”만으로 전체 계정을 한 번에 SQL로 갱신한다고 확정할 수는 없다. 일괄 배치, 접속 시 변환, 조회 시 계산 등 구현은 다를 수 있다. **데이터 의미의 전환이 필요하다는 것과 실제 DB Schema가 바뀐다는 것은 별개다.**

이벤트 변경도 같은 관점에서 볼 수 있다. 이벤트 시작·종료 시각, 상점, 퀘스트, 보상 조건을 함께 변경한다면 각각이 같은 규칙을 가리키는지 확인해야 한다. 이는 일반적인 예시이며, 이번 점검의 내부 작업 목록은 아니다.

### 2.3 서비스를 올리고 준비됐는지 확인한다

프로세스가 실행돼도 DB 연결, 설정 읽기, 캐시 준비, 다른 서비스 연결이 끝나지 않았을 수 있다. 의존성이 있는 구성 요소들은 준비 상태를 확인하고, 필요하면 재시도하며 기동한다.

Kubernetes의 `readinessProbe`는 **트래픽을 받을 준비가 됐는지** 판단하는 장치다. 실패하면 Pod를 일반 Service 트래픽의 준비된 대상으로 취급하지 않는다. `livenessProbe`는 재시작이 필요한 상태 판단, `startupProbe`는 느린 초기 기동 보호에 쓰인다. [Kubernetes 공식 문서: Probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)

**Readiness는 개발자가 정한 검사 조건을 통과했다는 뜻이다.** 로그인부터 결제·아이템 지급까지 모든 기능이 정확하다는 증명은 아니다.

### 2.4 실제 이용 경로를 검증하고 개방을 판단한다

일반적인 검증 예시는 다음과 같다.

| 확인 대상 | 확인하려는 것 |
|---|---|
| 로그인 → 캐릭터 접속 → 이동 | 핵심 이용 경로가 이어지는가 |
| 재화 차감 → 아이템 지급 | 거래 결과가 일관되고 중복되지 않는가 |
| 변환 전후 대상 수·값 비교 | 누락·중복·잘못된 변환이 없는가 |
| 이벤트·상점·보상 | 변경한 규칙과 실제 동작이 일치하는가 |
| 오류 로그·응답 지연·의존 서비스 | 개방을 막아야 할 이상 징후가 있는가 |

`Smoke test`는 핵심 경로가 기본적으로 동작하는지 짧게 확인하는 검사다. 자동 검사와 수동 확인을 조합할 수 있으며, 문제가 나오면 수정·재배포·재검증 또는 복구가 필요하다. 어떤 검사와 도구를 넥슨이 사용했는지는 이번 자료로 확인하지 않았다.

## 3. 왜 몇 시간이 필요할 수 있을까

**각 작업의 양뿐 아니라, 다음 단계가 기다려야 하는 조건이 있기 때문이다.**

- 데이터 작업은 대상 수·처리 속도·잠금·검증 방식에 따라 오래 걸릴 수 있다.
- 의존 서비스가 준비돼야 다음 단계의 검증을 진행할 수 있다.
- 코드·데이터·클라이언트가 함께 바뀌면 호환성을 확인할 범위가 넓어진다.
- 문제 발생 시 재작업하거나 복구할 여유 시간을 작업 창에 둘 수 있다.

여러 작업이 병렬로 진행되더라도 서비스 개방은 마지막 필수 조건이 충족될 때까지 기다려야 한다. 반대로 점검 시간이 길다는 사실만으로 DB가 느렸다거나 서버 수가 많았다고 판단할 수도 없다. **이번 공지만으로 7시간의 시간 배분과 병목을 산출할 수는 없다.**

### Service와 Rolling Update만 있으면 점검이 없어질까

Service는 Pod가 바뀌어도 사용할 수 있는 진입점을 제공하고, Deployment의 Rolling Update는 Pod를 점진적으로 교체한다. 그러나 이 기능들이 다음 문제를 자동으로 해결하지는 않는다.

- 구·신 버전이 같은 DB 값과 메시지를 서로 호환되게 해석하는가.
- 기존 클라이언트가 새 서버 프로토콜을 사용할 수 있는가.
- 장시간 유지한 연결과 서버 메모리의 세션 상태를 어떻게 처리하는가.
- 기존 거래가 끝나기 전에 서버를 종료하면 어떻게 복구하는가.

예를 들어 A 서버의 게임 세션은 A를 Backend에서 제외했다고 B 서버로 자동 이전되지 않는다. 연결을 종료하고 재접속하게 할지, 세션 상태를 외부에 저장할지, 별도 이전 절차를 만들지는 애플리케이션 설계에 달려 있다. HTTP 서비스에도 장기 연결과 세션이 있을 수 있으므로 “웹은 무조건 Stateless, 게임은 무조건 Stateful”로 나누지는 않는다.

Kubernetes는 Pod 종료 시 EndpointSlice에 종료 상태를 표시하고 일반 트래픽에서 제외되도록 처리하지만, 애플리케이션은 종료 유예 시간 안에 작업을 정리하도록 구현해야 한다. [Kubernetes 공식 문서: Pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination)

### Rollback의 대상부터 구분한다

| 복구 대상 | 필요한 판단 |
|---|---|
| Pod Template | 이전 Image·Template으로 돌아갈 수 있는가 |
| 설정·클라이언트 | 돌아간 서버와 호환되는가 |
| 변경된 DB 데이터 | 역변환·백업 복원·추가 보정 중 무엇이 가능한가 |
| 개방 후 발생한 거래 | 복구 과정에서 정상 거래까지 잃거나 중복 처리하지 않는가 |

`kubectl rollout undo`는 Deployment의 이전 Pod Template을 복원한다. 이미 변환한 이용자 데이터나 지급된 아이템을 취소하는 명령이 아니다. [Kubernetes 공식 문서: Rolling Back a Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#rolling-back-a-deployment)

일반적인 데이터 변경 준비에서는 복구 지점과 복원 가능 여부, 중간 실패 후 재실행해도 중복 변환되지 않는지 등을 검토할 수 있다. 예를 들어 “잔여 시간을 일정 비율로 줄이는 작업”이 두 번 적용되지 않도록 대상·완료 여부를 관리하는 문제다. 실제 복구 방법은 DB와 변경 설계에 따라 다르다.

이 구분은 기존 [[10_학습 노트/클라우드/Kubernetes/Lab_EKS Deployment 기초와 Rolling Update 실습#실제 장애 사례: Destiny 2 계정 데이터 손상과 전체 Rollback\|Destiny 2 장애 사례 정리]]와 이어진다. 프로그램을 되돌리는 것과 손상된 서비스 데이터를 복구하는 것을 따로 보아야 한다.

## 5. 보안과 NDC로 이어지는 학습

### 변경 권한과 변경 기록

운영 변경에는 권한이 필요하다. Kubernetes에서는 RBAC로 필요한 Resource·동작의 범위를 제한하고, Audit로 API 요청의 주체·시각·대상·처리 정보를 추적할 수 있다. 감사 기록의 범위와 저장 여부는 설정에 달려 있다. [RBAC 권장 사항](https://kubernetes.io/docs/concepts/security/rbac-good-practices/), [Auditing](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/)

운영 장애 분석에서도 “장애 직전에 무엇이 바뀌었는가”를 확인하기 위해 배포 기록·감사 로그·애플리케이션 로그를 연결한다. Kubernetes Audit만으로 애플리케이션 내부 거래나 DB 변경 전체가 기록되는 것은 아니다.

### 메이플스토리M DevSecOps 사례

넥슨의 [메이플로그: 메이플스토리 IP 개발 생태계 in NDC](https://blog.maplestory.nexon.com/stories/147818)는 메이플스토리M의 인프라 코드화와 DevSecOps 전환을 소개한다. 공식 소개 글에서 읽을 수 있는 학습 연결점은 다음과 같다.

- 기존 운영 자원을 Terraform 기반 코드 관리로 옮길 때, 매핑 오류로 정상 서버를 삭제할 위험을 다뤘다.
- 변경 코드 검토와 위험한 변경의 배포 차단을 운영 절차에 넣었다고 소개한다.
- 개발·보안·운영이 안전한 변경 방식에 합의하는 문제를 강조한다.

**이 자료는 메이플스토리M 인프라 전환 사례다.** PC 메이플의 이번 패치가 어떤 서버 구조로 실행됐는지, 왜 7시간을 잡았는지 증명하지 않는다. 또한 여기서는 공식 소개 글을 확인했으며 NDC 발표 영상 전체를 검증한 것은 아니다. 후속 학습에서는 해당 글에 연결된 발표를 통해 구체적인 전환 절차와 검증 방법을 살펴볼 수 있다.

## 근거와 남은 한계

- **1번류 — 로컬 1차 증거:** 위에 연결한 Service·Deployment 실습 노트의 기록. 현재 실행 환경의 재검증은 하지 않았다.
- **2번류 — 공식 외부 근거:** 본문에 링크한 메이플 공지·테스트월드 안내·넥슨 공식 소개 글·Kubernetes 문서.
- **3번류 — 비공식 외부 자료:** 이 노트의 근거로 사용하지 않았다.
- **4번류 — 모델 내부 지식:** 일반적인 점검 절차·거래·복구 설명 모델. 이번 서비스의 내부 구현 사실로 취급하지 않는다.

이번 점검의 실제 Runbook, 분 단위 작업 기록, 본 서버 데이터 변환 완료, 시간별 병목은 확인하지 않았다. 학습 대화의 가상 시간표와 “현재는 특정 작업 중일 것”이라는 추정은 사실 기록에 포함하지 않았다.
