# 2026-07-30 프로젝트 일일 로그

## 당분간의 최상위 계획 — 다음 멘토 상담 전 평가 가능한 상태 준비

- 다음 멘토 상담이 다음 주 화요일에서 다다음 주 화요일로 연기됐다.
- 팀 내부·AI 평가만으로 프로젝트 방향을 확정하기보다, 현업 멘토가 구체적으로 평가할 수 있는 실행 결과와 초안을 충분히 준비한다.
- 상담 전까지 인프라와 웹 애플리케이션을 팀 기준 약 90% 수준으로 준비하고, 보고서는 프로젝트의 방향성과 전체적인 느낌을 판단할 수 있는 초안까지 작성한다.
- 이때 `90%`는 프로젝트 전체 완성도가 아니라 `멘토 평가 준비도`다. 로그·탐지·자동 조치의 본편 완성도와 구분한다.
- 상담 전 목표는 정답을 미리 확정하는 것이 아니라, 작동하는 환경·증거·후보 시나리오·미정 질문을 현업자가 비교하고 보정할 수 있는 상태를 만드는 것이다.

## 주요 시행착오

| 문제 | 원인·확인 | 조치·상태 |
|---|---|---|
| IAM OIDC Provider 생성 실패 | 첫 Apply에서 `HTTP 302 / UnknownError` 발생 | 성공 Resource를 State에 유지하고 재계획·재시도해 완료 |
| Deploy Key 빈 목록 오류 | PowerShell StrictMode에서 `null.title` 접근 | 빈 배열 처리를 추가해 재실행 완료 |
| Windows 임시 Secret ACL 실패 | Account 문자열 처리 오류 | 현재 Windows Identity를 정확히 사용하도록 보정 |
| RDS `ERROR 3159` | MariaDB 11.8 `require_secure_transport=ON` | RDS Global CA Bundle 기반 TLS 연결 적용 |
| Argo Bootstrap 거부 | CRD가 `spec.syncPolicy.retry.refresh`를 지원하지 않음 | 비지원 필드를 제거하고 지원되는 Retry만 유지 |
| CloudFront 504·Target Timeout | ALB에서 Kubernetes Node 80/TCP로 가는 SG Rule 누락 | Primary·DR ALB→Node Ingress Rule 추가 |
| 의도하지 않은 Node Rolling Update | EKS Module이 최신 권장 AMI Release를 자동 추종 | 지역별 `ami_release_version` 고정 후보를 확인하고 현재는 보류 |
| Argo 자연 감지 시간 미측정 | UI `Refresh`와 수동 refresh annotation이 모두 개입 | 현재 설정 `180s`, Webhook 없음은 확인했으나 자연 Polling 실측은 후속으로 남김 |

## 막힌 점

| 문제 | 확인한 사실 | 다음 확인 |
|---|---|---|
| Down→Up 반복 재현 미완료 | `daily-up`과 Runtime E2E는 성공했지만 실제 `daily-down`을 아직 실행하지 않음 | Destroy 잔존 0, 다음 Cold Start, Down 상태 Push 후 복원까지 검증 |
| 팀 환경 이식성 미검증 | 개인 Account와 노트북에서는 작동했지만 다른 Account·노트북 증거가 없음 | State·Credential·Private Key 복사 없이 Source와 Parameter만으로 재생성 |
| 보안 본편 범위 미확정 | 현재 검증된 로그는 CloudTrail Management Event 중심 | 대표 시나리오별 WAF·ALB/CloudFront·EKS Audit·S3 Data Event·앱 로그 필요성을 결정 |
| 탐지·자동 조치 미구현 | 로그 저장 기반은 생겼지만 탐지 규칙·경보·대응 자동화는 없음 | 탐지 조건, 알림 대상, 자동 조치와 사람 승인 경계를 설계 |
| 최상위 목적과 대표 시나리오 미확정 | `로그·보안·자동 조치` 축은 있으나 팀의 최종 문장과 범위는 없음 | 작동 환경과 보고서 초안을 근거로 멘토에게 비교·보정 요청 |
| 보고서 초안 부재 | RAW와 실행 증거는 많지만 평가용 구조로 묶이지 않음 | 목표·As-built·시행착오·증거·후보·질문을 우선 작성 |

## 보안·비용·운영 주의

- 개인 AWS Account의 실행 성공을 다른 Account·노트북에서의 이식 완료로 간주하지 않는다.
- 현재 Runtime은 Argo CD와 웹 애플리케이션 검증을 위해 살아 있으며, `daily-down` 전까지 비용이 계속 발생한다.
- CloudTrail 전용 S3·CloudWatch는 Foundation이며 일반 Daily Destroy 대상이 아니다.
- 현재 검증된 보안 로그 범위는 CloudTrail Management Event 중심이다. 다른 로그와 탐지·자동 조치를 구현한 것으로 과장하지 않는다.
- Private Repository 조건에서 CodeQL은 의도적으로 Skip됐고, 이번 변경의 정적 보안 검사는 SL Scan Artifact로 보존됐다.
- Argo `Refresh`가 개입한 배포를 자연 Polling 성능 측정 결과로 사용하지 않는다.
- Access Key, Token, Password, Private Key, kubeconfig와 실제 Secret 값은 Vault에 기록하지 않는다.

## 보고서 재료

- 성과:
  - EKS가 없는 상태에서도 CI가 Image와 GitOps 선언을 보존하고, Runtime 생성 뒤 Argo CD가 최신 선언으로 복원하는 흐름을 실제 검증했다.
  - PR 병합에서 EKS Rolling Update와 외부 응답까지 Source Commit·Image Tag·GitOps Revision으로 추적했다.
  - Runtime과 별도 수명주기를 가진 CloudTrail 증거 보존 계층과 로컬 Hash Index를 구성했다.
- 시행착오:
  - IAM OIDC 일시 오류, Windows ACL, RDS TLS, Argo CRD Schema, ALB SG, EKS AMI Drift를 실제 실행 중 발견하고 원인별로 보정·보류했다.
  - 취약한 교육용 웹앱을 그대로 배포하지 않고 Security Level에 따라 취약·조치 동작을 구분했다.
  - Argo UI Refresh가 실험에 개입해 자연 감지 시간을 측정할 수 없었던 점을 별도 실험 조건으로 분리했다.
- 그림 / 표 후보:
  - `Foundation 보존 계층 ↔ Daily Runtime 생성·삭제 계층`
  - `PR Merge → GitHub Actions → ECR → GitOps Commit → Argo CD → ReplicaSet Rolling Update`
  - `CloudTrail → CloudWatch·S3 → Evidence Sync → SHA-256 Index`
  - `실패 증상 → 원인 → 조치 → 재검증` 타임라인
  - `상담 전 준비도와 보안 본편 완성도의 구분`
