## 주요 보안 검토

| 발견 | 영향 | 당일 결정·경계 |
|---|---|---|
| 자유로운 SSM Remote-host Port Forwarding | 변조된 Workflow가 Bastion을 경유해 IMDS·RDS 등 내부 Endpoint에 접근할 가능성 | 자유 입력 Document를 제거하고 EKS API로만 이어지는 고정 Proxy·Port 방식 검토 |
| Kubernetes `create` 및 Secret·`pods/exec` 권한 | 이름 제한이 불완전하고 DB 자격증명 조회·Container 임의 명령 실행으로 이어질 수 있음 | 관리자 Bootstrap의 Named Placeholder와 Exact `get/patch/update` 검토; Secret 조회와 `pods/exec` 제거 |
| 공식 DVWA의 `vulnerable.yml` | Secrets·Variables를 JSON/Base64로 출력해 Workflow 재사용 시 Secret 노출 가능 | 삭제 상태를 유지하고 신규 CI/CD에서 호출·재사용하지 않음 |
| Bastion SSH `0.0.0.0/0`와 과권한 Role | Bastion 침해 시 EKS 관리자 권한과 RDS Secret까지 피해가 확장될 수 있음 | 운영을 임의 중단하지 않고 사용자 IP `/32` 또는 SSM-only 전환을 후속 결정으로 보류 |
| DR ALB HTTP 80 공개 | DR 연결 후 CloudFront·WAF를 거치지 않는 직접 접근 경로가 될 수 있음 | 현재 DVWA Preview 범위에서는 제외하고 DR Failover 설계 때 별도 통제 검토 |
| 이동 가능한 GitHub Action tag | 외부 Action 변조 시 OIDC·ECR·Deploy Key를 다루는 Job에서 악성 코드 실행 가능 | 공식 Release의 Commit을 확인해 Full-length SHA로 고정하기로 결정 |
| 이동 가능한 Container Base Image tag | 같은 Git Commit을 다시 Build해도 Image Digest와 Package가 달라질 수 있음 | Digest 고정과 갱신 절차를 후속 공급망 Hardening으로 분리 |
| Bastion CLI Download 무결성 미검증 | 변조된 배포 Artifact가 EKS 관리자 권한을 가진 Bastion에 설치될 수 있음 | Version과 공식 Checksum 고정을 후속 후보로 기록 |

## 결정

| 결정 | 이유 | 영향 |
|---|---|---|
| 개인 계정 검증과 팀 계정 완료를 구분 | Account·Region별 선행 조건과 실제 운영 경계가 다름 | 개인 계정 Apply 성공을 팀 운영 계정 배포 완료로 주장하지 않음 |
| Foundation과 Daily Runtime을 별도 Root·State로 분리 | 매일 비용 자원을 제거하면서 CI/CD 연결과 최신 Image는 보존해야 함 | ECR·GitHub OIDC·IAM·GitHub 연결은 보존하고 VPC·EKS·RDS 등 Runtime은 매일 삭제하는 방향 |
| DVWA DB 데이터는 보존하지 않음 | 비용 절약용 Lab에 기존 데이터·Snapshot 복구가 필요하지 않음 | 다음 Apply에서 빈 DB와 기본 Schema·Seed를 자동 생성하도록 단순화 |
| GitHub 선언을 GitOps 복원의 기준으로 사용 | 수동 Kubernetes 객체는 Runtime 삭제와 함께 사라짐 | Apply 이후 Repository 인증과 Argo Application을 자동 재생성해야 함 |
| 공식 DVWA 취약 Workflow는 사용하지 않음 | Secret 노출을 학습용 CI/CD에 포함할 이유가 없음 | GitHub OIDC 임시 자격증명과 ECR 최소 권한 Role만 사용 |
| 알 수 없는 Resource는 자동 삭제하지 않음 | 잘못된 Drift 판정과 범위 밖 Resource 삭제를 막아야 함 | ID를 보고하고 중단하는 보수적 운영 원칙 유지 |

| Daily Script 신뢰성 결함 | SSM 1회 조회, 빈 State에서 제한된 Drift 검사, 잔존 과금 Resource 미확인, Argo 일시 실패 재시도 부재 | Bounded polling, Tag 기반 잔존 검사, Argo retry 보정 |
| 팀 계정·팀 노트북 이식성 미검증 | 개인 State·Credential·Private Key를 복사해서는 안 됨 | Account·Profile·Region·Path Parameter화 후 Source만으로 재생성 검증 |
| Terraform RDS 수명주기 불일치 | 현재 Code의 삭제 보호·Final Snapshot 설정이 매일 삭제 결정과 맞지 않음 | Daily Runtime 정책에 맞는 RDS 삭제 설정 검토 |
| 완전한 Reproducible Build 미달 | `sha-<commit>` Image tag만으로 Upstream Base Image 동일성을 보장하지 못함 | Base Image digest와 갱신 절차 결정 |

## 보안·비용·운영 주의

- Access Key, Token, Password, Private Key와 실제 Secret 값은 RAW·일일 로그에 기록하지 않는다.
- 개인 계정 Apply 결과는 팀 계정 배포 완료 증거로 사용하지 않는다.
- Bastion 공개 범위와 과권한 Role은 확인됐지만 기존 운영 경로를 임의로 중단하지 않았다.
- DR ALB 공개 경로는 이번 Preview Goal 밖이며, DR Backend 연결 전에 별도 접근 통제가 필요하다.
- Foundation/Daily Runtime 분리는 비용 절약 설계이지만 실제 Destroy·Cold Start 반복 검증 전에는 완성으로 판정하지 않는다.
- DVWA의 의도적 취약 Workflow와 Setup Endpoint를 운영 자동화에 그대로 연결하지 않는다.
