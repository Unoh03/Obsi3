# 1. 프로젝트 개요

## 1.1 프로젝트명

**온프레미스 및 AWS 환경 기반 웹 보안 취약점 점검과 통합 로그 분석 시스템**

## 1.2 프로젝트 목표

동일한 웹 서비스를 온프레미스와 AWS 환경에 각각 구축하고, 주요 웹·서버·네트워크 보안 취약점을 안전한 실험 환경에서 점검한다. 이후 WAF, 웹 서버, 애플리케이션, 데이터베이스 등에서 생성되는 로그를 수집·정규화·집계하여 보안 이벤트를 조회하고, 보안 조치 전후의 결과를 비교한다.

본 프로젝트는 단순히 취약점 공격 성공 여부를 보여주는 데 목적을 두지 않는다. 다음과 같이 취약점 진단부터 로그 분석, 보안 조치, 재검증까지의 흐름을 하나의 프로젝트로 완성하는 것을 핵심 방향으로 한다.

```text
온프레미스·AWS 환경 구축
→ 보안 취약점 점검
→ 정상·공격 시나리오 실행
→ 다계층 로그 수집
→ 로그 정규화·집계·조회
→ 보안 설정 및 코드 조치
→ 동일 테스트 재검증
```

## 1.3 추진 배경

일반적인 보안 프로젝트는 웹 취약점 재현, 클라우드 인프라 구축, 방화벽 설정, 로그 대시보드 구성 등을 각각 독립적으로 수행하는 경우가 많다. 이 경우 공격과 탐지, 대응의 관계가 명확하지 않고 실제 보안 운영 관점의 설명이 부족할 수 있다.

본 프로젝트는 하나의 공격 시나리오를 중심으로 다음 내용을 연결한다.

- 어떤 보안 설정 또는 코드가 취약한가

- 취약점이 실제로 어떤 요청을 통해 재현되는가

- 각 계층에서 어떤 로그가 생성되는가

- 로그를 어떤 기준으로 정리하고 조회할 수 있는가

- 보안 조치 후 동일 요청의 결과가 어떻게 바뀌는가

- 온프레미스와 AWS 환경의 보안 운영 방식에는 어떤 차이가 있는가

이상치 탐지, 머신러닝, 자동 대응, LLM 기반 사고 요약은 핵심 완료 범위에서 제외하고, 프로젝트 진행 상황에 따라 선택적으로 확장한다.

## 2.2 환경 구성

온프레미스와 AWS는 서로 직접 연결하지 않고, 동일한 조건을 적용할 수 있는 독립된 두 실험 환경으로 구성한다. 애플리케이션 코드, 합성 데이터, 테스트 계정 및 취약점 검증 시나리오는 최대한 동일하게 유지한다. 두 환경 모두 애플리케이션은 Docker 컨테이너로 패키징하고 Kubernetes로 오케스트레이션하여, 동일한 컨테이너 이미지와 매니페스트를 온프레미스·AWS에 동일하게 배포한다.

### 온프레미스 환경

```text
테스트 클라이언트
│
▼
방화벽
│
▼
Nginx + ModSecurity
│
▼
Web Application
│
▼
MYSQL
│
▼
중앙 로그 저장·조회 시스템
```

주요 구성요소는 Linux 서버, Nginx, ModSecurity, MySQL, Fluent Bit 또는 Filebeat, OpenSearch 또는 ELK로 구성한다.

### AWS 환경

```text
Internet
│
AWS WAF
│
Application Load Balancer
│
EC2 기반 Web Application
│
RDS MySQL
│
CloudWatch·S3·OpenSearch
```

AWS 환경에서는 VPC, Public·Private Subnet, ALB, AWS WAF, EC2, RDS, CloudWatch Logs, VPC Flow Logs 등을 활용한다. 데이터베이스는 외부에서 직접 접근할 수 없도록 Private Subnet과 Security Group을 적용한다.

## 2.3 가상 웹 서비스

합성 고객·상품·주문 데이터를 사용하는 간단한 주문관리 또는 쇼핑몰 서비스를 구현한다.

일반 사용자 기능은 로그인, 상품 검색, 상품 상세 조회, 본인 주문 조회, 프로필 조회로 구성한다. 운영자 기능은 고객 주문 조회, 주문 상태 변경, 서비스 현황 조회 정도로 제한한다.

| **데이터**  | **권장 규모** |
|-------------|---------------|
| 일반 사용자 | 100~300명     |
| 운영자      | 3~10명        |
| 상품        | 500~1,000개   |
| 주문        | 3,000~5,000건 |

모든 사용자 정보와 주문 정보는 합성 데이터로 생성하며 실제 개인정보는 사용하지 않는다.

# 3. 취약점 점검과 검증 시나리오

## 3.1 대표 시나리오

```text
1. 로그인 및 관리자 관련 경로 탐색
2. 테스트 계정을 대상으로 반복 로그인 요청
3. 정상 또는 테스트 계정 로그인
4. 본인 주문 조회
5. 주문 ID를 변경하여 타인 주문 조회
6. 주문 ID를 순차 또는 무작위로 반복 조회
7. 상품 검색 기능에서 제한된 SQL Injection 점검
8. 각 계층에서 발생한 로그 수집
9. 애플리케이션 코드와 보안 정책 조치
10. 동일 요청 재실행 및 결과 비교
```

## 3.2 핵심 취약점

| **취약점**         | **검증 목적**                       | **주요 로그**                                 | **조치 후 기대 결과**          |
|--------------------|-------------------------------------|-----------------------------------------------|--------------------------------|
| 불충분한 권한 검증 | 다른 사용자의 주문 접근 가능 여부   | 웹 접근 로그, 애플리케이션 감사 로그, DB 로그 | 타인 주문 요청 시 403          |
| 자동화 공격        | 반복 로그인 및 대량 조회 통제 여부  | 인증 로그, WAF 로그, 접근 로그                | Rate Limit, 계정 임시 잠금     |
| 불충분한 세션 관리 | 로그아웃·잠금 이후 세션 재사용 여부 | 인증·세션 로그                                | 기존 세션 사용 시 401 또는 403 |
| SQL Injection      | 입력값 검증과 WAF·DB 가시성 확인    | WAF, 웹, 애플리케이션, DB 오류 로그           | Parameter Binding 및 요청 차단 |

### 불충분한 권한 검증

대표 API는 다음과 같이 구성한다.

|                            |
|----------------------------|
| GET /api/orders/{order_id} |

취약 상태에서는 사용자의 로그인 여부만 확인하고 요청 사용자와 주문 소유자의 일치 여부를 확인하지 않는다. 보안 조치 후에는 일반 사용자가 본인의 주문만 조회할 수 있도록 서버 측 소유권 검증을 수행하고, 운영자는 명시된 역할과 권한에 따라 접근하도록 한다.

검증 시에는 본인 주문 조회, 타인 주문 단건 조회, 순차 ID 조회, 무작위 ID 조회, 느린 반복 조회, 운영자의 정상 다건 조회를 포함한다.

### 자동화 공격

로그인 시도와 주문 조회 API에 반복 요청 통제가 없는 상태를 점검한다. 한 계정에 대한 반복 로그인, 한 IP에서 여러 계정에 대한 로그인, 로그인 실패 후 성공, 주문 조회 API 반복 호출을 검증한다.

보안 조치로는 계정·IP 단위 Rate Limit, 계정 임시 잠금, 단위 시간당 요청 제한을 적용한다.

### 세션 관리

로그아웃 후 기존 세션 재사용, 유휴 세션 만료, 절대 만료 시간, 계정 잠금 후 기존 세션 사용 여부를 점검한다. 쿠키에는 Secure, HttpOnly, SameSite 설정을 적용한다.

### SQL Injection

상품 검색 API 한 곳만 제한적으로 취약하게 구성한다.

|                                      |
|--------------------------------------|
| GET /api/products/search?q={keyword} |

정상 검색 요청과 비정상 입력의 응답 차이, WAF 탐지 여부, 웹·애플리케이션·DB 로그 발생 여부를 확인한다. 전체 데이터베이스 조회, 데이터 삭제, 파일 시스템 접근, 운영체제 명령 실행 등은 범위에서 제외한다.

## 3.3 서버 및 방화벽 설정 점검

웹 취약점 외에도 다음 설정을 점검한다.

- root 원격 접속 제한

- SSH 접근 IP 제한

- 불필요한 서비스와 포트 비활성화

- 웹 서비스 프로세스 최소 권한

- 설정·백업 파일 외부 노출 방지

- 데이터베이스 외부 직접 접근 차단

- 로그 디렉터리 권한

- 보안 패치 적용 상태

- NTP 및 시각 동기화

- 방화벽 기본 차단과 최소 허용 정책

- WAF 로그와 차단 규칙 활성화

각 항목은 양호, 취약, 해당 없음으로 기록하고, 취약 항목은 조치 후 동일 기준으로 재점검한다.

## 3.4 컨테이너·쿠버네티스 취약점 점검

온프레미스와 AWS 양쪽 모두 애플리케이션을 Docker 컨테이너와 Kubernetes로 운영하므로, 컨테이너·오케스트레이션 계층의 대표 취약점을 동일한 기준으로 점검하고 조치 후 재검증한다.

| **취약점**             | **검증 목적**                                      | **주요 로그**                | **조치 후 기대 결과**                     |
|------------------------|----------------------------------------------------|------------------------------|-------------------------------------------|
| 취약한 컨테이너 이미지 | 알려진 CVE 및 오래된 베이스 이미지 사용 여부       | 이미지 스캔 로그             | Critical/High 취약점 미포함 이미지만 배포 |
| 과도한 컨테이너 권한   | privileged 모드, root 실행, 불필요 Capability 여부 | kubelet·컨테이너 런타임 로그 | non-root, Capability 최소화 적용          |
| Kubernetes RBAC 오설정 | 과도한 ClusterRole·기본 ServiceAccount 권한 여부   | kube-apiserver 감사 로그     | 최소 권한 Role·RoleBinding 적용           |
| Pod 간 네트워크 미제한 | NetworkPolicy 부재로 인한 Pod 간 자유 통신 여부    | CNI·네트워크 정책 로그       | 필요 통신만 허용하는 NetworkPolicy 적용   |
| Secret 평문 노출       | 환경변수·이미지 내 자격 증명 하드코딩 여부         | 매니페스트·감사 로그         | Kubernetes Secret/외부 시크릿 관리로 전환 |

점검은 이미지 취약점 스캔, 클러스터 설정 진단, 런타임 동작 확인 순으로 진행하며, 대표 점검 명령은 다음과 같다.

```bash
# 컨테이너 이미지 취약점 스캔
trivy image myapp:latest
# Kubernetes 클러스터 설정 진단
kube-bench run
# 과도한 권한을 가진 Pod 확인
kubectl get pods -A -o json | grep -i privileged
```

이미지 스캔·kube-bench·감사 로그는 기존 로그 수집 파이프라인에 동일하게 통합하여, 웹 계층 취약점과 같은 방식으로 조회·집계·재검증한다.

# 4. 로그 수집·정규화·조회

## 4.1 필수 로그 소스

| **계층**    | **온프레미스**         | **AWS**                    |
|-------------|------------------------|----------------------------|
| WAF         | ModSecurity Audit Log  | AWS WAF Log                |
| Web         | Nginx Access·Error Log | ALB Access Log             |
| Application | JSON 인증·감사 로그    | CloudWatch Application Log |
| Database    | MySQL Log              | RDS MySQL Log              |
| Network     | 방화벽 로그            | VPC Flow Logs              |
| System      | syslog, auth.log       | CloudWatch Agent 선택      |

## 4.2 로그 처리 흐름

```text
원본 로그 생성
→ 로그 수집기 전송
→ 형식 파싱
→ 공통 스키마 변환
→ 중앙 저장소 적재
→ 조건 검색 및 집계
→ 대시보드 시각화
```

## 4.4 핵심 조회·집계 기능

- 기간 및 환경별 로그 조회

## 5.3 프로젝트 성공 기준

- 온프레미스와 AWS 환경에 웹 서비스가 각각 정상 구축된다.

- 핵심 취약점 3~4개를 통제된 환경에서 점검한다.

- WAF·웹·애플리케이션·DB 로그를 실제로 수집한다.

- 서로 다른 로그를 공통 필드로 정규화한다.

- IP·사용자·세션·요청 ID 기준 조회가 가능하다.

- 반복 로그인, 타인 주문 접근, 대량 조회, SQL Injection 관련 이벤트를 집계할 수 있다.

- 보안 조치 후 동일 테스트를 재실행하여 결과를 비교한다.

- 온프레미스와 AWS의 보안 설정 및 로그 운영 차이를 정리한다.

- 실제 개인정보, 외부 시스템 공격, 실제 DDoS는 사용하지 않는다.

## 5.4 기대 효과와 차별성

본 프로젝트의 차별점은 취약점을 많이 구현하는 데 있지 않다. 취약점 점검 결과를 여러 계층의 로그와 연결하고, 조회·집계를 통해 사고 흐름을 재구성하며, 보안 조치 후 동일한 테스트를 수행한다는 점에 있다.

이를 통해 다음 역량을 보여줄 수 있다.

- 웹 취약점 진단과 보안 조치

- 온프레미스·AWS 보안 아키텍처

- 방화벽 및 WAF 정책

- 이기종 로그 수집과 정규화

- SIEM 관점의 검색·집계·대시보드

- 보안 테스트 재현성과 조치 후 회귀 검증

- 보안관제, 클라우드 보안, 로그 엔지니어링 직무 연계

이상치 탐지와 머신러닝은 프로젝트 핵심 흐름이 완성된 뒤 적용 가능한 보조 기능으로 유지하여, 기술 범위 확대보다 기본 보안 운영 흐름의 완성도를 우선한다.
