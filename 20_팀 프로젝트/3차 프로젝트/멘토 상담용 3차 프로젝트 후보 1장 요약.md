# 멘토 상담용 3차 프로젝트 후보 1장 요약

## 상담 배경

- 교육과정 3차 프로젝트의 상위 주제는 `퍼블릭 클라우드 기반 보안 운영`이다.
- 공지에는 IAM, 웹 위협, 네트워크, 로그, 모의해킹, 조치, IaC, DDoS, 백업 등 넓은 항목이 나열돼 있으나 필수·선택 구분은 아직 확인하지 못했다.
- 팀은 기술을 많이 넣는 것보다 **하나의 보안 질문을 공격·증적·조치·재검증까지 설명할 수 있는 방향**을 찾고 있다.
- 아래 세 안은 아직 후보이며, 합치거나 확정하지 않았다.

## 후보 3안

| 후보 | 한 문장 | 핵심 검증 | 강점 | 현재 고민 |
|---|---|---|---|---|
| **A. EKS 권한 오용 검증** | 침해된 것으로 가정한 Pod가 과도한 workload IAM 권한으로 S3 더미 객체에 접근하는 과정을 재현하고, 로그 확인 후 최소 권한 조치와 재검증을 수행한다. | `Pod → IRSA Role → S3 → EKS Audit Log·CloudTrail → IAM 조치 → 동일 조건 재검증` | 클라우드 IAM과 증적의 인과가 명확하고 과장 범위를 제한하기 쉽다. | `kubectl exec`로 최초 침투를 가정해도 유효한가? IRSA와 EKS Pod Identity 중 무엇이 적절한가? |
| **B. EKS 침투·위협 탐지** | 취약한 Pod에서 시작한 권한 오용이 AWS 리소스 접근으로 확산되는 흐름을 시연하고 로그 기반으로 탐지한다. | EKS·IAM 공격 경로와 CloudTrail·EKS 로그 분석 | 공격 서사가 직관적이고 모의공격팀·분석팀 협업을 보여주기 좋다. | 실제 container escape 없이 해당 표현을 쓰면 과장이다. 공격 후 조치·재검증도 보완해야 한다. |
| **C. 온프레미스·AWS 웹 보안 및 통합 로그** | 동일한 웹 서비스를 두 환경에 구성하고 IDOR·SQLi·세션·자동화 공격을 수행한 뒤 다계층 로그와 조치 전후를 비교한다. | 웹 공격·WAF·Application·DB 로그 정규화와 재검증 | 웹 취약점과 보안 운영 흐름이 구체적이고 원본 주제를 가장 넓게 다룬다. | 온프레미스·AWS·웹앱·Kubernetes·로그 플랫폼을 함께 다루면 중심축이 흐려질 수 있다. IaC와 AWS IAM 비중도 약하다. |

## 현재 판단

- **A안**은 하나의 클라우드 권한 경로를 깊게 검증하는 방향이다.
- **B안**은 공격 시연과 탐지 분석의 흡인력이 가장 강한 방향이다.
- **C안**은 웹 공격과 보안 운영 영역을 가장 넓게 보여주는 방향이다.
- 세 안의 기능을 모두 합치면 핵심 보안 질문이 사라질 수 있으므로, 먼저 중심축 하나를 선택한 뒤 필요한 요소만 가져오려 한다.

## 우선 질문

1. 공지된 항목들은 모두 구현해야 하는 필수 요구사항인가요, 아니면 팀별 주제에 맞게 선택하는 상위 영역인가요?
2. 신입 프로젝트 평가에서는 여러 보안 서비스를 구현한 폭과 하나의 공격 경로를 증적·조치·재검증까지 수행한 깊이 중 어디에 더 무게를 두시나요?
3. 위 세 방향 중 `퍼블릭 클라우드 기반 보안 운영`과 신입 포트폴리오를 함께 고려했을 때 가장 설득력 있는 중심축은 무엇인가요? 그렇게 판단하신 기준도 알고 싶습니다.

## 방향별 후속 질문

- **A·B안을 선택할 경우:** `kubectl exec`로 최초 침투를 통제해서 가정하고 이후 workload IAM 권한 오용을 검증하는 것도 유효한 보안성 점검인가요?
- **A·B안을 선택할 경우:** 신규 EKS 환경이라면 IRSA와 EKS Pod Identity 중 어떤 방식을 선택하는 것이 현재 실무와 학습 목적에 적절한가요?
- **C안을 선택할 경우:** 온프레미스와 AWS를 독립적으로 비교하는 것보다 AWS 한 환경에서 공격·로그·조치 흐름을 깊게 만드는 편이 더 나은가요?
- 공통적으로 반드시 남겨야 할 로그·증적과 과감히 제외해도 되는 산출물은 무엇인가요?
