# 1. 그대로 읽는 낭독형 대본

전체 약 10분을 기준으로 했다.

## 다이어그램 1 — 공격·수집·Wazuh 탐지

약 1분 35초

> 먼저 공격이 발생한 뒤, Wazuh가 이를 어떻게 탐지하는지 설명드리겠습니다.
> 
> 공격자는 DVWA의 Command Injection 취약점을 이용해 서버에 명령을 실행합니다. 실행되는 명령은 IMDS를 조회하는 명령인데요, 인스턴스 메타데이터 서비스의 약자이며 
> EC2 자기 자신에 대한 정보와, 그 EC2에 부여된 AWS 역할의 임시 자격증명을 내부에서 조회할 수 있게 해주는 서비스입니다.
> IMDS를 통해 서버에 부여된 AWS 역할을 알아내고, 그 권한으로 보호된 S3 파일을 읽습니다.
> 
> 저희는 이 공격과정을 두 가지 방법으로 수집했습니다.
> 
> 초록색 경로는 여러 AWS 로그를 5분마다 확인하는 방식입니다. 속도는 조금 느리지만 CloudTrail을 비롯한 여러 로그를 넓게 수집할 수 있고, 원본을 오래 보관하거나 나중에 다시 조사하기 좋습니다.
> 
> 분홍색 경로는 DVWA에서 중요한 사건이 발생하면 바로 Wazuh로 전달하는 방식입니다. 모든 내용을 보내는 것이 아니라, 명령어나 자격증명 같은 민감한 내용은 넣지 않고 탐지에 필요한 정보만 전달합니다.
> 
> 두 경로로 들어온 로그는 Wazuh에서 함께 확인합니다. Wazuh는 로그를 읽기 쉬운 항목으로 나눈 뒤, 미리 만든 Rule과 비교해 경보를 생성합니다.
> 
> Rule 100102는 빠른 전달 경로가 정상인지 확인하는 점검용 Rule입니다.
> 
> Rule 100110은 DVWA에서 AWS 임시 자격증명을 얻을 수 있는 주소의 출력이 실제로 반환됐는지를 확인합니다.
> 
> Rule 100111은 탈취한 역할로 S3 파일을 요청했고, 파일 내용이 실제로 반환됐는지를 확인합니다.
> 
> 이 두 경보는 자동으로 하나로 합쳐지는 것이 아닙니다. 발생 시각과 공격 식별값, Pod와 AWS 역할 등의 정보를 사람이 비교해 같은 공격인지 판단하도록 구성했습니다.

## 다이어그램 2 — Shuffle·GitOps 자동 대응

약 1분 30초

> 다음은 Wazuh가 만든 경보를 실제 대응으로 연결하는 과정입니다.
> 
> 여기서 Wazuh의 경보 전체를 그대로 Shuffle로 전달하지는 않습니다.
>
>먼저 Wazuh Integrator에서 자동 대응 대상으로 지정한 Rule 100110과 100111만 Custom Integration으로 전달합니다.
>
>그다음 `custom-shuffle-soc`라는 별도의 Integration Script가 Alert를 한 번 더 검증합니다. Rule ID만 확인하는 것이 아니라 Source, Account, Region, 탐지 단계, 실행 결과처럼 저희가 정의한 조건과 정확히 일치하는지 확인하고, 조건이 하나라도 맞지 않으면 외부로 전송하지 않습니다.
>
>검증을 통과한 경우에도 원본 Alert에서 불필요한 필드를 삭제하는 방식이 아니라, Shuffle의 대응에 필요한 값만 골라 새로운 JSON Payload를 만듭니다. 예를 들어 조기 탐지에서는 Rule ID와 발생 시각, TAKE ID, 대상 Pod의 Name과 UID, 공격 단계와 결과 정도만 전달합니다.
>
>`full_log`나 원본 Event ID처럼 외부 자동화에 직접 필요하지 않은 정보는 그대로 보내지 않고 SHA-256 Hash만 남겨, 원본을 노출하지 않으면서도 이후 동일 Event인지 검증할 수 있도록 했습니다.
>
>즉 저희 구조는 **대응 판단에는 상세 로그를 사용하되, SOAR에는 그 대응을 수행하는 데 필요한 최소 정보만 전달하는 Allowlist 방식**으로 구성했습니다.
> 
> Shuffle은 보안 경보를 받아 다음 작업을 실행하는 자동화 도구입니다. Shuffle에서도 입력값이 정해둔 형식과 정확히 일치하는지 다시 검사합니다.
> 여기서 Shuffle이 Kubernetes를 직접 변경하는 것은 아닙니다.
>
>Wazuh에서 전달받은 내용을 Shuffle이 다시 확인한 뒤, 조건이 맞으면 미리 정해둔 GitHub 자동화 작업을 실행합니다.
>
>GitHub에서는 대응에 필요한 설정만 변경해 저장소에 반영하고, Argo CD가 이 변경을 확인해서 실제 Kubernetes 환경에 적용합니다.
>
>Rule 100110이 발생하면 공격을 받은 Pod를 격리하는 작업을 실행하고, Rule 100111이 발생하면 DVWA의 보안 수준을 low에서 impossible로 변경하는 작업을 실행합니다.
> 
> 변경 내용은 GitHub에 기록되고, Argo CD가 이를 읽어 실제 EKS 환경에 반영합니다.
> 
> 따라서 Wazuh 경보부터 Shuffle 실행, GitHub 변경 기록, Argo CD 적용 결과까지 하나의 흐름으로 추적할 수 있습니다.

## 다이어그램 3 — Rule 100110과 침해 Pod 격리

약 1분 35초

> 이번에는 Rule 100110의 대응을 자세히 보겠습니다.
> 
> DVWA를 통해 AWS 임시 자격증명과 관련된 출력이 반환되면, 해당 사건이 빠른 전달 경로를 통해 Wazuh에 들어옵니다.
> 
> Wazuh는 단순히 명령 실행이 성공했다는 사실만 보지 않습니다. DVWA가 취약한 `low` 상태였는지, 임시 자격증명을 가져오는 단계였는지, 그리고 그 결과가 실제로 반환됐는지를 함께 확인합니다.
> 
> 조건이 모두 맞으면 Rule 100110 경보가 만들어집니다.
> 
> 이 경보는 다시 로컬 검증과 Shuffle 검증을 통과한 뒤, Pod 격리 Workflow를 실행합니다.
> 
> 여기서 중요한 점은 침해된 Pod를 바로 삭제하지 않는다는 것입니다.
> 
> 침해된 Pod는 나중에 조사할 증거이기 때문에 실행 상태로 보존합니다. 대신 정상적인 서비스 관리 대상에서 분리하고, 통신을 차단해 더 이상 외부와 연결되지 못하도록 합니다.
> 
> 그리고 서비스가 멈추지 않도록 정상 Pod를 하나 더 실행해 기존 서비스를 대신하게 합니다.
> 
> 정리하면, 침해된 Pod는 통신을 막은 채 증거로 남기고, 정상 Pod가 서비스를 계속 제공하는 방식입니다.
> 
> 이를 통해 증거 보존과 서비스 유지를 함께 보여주고자 했습니다.

## 다이어그램 4 — Rule 100111과 DVWA 보안 강화

약 1분 35초

> 다음은 Rule 100111입니다.
> 
> Rule 100110이 DVWA에서 AWS 자격증명과 관련된 출력이 반환된 사실을 본다면, Rule 100111은 그 권한으로 보호된 S3 파일을 실제로 읽었는지를 확인합니다.
> 
> 단순히 S3 요청을 보냈다는 이유만으로는 탐지하지 않습니다.
> 
> 정해둔 AWS 역할이 정해둔 S3 파일을 요청했고, 요청이 성공했으며, 실제 파일 내용이 반환됐다는 조건까지 확인합니다.
> 
> 이 기록은 CloudTrail에 남고, Wazuh가 5분마다 로그를 확인하는 과정에서 Rule 100111이 발생합니다.
> 
> 이후 원본 로그는 로컬에서 다시 검사합니다. Shuffle에는 계정, 역할, Bucket, 파일 이름과 원문을 보내지 않습니다. Rule 번호와 시각, 경보 식별값, 원문이 바뀌지 않았음을 확인할 수 있는 해시값만 보냅니다.
> 
> 검증에 성공하면 GitHub Workflow가 DVWA 설정 파일의 한 줄을 `low`에서 `impossible`로 변경합니다.
> 
> Argo CD는 이 변경을 발견하고 새 설정을 실제 DVWA에 적용합니다.
> 
> 다만 이 조치가 이미 반환된 S3 파일이나 발급된 AWS 자격증명을 회수하는 것은 아닙니다. 추가 공격을 어렵게 만드는 방어 조치이며, 실제 운영에서는 자격증명 폐기 같은 후속 대응도 필요합니다.

## PPT 42페이지 — 10분 Poll의 한계와 실제 개선

약 1분 50초

> 지금부터는 이 구조를 만들면서 어떤 문제가 있었고, 무엇을 새로 알게 됐는지 설명드리겠습니다.
> 
> 프로젝트 초기에는 다섯 종류의 로그를 Wazuh가 10분마다 확인했습니다.
> 
> 이 방법은 여러 로그를 넓게 수집하고 원본을 보관하는 데는 좋았습니다. 하지만 사고가 로그 확인 직후에 발생하면, 다음 확인 시간까지 최대 10분을 기다려야 했습니다.
> 
> 관제 시스템에서 위험한 사건을 최대 10분 뒤에 확인하는 것은 아쉬운 부분이었습니다.
> 
> 그래서 기존의 넓은 수집 경로는 유지하면서, DVWA의 중요한 위험 신호만 더 빨리 전달하는 경로를 추가했습니다.
> 
> 세 차례 측정한 결과, 사건 발생부터 Wazuh 경보까지 약 3.4초에서 6.4초가 걸렸고 누락은 없었습니다.
> 
> 여기서 기존 수집 방식을 없애지는 않았습니다.
> 
> 기존 방식은 여러 로그를 넓게 남기고 나중에 조사하는 데 필요했습니다. 새 경로는 중요한 신호를 빨리 확인하기 위해 추가한 것입니다.
> 
> 이후 멘토링과 추가 학습을 통해 속도만 빠르다고 좋은 관제는 아니라는 점도 다시 생각했습니다.
> 
> 잘못된 탐지로 정상 서비스를 막으면 오히려 피해가 생길 수 있습니다. 따라서 얼마나 빠른지만 볼 것이 아니라, 탐지가 얼마나 믿을 만한지와 자동 대응이 얼마나 안전한지도 함께 봐야 했습니다.
> 
> 여기서 새로운 질문이 생겼습니다.
> 
> DVWA에서 줄인 대기 시간을 다른 AWS 로그에서도 똑같이 줄일 수 있을까?
> 
> 이 질문을 해결하기 위해 AWS의 Telemetry와 로그 전달 방식을 조사했습니다.

## PPT 43페이지 — Telemetry와 지연 구간 판단

약 1분 55초

> 조사하면서 가장 먼저 알게 된 점은 같은 AWS 서비스라도 로그가 만들어지고 전달되는 방법이 하나가 아니라는 것입니다.
> 
> 여기서 Telemetry는 보안 상태를 판단하기 위해 관찰하는 로그와 이벤트 같은 정보를 뜻합니다.
> 
> 단순히 CloudFront 로그, WAF 로그라고 부르는 것만으로는 충분하지 않았습니다. 무엇을 관찰하는지, 어떤 방식으로 로그가 만들어지는지, AWS 어디에 저장되는지, 그리고 Wazuh까지 어떻게 보낼지를 따로 봐야 했습니다.
> 
> 저희는 전체 지연도 다섯 구간으로 나눠봤습니다.
> 
> 첫 번째는 사건이 발생한 뒤 로그가 만들어지는 시간입니다.
> 
> 두 번째는 만들어진 로그가 AWS의 저장 장소까지 도착하는 시간입니다.
> 
> 세 번째는 저장된 로그가 Wazuh까지 전달되는 시간입니다.
> 
> 네 번째는 Wazuh가 로그를 분석해 경보를 만드는 시간입니다.
> 
> 마지막은 Shuffle이 실제 대응을 실행하는 시간입니다.
> 
> DVWA의 빠른 전달 경로가 줄인 것은 주로 세 번째 구간입니다. 10분마다 확인하던 대기 시간을 없애고, 사건이 발생했을 때 바로 Wazuh로 전달했습니다.
> 
> 하지만 다른 AWS 로그는 로그 자체가 늦게 만들어질 수도 있습니다. 이런 경우 전달 방법만 바꿔서는 전체 시간이 크게 줄어들지 않습니다.
> 
> 따라서 무조건 가장 빨라 보이는 방법을 선택할 수는 없었습니다.
> 
> 탐지에 필요한 정보가 들어 있는지, 얼마나 늦게 도착하는지, 로그가 빠질 가능성은 없는지, 비용과 운영 부담은 어떤지를 함께 비교해야 합니다.
> 
> 저희가 내린 결론은 하나의 빠른 경로를 모든 로그에 복사하는 것이 정답은 아니라는 것입니다.
> 
> 기존의 넓은 수집 경로는 증거 보관과 조사에 계속 사용하고, 빠른 확인이 필요한 신호에는 별도의 전달 경로를 적용해야 합니다.
> 
> 즉 각 로그의 역할과 위험도에 맞게 수집 방법을 선택하는 것이 더 나은 관제라고 판단했습니다.

# 2. 발표자 노트형

문장을 외우지 않고 화면을 따라 말할 때 쓰는 버전이다.

## 다이어그램 1

**한 줄 핵심**

> 같은 공격을 빠른 경로와 넓은 경로로 수집해 Wazuh에서 함께 본다.

**말할 순서**

1. 왼쪽 공격 흐름 짚기  
    `DVWA 취약점 → AWS 역할 확인 → S3 파일 접근`
2. 초록색 경로  
    `5분마다 확인 / 느리지만 넓고 원본 조사에 유리`
3. 분홍색 경로  
    `중요한 DVWA 사건을 바로 전달 / 민감정보 제거`
4. Wazuh  
    `로그 정리 → Rule 비교 → 경보 생성`
5. Rule 차이
    - 100102: 통신 점검
    - 100110: 자격증명 관련 출력 반환
    - 100111: S3 파일 내용 실제 반환
6. 두 경보는 자동으로 하나가 아님  
    `시각과 식별값을 비교해 사람이 같은 사건인지 판단`

**굳이 말하지 않아도 되는 것**

- Lambda Allowlist의 세부 필드
- 모든 Payload 항목
- Rule Level 숫자

## 다이어그램 2

**한 줄 핵심**

> 경보를 바로 실행하지 않고 두 번 검증한 뒤, 허용된 대응만 실행한다.

**말할 순서**

1. Wazuh 경보 발생
2. 로컬에서 대상과 형식 확인
3. 민감정보는 외부로 보내지 않음
4. Shuffle이 다시 입력값 확인
5. 실패하면 아무것도 변경하지 않음
6. 성공하면:
    - 100110 → 침해 Pod 격리
    - 100111 → DVWA `low→impossible`
7. GitHub 변경을 Argo CD가 실제 환경에 적용
8. 경보부터 최종 변경까지 기록 연결

**강조 문장**

> 자동화했지만, 아무 경보나 자동 실행하지 않도록 검증 단계를 앞에 뒀습니다.

## 다이어그램 3

**한 줄 핵심**

> 침해된 Pod를 삭제하지 않고 통신만 막아 증거로 보존한다.

**말할 순서**

1. DVWA에서 자격증명 관련 출력 반환

## PPT 43페이지

**한 줄 핵심**

> 모든 로그에 같은 빠른 경로를 붙이는 것이 아니라, 로그마다 맞는 경로를 골라야 한다.

**말할 순서**

1. Telemetry 쉬운 정의  
    `보안 판단에 사용하는 로그와 이벤트`
2. 서비스 이름만 보면 안 됨
3. 지연을 다섯 부분으로 분리:
    - 사건 → 로그 생성
    - AWS 저장 장소 도착
    - Wazuh 전달
    - Wazuh 경보 생성
    - 자동 대응
4. DVWA에서 줄인 것은 주로 세 번째 대기
5. 다른 서비스는 로그 생성 자체가 느릴 수 있음
6. 비교할 기준:
    - 탐지에 필요한 정보
    - 도착 속도
    - 누락 가능성
    - 비용과 운영 난이도
7. 최종 결론:
    - 넓은 기존 경로는 유지
    - 빨라야 하는 신호만 별도 경로 적용

**마지막 문장**

> 결국 하나의 가장 빠른 경로가 정답이 아니라, 각 신호의 역할과 위험도에 맞는 경로를 선택하는 것이 더 나은 관제라고 판단했습니다.
