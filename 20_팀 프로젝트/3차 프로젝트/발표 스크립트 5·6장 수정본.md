# 발표 스크립트 5·6장 수정본

> 대상 자료: `3차_프로젝트_최종발표_ver3 (1).pptx` 27~41번 슬라이드  
> 작성 기준: 발표 시간보다 사실관계, 인과관계, 화면이 증명하는 범위를 우선한다.

## 27번 — 5장 전환

> 앞에서는 AWS 환경에서 어떤 로그를 수집하고, 개별 보안 기능이 어떤 신호를 만드는지 설명드렸습니다.
>
> 이제 이 신호들을 Wazuh에서 어떻게 탐지하고, Shuffle과 GitHub Actions를 거쳐 제한된 자동 대응으로 연결했는지 설명드리겠습니다.

## 28번 — 전체 보안관제 구조

> 저희가 구성한 보안관제 구조는 수집과 탐지, 대응의 세 단계로 나눌 수 있습니다.
>
> 먼저 AWS 영역에서는 CloudTrail, CloudWatch Logs, WAF 로그와 GuardDuty Finding 등 보안 판단에 필요한 기록을 생성하고 보존합니다.
>
> Wazuh는 사전에 승인한 로그만 읽기 권한으로 가져와 디코딩하고, 시나리오에 맞춘 탐지 Rule을 적용합니다. 여러 AWS 서비스와 애플리케이션에서 나온 기록을 한곳에서 조회하고 경보로 만드는 SIEM 역할입니다.
>
> 경보가 발생한 뒤에는 Shuffle이 자동 대응의 입구가 됩니다. Wazuh가 보낸 Rule ID와 필수 입력값을 다시 검사하고, 조건이 일치할 때만 미리 고정해 둔 GitHub Actions Workflow를 호출합니다.
>
> 즉, Wazuh가 의심 행위를 탐지하고, Shuffle이 실행 요청을 검증하며, GitHub Actions와 Argo CD가 허용된 변경만 적용하도록 역할을 분리했습니다.

## 29번 — 로그 수집 경로와 탐지 조건

> 모든 로그를 같은 방식으로 가져오지는 않았습니다.
>
> CloudFront, ALB, WAF, CloudTrail 등 여러 Source의 로그는 CloudWatch Logs와 Security Log S3를 통해 넓게 수집하고, Wazuh가 일정 주기로 확인하도록 구성했습니다. 이 경로는 다양한 증거를 빠뜨리지 않고 보존하고 조사하는 데 유리하지만, 다음 수집 주기까지 대기 시간이 생길 수 있습니다.
>
> 반면 DVWA에서 발생하는 고위험 애플리케이션 Event는 CloudWatch Logs Subscription, Lambda, SQS와 로컬 Bridge를 거쳐 Wazuh로 전달했습니다. 프로젝트에서는 이를 Push 경로라고 불렀습니다. 완전한 실시간을 뜻하는 것은 아니며, Wazuh의 다음 Poll 주기를 기다리지 않고 분석을 시작하기 위한 저지연 전달 경로입니다.
>
> Capital One 시나리오에서는 DVWA의 IMDS 관련 행위와, 이후 CloudTrail에 남은 보호 대상 S3 객체 접근을 서로 다른 증거로 탐지했습니다. TalentHook 시나리오에서는 S3 공개 정책 변경과 외부 객체 접근을 구분해 확인했습니다.
>
> 이처럼 하나의 로그만으로 사건 전체를 단정하지 않고, 발생 시각과 행위 주체, 대상 Resource, Event ID를 함께 비교하도록 설계했습니다.

## 30번 — Wazuh 통합 대시보드

> 수집된 로그는 Wazuh Dashboard에서 한 화면으로 조회했습니다.
>
> 이 화면에서는 CloudFront 요청 수와 HTTP 상태, 요청 경로, WAF의 Allow 또는 Block 결과를 함께 비교할 수 있습니다.
>
> 관제자가 단순히 요청 수가 증가했다는 이유만으로 공격이라고 판단하지 않고, 어떤 경로에서 어떤 응답이 발생했고 WAF가 어떻게 처리했는지를 함께 보도록 구성했습니다.
>
> 대시보드의 역할은 자동으로 사건의 원인을 결론 내리는 것이 아니라, 서로 다른 Source의 기록을 같은 시간축에서 조사할 수 있게 만드는 것입니다.

## 31번 — Capital One 시나리오의 두 탐지와 두 대응

> 첫 번째는 Capital One 침해 사례를 프로젝트 환경에 맞게 각색한 시나리오입니다.
>
> 취약한 DVWA에서 명령 실행을 통해 IMDS Credential endpoint의 출력이 반환되면 Rule 100110이 발생합니다. 이 Rule은 Credential 원문 자체를 수집했다는 뜻이 아니라, 워크로드가 자격증명 endpoint까지 접근해 응답을 돌려받은 고위험 행위를 탐지합니다.
>
> 별도로 CloudTrail에서 고정된 보호 대상 S3 객체에 대한 GetObject가 성공하고 실제 반환 바이트가 확인되면 Rule 100111이 발생합니다. 이 Rule은 S3 객체 읽기 성공에 대한 후행 증거입니다.
>
> 두 Rule은 자동으로 하나의 Incident로 결합되는 구조가 아닙니다. Rule 100110은 DVWA 애플리케이션 Event를 저지연 경로로 확인하고, Rule 100111은 CloudTrail에서 실제 S3 접근 결과를 확인하는 독립된 증거입니다. 발표에서는 같은 공격 실행의 시각과 식별 정보를 비교해 하나의 흐름으로 해석합니다.
>
> 대응도 증거의 성격에 맞게 분리했습니다. Rule 100110에는 침해가 의심되는 Pod의 격리와 보존을, Rule 100111에는 DVWA의 기본 보안 수준을 `low`에서 `impossible`로 전환하는 고정 Workflow를 연결했습니다.

## 32번 — Capital One 단계별 탐지 화면

> 이 화면은 Capital One 시나리오에서 발생한 Event와 Rule을 시간 순서로 조회하기 위해 만든 대시보드입니다.
>
> Rule 100110 Count는 IMDS Credential endpoint 출력 반환 조건에 맞은 Event가 몇 건인지 보여주고, Rule 100111 Count는 보호 대상 S3 객체 읽기 성공 조건에 맞은 CloudTrail Event가 몇 건인지 보여줍니다.
>
> 아래 표에서는 Event 시각과 TAKE ID, 공격 단계, 결과와 Rule ID를 직접 비교할 수 있습니다.
>
> 다만 두 Count가 함께 올랐다는 사실만으로 인과관계가 자동 증명되는 것은 아닙니다. 동일한 실행에서 나온 TAKE ID와 시간 범위, 역할 세션과 대상 객체를 함께 확인해야 같은 공격 흐름으로 판단할 수 있습니다.

## 33번 — Rule 100110·100111의 탐지 근거

> 왼쪽은 Rule 100110의 근거입니다. `stage`가 `imds_credential_fetch`, `status`가 `output_returned`로 기록되어 있어 단순한 Role 이름 조회가 아니라 Credential endpoint 호출 결과가 반환된 단계를 구분합니다.
>
> 오른쪽은 Rule 100111의 근거입니다. CloudTrail의 `GetObject`, 정해진 역할 세션, 보호 대상 객체와 성공 응답 조건을 함께 확인합니다.
>
> 이 슬라이드의 데이터는 계정 정보와 자격증명 같은 민감한 값을 발표 자료에 노출하지 않기 위해 `controlled-local-replay`로 재현한 화면입니다.
>
> 따라서 이 화면이 증명하는 범위는 두 가지입니다. 첫째, 정해진 필드 구조가 각 Rule 조건과 일치한다는 점, 둘째, Wazuh가 두 종류의 Event를 서로 다른 Rule로 구분한다는 점입니다. 이 화면 자체가 실제 AWS 공격 전체를 다시 실행했다는 증거는 아닙니다.

## 34번 — Shuffle 검증과 GitOps 자동 대응

> 이 페이지에는 자동 대응의 서로 다른 단계가 함께 들어 있습니다.
>
> 아래 Shuffle 화면의 `SUCCESS`와 `DISPATCHED`는 Wazuh에서 받은 입력값 검증을 통과했고, 고정된 GitHub Actions Workflow에 실행 요청을 전달했다는 뜻입니다. 이것만으로 Kubernetes나 DVWA의 최종 상태 변경까지 완료됐다고 판단하지는 않습니다.
>
> 또한 화면의 `SOC R110 Isolator 1`은 Shuffle App의 표시 이름이므로 실제 실행 Rule을 판정하는 근거로 사용하지 않습니다. 이 캡처에서는 전달된 Payload의 `rule_id=100111`과 연결된 GitHub Workflow를 기준으로 100111 대응을 구분해야 합니다.
>
> 위쪽 결과는 그 다음 단계의 증거입니다. GitHub Actions가 승인된 DVWA 설정만 변경하고, Argo CD가 해당 Git Revision을 EKS에 동기화한 뒤 기본 보안 수준이 `impossible`로 적용된 결과입니다.
>
> 따라서 자동 대응 완료는 Shuffle의 Dispatch 기록 하나가 아니라, Shuffle 실행 ID, GitHub Actions Run, Commit SHA, Argo CD Revision과 실제 Runtime 상태를 이어서 확인해야 합니다.

## 35번 — TalentHook 공개 S3 대응 흐름

> 두 번째는 TalentHook 공개 스토리지 사고를 프로젝트 환경에 맞게 각색한 시나리오입니다.
>
> 검증용 S3 버킷에 공개 정책이 적용되면 CloudTrail에 정책 변경 Event가 남고, Wazuh Rule 100120이 이를 탐지합니다.
>
> 이후 외부의 비인증 요청으로 검증용 객체가 실제 조회되는지도 별도로 확인합니다. 정책이 공개됐다는 사실과 데이터 접근이 성공했다는 사실을 구분해 증거를 남긴 것입니다.
>
> Rule 100120 경보가 Shuffle의 입력 검증을 통과하면 GitHub Actions가 공개 정책을 제거하고 Public Access Block을 다시 활성화합니다.
>
> 마지막에는 같은 비인증 요청을 다시 실행해 HTTP 403이 반환되는지 확인하고, 탐지부터 복구와 재검증까지의 결과를 Artifact로 보관합니다.

## 36번 — Rule 100120 공개 정책 변경 탐지

> 먼저 설정 변경에 대한 탐지 화면입니다.
>
> Wazuh Rule 100120은 검증 대상으로 고정한 버킷에서 발생한 `PutBucketPolicy` Event를 탐지합니다.
>
> 단순히 버킷 이름만 보는 것이 아니라, CloudTrail Event ID와 발생 시각, 행위 주체를 함께 남깁니다. 이 식별자는 뒤에서 외부 객체 접근과 자동 대응 실행 결과를 같은 실험으로 추적하는 기준이 됩니다.
>
> 이 단계가 증명하는 것은 공개 정책 변경 행위가 발생했다는 사실입니다. 실제 외부 데이터 접근 성공은 다음 화면에서 별도로 확인합니다.

## 37번 — 비인증 외부 객체 접근 확인

> 공개 정책이 적용된 상태에서 인증 정보가 없는 외부 요청으로 검증용 객체를 조회했습니다.
>
> 화면에는 `GetObject` Event와 요청 시각, 대상 객체, Source IP와 `curl` 기반 접근 정보가 남아 있습니다.
>
> 이를 통해 설정 파일에 공개 정책이 존재했다는 정적 사실을 넘어, 외부 요청이 실제 객체 접근으로 이어졌다는 것을 확인했습니다.
>
> 단, 이 실험은 실제 개인정보가 아니라 프로젝트에서 만든 고정 검증용 객체만을 대상으로 수행했습니다.

## 38번 — Shuffle Dispatch와 S3 비공개 복구 검증

> Rule 100120 경보가 Shuffle로 전달되면 Rule ID와 CloudTrail Event ID 등 고정된 입력 계약을 검증하고, 제한된 AWS Role을 사용하는 복구 Workflow를 호출합니다.
>
> 화면의 `DISPATCHED`는 Shuffle이 GitHub Actions에 실행 요청을 전달했다는 증거이지, S3 복구가 끝났다는 증거는 아닙니다.
>
> 최종 복구 여부는 GitHub Actions Run 성공, 실제 버킷 정책 제거, Public Access Block 활성화, 그리고 동일한 비인증 요청의 HTTP 403 결과를 함께 확인해 판단했습니다.
>
> 이처럼 탐지와 실행 요청, 실제 상태 변경, 재검증을 서로 다른 증거로 남겨 자동화가 중간에 실패하더라도 어느 단계에서 멈췄는지 추적할 수 있도록 했습니다.

## 39번 — 6장 전환

> 지금까지 공격 시나리오를 기준으로 로그 수집과 Wazuh 탐지, Shuffle 검증, 자동 대응과 재검증 과정을 설명드렸습니다.
>
> 마지막으로 실제로 확인한 결과와 현재 구현의 한계, 그리고 이후 개선해야 할 범위를 정리하겠습니다.

## 40번 — 검증 결과

> 프로젝트 결과는 세 가지로 정리할 수 있습니다.
>
> 첫째, 웹 취약점 공격과 클라우드 설정 변경을 통제된 환경에서 재현하고, 애플리케이션과 AWS 서비스에 남은 기록을 Wazuh에서 조회할 수 있도록 구성했습니다.
>
> 둘째, Capital One 시나리오에서는 IMDS Credential endpoint 출력 반환과 보호 대상 S3 객체의 GetObject 성공을 서로 다른 Rule로 탐지했습니다. 이를 기반으로 침해 Pod 격리와 DVWA 방어 수준 강화라는 서로 다른 대응을 연결했습니다.
>
> 셋째, TalentHook 시나리오에서는 S3 공개 정책 변경을 탐지하고 비공개 상태로 복구한 뒤, 동일한 비인증 요청이 HTTP 403으로 차단되는 것까지 확인했습니다.
>
> 결과적으로 공격 또는 이상 행위 발생, 로그 수집, Wazuh 탐지, Shuffle 입력 검증, 제한된 자동 대응, 실제 상태 확인과 증적 보존으로 이어지는 흐름을 시나리오 단위로 구현했습니다.

## 41번 — 한계와 확장 방향

> 다만 이 결과가 곧바로 실제 운영환경에 적용할 수 있는 완성형 관제 시스템이라는 의미는 아닙니다.
>
> 첫 번째 한계는 탐지 범위입니다. 현재 Rule과 대응은 Capital One과 TalentHook 시나리오에 맞춰 고정했기 때문에, 운영환경에서는 더 다양한 정상 행위와 공격 유형을 바탕으로 Rule을 지속적으로 튜닝해야 합니다.
>
> 두 번째는 대응 통제입니다. 현재는 사전에 정한 입력과 Workflow만 허용하고 가역적인 조치를 선택했지만, 운영환경에서는 사람의 승인, 긴급 중단, 실패 시 Rollback과 권한 분리를 더 강화해야 합니다.
>
> 세 번째는 정량 검증 범위입니다. 정량 측정을 전혀 하지 않은 것은 아닙니다. DVWA의 무해한 검증 Event가 Rule 100102 Alert로 생성될 때까지 세 차례 측정했고, 3.427초에서 6.439초가 걸렸으며 누락은 0건이었습니다.
>
> 하지만 표본이 세 건으로 작고, 이 측정은 Event부터 Wazuh Alert까지의 구간만 포함합니다. Rule 100110과 100111의 탐지 정확도, 오탐률, 장기간 누락률, Shuffle 이후 최종 조치까지의 전체 대응 시간은 운영 지표로 충분히 측정하지 못했습니다.
>
> 따라서 다음 단계에서는 탐지 범위를 넓히는 것뿐 아니라, 정확도와 오탐률, Event부터 최종 조치까지의 시간, 실패와 복구 결과를 지속적으로 측정해야 합니다.
>
> 정리하면 이번 프로젝트에서는 여러 보안 신호를 한곳에서 탐지하고, 검증된 입력만 제한적인 자동 대응으로 연결하는 기술적 기반을 확인했습니다. 이후에는 더 많은 운영 데이터와 통제 절차를 바탕으로 정확성과 대응 속도를 함께 개선해야 합니다.
>
> 이상으로 발표를 마치겠습니다. 감사합니다.

## 발표 전에 반드시 맞출 화면 문구

- 34번 화면의 `SOC R110 Isolator 1`과 Payload의 `rule_id=100111`은 시각적으로 혼동을 준다. 화면을 교체하지 않는다면 발표 대사에서 **표시 이름이 Rule 판정 근거가 아님**을 반드시 설명한다.
- 34번과 38번의 `DISPATCHED`는 최종 조치 완료가 아니라 Workflow 실행 요청 전달 성공이다.
- 41번의 기존 “정량적 측정 미수행” 문구는 실제 `Rule 100102 Event→Alert N=3` 측정과 충돌한다. 슬라이드 문구를 바꾸거나, 발표에서 제한된 측정이 있었음을 명시한다.
- Rule 100110과 100111은 Wazuh가 자동으로 상관분석한 하나의 Incident가 아니다. 동일 TAKE와 시각, 역할, 대상을 발표자가 비교해 연결한다.
