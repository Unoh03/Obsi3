# 발표 스크립트 5·6장 수정본

> 대상: `3차_프로젝트_최종발표_ver3 (1).pptx` 27~41번
> 기존 발표 대본은 사용하지 않고, 현재 PPT 화면과 구현 근거를 다시 대조해 작성했다.

## 발표 전 확인할 PPT 오류

### 34번 — 반드시 수정

- 화면 상단 결과는 `DEFAULT_SECURITY_LEVEL=impossible`이다.
- 하단 Payload는 `rule_id=100111`이다.
- 그러나 Shuffle App 이름은 `SOC R110 Isolator 1`, Action 이름은 `dispatch_rule_100110`이다.
- Rule `100110`은 Pod 격리, Rule `100111`은 `low → impossible` 대응이므로 한 화면의 식별 정보가 서로 충돌한다.

이 상태로는 화면을 근거로 “100111 대응이 정상 완료됐다”고 발표할 수 없다. 올바른 100111 Shuffle 실행 화면으로 교체하거나, 잘못된 App·Action 이름이 수정된 화면을 사용해야 한다.

### 38번 — 증명 범위 주의

화면의 `SUCCESS / DISPATCHED`는 Shuffle이 GitHub Actions Workflow 호출 요청을 전달했다는 근거다. 실제 S3 비공개 복구와 HTTP 403까지 주장하려면 GitHub Actions 완료 결과 또는 재검증 결과가 별도로 필요하다.

## 27번 — 5장 전환

> 지금까지는 AWS에서 어떤 로그를 만들고 수집했는지 설명드렸습니다.
>
> 이제 그 로그가 Wazuh의 탐지로 바뀌고, 탐지된 경보가 Shuffle을 거쳐 실제 대응으로 이어지는 과정을 두 가지 사고 시나리오로 보여드리겠습니다.

## 28번 — 전체 관제 구조

> 전체 구조는 세 부분으로 나눴습니다.
>
> AWS 관리형 기능은 GuardDuty Finding을 만들고 EventBridge와 SNS를 통해 운영자에게 알립니다. 별도로 Wazuh는 CloudTrail, WAF, ALB, CloudFront와 DVWA 로그를 모아 시나리오에 맞는 Rule로 탐지합니다.
>
> 탐지 뒤에는 Shuffle이 있습니다. Wazuh 경보를 곧바로 실행 명령으로 사용하지 않고, Shuffle이 허용된 Rule과 입력 형식인지 확인한 뒤 정해진 GitHub Actions Workflow만 호출합니다.
>
> 즉, 이 구조의 핵심은 탐지와 실행을 분리하고, 자동 대응 앞에 검증 단계를 둔 것입니다.

## 29번 — 두 수집 방식과 시나리오별 판단

> 로그 수집은 목적에 따라 두 가지 방식을 사용했습니다.
>
> CloudTrail과 여러 AWS 서비스 로그는 넓은 범위의 조사와 증거 보존을 위해 주기적으로 조회했습니다. 반면 DVWA의 고위험 Event는 다음 조회 주기를 기다리지 않도록 별도의 Push 전달 경로를 만들었습니다.
>
> 여기서 Push는 모든 신규 로그에 적용한 방식이 아니라 DVWA 애플리케이션 Event에 선택적으로 적용한 경로입니다.
>
> Capital One 시나리오에서는 IMDS 관련 Event와 역할 세션의 S3 접근을, TalentHook 시나리오에서는 공개 정책 변경과 비인증 객체 접근을 확인했습니다. 서로 다른 기록은 시각, 주체, 대상과 Event ID를 비교해 같은 사건인지 조사했습니다.

## 30번 — Wazuh 통합 대시보드

> 이 화면은 수집한 로그를 Wazuh에서 조회한 예시입니다.
>
> CloudFront 요청 수와 HTTP 상태, 많이 호출된 경로와 WAF 처리 결과를 한 화면에서 비교할 수 있습니다.
>
> 이 숫자 하나만으로 공격을 확정하는 것은 아닙니다. 평소와 다른 요청 증가나 오류가 보일 때 어떤 경로에서 발생했고 WAF가 어떻게 처리했는지 조사하기 위한 관제 화면입니다.

## 31번 — Capital One 시나리오 전체 흐름

> 첫 번째는 Capital One 사건을 프로젝트 환경에 맞게 각색한 시나리오입니다.
>
> DVWA의 명령 실행 취약점을 통해 IMDS Credential endpoint에 접근한 기록을 Rule 100110으로 탐지하고, 이어서 해당 역할로 보호 대상 S3 객체를 읽은 기록을 Rule 100111로 확인했습니다.
>
> 두 Rule은 같은 사실을 반복해서 탐지하는 것이 아닙니다. 100110은 DVWA에서 IMDS 대상 명령의 출력이 반환됐다는 애플리케이션 증거이고, 100111은 CloudTrail에서 S3 객체의 실제 바이트 반환을 확인한 AWS 증거입니다.
>
> 검증된 경보는 Shuffle을 거쳐 정해진 GitHub Actions 대응으로 연결하고, 실행 결과는 Commit과 Artifact로 남겼습니다.

## 32번 — Capital One 대시보드

> 이 대시보드에서는 Rule 100110과 100111의 발생 여부와 시간 흐름을 확인할 수 있습니다.
>
> 위쪽 Count는 여러 검증 실행에서 누적된 경보 수이며, 숫자 자체가 한 번의 공격 단계를 의미하지는 않습니다. 아래 시간 그래프와 개별 Event를 함께 봐야 어떤 실행에서 발생한 경보인지 확인할 수 있습니다.
>
> 따라서 이 화면의 목적은 두 Rule을 자동으로 상관분석하는 것이 아니라, 관제자가 두 종류의 증거를 같은 시간축에서 조사할 수 있게 하는 것입니다.

## 33번 — 두 Rule이 확인한 실제 필드

> 두 Rule의 차이는 원본 필드를 보면 더 명확합니다.
>
> 왼쪽 Rule 100110에는 대상이 `ec2_imds`, 단계가 `imds_credential_fetch`, 상태가 `output_returned`로 기록돼 있습니다. 단순히 IMDS에 접속을 시도한 것이 아니라 Credential endpoint를 대상으로 실행한 명령에서 출력이 반환된 경우입니다.
>
> 오른쪽 Rule 100111에는 `GetObject`와 Karpenter Node Role이 기록돼 있습니다. 이 Rule은 여기에 고정된 객체와 성공 응답, 반환 바이트 조건까지 일치할 때 발생하도록 만들었습니다.
>
> 다만 화면에 `controlled-local-replay`와 `live_aws=false`가 표시된 것처럼, 이 슬라이드는 민감정보를 제거한 재현용 Event입니다. 따라서 실제 공격 실행의 증거가 아니라 Rule이 어떤 필드를 구분하는지 보여주는 자료입니다.

## 34번 — 100111 자동 대응

> **현재 화면 교체 전에는 발표하지 않는다.**
>
> 올바른 화면으로 교체한 뒤에는 다음과 같이 설명합니다.
>
> Rule 100111 경보가 Shuffle의 입력 검증을 통과하면, 고정된 GitHub Actions Workflow가 DVWA의 기본 보안 수준을 `low`에서 `impossible`로 변경합니다.
>
> Shuffle의 `DISPATCHED`는 Workflow 호출 요청이 전달됐다는 의미이고, 최종 완료는 GitHub Actions 실행 성공과 Argo CD가 반영한 Git Revision, 실제 `DEFAULT_SECURITY_LEVEL=impossible` 상태를 함께 확인해 판단했습니다.
>
> 이 대응은 취약 코드를 새로 작성한 것이 아니라, DVWA에 이미 존재하는 방어 프로필 가운데 변경 범위가 고정되고 되돌릴 수 있는 설정을 자동 적용한 것입니다.

## 35번 — TalentHook 시나리오 전체 흐름

> 두 번째는 TalentHook 공개 스토리지 사고를 각색한 시나리오입니다.
>
> 검증용 S3 버킷의 공개 정책 변경을 Rule 100120으로 탐지하고, 실제 비인증 요청으로 객체가 조회되는지도 확인했습니다.
>
> 이후 Shuffle이 경보 입력을 검증하고 GitHub Actions가 공개 정책 제거와 Public Access Block 복구를 수행하도록 구성했습니다. 마지막에는 같은 비인증 요청이 HTTP 403으로 차단되는지 재검증하고 결과를 Artifact로 남기는 흐름입니다.

## 36번 — 공개 정책 변경 탐지

> 이 화면은 Wazuh Rule 100120이 발생한 결과입니다.
>
> CloudTrail의 `PutBucketPolicy` Event를 통해 검증 대상 버킷의 정책이 변경된 사실을 탐지했습니다. 아래에는 Rule ID와 Event 시각, 버킷 이름, CloudTrail Event ID가 함께 남아 있습니다.
>
> 이 단계에서 확인한 것은 공개 정책 변경입니다. 실제 외부 객체 조회까지 성공했는지는 다음 증거에서 별도로 확인했습니다.

## 37번 — 실제 비인증 객체 접근

> 공개 정책이 적용된 뒤 외부에서 인증 정보 없이 검증용 객체를 요청했습니다.
>
> 기록에는 `GetObject`, 대상 버킷과 객체, 외부 Source IP, 그리고 `curl` User-Agent가 남아 있고 `errorCode`는 비어 있습니다.
>
> 따라서 이 화면은 설정이 공개됐다는 사실을 넘어, 외부 요청으로 검증용 객체가 실제 조회됐다는 것을 보여줍니다.

## 38번 — S3 복구 Workflow 호출

> Rule 100120 경보를 받은 Shuffle은 Rule과 Event ID를 검증한 뒤, 제한된 AWS Role을 사용하는 GitHub Actions 복구 Workflow를 호출했습니다.
>
> 화면의 `SUCCESS`와 `DISPATCHED`는 이 호출 요청이 정상적으로 전달됐다는 뜻입니다. 이 캡처 하나만으로 S3가 비공개로 복구됐다고 말할 수는 없습니다.
>
> 최종 복구는 Workflow 완료 결과, 공개 정책 제거와 Public Access Block 상태, 그리고 동일한 비인증 요청의 HTTP 403 결과를 함께 제시할 때 확인할 수 있습니다.

## 39번 — 6장 전환

> 지금까지 두 시나리오를 통해 수집, 탐지, 검증과 자동 대응이 어떻게 이어지는지 설명드렸습니다.
>
> 마지막으로 이번 프로젝트에서 확인한 결과와 실제 운영환경에 적용하기 위해 남은 한계를 정리하겠습니다.

## 40번 — 검증 결과

> 결과는 세 가지로 정리했습니다.
>
> 웹 취약점 영역에서는 공격을 재현하고 관련 로그가 수집되는 탐지 기반을 확인했습니다.
>
> Capital One 시나리오에서는 IMDS 접근 Event와 Node Role을 이용한 S3 객체 접근을 서로 다른 로그에서 추적했습니다.
>
> TalentHook 시나리오에서는 S3 공개 설정 변경과 외부 객체 접근을 확인하고, 비공개 복구와 재검증으로 이어지는 대응 절차를 구성했습니다.
>
> 이를 통해 공격 재현부터 로그 수집, 탐지, 입력 검증, 대응과 증적 보존까지 하나의 관제 절차로 연결했습니다.

## 41번 — 한계와 확장 방향

> 이번 결과는 정해진 시나리오에서 핵심 관제 흐름이 작동하는지를 확인한 것입니다. 실제 운영환경에 바로 적용할 수 있는 완성형 시스템은 아닙니다.
>
> 먼저 탐지 Rule이 고정된 시나리오 중심이기 때문에 더 다양한 공격과 정상 행위를 반영한 튜닝이 필요합니다.
>
> 자동 대응도 현재는 정해진 절차만 실행합니다. 운영환경에서는 사람의 승인, 긴급 중단과 Rollback 같은 통제를 추가해야 합니다.
>
> 일부 전달 지연을 예비 관측했지만 표본이 적고 최종 대응까지 포함하지 않아 운영 성능으로 일반화하지 않았습니다. 앞으로는 경보 정확도와 오탐률, 탐지 시간과 전체 대응 시간을 충분한 표본으로 측정해야 합니다.
>
> 정리하면 이번 프로젝트에서는 관제 흐름의 구현 가능성을 확인했고, 다음 단계에서는 탐지 범위, 대응 안전장치와 운영 지표를 보완해야 합니다.
>
> 이상으로 발표를 마치겠습니다. 감사합니다.
