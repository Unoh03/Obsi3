# 발표 스크립트 5·6장 수정본

> 대상: `3차_프로젝트_최종발표_ver3 (1).pptx` 27~41번
> 기존 발표 대본은 사용하지 않고, 현재 PPT 화면과 구현 근거를 다시 대조해 작성했다.

## 27페이지 — 목차 전환

> 지금부터 저희 팀이 구축한 Wazuh·Shuffle 기반 보안관제와 자동 대응 구조를 설명드리겠습니다.  
> 단순히 로그를 저장하는 데서 끝내지 않고, 공격 행위를 탐지하고 검증된 경보를 실제 대응으로 연결하는 과정을 중심으로 말씀드리겠습니다.

## 28페이지 — Chapter 5 도입

> 저희 팀은 AWS와 애플리케이션에서 발생한 로그를 Wazuh에서 통합 분석하고, 사전에 정의한 조건을 만족한 경보만 Shuffle을 통해 자동 대응으로 연결했습니다.  
> 이 과정은 수집과 탐지, 경보 검증, GitOps 변경, 실제 운영 상태 반영의 순서로 구성했습니다.

## 29페이지 — 다이어그램 1: 공격·수집·Wazuh 탐지

> 먼저 Capital One 시나리오의 수집과 탐지 구조입니다.
> 
> 공격자는 DVWA의 Command Injection 취약점을 이용해 EC2 Metadata Service에 접근하고, 노드 역할의 임시 자격증명을 거쳐 보호된 S3 객체를 조회합니다.
> 
> 저희는 이 공격 과정에서 발생하는 로그를 두 가지 역할로 나누어 수집했습니다.
> 
> 첫 번째는 DVWA에서 발생한 위험 신호를 빠르게 전달하는 저지연 경로입니다.  
> CloudWatch Logs에 기록된 DVWA Audit Event를 Subscription Filter와 Lambda가 선별하고, SQS와 로컬 Bridge를 거쳐 Wazuh로 전달합니다.
> 
> 두 번째는 CloudTrail과 여러 AWS 로그를 주기적으로 조회하는 정기·광범위 수집 경로입니다.  
> 이 경로는 상대적으로 느리지만 더 넓은 범위의 원본 Evidence를 보존하고 후행 공격 사실을 확인하는 역할을 합니다.
> 
> Wazuh에서는 수신한 로그를 Decoder로 필드화한 뒤 세 가지 Rule로 판단합니다.
> 
> Rule 100102는 저지연 전달 경로가 정상적으로 작동하는지 확인하는 검증 Rule입니다. 자동 대응은 발생하지 않습니다.
> 
> Rule 100110은 DVWA 명령 실행 결과로 IMDS Credential Endpoint의 출력이 반환됐다는 사실을 탐지합니다.
> 
> Rule 100111은 CloudTrail에서 보호된 S3 객체의 실제 바이트가 반환된 사실을 탐지합니다.
> 
> 두 Rule은 하나의 자동 상관분석 Rule이 아니라, 서로 다른 침해 사실을 증명하는 독립된 경보입니다. Wazuh Dashboard에서는 발생 시각과 `take_id`, Pod, IAM Role, S3 객체 등의 필드를 비교해 하나의 공격 흐름으로 분석할 수 있도록 구성했습니다.

## 30페이지 — 다이어그램 2: SOAR·GitOps 자동 대응

> 다음은 탐지된 경보가 실제 대응으로 연결되는 전체 구조입니다.
> 
> Rule 100110이나 100111이 발생했다고 해서 즉시 시스템을 변경하지는 않습니다.  
> Wazuh Integration이 먼저 Rule, Source, 시각, 대상 리소스와 해시값을 로컬에서 검증합니다.
> 
> 검증을 통과한 경우에도 계정 정보나 원문 로그, 자격증명은 외부로 보내지 않고, 사전에 승인한 최소 필드만 Shuffle의 인증 Webhook으로 전달합니다.
> 
> Shuffle은 입력 형식과 고정된 Repository, Branch, Workflow를 다시 확인합니다. 계약 검증에 실패하면 GitHub Workflow를 호출하지 않고 아무 상태도 변경하지 않습니다.
> 
> Rule 100110은 침해 Pod의 격리와 보존 Workflow로 연결하고, Rule 100111은 DVWA의 방어 수준을 `low`에서 `impossible`로 변경하는 Workflow로 연결합니다.
> 
> GitHub Actions는 허용된 파일만 제한적으로 변경하고, Argo CD가 해당 Git Revision을 감지해 EKS에 적용합니다.
> 
> 이렇게 Wazuh Alert부터 Shuffle 실행, GitHub Run과 Commit, Argo Revision, 최종 Runtime 상태까지 연결해 추적할 수 있도록 구성했습니다.
> 
> 다만 자동 대응이 이미 유출된 자격증명이나 반환된 데이터를 회수하는 것은 아닙니다. 따라서 실제 운영에서는 IAM Session 무효화나 Credential 폐기 같은 후속 대응이 추가로 필요합니다.

## 31페이지 — 다이어그램 3: Rule 100110 Pod 격리

> Rule 100110의 대응을 조금 더 자세히 보겠습니다.
> 
> DVWA 명령 실행 결과에서 IMDS Credential Endpoint의 출력이 반환되면, 허용된 필드만 Lambda와 SQS, Local Bridge를 통해 Wazuh에 전달됩니다.
> 
> Wazuh는 `source=dvwa`, 명령 실행 성공, 보안 수준 `low`, 단계 `imds_credential_fetch`, 상태 `output_returned` 등의 조건을 함께 확인해 Rule 100110을 발생시킵니다.
> 
> 이후 로컬 Integration과 Shuffle이 Alert 형식, 이벤트 해시, 대상 Pod의 이름과 UID를 검증하고, 고정된 `soc-contain-dvwa.yml` Workflow만 호출합니다.
> 
> 여기서 격리는 새로운 격리 Pod를 단순히 하나 더 만드는 방식이 아닙니다.
> 
> 공격에 사용된 기존 Pod의 UID와 소유 관계를 확인한 뒤, 해당 Pod를 정상 Deployment 관리 대상에서 분리하고 격리 Label과 `deny-all` NetworkPolicy를 적용합니다. 기존 침해 Pod는 조사 증거로 보존하지만 외부 통신은 차단합니다.
> 
> 동시에 정상 ReplicaSet이 대체 Pod를 제공하기 때문에 서비스 자체는 계속 유지됩니다.
> 
> 즉 침해 대상을 삭제해서 증거를 잃는 대신, 침해 Pod는 격리·보존하고 정상 서비스는 별도의 Pod로 유지하는 방식입니다.

## 32페이지 — Capital One 전체 흐름 요약

> 앞의 상세 구조를 공격 시나리오 순서로 다시 정리하면 다음과 같습니다.
> 
> 취약한 DVWA에서 IMDS 접근이 발생하고, 애플리케이션 로그를 통해 Credential Endpoint 출력 반환을 확인합니다. 이후 CloudTrail에서는 해당 역할을 이용한 S3 객체 접근을 확인합니다.
> 
> 저희는 이 과정을 Rule 100110과 Rule 100111이라는 두 개의 독립된 증거로 나누었습니다.
> 
> 검증된 경보는 Shuffle과 GitHub Actions를 거쳐 제한된 범위의 대응으로 연결하고, Git Commit과 Argo Revision을 통해 변경 이력을 남깁니다.

## 33페이지 — Wazuh Dashboard 증거

> 이 화면은 실제로 Wazuh가 Rule 100110과 100111을 수신하고 탐지한 결과입니다.
> 
> 상단 Count는 각 Rule의 발생 횟수를 보여주고, 하단 Timeline에서는 두 경보가 발생한 시점을 비교할 수 있습니다.
> 
> 여기서 Count가 올라갔다는 사실만으로 두 경보의 인과관계가 자동으로 증명되는 것은 아닙니다. 상세 로그의 시각과 식별자를 함께 확인해야 같은 공격 흐름인지 판단할 수 있습니다.

## 34페이지 — Rule 100110·100111 로그 근거

> 왼쪽은 Rule 100110의 근거 로그입니다.
> 
> `resource=ec2_imds`, `security_level=low`, `stage=imds_credential_fetch`, `status=output_returned`를 통해 DVWA 명령 실행 결과로 IMDS Credential Endpoint 출력이 반환됐음을 확인합니다.
> 
> 오른쪽은 Rule 100111의 근거가 되는 CloudTrail Event입니다.
> 
> `eventName=GetObject`, `userIdentity.type=AssumedRole`과 역할 정보, 대상 객체와 Event ID를 통해 노드 역할을 이용한 S3 객체 접근을 확인합니다.
> 
> 이 화면은 민감정보를 제거한 통제된 재현 Event로, 두 Rule이 어떤 필드를 근거로 판단하는지를 보여줍니다.
> 
> 저희는 발생 시각과 Event ID, `take_id`, 역할과 대상을 함께 비교해 공격 흐름을 분석했습니다.

## 35페이지 — 다이어그램 4: Rule 100111 방어 강화

> Rule 100111은 단순히 S3 API 호출이 있었다는 이유로 발생하지 않습니다.
> 
> 고정된 보호 대상 객체에 대해 `GetObject`가 수행되고, `AssumedRole`이 사용됐으며, HTTP 200과 함께 실제 반환 바이트가 0보다 큰 경우를 확인합니다.
> 
> 즉 객체 조회를 시도한 것이 아니라, 보호 데이터가 실제로 반환된 사실을 침해 확정 조건으로 사용합니다.
> 
> Wazuh Integration은 CloudTrail 원문을 로컬에서 다시 검증하고, Rule ID와 발생 시각, Wazuh Alert ID, CloudTrail Event ID의 해시와 원문 해시만 생성합니다.
> 
> 계정, IAM Role, Bucket, Object 이름과 원문 로그는 Shuffle로 보내지 않습니다.
> 
> Shuffle이 이 다섯 개 필드와 해시 계약을 검증하면, 고정된 `soc-harden-dvwa.yml` Workflow를 호출합니다.
> 
> Workflow는 `deploy/dvwa/values.yml`의 `defaultSecurityLevel` 한 줄만 `low`에서 `impossible`로 변경합니다. Argo CD가 새 Git Revision을 감지하면 새로운 Pod와 Session에 강화된 보안 수준이 적용됩니다.
> 
> 이 대응은 이미 반환된 S3 데이터를 회수하거나 임시 자격증명을 폐기하지는 못합니다. 프로젝트에서는 추가 공격을 제한하는 방어 프로필 전환으로 범위를 한정했습니다.

## 36페이지 — TalentHook 시나리오 개요

> 두 번째는 TalentHook 시나리오입니다.
> 
> 이 시나리오는 S3 Bucket Policy가 변경돼 외부 공개 상태가 되고, 인증되지 않은 사용자가 실제 객체에 접근하는 흐름을 대상으로 합니다.
> 
> CloudTrail에서 정책 변경과 객체 접근을 수집하고, Wazuh Rule 100120으로 고정된 검증 대상 Bucket의 공개 설정 변경을 탐지합니다.
> 
> 이후 Shuffle은 검증된 경보를 GitHub Actions의 비공개 복구 Workflow로 전달하도록 구성했습니다.
> 
> 다만 이번 발표 자료에서 직접 확인한 증거 범위는 탐지와 외부 접근, 그리고 복구 Workflow 호출까지입니다. 최종 비공개 적용과 HTTP 403 재검증은 완료 증거에 포함하지 않았습니다.

## 37페이지 — Rule 100120 탐지

> 이 화면은 Wazuh에서 Rule 100120이 발생한 결과입니다.
> 
> CloudTrail의 `PutBucketPolicy` Event와 고정된 대상 Bucket 조건이 일치해, 공개 설정 변경에 대한 경보가 생성됐습니다.
> 
> 모든 Bucket Policy 변경을 침해로 판단하는 것이 아니라, 시나리오에서 지정한 대상과 현재 노출 조건을 함께 확인하도록 Rule 범위를 제한했습니다.

## 38페이지 — 외부 객체 접근 증거

> 다음은 공개 정책이 적용된 S3 객체에 외부 요청이 실제로 도달한 기록입니다.
> 
> `eventName=GetObject`, 외부 출발지 IP, `curl` User Agent와 대상 객체가 기록됐고, `errorCode`가 없기 때문에 요청이 차단되지 않았음을 확인할 수 있습니다.
> 
> 따라서 앞의 정책 변경 경보가 단순한 설정 변경에 그치지 않고, 실제 외부 객체 접근으로 이어질 수 있었음을 보여줍니다.

## 39페이지 — Shuffle Workflow 호출

> Wazuh가 생성한 Rule 100120 경보는 Shuffle에서 다시 검증된 뒤 GitHub Actions 복구 Workflow로 전달됐습니다.
> 
> 화면의 `DISPATCHED` 상태와 Workflow Run ID는 Shuffle이 고정 Workflow 호출에 성공했다는 사실을 보여줍니다.
> 
> 다만 이 화면만으로 GitHub Actions의 최종 성공이나 S3 비공개 전환, 이후 HTTP 403까지 증명할 수는 없습니다.
> 
> 따라서 이번 검증 결과는 자동 복구 Workflow 호출까지로 한정합니다.

## 40페이지 — Chapter 6 전환

> 지금까지는 실제로 구현한 수집·탐지·대응 구조를 설명드렸습니다.
> 
> 다음으로 검증을 통해 확인한 결과와 현재 구조의 한계, 그리고 이를 바탕으로 정리한 확장 방향을 말씀드리겠습니다.

## 41페이지 — 검증 결과

> 웹 취약점 영역에서는 공격 재현 이후 로그가 수집되고 Wazuh 탐지로 이어지는 기반을 확인했습니다.
> 
> Capital One 시나리오에서는 IMDS 접근과 노드 역할을 이용한 S3 객체 접근을 서로 다른 Rule로 탐지하고, Pod 격리·보존과 DVWA 방어 프로필 전환으로 연결했습니다.
> 
> TalentHook 시나리오에서는 공개 설정 변경과 외부 객체 접근을 확인하고, 비공개 복구 Workflow 호출까지 연결했습니다.
> 
> 이를 통해 공격 재현, 로그 수집, 탐지, 검증, 제한된 대응과 증적 연결로 이어지는 통합 관제 흐름을 구성했습니다.
> 
> 다만 모든 단계가 동일한 수준으로 검증된 것은 아니며, 검증된 범위와 후속 과제를 구분했습니다.

## 42페이지 — 현재 한계와 확장 방향

> 현재 탐지 Rule은 고정된 시나리오를 중심으로 구성돼 있어, 다양한 공격 유형과 운영 환경을 포괄하려면 Rule 확대와 장기간 튜닝이 필요합니다.
> 
> 자동 대응 역시 사전에 정한 제한적 조치만 수행합니다. 실제 운영에서는 승인, 중단, Rollback과 같은 안전장치를 더 강화해야 합니다.
> 
> 또한 이번 프로젝트에서는 경보 정확도와 탐지·대응 시간을 정량적인 운영 지표로 충분히 측정하지 못했습니다.
> 
> 따라서 후속 과제는 단순히 자동화 범위를 넓히는 것이 아니라, 탐지 Rule 확대, 대응 안전장치 강화, 운영 지표를 이용한 검증의 순서로 진행해야 합니다.

## 43페이지 — 10분 Poll의 한계와 저지연 개선

> 프로젝트 초기에는 CloudFront, ALB, WAF, DVWA, CloudTrail의 다섯 Source를 Wazuh가 10분 주기로 조회했습니다.
> 
> 이 구조는 넓은 Coverage와 원본 Evidence 보존, Replay와 장기 조사에는 유효했습니다. 하지만 Event가 Poll 직후 발생하면 Wazuh 입력까지 최대 10분을 추가로 기다릴 수 있었습니다.
> 
> 이 한계를 줄이기 위해 기존 Poll·Archive 경로는 유지하면서, DVWA 위험 신호에는 별도의 저지연 전달 경로를 추가했습니다.
> 
> Event 발생부터 Wazuh Alert까지 세 차례 측정한 결과는 3.427초에서 6.439초였고 누락은 없었습니다.
> 
> 여기서 중요한 점은 Poll을 모두 제거한 것이 아니라는 것입니다. 광범위 Evidence를 보존하는 기존 경로와 위험 신호를 빠르게 전달하는 경로를 서로 다른 역할로 함께 유지했습니다.
> 
> 멘토링에서는 속도만이 아니라 탐지 정확도, 오탐 피해와 자동화의 안전 범위도 중요하다는 피드백을 받았습니다.
> 
> 이후 별도로 학습한 결과, 속도와 정확도 중 하나만 선택하는 것이 아니라 환경과 신호의 역할에 맞춰 균형을 결정해야 한다고 판단했습니다.
> 
> 여기서 다음 질문이 생겼습니다.
> 
> DVWA에서 줄인 Poll 대기를 다른 AWS Source에도 적용할 수 있는가?
> 
> 이 질문이 Telemetry와 로그 지연 구조를 조사한 출발점이 됐습니다.

## 44페이지 — Telemetry 지연 설계 판단

> 조사 과정에서 먼저 같은 서비스 이름으로 묶여 있던 관찰 단위를 분리했습니다.
> 
> 실제 관제 경로를 판단하려면 Service나 Resource뿐 아니라 관찰하려는 행위, Telemetry Signal, 로그 생성 방식, AWS Destination, SIEM 전달 경로와 최종 Rule을 각각 구분해야 했습니다.
> 
> 또한 전체 지연을 다섯 구간으로 나누었습니다.
> 
> A는 Event에서 로그가 생성되는 시간, B는 AWS의 소비 지점까지 도착하는 시간, C는 저장 지점에서 Wazuh까지 전달되는 시간, D는 Wazuh가 Rule을 평가해 Alert를 만드는 시간, E는 SOAR가 실제 조치를 수행하는 시간입니다.
> 
> DVWA 저지연 경로가 줄인 부분은 주로 C 구간의 Poll 대기였습니다. 그러나 다른 Source는 로그 자체를 생성하거나 AWS 내부에서 전달되는 A와 B 구간의 지연이 남을 수 있습니다.
> 
> 따라서 Event-driven이라는 이유만으로 모든 Source가 DVWA와 같은 속도를 보장하지는 않습니다.
> 
> 저희는 Source별 Route를 판단할 때 탐지 가치와 필요한 필드, 지연과 적시성, 누락과 재전송, 보안 경계, 비용과 운영 복잡도를 함께 비교해야 한다고 정리했습니다.
> 
> 검증된 기존 Poll·Archive 구조는 Baseline으로 유지하고, 저지연 후보는 동일한 Runtime 검증을 통과한 뒤 단계적으로 적용하는 것이 안전합니다.
> 
> 이번 프로젝트를 통해 얻은 최종 결론은 하나의 가장 빠른 경로가 정답이 아니라는 것입니다.
> 
> **각 신호가 무엇을 증명하는지 구분하고, 그 역할과 위험에 맞는 수집·탐지·대응 경로를 선택하는 것이 더 나은 보안관제라고 판단했습니다.**
