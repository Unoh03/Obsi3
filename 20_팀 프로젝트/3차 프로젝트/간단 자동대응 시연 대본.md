# 간단 자동대응 시연 대본

> [!IMPORTANT] 범위
> 이 대본은 **DVWA low 확인 → 통제된 공격 → Rule 100110 → 공격 Pod 자동 격리 →
> Rule 100111 → DVWA impossible 자동 배포**까지만 보여준다. WAF 조치와 재공격은 포함하지
> 않는다. 구현 파일을 직접 여는 장면은 Wazuh Rule 파일 하나뿐이며, 나머지는 브라우저와
> Web GUI에서 확인한다.

상세 설명은 [[시연 대본]], 장면별 구현 근거는 [[시연 장면별 근거 파일]]을 참고한다.

## 0. 영상 목표와 편집 후 시간

이 영상은 제품 이름이나 설정 화면을 나열하지 않고, 하나의 통제된 공격에서
`실제 행위 → 로그 → Rule → 자동 대응 → 검증된 결과`가 이어지는지를 보여준다.

편집 후 목표 길이는 **약 7분 5초**다. 화면 전환을 포함해 8분 안에 끝내고, 9분 30초를
넘기면 동작 증거를 삭제하지 말고 반복 설명을 줄인다.

| 구간 | 목표 시간 |
| --- | ---: |
| 장면 0 — 시연 목적 | 25초 |
| 장면 1 — 시작 상태 | 35초 |
| 장면 2 — 통제된 공격 실행 | 40초 |
| 장면 3 — Rule 100110 조기탐지 | 1분 10초 |
| 장면 4 — 실제 Pod 격리 | 1분 40초 |
| 장면 5 — Rule 100111 침해확정 | 편집 후 1분 5초 |
| 장면 6 — 자동 low → impossible | 1분 30초 |

CloudTrail 도착을 기다리는 실제 시간은 삭제하지 않고 15~20초로 배속한다.

## 1. 촬영 화면

브라우저 탭을 다음 순서로 준비한다.

1. DVWA `https://unoh.click/security.php`
2. Wazuh `Capital One SOC 탐지 로그 분석 (촬영용)`
3. Shuffle Cloud Workflow·Execution
4. GitHub `Unoh03/Uns-DVWA` Actions
5. Argo CD `dvwa` Application

추가로 다음 두 창만 준비한다.

- PowerShell 7: 공격 명령 실행
- VS Code: 다음 Rule 파일만 열어 둔다.
  `D:\Wazuh\wazuh-docker\single-node\config\wazuh_cluster\rules\capital_one_rules.xml`

Account ID, Bucket 전체 이름, Credential, Cookie, Token, PAT는 녹화에 노출하지 않는다.

## 2. 시작 전 확인

화면 밖에서 Reset과 Health 검증을 마친다. 녹화 시작 전 다음 상태여야 한다.

- DVWA Security Level: `low`
- Argo CD: 정상 DVWA Pod `Healthy`
- 이전 격리 Pod와 Quarantine Request 없음
- Wazuh 시간 범위: `Last 30 minutes`
- Rule `100110`, `100111` 시작 Count 기록
- Shuffle과 GitHub Actions에 이번 TAKE의 실행 기록 없음

하나라도 다르면 촬영을 시작하지 않는다.

## 장면 0 — 시연 목적

**목표 시간:** 25초

**화면:** Wazuh 촬영용 Dashboard 전체 → DVWA

### 조작

1. Dashboard 제목과 상단의 Rule 100102·100110·100111 지표를 보여준다.
2. DVWA 탭으로 이동한다.

### 대사

> 이 시연은 Capital One 사고의 핵심 공격 흐름에서 착안해, 승인된 교육 환경에서
> IMDS 임시 자격증명이 S3 객체 접근으로 이어지는 과정을 재구성한 것입니다.

> 분산된 로그를 Wazuh에서 두 단계로 탐지하고, 각 Alert가 Shuffle을 거쳐 실제 Workload
> 격리와 애플리케이션 보안 강화로 이어지는지를 Runtime 화면으로 확인하겠습니다.

> 상단의 Rule 100102는 수집 경로의 정상 상태를 확인하는 안전한 검증 Event이고,
> Rule 100110과 100111이 이번 공격을 탐지하는 Rule입니다.

## 장면 1 — 시작 상태

**목표 시간:** 35초

**화면:** DVWA → Wazuh → Argo CD

### 조작

1. DVWA에서 `Security level is currently: low`를 보여준다.
2. Wazuh에서 Rule 100110·100111의 시작 Count를 보여준다.
3. Argo CD에서 기존 DVWA Pod가 정상 상태임을 보여준다.

### 대사

> 현재 DVWA의 보안 수준은 low이고 서비스는 정상 동작 중입니다. Wazuh의 두 탐지 Rule은
> 아직 이번 공격을 감지하지 않았으며, Argo CD에도 격리된 Pod가 없습니다.

> 지금부터 승인된 교육용 공격을 한 번 실행하겠습니다. 첫 번째 Rule은 AWS Credential
> endpoint 접근 징후를 조기에 탐지하고, 두 번째 Rule은 이후 CloudTrail에서 고정된 가짜
> S3 Object의 실제 바이트 반환을 확인합니다.

## 장면 2 — 통제된 공격 실행

**목표 시간:** 40초

**화면:** PowerShell 7 → Wazuh Dashboard

### 조작

PowerShell 7에서 다음 명령을 실행한다.

~~~powershell
Set-Location D:\terraform\aws_terraform_build_code

$attack = @{
  AwsProfile = 'terra-user'
  SkipAlarmWait = $true
  ConfirmRun = 'RUN CAPITAL ONE BASELINE'
}
.\observability\scenarios\Invoke-CapitalOneBaseline.ps1 @attack
~~~

명령이 끝나면 Wazuh Dashboard로 이동한다.

### 대사

> 공격 Runner는 DVWA Command Injection을 통해 EC2 Metadata Service의 Role 조회와
> Credential endpoint 접근을 순서대로 수행합니다. 이후 이미 메모리에 받은 짧은 수명의
> 임시 Credential로 고정된 가짜 교육용 Object 하나만 읽습니다.

> Credential, 원문 Command, Cookie와 응답 본문은 화면이나 Evidence에 저장하지 않습니다.
> 이제 Wazuh에서 서버가 실제로 분류한 공격 단계를 확인하겠습니다.

## 장면 3 — Rule 100110 조기탐지

**목표 시간:** 1분 10초

**화면:** Wazuh `[촬영] 20 공격 진행 단계` → `[촬영] 10 Rule 100110 수신 로그 — 필드 분해` →
`[촬영] 10-1 Rule 100110 원문 필드 해설` → `[촬영] 02 자격증명 탈취 징후 — Rule 100110` →
VS Code의 `capital_one_rules.xml`

### 조작

1. `[촬영] 20 공격 진행 단계`에서 `imds_role_discovery`와 `imds_credential_fetch`를 시간순으로 보여준다.
2. `[촬영] 10`에서 Rule 100110 Event의 실제 필드를 펼쳐 보여준다.
3. `[촬영] 10-1`의 해설과 실제 필드를 짧게 연결한다.
4. `[촬영] 02` Count가 시작값보다 1 증가했음을 보여준다.
5. VS Code에서 Rule 100110 부분만 연다.

### 대사

> 첫 번째 Event는 Role 이름 조회이고, 두 번째 Event는 Credential endpoint에서 출력이
> 반환된 단계입니다. Rule 100110은 단순한 Metadata 조회가 아니라 두 번째 단계만 조기에
> 탐지하기 위해 만들었습니다.

> Rule 파일을 보면 DVWA의 저지연 수집 경로에서 온 command.execution Event인지,
> 요청 경로가 Command Injection 기능인지, 대상이 EC2 IMDS인지, 보안 수준이 low인지,
> Stage가 imds_credential_fetch인지 확인합니다. 마지막으로 실행 성공과 출력 반환까지
> 정확히 일치해야 Level 12 Alert가 발생합니다.

> 이 Alert는 Credential 원문이나 S3 접근 성공을 증명하지는 않습니다. 그러나 다음 공격
> 단계로 이어질 가능성이 높은 구체적인 징후이므로, 고정된 자동 격리를 시작합니다.

## 장면 4 — Shuffle에서 실제 Pod 격리까지

**목표 시간:** 1분 40초

**화면:** Wazuh → Shuffle Cloud → GitHub Actions → Argo CD → DVWA

### 조작

1. Wazuh Alert의 시각과 ID를 보여준다.
2. Shuffle Cloud에서 대응한 Execution이 성공했음을 보여준다.
3. GitHub Actions에서 `SOC Quarantine DVWA Pod` Run과 성공 상태를 보여준다.
4. Argo CD를 Refresh하고 다음을 보여준다.
   - 완료된 Quarantine Job
   - `dvwa-quarantined-pod-deny-all` NetworkPolicy
   - Orphaned 상태로 보존된 기존 공격 Pod
   - ReplicaSet 아래에서 Ready인 새 정상 Pod
5. 가능하면 Argo Web Terminal에서 격리 Pod의 Egress 요청이 timeout 되는지 확인한다.
6. DVWA 사이트가 새 정상 Pod를 통해 계속 응답하는지 확인한다.

Argo Web Terminal의 격리 Pod에서 다음 요청을 실행한다.

~~~sh
curl --connect-timeout 3 --max-time 5 \
  http://dvwa.dvwa.svc.cluster.local/login.php
~~~

### 대사

> Wazuh는 Alert 전체를 그대로 외부로 보내지 않고 로컬에서 허용된 Rule과 필드를 검증한
> 뒤 최소 Payload만 Shuffle에 전달합니다. Shuffle은 이 Event를 다시 검증하고 고정된
> GitHub Workflow만 호출합니다.

> GitHub Workflow가 격리 요청을 Git에 기록하면 Argo CD가 그 Revision을 배포합니다.
> 여기 보이는 Orphaned Pod는 새로 만든 격리용 Pod가 아니라, 공격을 처리했던 원래 Pod의
> 소유 관계를 분리해 살아 있는 증거로 보존한 것입니다.

> 이 Pod에는 Ingress와 Egress를 모두 막는 NetworkPolicy가 적용됩니다. 동시에 ReplicaSet
> 아래의 새 정상 Pod가 서비스를 이어가므로 사이트 전체를 중단하지 않습니다.

> Argo의 경고와 NetworkPolicy 표시만으로 성공을 단정하지 않고, 격리 Pod의 실제 요청이
> timeout 되고 DVWA 서비스는 계속 응답하는 것을 함께 확인합니다.

> Shuffle Execution, GitHub Run, Argo Revision과 실제 Pod 상태가 같은 Alert에서 이어졌으므로
> Rule 100110이 실제 자동 격리로 연결된 것을 확인할 수 있습니다.

## 장면 5 — Rule 100111 대기와 침해확정

**목표 시간:** 편집 후 1분 5초

**화면:** Wazuh `[촬영] 11 Rule 100111 수신 로그 — 필드 분해` →
`[촬영] 11-1 Rule 100111 원문 필드 해설` → `[촬영] 03 S3 객체 유출 확인 — Rule 100111` →
VS Code의 같은 Rule 파일

### 조작

1. Wazuh Dashboard의 시간 범위와 Rule 100111 시작 Count를 보여준다.
2. Refresh만 하면서 Rule 100111을 기다린다.
3. 대기 구간은 편집에서 배속하되 실제 경과 시간을 자막으로 남긴다.
4. Rule 100111 Count가 1 증가하면 `[촬영] 11`의 CloudTrail Event 필드를 펼친다.
5. `[촬영] 11-1`의 해설과 실제 필드를 짧게 연결한다.
6. `[촬영] 03` Count가 시작값보다 1 증가했음을 보여준다.
7. VS Code에서 같은 파일의 Rule 100111 부분만 연다.

### 대사

> Pod 격리는 끝났지만, S3 접근 성공은 별도의 CloudTrail 근거로 확인합니다. 이 Event는
> 현재 Wazuh가 10분 주기로 수집하므로 도착까지 시간이 걸릴 수 있습니다. Event를 다시
> 주입하거나 Workflow를 수동 실행하지 않고 같은 TAKE를 기다리겠습니다.

> Rule 100111이 도착했습니다. 이 Rule은 GetObject라는 이름만 보지 않습니다. 고정된 Lab의
> Account와 Region, 예상한 Assumed Role, 고정된 가짜 Object, HTTP 200과 양수 바이트 반환을
> 모두 요구합니다.

> 따라서 이 Alert가 증명하는 것은 승인된 가짜 Object의 실제 바이트가 반환됐다는 사실입니다.
> S3 전체가 유출됐다는 뜻은 아닙니다. 이 조건을 만족하면 Level 14 Alert가 발생하고 두 번째
> 자동 대응이 시작됩니다.

## 장면 6 — 자동 low → impossible

**목표 시간:** 1분 30초

**화면:** Wazuh → Shuffle Cloud → GitHub Actions → Argo CD → DVWA

### 조작

1. Rule 100111 Alert와 같은 시각의 Shuffle Execution을 보여준다.
2. GitHub Actions의 `SOC Harden DVWA Security Level` Run을 연다.
3. GitHub Web에서 `defaultSecurityLevel: low → impossible` 한 줄 Diff를 보여준다.
4. Argo CD에서 해당 Commit Revision과 새 DVWA Pod를 보여준다.
5. 새 DVWA Session에서 `Security level is currently: impossible`을 보여준다.

### 대사

> Rule 100111의 경우에도 Wazuh는 전체 CloudTrail 원문을 Shuffle로 보내지 않습니다.
> Rule ID, 발생 시각, Alert ID와 원문을 대신하는 Hash만 전달합니다.

> Shuffle은 최소 Payload를 검증한 뒤 고정된 Hardening Workflow를 호출합니다. Workflow가
> 변경하는 값은 DVWA의 기본 보안 수준 하나이며, GitHub Web에서 low에서 impossible로
> 바뀐 한 줄 Diff를 확인할 수 있습니다.

> 이 Commit을 Argo CD가 배포하면서 새 DVWA Pod가 올라왔습니다. 새 Session에서 확인한
> 현재 보안 수준은 impossible입니다.

> 결과적으로 Rule 100110은 S3 접근 전에 가까운 고위험 징후를 탐지해 공격 Pod를 자동
> 격리했고, Rule 100111은 CloudTrail에서 가짜 Object의 바이트 반환을 확인한 뒤 DVWA의
> 보안 수준을 자동으로 low에서 impossible로 변경했습니다.

> Pod 격리는 공격 Workload의 네트워크를 차단하고 증거를 보존하는 조치이며,
> low에서 impossible로의 변경은 애플리케이션 취약 기능을 완화하는 별도의 조치입니다.

## 3. 촬영 중단 조건

다음 중 하나라도 발생하면 성공 장면으로 사용하지 않는다.

- 시작 시 DVWA가 low가 아님
- Rule 100110이 Role 조회 단계에도 발생함
- Source Event와 다른 Pod가 격리됨
- 사람이 Shuffle 또는 GitHub Workflow를 수동 실행해야 했음
- 공격 Pod가 삭제돼 증거가 보존되지 않음
- 격리 Pod의 Data Plane 통신이 성공함
- 새 정상 Pod가 Ready가 아니거나 DVWA 서비스가 중단됨
- Rule 100111의 CloudTrail Event와 Alert를 연결할 수 없음
- GitHub Diff가 보안 수준 한 값 외의 파일이나 내용을 변경함
- Argo Revision과 GitHub Commit이 다름
- 새 DVWA Session이 여전히 low임

## 4. 편집 원칙

- CloudTrail 대기 구간만 배속한다.
- 배속 시작·종료 시각과 실제 경과 시간을 자막으로 표시한다.
- 다른 TAKE의 Alert, Shuffle Execution, GitHub Run을 섞지 않는다.
- 화면 밖에서 Workflow를 수동 호출한 장면은 자동 대응 증거로 사용하지 않는다.
- 최종 영상은 DVWA의 `impossible` 확인 직후 종료한다.
