## 현재 맥락

- 학원 3차이자 마지막 프로젝트가 `2026-07-28`에 시작됐다. 원본 주제는 `퍼블릭 클라우드 기반 보안 운영`으로 범위가 넓다.
- 현재 조원들은 이번 프로젝트에서 처음 만난 사람들이다.
- 초반에는 Container Escape, Kubernetes 권한 오용, 모의해킹 같은 공격 수단을 먼저 정하려 했다.
- 멘토 상담을 통해 `보안에 집중한 것`이 잘못이 아니라, **보호할 서비스와 인프라가 정해지기 전에 공격 수단부터 고정한 순서**가 문제였음을 확인했다.
- 현재의 기본 흐름은 다음과 같다.

```text
실제 사고 사례
→ 보호할 서비스·사용자·데이터·정상 흐름
→ 기존 인프라와 필요한 변경
→ 공격·장애를 시험 입력으로 사용
→ 로그·차단·피해·복구 확인
→ 조치 후 같은 조건으로 재점검
```

- 기존 2차 프로젝트의 AWS 인프라를 출발점으로 재활용하고 Terraform으로 다시 구성하는 방향이 공유됐다.
- 강사는 완전 자동 CI/CD를 기본 조건으로 요구했다. 구체적인 Build·Registry·Deploy 방식은 아직 정해지지 않았다.
- 실제 사고 사례를 먼저 조사한 뒤, 필요한 조건을 실험 환경에 구현하는 방향을 팀에서 논의했다.
- DVWA 사용은 가능하다. 현재는 로컬 `127.0.0.1:4280`에서만 검증했으며, 최종 서비스나 개조 범위는 사고 사례가 정해진 뒤 판단한다.
- 공격이 WAF 등에 막히더라도 차단 Rule, 로그, 통과·실패 원인과 조치 전후 차이를 남기면 유효한 결과다.
- 운호는 공격 시나리오와 취약점 검증에 관심이 있지만, 관심 기술을 프로젝트 목적보다 먼저 확정하지 않으려 한다.
- Terraform은 운호의 주 담당이 아니다. 다만 담당자 의존으로 프로젝트가 막힐 경우를 대비해 전체 구조를 이해하고 질문하거나 일부를 이어받을 수 있도록 후보 아키텍처 자료를 마련했다.

## 확정된 것과 아직 확정되지 않은 것

### 현재 확인된 방향

- 기존 2차 인프라를 출발점으로 검토한다.
- Terraform 재구성과 완전 자동 CI/CD를 포함한다.
- 실제 사고 사례를 먼저 조사한다.
- 공격뿐 아니라 장애, 차단, 로그, 복구와 조치 후 재점검을 결과로 다룬다.
- DVWA는 사용할 수 있지만 현재는 로컬 검증 후보일 뿐이다.
- 시행착오를 실시간으로 기록한다.

### 아직 미정

- 재현할 실제 사고 사례
- 최종 서비스 기능과 보호할 데이터
- 팀의 최종 아키텍처
- 2차 인프라에서 실제 재사용할 Resource
- Terraform 담당 범위와 인수 가능 범위
- CI/CD Repository·Artifact·Registry·배포 Target
- DVWA를 그대로 쓸지, 필요한 기능만 개조할지
- 공격·장애별 로그와 증적 Mapping
- 팀 역할과 최종 팀 계획서

## 해석할 때 지킬 경계

- 운호·타조·우수현의 세 계획과 종합 평가는 **상담 전 후보**이며 최종 팀안이 아니다.
- `architecture/`의 그림은 비상 대비용 후보 구조이며 실제 Terraform이나 Runtime으로 검증된 구성이 아니다.
- 멘토의 말을 절대적인 정답으로 받아들이거나, 반대로 조원 의견만으로 기존 통찰을 버리지 않는다.
- 하나의 공격 기술에 프로젝트를 억지로 맞추지 않는다.
- 로그 이름을 나열하는 것과 실제 Event가 어느 로그에 남는지 검증한 것을 구분한다.
- 실제 구축, 설계만 한 항목, AI가 제안한 항목을 구분한다.
- Secret, Access Key, Token, Cookie, 비밀번호, kubeconfig는 대화나 문서에 기록하지 않는다.
- 승인된 팀 소유 환경 밖에서는 공격을 시도하지 않는다.
