## 7.1 DVWA 저지연 Route의 구현과 측정

### 첫 번째 개선의 상세 근거

앞의 다이어그램에서 요약한 첫 번째 개선은 5개 Source의 정기 수집을 폐기한 것이 아니라, **DVWA 위험 신호에만 저지연 전달 경로를 추가한 것**이다. 기존 Poll·Archive는 폭넓은 Evidence와 재조회 경로로 유지하고, CloudWatch Logs에 도착한 DVWA Audit Event는 다음 Poll을 기다리지 않고 Wazuh로 전달했다.

> [!note] 현재 설정과의 관계
> 현재 Repository의 Poll 주기는 촬영 대기 시간을 줄이기 위해 `5m`으로 조정되어 있다. Chapter 7에서 설명하는 출발점은 Git 이력으로 확인되는 최초 `10m` 설계이며, `10m → 5m` 변경은 시연 운영 조정이다. Poll 주기를 줄였어도 주기 경계에 따른 대기와 Source 고유 지연이 남는다는 구조적 문제는 같다.

초기 `10m`과 현재 `5m`은 모두 주기 경계에 따른 대기를 남긴다. 이 대기는 후속 분석 모델에서 주로 **AWS 소비 지점에서 Wazuh 입력까지의 C 구간**에 해당하며, Source 고유 A+B 지연과는 구분한다.

### 구현 Route

```text
DVWA Audit Event
→ CloudWatch Logs
→ Subscription Filter
→ Lambda Allowlist·정규화
→ SQS Buffer·DLQ
→ Local Outbound Bridge
→ Wazuh localfile(JSON)
→ Decoder·Rule
```

| 구성요소 | 역할 | 설계 이유 |
|---|---|---|
| **DVWA Audit Event** | Command 실행 직후 구조화 Event 생성 | 원문 Command나 Credential이 아니라 탐지에 필요한 상태를 명시적으로 기록 |
| **CloudWatch Logs Subscription Filter** | Log Group에 들어온 Event를 Lambda로 전달 | CloudWatch Logs 이후의 주기적 Poll 대기를 제거 |
| **Lambda** | Account·Log Group을 검증하고 허용 Field만 정규화 | Cookie, Credential, Command 원문과 응답의 불필요한 외부 전달 방지 |
| **SQS·DLQ** | Event Buffer, Retry 경계, 실패 격리 | 로컬 Wazuh가 일시 중지되어도 Event를 즉시 잃지 않도록 함 |
| **Local Bridge** | Reader Role로 SQS를 Long Poll하고 검증된 JSONL 기록 | 인터넷에서 로컬 Wazuh로 Inbound Port를 열지 않는 Outbound 소비 구조 유지 |
| **Wazuh localfile·Rule** | JSON Event를 분석하고 Alert 생성 | 중앙 SIEM에서 기존 Source와 함께 탐지·조회 |

애플리케이션이 Wazuh로 직접 전송하면 Hop 수는 줄일 수 있지만, 애플리케이션과 SIEM의 강결합, 로컬 Inbound 노출, Buffer·Retry 부재가 생긴다. 현재 Route는 무조건 가장 짧은 경로보다 **저지연, 내구성, 최소 정보 전달, Outbound 보안 경계의 균형**을 선택한 구조다.

### 프로젝트 Runtime 관측

안전한 Validation Event 세 건을 전송해 DVWA Event부터 Wazuh Rule `100102` Alert까지 측정했다.

| Take | Event→Lambda | Lambda→Bridge | Bridge→Alert | 총지연 |
|---|---:|---:|---:|---:|
| `wazuh-push-20260817T102046747Z` | 3.134초 | 2.207초 | 1.098초 | **6.439초** |
| `wazuh-push-20260817T102127824Z` | 2.426초 | 0.240초 | 0.761초 | **3.427초** |
| `wazuh-push-20260817T102209527Z` | 2.381초 | 0.242초 | 1.138초 | **3.761초** |

- 세 Event 모두 Rule `100102` Alert로 생성되었으며 누락은 0건이었다.
- 세 Take ID는 Live JSONL과 Wazuh Alert에서 각각 한 건으로 확인되었다.
- 총지연은 프로젝트 관측값이지 AWS 서비스의 SLA나 일반 보장값이 아니다.
- 이 측정은 Event부터 Wazuh Alert까지의 **A+B+C+D 합계**이며, Shuffle 전달과 최종 Action인 E 구간은 포함하지 않는다.
- N=3의 정상 실행 관측은 경로의 가능성과 당시 상태를 보여주지만 장기 부하, Crash Window, 모든 장애 상황을 증명하지는 않는다.

## 7.2 멘토 상담 이후 Evidence 역할과 대응 범위 재정립

### 멘토 상담이 바꾼 질문

저지연 Route를 처음 구현했을 때는 DVWA Push를 `빠른 Route`, 기존 Poll을 `느린 Route`라고 구분했다. 멘토 상담에서는 이러한 속도 중심 표현보다 공격 특징을 이해한 Rule 설계와 반복 튜닝이 중요하고, 자동화할 수 있는 조치와 자동화해도 안전한 조치는 구분해야 한다는 조언을 받았다.

이 피드백은 Telemetry 개념이나 A/B/C/D/E 모델을 직접 알려준 원인이 아니다. 다만 빠른 Alert 하나만으로 침해를 확정하거나 넓은 조치를 실행해도 되는지 재검토하고, 서로 다른 지연의 로그를 **속도 경쟁이 아니라 Evidence 역할의 차이**로 설명하는 전환점이 되었다.

따라서 두 경로를 경쟁 관계로 설명하지 않고 다음과 같이 재정리하였다.

```text
하나의 Incident 흐름
├─ 저지연 신호: 위험을 먼저 알리고 제한적·가역적 대응을 시작
├─ 후행 Evidence: 실제 성공 여부와 영향 범위를 더 높은 신뢰도로 확인
└─ Archive·Poll: 원본 보존, Replay, 누락 보완, Historical Investigation
```

### Rule별로 분리한 보안 사실

| Rule | 입력 Source | 조건의 핵심 | 정확히 증명하는 사실 | 증명하지 않는 것 |
|---|---|---|---|---|
| `100102` | DVWA 안전 Validation Event | `push`, `dvwa`, `wazuh.push.validation`, `SAFE_VALIDATION_EVENT` | 지정 Validation Event가 Push Route를 거쳐 Wazuh까지 도착함 | 공격이나 침해 발생 |
| `100110` | DVWA 서버 Audit Event | `command.execution`, `ec2_imds`, `imds_credential_fetch`, `output_returned`, `low` | IMDS Credential endpoint 대상 명령에서 출력이 반환됨 | Credential의 외부 재사용이나 S3 접근 성공 |
| `100111` | CloudTrail S3 Data Event | 승인 Account·Region·Role·Bucket·Object, `GetObject`, HTTP `200`, 반환 바이트 양수 | 보호 S3 Object의 실제 바이트가 반환됨 | 앞선 DVWA Event와 동일 사건이라는 자동 인과 판정 |

Rule `100110`과 Rule `100111`을 하나로 합치지 않은 이유는 두 Rule이 관찰하는 공격 단계, 원본 Source, 도착 지연과 증명 범위가 다르기 때문이다. 하나의 Rule로 합치면 IMDS Credential endpoint 출력 반환과 실제 S3 데이터 반환이라는 서로 다른 보안 사실을 구분하기 어렵다.

### Rule 100110 — 제한적 Workload 격리·보존

```text
Wazuh Rule 100110 Alert
→ 로컬 Integrator가 Rule·Level·Source·Account·Region·단계·Pod 형식을 재검증
→ Credential·Cookie·Command 원문과 응답을 제외한 최소 Payload 전송
→ Shuffle이 인증 Header·Schema·신선도·고정 대상 검증
→ 고정 soc-contain-dvwa.yml 호출
→ GitOps 격리 요청 Commit
→ Argo CD Sync
→ Kubernetes Job이 실제 Pod UID·Label·ReplicaSet·Deployment 소유 관계 재검증
→ 대상 Pod를 소유 관계에서 분리하고 quarantined Label·deny-all NetworkPolicy 적용
→ Deployment가 정상 서비스를 위한 대체 Pod 유지
```

이 방식은 Alert에 들어 있는 임의 Namespace나 Workload를 그대로 조치하지 않는다. 고정된 DVWA 범위에서 실제 Pod UID와 소유 관계가 모두 일치할 때만 원본 Pod를 격리·보존한다. 격리된 Pod는 삭제하지 않으므로 조사 대상을 남기고, Deployment는 새 정상 Pod를 생성해 서비스 연속성을 유지한다.

### Rule 100111 — 사전 승인된 애플리케이션 완화

```text
Wazuh Rule 100111 Alert
→ 로컬 Integrator가 CloudTrail 전체 조건을 재검증
→ Rule ID·Event 시각·Wazuh Alert ID·Event ID SHA-256·원문 SHA-256만 전송
→ Shuffle이 인증 Header·Schema·신선도·해시 형식 검증
→ 고정 soc-harden-dvwa.yml 호출
→ defaultSecurityLevel: low → impossible 변경 Commit
→ Argo CD가 정확한 Git Revision을 EKS에 동기화
→ 새 DVWA Pod·Session에서 impossible 적용
```

DVWA의 `low` 구현은 사용자 입력을 그대로 `shell_exec()`의 `ping` 인자에 연결한다. `impossible` 구현은 Anti-CSRF Token을 검사하고 입력을 IPv4 형식으로 검증한 뒤 제한된 `ping` 명령만 실행한다. 따라서 전환 후 공격 경로의 실제 동작은 달라진다.

다만 이 조치는 프로젝트 핵심이 아닌 취약 애플리케이션의 Source Patch를 자동 생성하는 대신, DVWA에 이미 존재하고 결과를 재현할 수 있는 방어 프로필을 선택한 것이다. 운영환경의 근본 조치는 취약 코드 수정, Code Review, 새 Image 배포, Credential 영향 조사와 회귀 검증까지 포함해야 한다.

### 현재 자동 대응의 안전장치

| 통제 | 구현 내용 |
|---|---|
| **입력 최소화** | 원문 Credential·Cookie·Command·응답은 Shuffle로 보내지 않고 Rule별 허용 Field 또는 Hash만 전달 |
| **대상 고정** | 승인된 Account·Region·Repository·Branch·Workflow와 DVWA 범위만 허용 |
| **변경 고정** | 지정 GitOps 값 이외의 파일이나 Diff가 발생하면 Workflow 중단 |
| **대상 재검증** | 격리 직전 Kubernetes의 실제 Pod UID와 소유 관계를 다시 확인 |
| **동시 실행 통제** | Workflow concurrency와 상태 기반 멱등 처리로 충돌 억제 |
| **추적 가능성** | Alert ID·Event Hash·Workflow Run·Commit SHA·Argo Revision 연결 |
| **가역성** | Reset Workflow로 격리 요청과 `impossible` 상태를 기준선으로 복구 |

### 현재 판단의 경계

- Rule `100110`은 공격 스크립트가 끝나기 전의 선제 차단을 보장하지 않는다. 시연에서는 공격 완료 뒤 Alert Count가 증가했으며, Rule `100111`보다 먼저 위험을 알리고 제한적 대응을 시작하는 신호로 해석한다.
- Rule `100110`과 Rule `100111`은 자동 Correlation 결과가 아니라 서로 다른 원본 Event가 증명하는 독립 Evidence다.
- Pod 격리는 이미 유출된 STS Credential을 폐기하지 않는다. 현재 자동화 범위는 Workload·Network Containment이며 Permission·Credential 대응은 후속 과제다.
- `low → impossible`은 새로운 방어 Source Patch를 자동 생성한 것이 아니라, DVWA에 이미 존재하는 사전 승인 방어 프로필로 전환한 것이다.

## 7.3 구현 대신 후속 조사를 선택한 이유

정확도와 자동 Correlation을 더 고도화하려면 장기간의 Rule 튜닝과 반복 검증이 필요했다. 또한 5개 Source의 Route를 변경하면 전달 경로뿐 아니라 Wazuh 입력·Rule, 중복·누락, 장애 복구와 자동 대응까지 기존과 같은 수준으로 다시 검증해야 했다.

프로젝트의 남은 기간에는 이 전체 구현과 Runtime Evidence 재확보를 완료하기 어려웠다. 검증된 Baseline을 억지로 교체하는 대신, 실제 구현에서 생긴 다음 질문을 후속 조사 대상으로 선택했다.

> **DVWA에서 Poll 대기를 제거한 방식을 WAF·ALB·CloudFront·CloudTrail에도 그대로 적용할 수 있는가?**

이 결정은 시간 부족을 현재 Route의 기술적 정당성으로 사용하는 것이 아니다. **검증된 구현과 미검증 개선 후보를 섞지 않고, 적용 가능성과 검증 비용을 먼저 조사한 뒤 Future Work로 분리한 Scope 결정**이다.

## 7.4 Telemetry 기반 후속 설계

### 조사 결과 — 동일 Pipeline을 그대로 복제할 수 있는가

조사 결과, 5개 Source 모두 전송 계층을 Event-driven 후보로 바꿀 수는 있지만 모두 DVWA와 같은 속도를 보장할 수는 없었다. `Event-driven`은 Event가 AWS 소비 지점에 도착한 이후의 Poll 대기를 줄이는 방식이지, Source가 원본 Telemetry를 생성·전달하는 고유 지연까지 자동으로 제거하는 말이 아니기 때문이다.

### Telemetry를 새로운 평가 단위로 도입

Telemetry는 로그의 다른 이름이 아니라 시스템의 상태·행위·성능·사건을 외부에서 관찰하기 위한 Log·Metric·Trace·Event 등의 상위 개념이다. 이 프로젝트에서 중요한 발견은 용어 자체보다 **하나의 AWS Resource에도 서로 다른 Telemetry mechanism과 Delivery path가 존재할 수 있다는 점**이다.

```text
Service / Resource
≠ Observed Activity
≠ Telemetry Signal
≠ Logging Mechanism
≠ Record / Schema
≠ Initial Destination
≠ SIEM Transport Route
≠ Detection Rule
```

예를 들어 같은 CloudFront Viewer Request를 기록해도 Standard Logging과 Real-time Access Logging은 생성·전달 방식과 사용 가능 지연이 다르다. ALB도 Legacy S3 Access Logs와 CloudWatch Logs 기반 Vended Logs를 같은 하나의 경로로 평가할 수 없다. 따라서 `CloudFront가 느리다`, `ALB는 5분짜리다`라고 서비스 이름만으로 말하지 않고, **Resource × Telemetry mechanism × Destination × SIEM Transport** 단위로 평가해야 한다.

### 프로젝트 A/B/C/D/E 지연 모델

| 구간 | 시작과 끝 | 의미 | 프로젝트에서의 예시 |
|---|---|---|---|
| **A** | 실제 Event → Log·Event Record 생성 | Source 생성·집계 지연 | DVWA Audit Record 작성, Flow Log 집계 |
| **B** | Record 생성 → AWS 소비 지점에서 사용 가능 | Source-native Delivery 지연 | CloudTrail→CWL/S3, CloudFront→Kinesis |
| **C** | AWS 소비 지점 → Wazuh 입력 | SIEM Transport 지연 | 10분 Poll 또는 Subscription→Lambda→SQS→Bridge |
| **D** | Wazuh 입력 → Alert·Integrator | Decoder·Rule 평가와 Alert 처리 | Wazuh JSON Decoder, Rule `100110`, Integratord |
| **E** | Wazuh Alert → 최종 Action 결과 | SOAR 전달·Workflow·Action 지연 | Shuffle→GitHub Workflow→Argo CD→EKS 상태 변경 |

```text
t0 실제 행위 발생
t1 AWS 소비 지점 도착
t2 Wazuh 입력
t3 Wazuh Alert 생성
t4 최종 Action 완료

A+B = t1 - t0
C   = t2 - t1
D   = t3 - t2
E   = t4 - t3
E2E = t4 - t0
```

A/B/C/D/E는 AWS나 Wazuh가 정의한 공식 표준이 아니라, 이 프로젝트에서 지연 원인을 분리하기 위해 정립한 분석 모델이다. 감지 완료를 말하려면 D까지, 최종 자동 대응 완료를 말하려면 E까지 측정해야 한다.

```text
Telemetry 사용 가능 지연(A+B)
≠ SIEM Transport 지연(C)

Event-driven
≠ A+B가 0초라는 뜻

Poll 제거
= 주로 C의 불필요한 대기를 줄이는 것

전체 Event-to-Action
= A+B+C+D+E
```

### 가장 적합한 Route를 찾는 방법

1. 프로젝트 Resource와 탐지하려는 행위를 목록화한다.
2. Resource별 Telemetry signal, Logging mechanism과 Initial Destination 후보를 조사한다.
3. AWS 공식 문서에서 A+B 지연, Sampling, Best-effort, 전달 보장 특성을 확인한다.
4. 각 AWS 소비 지점에서 Wazuh까지의 C Route를 설계한다.
5. 탐지 가치, 지연, 신뢰성, 보안 경계, 비용과 운영 복잡도를 비교한다.
6. 우선 검증할 Target Candidate를 선택한다.
7. 정상·공격·장애 Runtime 검증을 통과한 후보만 As-built로 승격한다.

`가장 빠른 Route`와 `가장 적합한 Route`는 같지 않을 수 있다. 다음 조건을 함께 평가해야 한다.

- 필요한 보안 Field와 탐지 가치
- A+B와 C 지연
- 누락·중복·순서 역전·Sampling 가능성
- Buffer·Retry·DLQ·Replay와 멱등 처리
- 로컬 Wazuh Inbound 노출 여부
- IAM 최소권한과 민감정보 전달 범위
- 비용과 운영 복잡도
- Archive와 Correlation 가능성

### Source별 재평가 결과

| Source·Telemetry | 현재 As-built | 우선 검토 Target Candidate | 공식 사실과 남는 검증 |
|---|---|---|---|
| **DVWA Custom Audit** | CWL→Subscription→Lambda→SQS→Bridge→Wazuh | 현재 Route 유지 후보 | 프로젝트 N=3에서 A+B+C+D 3.427~6.439초, 누락 0. 구간별 Clock·장기 장애·E 포함 재측정 필요 |
| **AWS WAF Request Logs** | CWL→Wazuh Poll | CWL Subscription→Lambda→SQS→Bridge | CWL ingest 이후 C Poll 제거 후보. WAF 고유 A+B 정량값, 중복·누락·비용 Runtime 검증 필요 |
| **ALB Legacy S3 Access Logs** | S3→Wazuh Poll | 같은 Legacy라면 S3 ObjectCreated→SQS, 또는 Vended Logs 비교 | Legacy는 노드별 5분 Log file 게시와 eventual consistency. Archive에는 유효하나 저지연 주 탐지에는 제약 |
| **ALB Vended Logs** | 미사용 | CWL→Subscription 또는 Firehose 기반 Route | CWL·Firehose·S3 Destination을 지원하나 이벤트별 정량 지연은 공식 확인되지 않음. Legacy 대비 우월성은 Runtime 비교 전 확정하지 않음 |
| **CloudFront Standard Logs** | CWL 계열→Wazuh Poll | Archive·Historical 경로로 유지 | 일반적으로 Event 후 1시간 이내, 일부 Entry 최대 24시간 지연 가능. C만 바꿔도 Standard의 A+B는 남음 |
| **CloudFront Real-time Logs** | 미사용 | Kinesis→Consumer/Lambda→SQS→Bridge | 요청 후 수초 내 Kinesis 전달 후보. Best-effort, Sampling, 비용, Consumer 운영과 WAF 중복 검증 필요 |
| **CloudTrail S3 Data Event** | CWL→Wazuh Poll | CWL→Subscription→Lambda→SQS→Bridge | Trail Log는 API 호출 후 평균 약 5분 전달이며 보장값이 아님. C는 줄일 수 있지만 고유 A+B는 남음 |

이 표의 후보는 구현 완료나 성능 우월성을 의미하지 않는다. 특히 Destination을 Event-driven 방식으로 바꾸어도 앞단 Logging mechanism의 A+B가 느리면 전체 지연은 그대로 남을 수 있다.

### Target Architecture

```text
Source별 적합한 Telemetry mechanism
→ AWS-native Event-driven Destination
→ Buffer / Retry / DLQ
→ Local Outbound Bridge
→ Wazuh 중앙 분석·Correlation
→ 검증된 Alert만 Shuffle·고정 Workflow로 전달

기존 Poll / Archive
→ 원본 보존
→ Replay
→ 누락 보완
→ Historical Investigation
```

이 구조는 모든 Source를 같은 Transport에 억지로 넣는 설계가 아니다. Source별 고유 지연과 정보 가치를 인정하면서, 가능한 곳의 C Poll 대기를 제거하고 Wazuh에서 하나의 Incident 흐름으로 분석하는 구조다. Poll과 Archive는 실패한 레거시가 아니라 주 탐지 경로를 보완하는 Evidence 계층으로 역할을 재배치한다.

### Target Architecture의 재검증 범위

후속 후보를 실제 구조에 반영하려면 단순히 AWS Logging 설정 하나를 바꾸는 것으로 끝나지 않는다.

```text
Terraform과 AWS Telemetry 설정
→ Destination·Buffer·IAM
→ Wazuh 입력·Decoder·Rule
→ Source 간 Correlation
→ 중복·누락·순서·재시도·DLQ
→ 자동 대응의 Blast Radius와 Rollback
→ Runtime Evidence 재수집
```

따라서 7.3에서 Future Work로 분리한 후보가 실제 As-built로 승격되려면 위 항목을 정상·공격·장애 조건에서 다시 검증하고 Runtime Evidence를 확보해야 한다. 이 목록은 구현하지 못한 이유를 반복하는 설명이 아니라, 후속 구현의 완료 조건이다.

### 남은 자동화 과제

#### 자동 Incident Correlation

현재 Rule `100110`과 Rule `100111`은 자동으로 하나의 Incident Object에 합쳐지지 않는다. 후속 Target에서는 Event 시각, `take_id`, Pod 이름·UID, IAM Principal·Role Session, Bucket·Object Key, Source IP와 Request ID 등을 이용해 다음 상태를 자동 갱신해야 한다.

```text
초기 의심
→ 추가 Evidence 수집
→ 침해확정 / 기각 / 불확실
→ 대응 범위 조정
```

공통 Stable ID가 없는 Source 사이의 관계는 완전한 일대일 Join이 아니라 시간 창과 여러 Evidence를 이용한 추론이 될 수 있다. 또한 로그가 보이지 않았다는 사실만으로 행위 부재를 증명하지 않고 Telemetry Coverage와 Delivery 완료를 먼저 확인해야 한다.

#### Containment의 세 축

| 대응 축 | 현재 구현 | 후속 과제 |
|---|---|---|
| **Workload / Network** | DVWA Pod 격리·보존, deny-all NetworkPolicy, 정상 대체 Pod 유지 | Node 격리·교체와 다른 Workload 영향 검증 |
| **Resource / Permission** | 미구현 | S3 Bucket Policy·IAM Policy를 이용한 고정 범위 접근 제한 |
| **Credential / Session** | 미구현 | 탈취 Role Session 식별, 권한 영향 제한, 재사용 가능성 조사 |

현재 DVWA는 전용 Pod Identity가 아니라 공유 EC2 Node Role을 사용한다. Role 전체를 자동 차단하면 다른 Workload까지 영향을 받을 수 있으므로 실행하지 않았다. 향후 DVWA 전용 EKS Pod Identity와 최소권한 Role을 적용하면 탐지 대상과 Permission·Credential 대응 대상을 더 정확하게 일치시킬 수 있다.

## 부록용 원고 — AI 보조 AWS Telemetry 후보 조사

프로젝트 5개 Source만으로 끝내지 않고, 자주 사용하는 AWS Resource에서 저지연 보안관제에 활용할 수 있는 Telemetry 후보를 AI로 폭넓게 수집하였다. AI는 누락하기 쉬운 후보를 찾고 비교표 초안을 만드는 데 사용했으며, 근거로 취급하지 않았다. 각 후보의 지원 Destination, 지연, Sampling·Best-effort·집계 특성은 AWS 공식 문서로 다시 확인하고, 구현·Runtime 검증 전에는 `Target Candidate`로 표시한다.

| Resource·Telemetry mechanism | 저지연 Route 후보 | 주의할 점 |
|---|---|---|
| **CloudWatch Logs Subscription** | CWL→Lambda/Kinesis/Firehose→SIEM | CWL ingest 후 전달을 줄일 뿐 원본 Source A+B는 제거하지 않음. Throttle·재시도·실패 모니터링 필요 |
| **S3 Object Event** | S3 EventBridge/SQS→Bridge→Wazuh | Object 생성·삭제 Event이며 `GetObject` 접근 감사의 대체재가 아님 |
| **VPC Flow Logs** | 1분 집계→CWL→Subscription→Wazuh | Packet 실시간 로그가 아니라 Flow 집계이며 best-effort |
| **Route 53 Query Logs** | Route 53→CWL→Subscription→Wazuh | Public/Resolver 로그의 Coverage와 Cache 동작 차이 확인 필요 |
| **EKS Control Plane·Audit Logs** | EKS→CWL→Subscription→Wazuh | Kubernetes API·Audit 분석에 유효하나 Source 전달 지연과 비용 측정 필요 |
| **API Gateway Access Logs** | API Gateway→CWL→Subscription→Wazuh | Data tracing은 민감정보 노출 위험이 있어 운영환경에서 제한 필요 |
| **RDS·Aurora DB Logs** | RDS→CWL→Subscription→Wazuh | Engine별 지원 로그와 Audit 설정이 다름 |
| **GuardDuty Finding** | GuardDuty→EventBridge→SQS/Lambda→SIEM·SOAR | 신규 Finding과 반복 Finding의 집계 주기가 다를 수 있음 |
| **Security Hub Finding** | Security Hub→EventBridge→SQS/Lambda→SIEM·SOAR | 최종 지연은 GuardDuty 등 Upstream Finding 생성 시간에도 좌우됨 |
| **AWS Config Change** | Config→EventBridge→SQS/Lambda→SIEM | 변경 감지와 전달 특성, best-effort 조건 확인 필요 |

| 판정 구분 | 보고서에서의 표기 |
|---|---|
| AWS 공식 문서가 명시한 지원 방식·지연·제약 | **공식 사실** |
| 공식 사실과 현재 Runtime을 바탕으로 한 해석 | **프로젝트 판단** |
| 구현·Runtime 비교 전의 개선안 | **Target Candidate / 미검증** |
| AI가 제안했지만 공식 확인 전인 항목 | **조사 후보 / 보고서 결론에서 제외** |

### 짧게 보여줄 코드 후보 1 — Subscription과 Buffer

```hcl
redrive_policy = jsonencode({
  deadLetterTargetArn = aws_sqs_queue.wazuh_push_primary_dlq[0].arn
  maxReceiveCount     = 5
})

resource "aws_cloudwatch_log_subscription_filter" "wazuh_push_dvwa" {
  log_group_name  = aws_cloudwatch_log_group.dvwa_primary.name
  filter_pattern  = ""
  destination_arn = aws_lambda_function.wazuh_push_primary[0].arn

```
