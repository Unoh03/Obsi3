## 338페이지 — 7.1 종합 보안 평가

### 7.1 종합 보안 평가

본 프로젝트는 AWS와 EKS에서 발생한 보안 신호를 Wazuh에서 탐지하고, 검증된 Alert만 Shuffle과 고정 GitHub Workflow를 통해 실제 대응으로 연결하는 보안관제 체계를 구현하였다.

| 구분 | 구현 결과 |
|---|---|
| **수집** | DVWA 저지연 Event와 AWS·EKS 로그를 Wazuh에 중앙 수집하였다. |
| **탐지** | Rule `100102`로 전달 경로 건전성을, Rule `100110`으로 IMDS Credential endpoint 대상 명령의 출력 반환을, Rule `100111`로 보호 S3 Object의 실제 바이트 반환을 구분해 탐지하였다. |
| **1차 대응** | Rule `100110` Alert의 Rule·Schema·Pod 이름·UID를 검증한 뒤 침해 Pod를 격리·보존하고 정상 서비스를 위한 대체 Pod를 유지하였다. |
| **2차 대응** | Rule `100111` Alert의 CloudTrail 조건과 해시를 검증한 뒤 DVWA의 사전 승인된 방어 프로필을 `low`에서 `impossible`로 전환하였다. |
| **추적·복구** | Wazuh Alert, Shuffle Execution, GitHub Actions Run, Git Commit, Argo CD Revision을 연결하고 Reset Workflow로 기준선을 복구하였다. |

이 결과는 **공격 징후 탐지 → 제한된 자동 격리 → S3 침해확정 → 애플리케이션 완화 → GitOps 기반 추적·복구**를 하나의 시나리오로 연결했다는 데 의미가 있다.

다만 Pod 격리는 이미 유출된 Node Role 자격증명을 폐기하지 않으며, `low → impossible`은 취약 코드를 새로 작성한 Source Patch가 아니다. 현재 결과는 고정된 실습 범위에서 자동 대응의 통제 가능성·추적 가능성·복구 가능성을 검증한 것이다.

## 339페이지 — 7.2 보안관제 체계 구축 효과 및 목표 달성도

### 7.2 보안관제 체계 구축 효과 및 목표 달성도

프로젝트의 핵심 질문은 다음과 같았다.

> **흩어진 AWS·EKS 보안 신호를 공격 단계에 따라 구분하고, 탐지 결과를 실제 대응과 재검증까지 연결할 수 있는가?**

| 평가 항목 | 결과 | 범위 |
|---|---|---|
| 서로 다른 계층의 보안 신호 구분 | 달성 | DVWA Audit Event와 CloudTrail S3 Data Event를 별도 Rule로 탐지 |
| 검증된 Alert만 자동 대응 | 달성 | Wazuh 로컬 검증, Shuffle 입력 계약, 고정 Workflow 적용 |
| 침해 Workload의 확산 제한 | 달성 | UID와 소유 관계가 일치하는 DVWA Pod만 격리·보존 |
| 애플리케이션 완화 배포 | 달성 | Rule `100111` 이후 고정된 `low → impossible` 전환 |
| 대응 이력 추적과 기준선 복구 | 달성 | Workflow Run·Commit·Argo Revision·Reset 기록 |
| Rule `100110`과 `100111` 자동 상관분석 | 미구현 | 관제자가 Timeline과 공통 문맥을 비교해 동일 사건 여부 판단 |
| 탈취 Credential·IAM Session 대응 | 미구현 | 현재는 Workload 격리와 애플리케이션 완화까지 수행 |

따라서 본 프로젝트는 범용 Incident Response Platform을 완성한 것이 아니라, **고정된 Capital One 실습 시나리오에서 수집·탐지·검증·자동 대응·복구의 폐쇄 루프를 구현하고 그 경계를 확인한 프로젝트**로 평가한다.

## 340페이지 — 7.3 프로젝트 수행 중 이슈 및 설계 변경

### 7.3 프로젝트 수행 중 이슈 및 설계 변경

구현 과정에서는 단순한 오류 수정뿐 아니라 탐지와 대응의 의미 자체를 여러 차례 재정의하였다.

| 초기 문제 | 재검토한 판단 | 최종 반영 |
|---|---|---|
| 하나의 Rule이 조기 징후와 침해확정을 모두 표현 | 서로 다른 Source가 증명하는 사실과 도착 시간이 다름 | Rule `100110`과 `100111`을 독립 증거로 분리 |
| Alert가 지정한 대상을 그대로 자동 조치 | 위조·오탐 Alert가 임의 대상에 영향을 줄 위험 | Rule별 Schema, Allowlist, 해시, 고정 Repository·Workflow 적용 |
| 침해 Pod를 삭제하면 증거와 서비스가 함께 사라짐 | 증거 보존과 정상 서비스 지속이 모두 필요 | 원본 Pod를 소유 관계에서 분리해 격리·보존하고 대체 Pod 유지 |
| `low → impossible`을 자동 Source Patch처럼 설명 | DVWA에 이미 존재하는 방어 구현을 선택하는 조치임 | 고정·가역 방어 프로필 배포로 범위를 명시 |
| 빠른 경로와 느린 경로를 별개의 관제로 인식 | 하나의 Incident 안에서도 Source별 지연과 역할이 다를 수 있음 | 저지연 신호는 초기 대응, 후행 로그는 침해확정·조사 Evidence로 사용 |

특히 Rule `100110`은 공격 스크립트 완료 전에 차단했음을 보장하는 Rule이 아니다. 실제 시연에서는 공격 완료 뒤 Count가 증가했으므로, **5분 주기로 수집되는 Rule `100111`보다 먼저 관제와 대응을 시작하게 하는 저지연 경보**로 해석한다.

## 341페이지 — 7.4 잔여 위험 및 후속 설계 ①

### 구현 이후 새롭게 정립한 Telemetry와 지연 모델

초기에는 `CloudFront 로그`, `ALB 로그`, `CloudTrail 로그`처럼 AWS 서비스마다 대표 로그가 하나씩 존재하는 것으로 단순화하였다. 그러나 Runtime 검증과 멘토 피드백, 공식 문서 재검토를 통해 **같은 서비스에서도 Telemetry mechanism과 전달 Route에 따라 지연·보존·정보 가치가 달라진다**는 점을 확인하였다.

```text
Service / Resource
≠ Telemetry Signal
≠ Logging Mechanism
≠ Initial Destination
≠ SIEM Transport Route
≠ Detection Rule
```

예를 들어 동일한 CloudFront 요청을 관찰하더라도 Standard Logging과 Real-time Logging은 생성·전달 방식과 지연 특성이 다르다. ALB도 Legacy S3 Access Logs와 Vended Logs를 동일한 수집 방식으로 평가할 수 없다.

로그의 End-to-End 지연도 하나의 숫자가 아니라 다음 구간으로 나누어야 한다.

| 구간 | 의미 |
|---|---|
| **A** | 실제 Event 발생부터 Log·Event Record 생성까지 |
| **B** | 생성된 Record가 AWS 소비 지점에 도착할 때까지 |
| **C** | AWS 소비 지점에서 Wazuh 입력까지 전달되는 시간 |
| **D** | Wazuh Decoder·Rule 평가와 Alert·Integrator 처리 시간 |
| **E** | Shuffle 전달부터 Workflow와 최종 Action 완료까지 |

`Event-driven` 전환이나 Poll 제거는 주로 C 구간의 불필요한 대기 시간을 줄인다. 원본 Source의 A+B 지연까지 자동으로 사라지는 것은 아니다. 이번 프로젝트에서는 전체 A~E 구간을 동일한 기준 시각으로 분리 측정하지 못했으며, 이는 후속 검증 과제로 남았다.

## 342페이지 — 7.4 잔여 위험 및 후속 설계 ②

### 현재 수집 구조와 Source별 Target Route

현재 구현은 DVWA 저지연 Event에는 CloudWatch Logs Subscription 기반 전달을 적용하고, 일부 AWS Source에는 주기적 Poll과 Archive 기반 조사를 함께 사용한다.

```text
현재 As-built

DVWA Audit Event
→ CloudWatch Logs Subscription
→ Lambda Allowlist
→ SQS Buffer
→ Local Bridge
→ Wazuh

AWS 원본 로그
→ CloudWatch Logs 또는 Security S3
→ 주기적 수집
→ Wazuh 조사·침해확정 Evidence
```

후속 검토에서 확인한 Source별 개선 후보는 다음과 같다.

| Source | 후속 Target Candidate | 남는 검증 |
|---|---|---|
| **AWS WAF** | CloudWatch Logs Subscription 기반 Event-driven 전달 | A+B 실측, 중복·누락·비용 검증 |
| **ALB** | Vended Logs Runtime 평가 또는 Legacy S3 ObjectCreated Event 활용 | Legacy와 Vended의 실제 지연·필드·비용 비교 |
| **CloudFront** | 고유 Field의 저지연 탐지가 필요할 때 Real-time Logs와 Kinesis 평가 | Best-effort, Sampling, WAF 중복, Consumer 운영 검증 |
| **CloudTrail** | CloudWatch Logs Subscription으로 C 구간 Poll 대기 축소 | CloudTrail 고유 A+B 지연은 유지됨 |

기존 Poll과 Archive는 폐기 대상이 아니다. Event-driven 경로를 주 탐지 경로로 확대하더라도 원본 보존, Replay, 누락 보완, 사후 조사와 Historical Analysis 경로로 유지할 가치가 있다.

따라서 목표는 모든 Source를 동일한 Transport로 강제하는 것이 아니라, **Source별로 적합한 Telemetry와 Route를 선택하고 Wazuh에서 하나의 Incident 흐름으로 분석하는 것**이다.

## 343페이지 — 7.4 잔여 위험 및 후속 설계 ③

### 자동 상관분석과 3축 Containment의 미구현 범위

현재 Rule `100110`과 Rule `100111`은 서로 다른 계층의 독립 증거다. 두 Alert가 자동으로 하나의 Incident Object에 합쳐지는 것은 아니며, 관제자가 Timeline에서 다음 문맥을 비교해 동일 사건 여부를 판단한다.

- Event 시각과 허용된 조사 시간 창
- `take_id`와 Event ID
- Pod 이름·UID와 Workload Label
- IAM Principal과 Role Session
- Bucket·Object Key
- Source IP, URI, Request ID 등 보조 문맥

후속 Target은 이 공통 문맥을 이용해 `초기 의심 → 추가 Evidence 수집 → 침해확정 또는 불확실` 상태를 자동 갱신하는 Incident Correlation 구조다. 공통 Stable ID가 없는 Source는 완전한 일대일 대응이 아니라 여러 Evidence를 이용한 추론이 필요하다.

자동 대응의 범위도 다음 세 축으로 분리해야 한다.

| 대응 축 | 현재 구현 | 후속 과제 |
|---|---|---|
| **Workload / Network** | 침해 DVWA Pod 격리·보존과 대체 Pod 유지 | Node 격리·교체 및 다른 Workload 영향 검증 |
| **Resource / Permission** | 미구현 | S3 Bucket Policy·IAM Policy를 이용한 제한적 접근 차단 |
| **Credential / Session** | 미구현 | 탈취 Role Session 식별·권한 제한·Credential 영향 조사 |

현재 시나리오는 DVWA 전용 IAM Role이 아니라 공유 EC2 Node Role을 사용한다. Role 전체를 자동 차단하면 다른 Workload까지 영향을 받을 수 있으므로 실행하지 않았다. 향후 DVWA 전용 EKS Pod Identity와 최소권한 Role을 적용하면 탐지 대상과 권한 대응 대상을 더 정확하게 일치시킬 수 있다.

## 344페이지 — 7.4 잔여 위험 및 후속 설계 ④

### 검증된 Baseline을 유지한 이유와 후속 검증 순서

프로젝트 후반에 일부 AWS Source에는 현재 Polling 방식보다 저지연일 가능성이 있는 Event-driven Telemetry와 전달 Route가 존재한다는 점을 확인하였다. 그러나 이는 단순한 로그 설정 변경이 아니다.

```text
Terraform 및 AWS 로그 설정
→ 전달 Destination과 Buffer
→ Wazuh 입력·Decoder·Rule
→ Source 간 Correlation
→ 중복·누락·재시도·DLQ
→ 자동 대응의 Blast Radius와 Rollback
→ Runtime Evidence 재수집
```

구조를 변경하면 위 전체 구간을 다시 검증해야 한다. 따라서 미검증 신규 구조를 완료 결과에 섞기보다, 실제 Runtime Evidence가 확보된 현재 Baseline을 유지하고 개선안을 Target Architecture로 분리하였다.

후속 검증은 다음 순서로 진행한다.

1. Source별 Telemetry mechanism과 공식 지연·보존 특성을 확정한다.
2. A/B/C/D/E 구간별 Timestamp와 Clock 기준을 정의한다.
3. 정상·공격 Event를 반복해 지연, 누락, 중복과 순서 역전을 측정한다.
4. SQS Buffer, Retry, DLQ, Replay와 멱등 처리의 장애 복구를 검증한다.
5. Correlation Key와 시간 창을 적용해 False Positive와 False Negative를 평가한다.
6. 대응 범위, 서비스 영향, 증거 보존과 Rollback을 다시 검증한다.

> **구현을 많이 추가하는 것보다, 검증된 범위와 후속 설계를 명확히 구분하는 것이 최종 결과의 신뢰성을 높인다고 판단하였다.**
