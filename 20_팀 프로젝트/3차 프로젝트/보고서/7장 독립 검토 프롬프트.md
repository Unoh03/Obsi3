# Chapter 7 독립 검토 프롬프트

> [!important] 사용 목적
> 이 프롬프트는 **Chapter 7만** 독립 검토하기 위한 것이다. Chapter 5와 다른 장은 검토 대상에 포함하지 않는다. 이전 독립 검토가 기술 서술의 옳고 그름에 치우친 문제를 바로잡고, 독자가 Chapter 7의 설계 발전 과정과 인과관계를 실제로 이해할 수 있는지를 우선 판정한다.

## 권장 실행 설정

- Model: `gpt-5.6-sol`
- Reasoning effort: `max`
- `fork_turns: none`
- 이전 대화와 Codex Memory를 읽지 않는다.
- 허용 입력은 다음 세 파일뿐이다.
  - `D:\terraform\aws_terraform_build_code\.review-input\7챕터_개선할 점 - A4.pdf`
  - `D:\terraform\aws_terraform_build_code\.review-input\7.0 관제 고도화 과정-1_문제·개선·새 질문.drawio.png`
  - `D:\terraform\aws_terraform_build_code\.review-input\7.0 관제 고도화 과정-2_Telemetry·지연·설계 판단.drawio.png`
- 같은 폴더의 Chapter 5 자료와 그 밖의 파일은 읽지 않는다.
- 검토 범위: 15쪽 PDF 전체. 두 PNG는 PDF 앞부분에 배치된 두 다이어그램을 원본 해상도로 읽기 위한 보조 입력이다.
- Canva 편집, 파일 수정, 웹 검색, 저장소 전체 감사는 수행하지 않는다.

## 복사해서 사용할 프롬프트

```text
당신은 보안 기술 감사를 수행하는 사람이 아니라, 최종 프로젝트 보고서의 Chapter 7을 처음 읽는 독립 검토자다.

다음 세 파일만 입력으로 사용하라.

1. `D:\terraform\aws_terraform_build_code\.review-input\7챕터_개선할 점 - A4.pdf`
2. `D:\terraform\aws_terraform_build_code\.review-input\7.0 관제 고도화 과정-1_문제·개선·새 질문.drawio.png`
3. `D:\terraform\aws_terraform_build_code\.review-input\7.0 관제 고도화 과정-2_Telemetry·지연·설계 판단.drawio.png`

15쪽 PDF 전체가 Chapter 7 검토 범위다. 두 PNG는 PDF 앞부분의 첫 번째·두 번째 다이어그램을 원본 해상도로 읽기 위한 보조 입력이므로, PDF와 별개의 추가 성과로 중복 평가하지 마라. 같은 `.review-input` 폴더에 있는 Chapter 5 PDF, `관제 올인원` 파일, `_render` 폴더 및 그 밖의 모든 파일은 열거나 참고하지 마라. 이전 대화·Codex Memory·다른 AI의 평가도 참고하지 말고, Canva·PDF·PNG·저장소 파일을 수정하지 않은 채 검토 결과만 반환하라.

이번 검토의 최우선 목적은 개별 기술 문장이 완벽한지 검사하는 것이 아니다. 독자가 다음 설계 발전 과정을 자연스럽게 따라갈 수 있는지 판정하는 것이다.

1. 처음에는 여러 Source를 10분 Poll로 수집했다.
2. 원본 보존과 넓은 Coverage에는 유효했지만, 다음 Poll까지 초기 탐지가 늦어질 수 있다는 문제를 발견했다.
3. 이 문제를 줄이기 위해 DVWA Event를 Wazuh로 저지연 전달하는 별도 Route를 실제로 구현하고 측정했다.
4. 당시에는 이를 빠른 Route와 느린 Route로 이해했다.
5. 멘토 상담은 속도뿐 아니라 탐지 정확도, 오탐 피해, 자동 대응의 안전 범위를 다시 생각하게 만든 전환점이었다.
6. 그러나 멘토가 Telemetry나 A/B/C/D/E 모델을 직접 알려준 것은 아니다.
7. 이후 더 높은 정확도와 완전한 Correlation에는 장기간의 Rule 튜닝과 재검증이 필요하다고 판단했다.
8. 남은 기간에는 전체 구조를 교체하지 않고, “DVWA에서 Poll 대기를 줄인 방식을 다른 AWS Source에도 적용할 수 있는가?”를 별도로 조사했다.
9. 그 과정에서 Service, Telemetry mechanism, Destination, SIEM Route를 분리해 봐야 한다는 점과 Event-driven이 곧 동일한 저지연을 보장하지 않는다는 점을 배웠다.
10. 지연을 A+B+C+D+E로 나누고 Source별 후보를 재평가했으며, 검증된 현재 구조는 Baseline으로 유지하고 미구현 후보는 Target Architecture와 Future Work로 분리했다.

이 열 단계는 사실 목록이 아니라 Chapter 7이 전달하려는 하나의 인과관계다. 특히 다음과 같이 읽히면 안 된다.

- 처음부터 Telemetry 기반 Target Architecture를 목표로 계획한 프로젝트
- 멘토가 “속도는 중요하지 않다”고 말해 저지연 Route를 부정한 이야기
- 멘토 피드백 때문에 곧바로 Telemetry를 알게 된 이야기
- 시간이 없어서 구현을 포기한 뒤 이론만 덧붙인 이야기
- 가장 빠른 Route가 항상 가장 좋은 Route라는 주장
- 현재 구현과 미검증 후보를 같은 성과로 제시한 이야기

## 검토 우선순위

다음 순서로 판단하라.

1. **독자에게 실제로 읽히는 이야기**
2. **단계 사이의 원인과 결과**
3. **앞의 두 다이어그램이 이후 본문의 흐름을 제대로 예고하는지**
4. **본문이 다이어그램을 반복하지 않고 근거와 판단을 한 단계 더 깊게 설명하는지**
5. **현재 성과, 판단 변화, 후속 학습, 미구현 후보의 경계가 자연스럽게 이해되는지**
6. **강사·멘토·포트폴리오 검토자가 작성자의 문제 발견, 실제 개선, 성찰, 조사 방법, Scope 판단 능력을 확인할 수 있는지**
7. 문장 가독성과 용어 설명
8. 기술적 세부 정확성

기술 검증은 8순위다. 저장소를 뒤지거나 웹 검색으로 기술 사실을 전수 감사하지 마라. 정확한 버전, Field 이름, Rule 조건, Runtime 증명 상태처럼 서사의 중심과 무관한 세부사항에 검토 분량을 쓰지 마라. 다만 기술 표현 하나가 Chapter 7의 결론을 뒤집거나 보고서 신뢰성을 심각하게 훼손하는 경우에만 마지막 부록에 최대 3건까지 별도로 적어라.

## 반드시 판정할 질문

1. 첫 두 다이어그램만 본 독자가 “왜 Chapter 7이 필요한가”를 10초 안에 이해할 수 있는가?
2. 다이어그램 이후 본문은 같은 말을 길게 반복하는가, 아니면 각 판단의 근거를 확장하는가?
3. `10분 Poll → DVWA 저지연 Route → 멘토 상담 → 추가 고민 → Telemetry 조사 → A/B/C/D/E → Source 재평가 → Target Architecture`의 연결이 끊기는 지점이 있는가?
4. 멘토 상담은 정확도·오탐·안전 범위를 재검토한 계기로 읽히며, Telemetry 발견의 직접 원인으로 왜곡되지 않는가?
5. 속도와 정확도를 양자택일하지 않고 환경과 대응 위험에 맞춰 균형을 다시 잡은 과정으로 읽히는가?
6. 시간 제약은 변명이나 포기로 보이는가, 검증된 Baseline과 미검증 후보를 분리한 Scope 결정으로 보이는가?
7. Telemetry와 A/B/C/D/E는 교과서 지식 자랑이 아니라 실제 지연 문제를 다른 Source에 일반화하기 위한 분석 도구로 등장하는가?
8. Source별 후보와 Target Architecture가 앞선 조사에서 도출된 결론으로 보이는가, 갑자기 추가된 기술 목록으로 보이는가?
9. AI 확장 조사는 판단을 대신한 것처럼 보이는가, 후보를 넓힌 보조 수단으로 보이는가?
10. 마지막 결론이 Chapter 7 전체에서 실제로 증명된 내용인가?

## 출력 형식

다음 순서를 지키고 불필요하게 긴 기술 해설은 하지 마라.

### 1. 최종 판정

`승인 / 보정 후 승인 / 재구성 필요` 중 하나를 선택하고 두 문장 이내로 이유를 적는다.

### 2. 처음 읽은 독자에게 실제로 남는 이야기

Chapter 7을 다 읽은 독자가 기억할 내용을 3~5문장으로 요약한다. 저자의 의도를 반복하지 말고, PDF에서 실제로 그렇게 읽힌 내용만 적는다.

### 3. 인과관계 점검

아래 각 연결을 `명확 / 약함 / 끊김 / 왜곡` 중 하나로 판정하고, 해당 페이지 번호가 아니라 **페이지 제목·소제목·눈에 보이는 문구**로 위치를 특정한다.

- 10분 Poll의 문제 → DVWA 저지연 Route 구현
- 실제 개선 → 멘토 상담 후 판단 재검토
- 판단 재검토 → 구현 범위 결정
- 구현 범위 결정 → 다른 Source 적용 가능성 조사
- 조사 → Telemetry 평가 단위 도입
- Telemetry 구분 → A/B/C/D/E 지연 모델
- 지연 모델 → Source별 재평가
- Source별 재평가 → Target Architecture와 Future Work

### 4. 가장 큰 흐름 문제

최대 5건만 중요도순으로 적는다. 각 항목은 반드시 다음 네 줄로 작성한다.

- 위치:
- 현재 독자가 받아들일 의미:
- 저자 의도와의 차이:
- 최소 수정안: 삭제·추가·이동·대체 중 하나와 실제 대체 문구

새 페이지나 대규모 기술 설명을 먼저 제안하지 마라. 기존 배치 안에서 가능한 최소 수정부터 제시한다.

### 5. 반복과 밀도

첫 두 다이어그램과 이후 본문 사이에서 정말 불필요한 반복만 최대 3건 적는다. 자세한 근거 설명까지 반복으로 오인해 삭제하지 마라.

### 6. 반드시 보존할 부분

Chapter 7의 의도와 포트폴리오 가치를 가장 잘 보여주는 부분을 최대 5건 적는다. 수정 제안 때문에 이 부분이 사라지지 않도록 한다.

### 7. 기술 문제 부록

서사의 결론이나 보고서 신뢰성을 실제로 훼손하는 중대한 문제만 최대 3건 적는다. 없다면 `없음`이라고 쓴다. 이 부록이 전체 검토의 중심이 되어서는 안 된다.

### 8. 최종 한 문장

현재 Chapter 7이 전달하는 핵심과, 저자가 의도한 핵심이 일치하는지를 한 문장으로 판정한다.
```

## 검토 결과를 받을 때의 판정 기준

좋은 검토 결과는 다음 특징을 가진다.

- 기술 용어보다 독자가 받아들인 서사를 먼저 말한다.
- 문제의 수보다 가장 큰 흐름 단절을 우선한다.
- `현재 문구 → 독자 해석 → 의도와의 차이 → 최소 대체 문구`가 연결된다.
- Chapter 7의 포트폴리오 가치를 `문제 발견`, `실제 개선`, `판단 변화`, `후속 조사`, `검증 경계`로 평가한다.
- 기술 문제 부록이 본문보다 길지 않다.

다음과 같으면 이전 검토 실패가 반복된 것이다.

- 첫 답변부터 Rule·Field·AWS 기능의 사실 검증으로 시작한다.
- 저장소에서 틀린 표현을 많이 찾은 것을 검토 성과로 삼는다.
- 서사를 말하지 않고 문장별 정오표만 반환한다.
- 새로운 기술 설명을 계속 추가하라고 권한다.
- Chapter 5나 프로젝트 전체로 범위를 넓힌다.
