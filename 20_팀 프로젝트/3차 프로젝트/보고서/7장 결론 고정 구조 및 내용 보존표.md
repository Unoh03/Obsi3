# 7장 결론 고정 구조 및 내용 보존표

> [!important] 작성 기준
> 이 문서는 Chapter 7 재작성의 기준 문서다. 이전 대화 요약이나 기존 초안과 충돌하면 이 문서의 인과관계와 순서를 우선한다. 아래 서사 순서와 기술 내용 보존 원칙은 바꾸지 않는다.

## Chapter 7의 목적

Chapter 7은 Telemetry 개념을 별도로 설명하는 교과서식 장이 아니다.

> **10분 Poll 기반 관제의 지연 문제를 발견하고 DVWA 저지연 Route를 구현한 뒤, 멘토 상담과 추가 호기심 기반 조사를 거쳐 Source별 Telemetry와 지연 구간을 재평가하게 된 설계 발전 과정을 보여준다.**

현재 구현의 성과, 판단이 바뀐 계기, 새롭게 정립한 분석 모델, 구현하지 못한 Target Architecture를 하나의 인과관계로 연결한다.

## 고정 인과관계

```text
초기: 모든 Source를 10분 Poll로 수집
→ 사고 발생 뒤 Poll 대기 때문에 관제 인지가 늦어질 수 있다는 문제 발견

긴급 개선: DVWA Push 저지연 Route 구현
→ 당시에는 빠른 Route / 느린 Route로 구분

멘토 상담
→ 속도만큼 탐지 정확도와 오탐 방지가 중요하다는 조언
→ 빠른 신호와 느린 신호의 역할 및 표현을 다시 검토하는 계기

이후 추가 고민
→ 정확도와 Correlation을 완전히 검증하려면 장기간이 필요
→ 남은 프로젝트 기간에는 전체 구현·재검증이 어려움
→ 대신 “DVWA Push 방식을 다른 AWS Source에도 적용할 수 있는가?”를 조사

호기심 기반 조사
→ 같은 서비스에도 서로 다른 Telemetry mechanism이 있음을 확인
→ Event-driven과 low-latency가 같은 뜻이 아님을 확인
→ Service × Telemetry × Route 단위로 재평가
→ A/B/C/D/E 지연 모델 정립
→ Source별 Target Candidate와 후속 검증 계획 도출

확장 조사
→ AI로 자주 사용하는 AWS Resource의 후보 Route를 폭넓게 수집
→ 공식 문서로 사실·지연·제약을 다시 확인
→ 공식 사실 / 프로젝트 판단 / 미검증 후보를 분리
```

### 멘토 피드백의 정확한 역할

멘토 피드백은 Telemetry 개념이나 A/B/C/D/E 모델을 직접 알려준 원인이 아니다.

- 멘토 피드백: 속도만이 아니라 정확도, 오탐, 대응 범위를 다시 보게 만든 **전환 계기**
- Telemetry 발견: 이후 DVWA Push Route를 다른 Source에도 일반화할 수 있는지 호기심으로 조사하다 얻은 **후속 학습 결과**
- A/B/C/D/E 모델: Source마다 느린 원인이 다르다는 점을 설명하기 위해 프로젝트에서 정립한 **분석 모델**

따라서 `멘토 피드백으로 속도 중심 설계의 한계를 깨달아 Telemetry를 도입했다`처럼 직접 인과관계로 쓰지 않는다.

## 고정 서사 순서

### 1. 출발점 — 10분 Poll 기반 수집의 한계

- 초기에는 여러 AWS·EKS Source를 10분 주기로 Poll했다.
- Event가 Poll 직후 발생하면 다음 수집까지 최대 10분을 기다릴 수 있었다.
- 이 10분은 주로 SIEM Transport의 Poll 대기인 C 구간에 추가된다.
- Alert 인지 시점은 A+B+C+D이며, 자동 대응 완료까지 보면 A+B+C+D+E다.
- 원본 보존과 후행 조사에는 유효하지만 신속한 초기 대응 Trigger로는 부족했다.

### 2. 첫 번째 개선 — DVWA Push 저지연 Route

```text
DVWA Audit Event
→ CloudWatch Logs
→ Subscription Filter
→ Lambda Allowlist
→ SQS Buffer
→ Local Outbound Bridge
→ Wazuh Decoder·Rule
```

- 애플리케이션이 행위 직후 구조화 Audit Event를 생성했다.
- Subscription Filter가 CloudWatch Logs 이후의 Poll 대기를 제거했다.
- Lambda가 민감정보를 제거하고 허용한 Field만 통과시켰다.
- SQS가 Buffer 역할을 담당했다.
- Local Bridge가 Wazuh Inbound Port를 노출하지 않고 Outbound 방식으로 Event를 소비했다.
- 무해 검증 Event N=3에서 DVWA Event부터 Rule `100102` Alert까지 `6.439 / 3.427 / 3.761초`, 누락 0건이 관측됐다.
- 이 측정은 A+B+C+D 합계이며 각 구간의 독립 측정이나 Shuffle E 구간을 포함하지 않는다.

### 3. 멘토 상담 — 속도와 정확도의 역할 재검토

- 멘토는 속도보다 정확도와 오탐 방지가 중요하다는 취지의 조언을 했다.
- 이 조언은 빠른 Route를 폐기하거나 Telemetry 공부를 직접 촉발한 단일 원인이 아니다.
- 빠른 신호만으로 침해를 확정하거나 광범위한 자동 조치를 실행해도 되는지 다시 검토하는 계기가 됐다.
- 이후 표현을 `빠른 관제 / 느린 관제`에서 하나의 Incident 안에서 역할이 다른 독립 Evidence로 변경했다.

```text
Rule 100110
→ IMDS Credential endpoint 대상 명령의 출력 반환
→ 저지연 Alert와 제한적·가역적 Workload 격리

Rule 100111
→ 보호 S3 Object의 실제 바이트 반환
→ 후행 고신뢰 Evidence와 고정 애플리케이션 완화
```

- Rule `100110`은 공격 스크립트 완료 전 차단을 보장하지 않는다.
- Rule `100110`과 Rule `100111`은 자동 상관분석 결과가 아니라 서로 다른 계층의 독립 증거다.

### 4. 두 번째 질문 — DVWA Push를 다른 Source에도 적용할 수 있는가

- 더 높은 정확도와 완전한 Correlation을 구현·검증하려면 장기간이 필요하다고 판단했다.
- 남은 기간에는 전체 Route를 교체하고 기존과 같은 수준의 Runtime Evidence를 다시 확보하기 어려웠다.
- 구현 대신 `DVWA에서 Poll 대기를 제거한 방식을 WAF·ALB·CloudFront·CloudTrail에도 적용할 수 있는가?`를 조사했다.

### 5. 후속 학습 — Telemetry를 평가 단위로 도입

```text
Service / Resource
≠ Telemetry Signal
≠ Logging Mechanism
≠ Initial Destination
≠ SIEM Transport Route
≠ Detection Rule
```

- Telemetry는 Log의 다른 이름이 아니라 Log·Metric·Trace·Event 등을 포괄하는 관측 신호의 상위 개념이다.
- 이 보고서의 핵심은 Telemetry 분류 자체가 아니라 같은 Resource에도 서로 다른 Logging mechanism과 Route가 존재한다는 점이다.
- ALB Legacy S3 Access Logs와 Vended Logs, CloudFront Standard Logs와 Real-time Logs를 같은 하나의 Source로 취급하지 않는다.
- 앞으로 Route는 `서비스 이름`이 아니라 `Resource × Telemetry mechanism × Destination × Transport` 단위로 평가한다.

### 6. 지연 원인 분해 — 프로젝트 A/B/C/D/E 모델

| 구간 | 의미 |
|---|---|
| **A** | 실제 Event 발생부터 Log·Event Record 생성까지 |
| **B** | 생성된 Record가 AWS 소비 지점에 도착할 때까지 |
| **C** | AWS 소비 지점에서 Wazuh 입력까지 전달되는 시간 |
| **D** | Wazuh Decoder·Rule 평가와 Alert·Integrator 처리 시간 |
| **E** | Shuffle 전달부터 Workflow와 최종 Action 완료까지 |

```text
t0 실제 행위 발생
t1 AWS 소비 지점 도착
t2 Wazuh 입력
t3 Wazuh Alert 생성
t4 최종 Action 완료

A+B = t1 - t0
C   = t2 - t1
D   = t3 - t2
E   = t4 - t3
E2E = t4 - t0
```

- A/B/C/D/E는 AWS나 Wazuh의 공식 표준이 아니라 프로젝트에서 정립한 분석 모델이다.
- Event-driven 전환이나 Poll 제거는 주로 C를 줄이며 Source 고유의 A+B까지 제거하지는 않는다.
- 후속 Runtime에서는 공통 Clock 기준, Event ID·Hash, 반복 표본을 이용해 구간별로 측정해야 한다.

### 7. Source별 개선 Route를 찾는 방법

1. 프로젝트에서 사용하는 Resource와 탐지 목적을 목록화한다.
2. Resource별 Telemetry mechanism과 Destination 후보를 조사한다.
3. 공식 문서에서 A+B 지연, 전달 보장, Best-effort·Sampling 특성을 확인한다.
4. 각 후보의 C 구간 SIEM Transport를 설계한다.
5. 탐지 가치, 지연, 신뢰성, 보안 경계, 비용, 운영 복잡도를 비교한다.
6. 우선 검증할 Target Candidate를 선정한다.
7. 반복 Runtime 검증을 통과한 후보만 As-built로 승격한다.

`가장 빠른 Route`를 바로 `가장 좋은 Route`로 판단하지 않는다. 다음 항목을 함께 평가한다.

- 필요한 보안 Field와 탐지 가치
- A+B와 C 지연
- 누락·중복·순서 역전 가능성
- Buffer·Retry·DLQ·Replay
- Local Wazuh Inbound 노출 여부
- 비용과 운영 복잡도
- 기존 Archive와 Correlation 가능성

### 8. 프로젝트 Source 재평가

| Source | 현재 Route | 우선 검토 후보 | 중요한 판단 |
|---|---|---|---|
| **DVWA** | CWL→Subscription→Lambda→SQS→Bridge | 현재 Route 유지 후보 | 저지연·Buffer·Outbound 보안 경계의 균형, A~E 구간별 재측정 필요 |
| **WAF** | CWL→주기적 Poll | CWL Subscription | C의 Poll 대기 제거 후보, A+B·중복·비용 실측 필요 |
| **ALB** | Legacy S3→Poll | Vended Logs 또는 Legacy S3 ObjectCreated | Legacy 파일 생성 지연과 Vended Runtime 비교 필요 |
| **CloudFront** | Standard Logging | Real-time Logs→Kinesis | 수초 단위 후보지만 비용·Sampling·WAF 중복·Consumer 운영 검증 필요 |
| **CloudTrail** | S3→Poll | CWL→Subscription | C는 줄일 수 있지만 CloudTrail 고유 A+B는 남음 |

- 현재 Route, 공식 사실, 프로젝트 판단, 미검증 Target Candidate를 표에서 분리한다.
- 기존 Poll과 Archive는 폐기하지 않고 Evidence·Replay·누락 보완·Historical Investigation 경로로 유지한다.

### 9. Target Architecture와 구현하지 않은 이유

```text
Source별 적합한 Telemetry
→ AWS-native Event-driven Destination
→ Buffer / Retry / DLQ
→ Outbound Bridge
→ Wazuh 중앙 분석·Correlation

기존 Poll / Archive
→ 원본 보존
→ Replay
→ 누락 보완
→ Historical Investigation
```

- 개선 후보를 실제 구조에 반영하려면 Terraform, 전달 Route, Wazuh 입력·Rule, Correlation, 중복·누락, 장애 복구와 Evidence를 모두 다시 검증해야 했다.
- 프로젝트 후반의 남은 기간에는 이 수준의 구현과 재검증을 완료하기 어려웠다.
- 시간 부족은 Scope 결정의 현실적 제약이며, 기존 Route가 기술적으로 최적이라는 근거로 사용하지 않는다.
- 검증된 Baseline은 유지하고 개선 후보는 Target Architecture와 후속 Runtime 검증 대상으로 분리한다.

### 10. AI를 이용한 확장 조사

- 프로젝트 5개 Source를 넘어 자주 사용하는 AWS Resource의 저지연 Telemetry 후보를 폭넓게 탐색한다.
- AI는 후보 발굴과 비교표 초안에 사용하고 근거 자료로 취급하지 않는다.
- 각 항목은 AWS 공식 문서로 Logging mechanism, Destination, 지연, 전달 제약을 재확인한다.
- 결과는 본문 결론이 아니라 `확장 조사 — 자주 사용하는 AWS Resource의 저지연 보안 Telemetry 후보` 부록으로 분리한다.

| 구분 | 보고서 표기 |
|---|---|
| AWS 공식 문서로 확인한 사실 | 공식 사실 |
| 공식 사실과 현재 Runtime을 바탕으로 한 설계 해석 | 프로젝트 판단 |
| 구현·Runtime 비교 전 후보 | Target Candidate / 미검증 |

## 작성 금지와 필수 표현

### 쓰지 않는다

- `멘토 피드백으로 Telemetry와 A/B/C/D/E 모델을 알게 됐다.`
- `10분 Poll 때문에 전체 시스템이 정확히 10분 느렸다.`
- `Event-driven이면 실시간이다.`
- `A/B/C/D/E는 공식 표준 모델이다.`
- `가장 빠른 Route가 가장 좋은 Route다.`
- `Target Candidate를 구현·검증했다.`
- `시간이 없었으므로 현재 Route가 최적이다.`

### 반드시 포함한다

- 멘토 피드백은 정확도·오탐·대응 범위를 재검토한 계기다.
- Telemetry는 이후 Push 일반화 가능성을 호기심으로 조사하다 발견했다.
- 감지는 D까지, 자동 대응 완료는 E까지 포함한다.
- 현재 구현, 공식 사실, 프로젝트 판단, 미검증 후보를 구분한다.
- 기존 기술 설명은 서사에 종속시키되 삭제하지 않는다.

## 완료 조건

- 10분 Poll → DVWA Push → 멘토 상담 → 호기심 기반 Telemetry 조사 → A/B/C/D/E → Source 재평가 → Target Architecture의 인과관계가 끊기지 않는다.
- 기존 초안의 기술 설명이 위 보존표 중 한 위치에 모두 배치된다.
- 기술 개념만 나열하지 않고 각 개념이 어떤 Runtime 문제를 설명하기 위해 등장했는지 보여준다.
- 미구현 후보는 구현 결과처럼 쓰지 않는다.
- 본문에는 프로젝트 5개 Source를, 범용 AWS Route 표는 부록에 둔다.
