# 8.19 멘토님과 상담 — 최신 판정

> [!IMPORTANT]
> 이 문서가 상담 후 설계·운영 해석의 최신 정본이다.  
> `[[8.19 멘토님과 상담 - 원본 기록 (SUPERSEDED)]]`의 `UNRESOLVED` 구간과 잠정 표는 검토 이력일 뿐이며, 현재 판단으로 사용하지 않는다.

## 출처 구분

| 구분 | 이 문서에서의 취급 |
|---|---|
| 멘토 현업 경험 | 현업 사례·운영 감각으로 보존하되 보편 표준으로 일반화하지 않음 |
| 공식 자료 | NIST, AWS, Microsoft 등 1차 자료로 확인된 범위만 공식 근거로 사용 |
| 현재 Repository / Runtime | Source, 설정, 로그, Evidence가 직접 확인된 상태 |
| 프로젝트 판단 | 공식 사실과 Runtime을 바탕으로 한 설계 해석. 미구현 항목은 Target Candidate로 표시 |

## 상담에서 유효하게 남은 핵심

### SIEM / Wazuh

- 로그 중앙화만으로 관제가 완성되는 것은 아니다.
- 실제 탐지 품질은 공격 특성 이해, Rule 설계, 환경별 튜닝, 오탐·미탐 검토에 좌우된다.
- 단일 Alert만 보지 않고 자산·취약점·다른 Source의 Evidence와 함께 판단해야 한다.
- `어떤 Rule을 왜 만들었고 실제 Runtime에서 어떤 Alert와 후속 동작이 발생했는가`를 설명할 수 있어야 직접 구현했다는 증거가 된다.

### SOAR / Shuffle

- 반복 대응의 자동화는 SOAR의 명확한 가치다.
- 자동화 가능 여부와 자동화해도 안전한지는 별도 문제다.
- 자동 조치는 오탐 피해, 범위, 가역성, Allowlist, 권한, 복구 절차를 함께 설계해야 한다.
- 사람이 사라지는 것이 아니라 반복 조치에서 Threat Hunting, Rule·Workflow 고도화, 새로운 위협 조사로 업무 비중이 이동한다.

## 멘토 주장 중 일반화하지 않을 것

- `사전 / 실시간 / 사후 관제`는 현업 설명 프레임으로는 쓸 수 있지만 보편적 공식 3분류 표준으로 제시하지 않는다.
- `실시간 관제에서도 정확도가 속도보다 항상 우선`은 멘토의 운영 철학이지 보편적 공식 우선순위가 아니다. 위험도와 조치 영향에 따라 정확도와 적시성을 함께 최적화해야 한다.
- 방화벽 로그가 법원에서 유일하게 채택된다는 취지의 발언은 법적 사실로 사용하지 않는다.
- 특정 기업의 Wazuh 사용 여부는 별도 공식 확인 없이는 외부 발표에 사용하지 않는다.
- Alert 2개 분리 질문에 대한 DDoS 답변은 Alert grouping·deduplication·incident correlation의 핵심을 충분히 다루지 못했으므로 설계 근거로 사용하지 않는다.

# DVWA Push + 5-Source Poll의 최종 해석

## 결론

A와 B 중 하나만 고르는 문제가 아니었다.

> **하나의 Incident Detection/Response 흐름 안에서 Source별 Telemetry mechanism과 도착 지연은 달라도 된다. 가능한 Source는 Event-driven으로 중앙 SIEM에 보내고, 원본 Archive/Poll은 보존·Replay·누락 보완·상세 조사 역할로 유지한다.**

따라서 다음 표현은 폐기한다.

```text
빠른 관제 vs 느린 관제
실시간 관제 vs 사후 관제
모든 Source는 동일한 하나의 Transport를 써야 한다
```

대신 다음 구조로 설명한다.

```text
Source별 Telemetry
→ Source별 적합한 Delivery / Transport
→ Wazuh 중앙 수집·탐지
→ 동일 Incident 문맥에서 Evidence 연계
→ Shuffle 대응 Orchestration
```

Transport가 여러 개라는 사실과 Incident 흐름이 여러 개라는 말은 다르다.

## 현재 As-built와 Target

### 현재 As-built

```text
DVWA 저지연 Push
→ 초기 고신뢰 탐지 Trigger

기존 5-Source Poll / Query / Archive
→ 후행 Investigation / Confirmation / Evidence
```

현재는 5개 Source가 자동으로 하나의 Incident Object에 합쳐지는 구조가 아니다.

```text
현재
→ Wazuh 중앙 수집
→ Dashboard / Query / Script / 운영자 해석으로 Evidence 연계

Target
→ 공통 Correlation Key와 시간 창을 이용한 자동 Enrichment / Correlation
```

가능한 상관 키:

- `event_id`, `request_id`, Trace ID
- Principal / Role Session
- Source IP
- URI / Route
- Bucket / Key
- Event time window
- WAF Label / Action

공통 Stable ID가 없는 Source끼리는 완전한 일대일 대응이 아니라 다중 Evidence 기반 추론일 수 있다.

### Target Architecture

```text
각 Source에 적합한 저지연 Telemetry mechanism
→ Event-driven AWS Destination
→ Buffer / Retry / DLQ
→ Local Bridge 또는 적합한 Consumer
→ Wazuh

기존 Poll / Archive
→ 원본 보존
→ Replay
→ 누락 보완
→ Historical Investigation
```

이 Target은 공식 문서 기반 개선 후보이며, 모든 Route가 Runtime 비교로 검증된 것은 아니다.

# 현재 Runtime 상태

| Gate | 상태 | 완료 의미 |
|---|---|---|
| G0~G2 | PASS | Workflow 구조, Header 인증, 합성 Payload 왕복, wrong/missing Header 거절 |
| G3 | strict Runtime PASS | Wazuh Integrator, Rule, Sanitizer, Secret 경계, Manager 적용 |
| G4 | **미완료** | 실제 Rule `100103` Alert와 Shuffle Execution의 전단사 Runtime Evidence 없음 |

따라서 G4 완료 전에는 다음을 주장하지 않는다.

```text
실제 Alert → Shuffle Execution E2E PASS
Wazuh와 Shuffle의 실제 사건 연동 완료
```

G4는 기존 Goal 그대로 먼저 완료한다.

```text
Rule 100103 Alert
→ wazuh-integratord
→ custom-shuffle-soc
→ 인증된 Shuffle Webhook
→ repeat_back_to_me
→ Alert ↔ Execution 일대일 Evidence
```

# 보정된 Incident 시나리오

## 1. 초기 탐지

```text
DVWA 저지연 Push Event
→ Wazuh Rule 100103
→ IMDS 대상 명령 실행 성공
→ 임시 자격증명 탈취 및 S3 접근 위험
→ Incident: SUSPECTED
```

Rule `100103` 하나만으로 `S3가 실제로 털렸다`고 말하지 않는다.

```text
확인 가능한 의미
IMDS 대상 명령 실행 성공
→ Credential 탈취 가능성 증가
→ S3 접근 위험 증가

아직 확인되지 않은 것
실제 자격증명 획득
실제 GetObject 성공
데이터 유출 범위
```

## 2. 초기 Containment

> **강한 격리 = 공격 경로를 확실히 끊되 Blast Radius는 사전에 고정한 격리**

현재 Lab에서 우선 검토할 조치:

```text
DVWA Workload Quarantine
+
validation/* 범위의 추가 접근 제한
```

Containment는 세 축으로 분리한다.

### A. Workload / Network Containment

- DVWA Pod / Workload 격리
- 공격 실행 지점의 추가 통신 차단
- 정상 서비스 영향과 복구 절차 확인

### B. Resource / Permission Containment

- `validation/*` Lab 범위 Explicit Deny
- 필요 시 Bucket Policy·IAM Policy 제한
- 공유 Node Role 전체 `DenyAll`은 다른 Workload 영향 때문에 자동 실행하지 않음

### C. Credential / Session Response

- 실제 사용 Principal과 Role Session 식별
- 탈취·재사용 가능성 및 다른 Resource 권한 조사
- 가능한 범위에서 세션·권한 영향 제한
- 장기적으로 DVWA 전용 Pod Identity / IAM Role로 Blast Radius 축소

Workload 격리만으로 이미 탈취된 STS Credential이 자동 폐기되는 것은 아니다. 세 축을 함께 조사한다.

## 3. 5-Source 후행 조사

```text
WAF
→ Edge 검사 결과, Action, Label

CloudFront
→ Viewer Request와 Edge 도달

ALB
→ Target 전달 경로

DVWA
→ 실제 명령 실행과 Request 문맥

CloudTrail S3 Data Event
→ GetObject 등 AWS API 성공·실패
```

## 4. 판정은 3분기로 한다

### CONFIRMED

다음처럼 공격 문맥과 연결되는 성공 Evidence가 존재한다.

- 동일하거나 상관 가능한 Principal / Role Session
- 대상 Bucket·Key 또는 승인 Prefix 일치
- 공격 시간 창 일치
- 성공 응답
- Source IP, User-Agent, Request ID 등 보조 문맥 일치

```text
상관 가능한 GetObject 성공
→ CONFIRMED
```

### REJECTED / NOT CONFIRMED

단순히 로그가 안 보인다는 이유가 아니라 다음 조건을 확인해야 한다.

- CloudTrail Data Event Coverage 정상
- 대상 Bucket·Prefix·Region·시간 창 정확
- 충분한 Delivery 대기 후 조회
- 동일 공격 문맥의 명시적 AccessDenied / 실패 Evidence
- 다른 Source에도 성공 경로 없음

```text
정상 Coverage + 명시적 실패 Evidence
→ REJECTED / NOT CONFIRMED
```

### INCONCLUSIVE

다음 경우는 기각하지 않는다.

- 대상 Event가 조회되지 않음
- Data Event 활성화·Selector·Prefix 불확실
- 조사 시간 창 또는 Delivery 완료 불확실
- Telemetry 누락·best-effort·보존 상태 불확실

```text
로그 부재 또는 Coverage 불확실
→ INCONCLUSIVE
```

> **Absence of evidence는 Telemetry Coverage가 검증되지 않았다면 evidence of absence가 아니다.**

# 공식 자료와 연결

## NIST

NIST SP 800-61r3는 여러 Source의 Event를 분석·상관하여 Incident Criteria 충족 여부를 판단하는 방향을 제시한다. `SUSPECTED / CONFIRMED`는 NIST 공식 상태명은 아니지만 프로젝트 내부 confidence model로 사용할 수 있다.

- [NIST SP 800-61r3](https://csrc.nist.gov/pubs/sp/800/61/r3/final)

## AWS Incident Response

AWS는 confirmed뿐 아니라 sufficiently suspected threat에도 사전 정의된 Containment를 적용하고 이후 Investigation을 계속할 수 있다고 설명한다. 조치는 범위·가역성·증거 보존·서비스 영향을 고려해야 한다.

- [AWS Security Incident Response — Containment](https://docs.aws.amazon.com/security-ir/latest/userguide/contain.html)

## Microsoft Sentinel 비교

Sentinel은 NRT Rule과 Scheduled Rule, Incident 갱신, Automation Rule / Playbook을 함께 지원한다. 이를 발표에서 **유사한 운영 패턴**으로 비교할 수 있지만, 프로젝트의 `DVWA Push / 5-Source Poll`과 동일 구현이라고 말하지 않는다.

발표용 문장:

> Microsoft Sentinel도 NRT 분석 규칙으로 빠른 신호를 탐지하고, Scheduled 분석과 추가 Alert로 같은 Incident의 문맥을 보강하며, Incident 생성·갱신 시 Playbook을 실행할 수 있습니다. 저희도 이와 유사하게 초기 고신뢰 신호로 제한적 대응을 시작하고, 이후 여러 Source의 Evidence로 사건을 확인하도록 설계했습니다.

- [Microsoft Sentinel — Near-real-time analytics rules](https://learn.microsoft.com/azure/sentinel/near-real-time-rules)
- [Microsoft Sentinel — Scheduled analytics rules](https://learn.microsoft.com/azure/sentinel/scheduled-rules-overview)
