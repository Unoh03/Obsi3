# 2026-08-19 상담 후 재정리

> 아래는 상담 직후 원메모를 수정한 것이 아니라, 녹취를 다시 보고 대화하면서 정리한 **사후 해석·검토 메모**다.  
> 멘토 발언, 현재 구현 사실, 공식 자료로 별도 검증한 내용, 아직 결론이 나지 않은 설계 판단을 섞지 않도록 구분한다.

## 상담에서 얻은 핵심

### Wazuh / SIEM / 탐지 Rule

- 로그를 중앙화했다는 것 자체가 관제의 완성이 아님.
- 실제 탐지 품질은 Rule을 어떻게 만들고 튜닝하느냐에 크게 좌우됨.
- 멘토님들은 여러 보안 장비의 로그를 보고 위협이 될 만한 패턴·행위를 찾아 SIEM 정책/Rule로 만드는 작업을 한다고 설명함.
- 장비마다 로그의 특징이 다르기 때문에 방화벽, IPS로 추정되는 장비, WAF 등 장비 카테고리별 이해가 필요함.
- 좋은 Rule을 만드는 방법에 대해 멘토님은 결국 **공격 자체를 많이 공부하고 공격의 특징을 알아야 한다**고 답함.
- 실시간 관제 정확도를 높이는 작업은 환경별 튜닝과 반복 분석이 많이 필요함. 멘토 표현으로는 상당 부분 "노가다"에 가까움.
- 단일 장비의 탐지만 그대로 믿는 것이 아니라, 필요하면 외부 인사이트 정보나 자산의 취약점 정보 등을 함께 보아 유효성을 높인다고 설명함.
- 예: PHP를 사용하지 않는 환경에서 PHP 공격 로그가 대량 발생했다면, 탐지 자체와 실제 환경에서의 위협 유효성은 다르게 판단할 수 있음.
- 탐지 Rule 생성·고도화에도 AI/LLM을 일부 활용하고 있으며, 멘토님 회사(이글루)에서는 자체 sLLM을 이용해 행위·이상행위 추출 등에 활용한다고 설명함.

### Shuffle / SOAR / 자동화

- 멘토 설명에서 SOAR의 가장 뚜렷한 역할은 **반복되는 대응 업무 자동화**였음.
- 과거에는 공격 IP를 사람이 로그에서 확인하고 방화벽에 수동 등록하는 과정에서 잘못된 IP를 보거나 잘못 입력하는 등의 실수가 있었고, SOAR 도입 후 이런 반복 조치의 수작업 오류가 크게 줄었다는 현업 경험을 말함.
- 단순 조건의 대응부터 시작하고, 이후 여러 조건을 YES/NO decision으로 연결해 복잡한 Workflow로 고도화할 수 있다고 설명함.
- 따라서 `단순한 조치만 SOAR / 복잡한 판단은 무조건 사람` 같은 고정 경계가 있다고 보긴 어려움.
- Pod 격리도 필요한 로그·조건·대상이 명확히 정의되고 실제 연동이 가능하다면 자동화 후보가 될 수 있다는 취지의 답변을 받음.
- 다만 **자동화할 수 있는 것**과 **자동화해도 안전한 것**은 별개임. 후자는 대상 범위, 오탐 피해, 가역성, Allowlist, 권한 범위 등을 별도로 검토해야 함.
- "경보가 울려도 아무 행동 안 한다. SOAR가 다 한다"는 발언은 관제자가 필요 없다는 뜻으로 해석하면 안 됨.
  - 반복 대응은 자동화하고,
  - 사람은 Threat Hunting, Rule/Workflow 고도화, 새로운 취약점·기술 조사, AI 활용 같은 쪽에 더 시간을 쓰는 것으로 이해하는 게 자연스러움.

## 빠른 경로 / 느린 경로 논쟁

이 부분은 아직 결론을 확정하지 않는다.

### 현재 구현·설계 사실

현재 프로젝트에는 성격이 다른 두 전달/조회 경로가 존재함.

#### DVWA Push

- CloudWatch Logs에서 저지연으로 Wazuh 쪽에 전달하는 구조.
- S3 Poll보다 탐지 지연이 짧음.
- 현재 대표 저지연 Event는 DVWA `command.execution` 계열.
- Rule `100103`의 빠른 Trigger로 사용하도록 설계됨.
- 현재 Source coverage는 5-Source 전체보다 좁음.

#### 기존 5-Source Poll / Evidence

- DVWA, WAF, ALB, CloudFront, CloudTrail 등 더 넓은 Source를 한곳에서 연계해 볼 수 있도록 만든 경로.
- S3 저장 및 Poll 주기 때문에 저지연 Push보다 늦음.
- 현재 repo 설계에서는 공격 경로·성공 여부·영향을 확인하는 조사 Evidence 역할을 부여해 둠.

### 처음 이 구조를 만든 이유

처음에는 Wazuh가 S3에서 Poll하는 방식으로 시작했는데 실제 관제용으로 보기에는 지연이 너무 컸음.

상담 당시 설명에서는 S3 비용도 같이 언급했지만, **핵심 문제는 비용보다 latency였음.**

```text
S3/Poll
→ Source coverage는 넓음
→ 하지만 저장·수집·Poll 때문에 수분~10분 이상 늦어질 수 있음

Push
→ 저지연 탐지에 유리
→ 현재는 볼 수 있는 Source 범위가 더 좁음
```

그래서 저지연 Push를 추가했고, 빠른 경로에 없는 상세 Source는 기존 Poll 경로를 유지해 보완하려 했음.

### 멘토와 충돌한 지점

- 멘토님들은 `빠른 경로 / 느린 경로`라는 표현을 현업 관제에서 사용하지 않는다고 함.
- 특히 같은 대상을 보고 같은 결과를 얻으려는 것이라면 왜 두 경로로 나누는지 이해하기 어렵다고 지적함.
- 멘토2는 나중에 **"안 된다고 한 것이 아니라, 현업에서는 저렇게 쓰지 않는다"**고 명확히 정정함.
- 따라서 현재 구조가 기술적으로 틀렸다고 바로 결론내릴 수는 없음.
- 다만 이걸 `빠른 관제 vs 느린 관제`처럼 하나의 관제 체계를 두 종류로 나눈 것으로 설명하면 오해가 매우 큼.

### 상담 중 설명 실수 가능성

후반에 내가 두 경로의 이유를 다시 설명하면서 `비용`을 강조함.

그 결과 멘토 답변이 다음 trade-off로 흘러감.

```text
비용을 아낄 것인가
vs
분석할 수 있는 Source/Insight 범위를 넓힐 것인가
```

하지만 내가 실제로 해결하려 했던 문제는:

```text
실시간 탐지에 필요한 latency
vs
더 넓은 Source coverage
```

에 가까웠음.

당시 `비용`이 아니라 `시간/지연`을 핵심으로 설명했다면 멘토 답변이 일부 달라졌을 가능성은 있음. 다만 `빠른 경로/느린 경로라는 표현을 현업에서는 쓰지 않는다`는 지적 자체는 남았을 가능성이 높음.

## 현재 잠정 해석 — UNRESOLVED

아직 1번과 2번 중 어느 쪽이 더 정확한지 확정하지 않는다.

### 해석 A — 서로 다른 역할의 두 데이터 경로

```text
저지연 Push
→ 실시간 탐지·초기 대응 Trigger

5-Source Poll
→ 후행 Investigation / Confirmation / Evidence
```

이 해석에서는 둘이 같은 일을 중복하는 것이 아니라 **latency와 정보량이 다른 두 경로가 하나의 Incident 처리 과정에서 서로 다른 역할**을 담당함.

이 경우 기존 `빠른 경로 / 느린 경로`라는 명칭보다 다음 같은 표현이 더 적절할 수 있음.

```text
저지연 탐지·초기 대응 경로
후행 조사·증적 분석 경로
```

하지만 이것도 아직 확정 표현이 아님.

### 해석 B — 가능한 한 하나의 실시간 SIEM 흐름으로 통합

- 현업 관점에서는 가능한 Source를 하나의 실시간/근실시간 ingestion과 correlation 흐름으로 모으는 것이 더 자연스러울 수 있음.
- 그렇다면 기존 5-Source Poll은 별도의 "느린 관제"가 아니라 archive, historical evidence, fallback, 추가 조사용 데이터 정도로만 남기는 편이 더 맞을 수 있음.
- 이 경우 현재 두 경로 분리는 구현 제약 때문에 생긴 임시 architecture compromise일 수 있음.

### 아직 확정하면 안 되는 표현

현재는 아래를 확정적으로 쓰지 않는다.

```text
빠른 경로 = 실시간 관제
느린 경로 = 사후 관제
```

직관적으로는 일부 맞을 수 있지만, 5-Source Evidence가 사건이 완전히 끝난 뒤에만 쓰이는 것은 아니고 진행 중인 Incident의 조사·확인에도 사용될 수 있기 때문.

또한 `느린 경로 = 사후 관제`라고 해버리면 멘토가 말한 실시간 관제와 침해사고 분석의 업무 구분까지 현재 기술 경로와 억지로 등치할 위험이 있음.

## 이미 별도 팩트체크한 멘토 주장

### `사전 / 실시간 / 사후 관제`라는 3분류

- 상담에서 멘토는 사전·실시간·사후로 설명함.
- 이후 별도로 공식 자료를 확인했을 때, 이 구분은 현업 설명용 프레임으로는 사용할 수 있지만 **보안관제의 보편적·공식 3분류 표준이라고 단정하기는 어려움.**
- 공식 프레임워크는 다른 분류를 사용하기도 하므로, 발표에서 표준 용어처럼 인용하지 않는 편이 안전함.

### `실시간 관제에서도 정확도가 속도보다 우선`

- 멘토들의 현업 경험·운영 철학으로는 명확한 답변이었음.
- 그러나 별도 공식 자료 검토 결과 **`정확도 > 속도`라는 보편적인 공식 원칙이 있는 것은 아님.**
- 실제 보안 운영에서는 탐지 정확도와 적시성 모두 요구되며, 위험도와 자동 조치의 영향에 따라 균형이 달라짐.
- 따라서 이 내용은 `멘토 현업 경험`으로 기록하고 일반 공식 규칙으로 확대하지 않음.

## 멘토 경험으로 보존하되 일반화하지 않을 것

- 현업에서 `빠른 경로 / 느린 경로`라는 표현을 사용하지 않는다는 경험.
- Rule 작성·튜닝을 위한 반복 로그 분석 방식.
- 과거 수동 IP 차단 단계에서 발생한 실수와 SOAR 도입 후 감소 경험.
- SOAR를 반복 업무 자동화에 주로 활용한다는 경험.
- 이글루 자체 sLLM 활용 사례.
- Wazuh를 특정 대기업/토스에서 실제 사용한다는 발언은 필요하면 별도 사실 확인 후 외부 발표에 사용.

## 추가 팩트체크가 필요한 주장

- 방화벽 로그가 법원에서 "유일하게" 증거로 채택된다는 취지의 발언.
  - 상담 내용으로는 기록하되 법적·포렌식 일반 사실로 사용하면 안 됨.
- 특정 기업의 Wazuh 사용 현황과 규모.
- SOAR의 수집/탐지/분석/대응/보고 역할 경계를 공식 제품/표준 정의처럼 사용할지 여부.

## 후속 검증 주제

> **현재 DVWA Push + 5-Source Poll을, 공식 Incident Response / SIEM / SOAR 관점에서 어떤 구조로 해석하는 것이 가장 정확한가?**

다음 단계에서 공식 문서와 현재 Repository Source를 기준으로 검증할 것.

### 확인할 질문

- 저지연 탐지와 후행 조사를 별도 ingestion/data path로 유지하는 것이 일반적으로 타당한가?
- 5-Source Poll은 실시간 관제의 일부인가, Investigation/Confirmation용인가, 아니면 Post-incident 분석용인가?
- 같은 Incident의 fast signal과 더 풍부한 후행 Evidence를 실제 SIEM/SOAR에서는 어떻게 연계하는가?
- 현재 프로젝트의 `SUSPECTED → CONFIRMED` 확신도 모델은 타당한가?
- 고신뢰 저지연 신호로 좁고 가역적인 Containment를 먼저 수행하고, 추가 Evidence로 침해 성공 여부를 확인하는 구조는 타당한가?
- 현재 두 경로가 역할 분담인지, 아니면 같은 목적을 중복 구현한 것인지?
- 가능하다면 현재 5-Source도 실시간/근실시간 ingestion으로 통합하는 것이 더 나은가?
- Poll 경로를 유지한다면 그것의 정확한 역할은 무엇이어야 하는가?
- 현재 구조를 유지할 경우 발표와 문서에서 어떤 명칭을 사용해야 가장 오해가 적은가?
- `빠른/느린`이 단순 내부 transport 명칭이라면 내부 구현 용어로만 남기고 운영/관제 모델의 이름에서는 제거하는 것이 맞는가?

## 현재 Repository 문서 반영 원칙

이 논쟁이 해결되기 전에는 Terraform Repository의 설계 정본을 성급하게 수정하지 않는다.

현재 생각 정리와 상담 해석은 이 Obsidian 노트에 남기고, 후속 공식 검증으로 결론이 난 뒤에만 Repository 정본에 반영한다.

문서 역할은 가능하면 다음처럼 구분하는 방향이 좋음.

```text
CAPITAL-ONE-INCIDENT-RESPONSE-SCENARIO.md
= WHY / WHAT
= 대응 의미와 설계 결정의 정본

CAPITAL-ONE-SOC-E2E-BLUEPRINT.md
= HOW
= Hop / Interface / Schema / 기술 계약

CAPITAL-ONE-SOC-DEMO-PLAN.md
= VERIFY
= Gate / 완료 조건 / 실행 순서

CAPITAL-ONE-SOC-DEMO-RECORDING-SCRIPT.md
= PRESENT
= 실제 시연 화면 / 조작 / 내레이션

OBSERVABILITY-CURRENT-STATUS.md
= NOW
= 현재 Runtime 상태와 다음 작업

이 Obsidian 상담 노트
= THINKING / HISTORY
= 멘토 발언 / 의문 / 사후 검토 / 미해결 판단
```

같은 설계 결정을 여러 Markdown 파일에서 각각 장문으로 정본처럼 반복하면 이후 한 곳만 수정되어 문서가 충돌하기 쉬움. 최종 결론이 나면 의미상의 결정은 한 정본에 두고, 다른 문서는 필요한 만큼 링크/참조하는 방향으로 정리할 것.

### Codex Goal과의 관계

현재 G4 목표의 `fast path`는 기존 저지연 DVWA/AWS Event transport path를 가리키는 내부 구현 식별자로 볼 수 있으므로, **멘토 상담만을 이유로 Goal을 지금 다시 뜯어고치지는 않음.**

우선은 실제 `Rule 100103 Alert ↔ Shuffle Execution` 일대일 Runtime Evidence를 닫고, 이후 공식 검증 결과에 따라 발표·보고서의 관제 모델 표현과 Repository 정본을 보정하는 순서가 더 안전함.
