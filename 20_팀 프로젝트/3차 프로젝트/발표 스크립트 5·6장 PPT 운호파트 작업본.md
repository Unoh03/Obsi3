## 슬라이드 27 — 5장 목차

> 지금부터 Wazuh와 Shuffle을 이용해 보안 경보를 탐지하고, 실제 대응으로 연결한 과정을 설명드리겠습니다.

## 슬라이드 28 — 공격·수집·Wazuh 탐지

> 먼저 공격이 발생한 뒤 Wazuh 경보가 만들어지는 흐름입니다.
>
> 공격자는 DVWA의 Command Injection 취약점으로 서버 내부 명령을 실행합니다. 이후 IMDS(인스턴스 메타데이터 서비스)라는 내부 정보 서비스를 통해 서버에 부여된 AWS 역할과 임시 자격증명을 확인하고, 그 권한으로 보호된 S3 파일을 읽습니다.
>
> 저희는 이 과정을 두 가지 경로로 수집했습니다.
>
> 초록색 경로는 S3와 CloudWatch Logs를 Wazuh가 5분마다 확인하는 정기 수집 경로입니다. 조금 늦을 수 있지만 여러 AWS 로그를 넓게 수집하고, 원본 보관과 사후 조사에 활용할 수 있습니다.
>
> 분홍색 경로는 DVWA의 중요한 사건만 빠르게 전달하는 경로입니다. DVWA가 관제용 Event를 만들 때 실제 명령어나 자격증명 원문은 처음부터 넣지 않습니다. 이후 CloudWatch Logs에서 Lambda로 전달되면 허용된 필드만 다시 골라 형식을 맞추고, SQS와 Local Bridge를 거쳐 Wazuh로 전달합니다.
>
> Wazuh에서는 Rule 100102로 이 빠른 전달 경로가 정상인지 확인합니다. Rule 100110은 IMDS 자격증명 주소에서 출력이 실제로 반환된 시점을 조기에 탐지하고, Rule 100111은 CloudTrail 기록을 통해 보호된 S3 파일의 바이트가 실제로 반환된 사실을 확인합니다.
>
> 두 경보는 도착 시점이 다르고 자동으로 하나로 합쳐지지는 않습니다. 발생 시각과 공격 식별값, Pod, AWS 역할, S3 Object를 비교해 같은 사건인지 판단하도록 구성했습니다.

## 슬라이드 3 — SOAR·GitOps 자동 대응 폐쇄루프

> 다음은 Wazuh 경보가 실제 대응으로 이어지는 전체 구조입니다.
>
> 먼저 Wazuh Integrator가 자동 대응 대상으로 지정한 Rule 100110과 100111 경보만 골라, 저희가 만든 연계 스크립트로 넘깁니다.
>
> 이 `custom-shuffle-soc` 연계 스크립트는 Rule 번호만 보는 것이 아니라 Source, Account, Region, 공격 단계와 결과가 저희가 정한 조건과 맞는지 다시 확인합니다. 조건이 맞지 않으면 외부로 전송하지 않습니다.
>
> 검증에 성공해도 전체 Alert를 그대로 보내지 않습니다. 대응에 필요한 값만 골라 새로운 JSON을 만들고, 원본 Event나 Log는 SHA-256 값으로 바꿔 동일한 사건인지 확인할 수 있게 했습니다.
>
> Shuffle에서도 인증 정보, 입력 형식, 발생 시각과 해시값을 다시 검사합니다. 검증에 실패하면 GitHub 작업을 실행하지 않기 때문에 실제 환경도 바뀌지 않습니다.
>
> 여기서 Shuffle이 Kubernetes를 직접 변경하는 것은 아닙니다. 검증을 통과하면 사건에 맞는 GitHub Actions Workflow를 선택해 실행합니다. GitHub Actions는 `values.yaml`에서 허용된 설정만 바꾸고, Argo CD가 이 Git 변경을 감지해 EKS에 반영합니다.
>
> Rule 100110은 침해된 Pod를 격리하고, Rule 100111은 DVWA의 보안 수준을 `low`에서 `impossible`로 높입니다. 이후 Wazuh Alert ID부터 Shuffle 실행, GitHub Run과 Commit, Argo CD Revision, 실제 Runtime 상태까지 연결해 대응 과정을 추적합니다.

## 슬라이드 5 — Rule 100110과 침해 Pod 격리

> 이번에는 Rule 100110의 대응을 확대해서 보겠습니다.
>
> DVWA에서 IMDS 자격증명 주소의 출력이 반환되면, 이 사건은 CloudWatch Logs, Lambda, SQS, Local Bridge를 거쳐 Wazuh로 빠르게 전달됩니다. Wazuh는 DVWA의 보안 수준이 `low`인지, 자격증명을 가져오는 단계인지, 실행 결과와 출력 반환 상태가 모두 맞는지 확인한 뒤 Rule 100110 경보를 만듭니다.
>
> 이후 연계 스크립트와 Shuffle이 대상 Pod의 이름과 UID, 사건 식별값을 다시 검증하고, 고정된 `soc-contain-dvwa.yml` Workflow만 실행합니다.
>
> GitHub Actions는 격리 대상과 관련된 `values.yaml` 설정만 변경하고, Argo CD가 이 변경을 EKS에 반영합니다.
>
> 중요한 점은 침해된 Pod를 바로 삭제하지 않는다는 것입니다. 대상 Pod의 UID와 소유 관계를 다시 확인한 뒤 정상 서비스 대상에서 분리하고, `deny-all` NetworkPolicy로 통신을 차단합니다. 침해 Pod는 조사할 수 있도록 보존하고, 정상 ReplicaSet이 대체 Pod를 제공해 서비스는 계속 유지합니다.

## 슬라이드 6 — Rule 100111과 DVWA 보안 강화

> Rule 100111은 조기 징후보다 한 단계 뒤의 사건을 확인합니다.
>
> 침해된 AWS 역할이 정해둔 S3 Object를 요청했고, HTTP 200과 함께 실제 바이트가 반환되면 CloudTrail Data Event가 남습니다. Wazuh는 이 기록을 정기 수집한 뒤 Account, Region, Role, Bucket, Object와 반환 바이트 조건까지 모두 확인해 Rule 100111 경보를 만듭니다.
>
> 상세 원문은 로컬 연계 스크립트에서 검증하지만, Shuffle에는 계정이나 역할, Bucket, Object 원문을 보내지 않습니다. Rule 번호, 발생 시각, Wazuh Alert ID와 두 개의 SHA-256 값, 총 다섯 개 필드만 전달합니다.
>
> Shuffle 검증을 통과하면 고정된 `soc-harden-dvwa.yml` Workflow를 실행합니다. GitHub Actions는 `values.yaml`의 보안 수준 한 줄만 `low`에서 `impossible`로 변경하고, Argo CD가 새 설정을 DVWA에 적용합니다.
>
> 이 조치는 같은 취약점의 재사용을 어렵게 만들지만, 이미 반환된 S3 파일이나 발급된 자격증명을 회수하는 조치는 아닙니다. 실제 사고에서는 자격증명 폐기와 권한 축소 같은 후속 대응이 별도로 필요합니다.

## 슬라이드 8 — 두 경보의 근거 필드 비교

> 왼쪽은 Rule 100110의 근거입니다. DVWA의 보안 수준이 `low`였고, IMDS 자격증명 조회 단계에서 출력이 반환됐다는 필드를 확인할 수 있습니다.
>
> 오른쪽은 Rule 100111의 근거입니다. CloudTrail의 `GetObject` 기록과 공격에 사용된 AWS 역할을 확인할 수 있습니다.
>
> 이 화면은 두 Rule이 어떤 필드로 연결되는지 확인하기 위해 만든 통제된 로컬 재현 자료입니다. 따라서 Rule과 데이터 연결 구조를 검증하는 근거이지, 이 화면 자체를 새로운 Live AWS 공격 성공 증거로 사용하지는 않습니다.

## 슬라이드 9 — Shuffle 검증과 GitHub 실행 결과

> 아래 화면에서 Shuffle은 Rule 100111 입력을 검증한 뒤 GitHub Workflow 실행을 요청했고, 그 결과로 Workflow Run ID를 받았습니다.
>
> 여기서 `DISPATCHED`는 요청이 GitHub까지 전달됐다는 뜻이지, 보안 설정 변경이 끝났다는 뜻은 아닙니다.
>
> 실제 완료 여부는 별도로 확인해야 합니다. 위쪽 화면처럼 EKS Deployment와 Pod가 정상 상태인지 확인하고, `DEFAULT_SECURITY_LEVEL`이 실제로 `impossible`로 반영됐는지까지 확인해야 대응 완료라고 판단할 수 있습니다.

## 슬라이드 11 — 외부 S3 객체 접근 확인

> 공개 설정이 실제 노출로 이어졌는지도 확인했습니다.
>
> 화면에는 외부 IP에서 `curl`로 S3 Object를 요청한 시각과 대상 파일, 접근에 사용된 정보가 기록돼 있습니다. 오류 없이 `GetObject`가 수행된 것을 통해 복구 전에는 외부에서 객체를 읽을 수 있었음을 확인했습니다.

## 슬라이드 12 — S3 비공개 자동 복구

> Rule 100120 경보가 발생하면 Shuffle이 Rule과 Event ID를 검증한 뒤, 정해진 GitHub Actions 복구 Workflow를 실행합니다.
>
> GitHub Actions는 제한된 AWS 역할을 사용해 S3 Public Access Block을 활성화하고 공개 Bucket Policy를 제거합니다. 이후 외부에서 같은 객체를 다시 요청해 403이 반환되는지 확인하고, Workflow Run과 결과 파일을 증적으로 남깁니다.
>
> 화면의 `SUCCESS`와 `DISPATCHED`는 복구 요청이 GitHub로 전달됐다는 증거입니다. 이것만으로 복구 완료라고 판단하지 않고, 실제 Bucket Policy와 Public Access Block 상태, 외부 재요청의 403 결과까지 확인해야 합니다.

## 슬라이드 15 — 현재 한계와 확장 방향

> 다만 현재 결과를 실제 운영 수준의 완성된 관제라고 보기는 어렵습니다.
>
> 탐지 범위는 미리 정한 시나리오와 고정된 조건을 중심으로 검증했고, 자동 대응도 정해진 절차만 수행합니다. 또한 경보 정확도나 전체 탐지 시간, 실제 대응 완료 시간 같은 운영 지표를 충분히 반복 측정하지 못했습니다.
>
> 다음 단계에서는 공격 유형과 Rule을 늘리고, 자동 대응에 승인과 중단, Rollback 기능을 추가해야 합니다. 그리고 경보 정확도와 탐지·대응 시간을 계속 측정해, 빠르기만 한 자동화가 아니라 잘못된 대응을 통제할 수 있는 관제로 발전시켜야 합니다.

## 슬라이드 16 — 10분 Poll의 한계와 실제 개선

> 이 구조를 만들면서 가장 먼저 발견한 문제는 Polling 대기 시간이었습니다.
>
> 프로젝트 초기에는 다섯 종류의 로그를 Wazuh가 10분마다 확인했습니다. 여러 로그를 넓게 수집하고 원본을 보관하는 데는 좋았지만, 사고가 확인 직후에 발생하면 다음 수집까지 최대 10분을 기다려야 했습니다.
>
> 그래서 기존의 정기 수집 경로는 유지하면서, DVWA의 중요한 사건만 빠르게 보내는 별도 경로를 추가했습니다. 현재 다이어그램의 정기 경로는 5분 Polling으로 줄였고, DVWA 저지연 경로에서는 Poll 대기 자체를 제거했습니다.
>
> 무해한 검증 Event를 세 차례 측정한 결과, 사건 발생부터 Wazuh 경보까지 3.427초에서 6.439초가 걸렸고 누락은 없었습니다. 이 수치는 공격 전체나 Shuffle 대응 시간까지 측정한 값이 아니라, DVWA Event가 Wazuh 경보로 만들어질 때까지의 지연입니다.
>
> 여기서 기존 경로를 없애지 않은 이유는 원본 증거와 넓은 조사 범위가 계속 필요했기 때문입니다. 이 개선을 통해 속도뿐 아니라 탐지 정확도와 자동 대응 범위도 함께 봐야 한다는 새로운 질문이 생겼습니다.

## 슬라이드 17 — Telemetry 지연 설계 판단

> 이 질문을 해결하기 위해 Telemetry, 즉 보안 판단에 사용하는 로그와 Event가 만들어지고 전달되는 과정을 다시 나눠봤습니다.
>
> 먼저 무엇을 관찰하는지와 어떻게 전달하는지를 분리했습니다. 위쪽처럼 서비스와 자원, 실제 행동, 관찰할 신호를 정하고, 별도로 로그 생성 방식과 AWS 저장 위치, Wazuh 전달 경로, 마지막 Rule과 대응을 연결했습니다.
>
> 전체 지연도 다섯 구간으로 나눴습니다. 사건 뒤 로그가 만들어지는 구간, AWS 저장 위치까지 도착하는 구간, Wazuh로 전달되는 구간, Wazuh가 경보를 만드는 구간, 마지막으로 자동 대응 구간입니다.
>
> DVWA 저지연 경로가 직접 줄인 것은 세 번째인 Wazuh 전달 대기였습니다. 하지만 다른 AWS 로그는 로그 생성이나 AWS 내부 전달부터 늦을 수 있기 때문에, 똑같은 Push 구조를 붙인다고 전체 시간이 항상 줄어드는 것은 아닙니다.
>
> 따라서 탐지에 필요한 정보가 있는지, 얼마나 늦게 도착하는지, 누락 가능성과 보안 경계, 비용과 운영 부담이 어떤지를 함께 비교해야 합니다.
>
> 최종 결론은 하나의 가장 빠른 경로를 모든 로그에 적용하는 것이 아니라, 기존의 검증된 수집 경로는 보존하고 각 신호의 역할과 위험도에 맞는 전달 경로를 선택해야 한다는 것입니다.
