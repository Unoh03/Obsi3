# SOC 침해 대응 시연 대본

> [!IMPORTANT] 이 문서의 역할
> 발표자가 이미 공격 흐름과 대응 원리를 알고 있는 상태에서 실제 화면을 가리키며 그대로
> 읽는 촬영용 대본이다. 제품 이름만 나열하지 않고 **왜 이 구조와 Rule을 만들었는지,
> 실제 Event가 어떤 경로로 Alert와 자동 행동까지 이어지는지, 화면이 무엇을 증명하고
> 무엇은 증명하지 못하는지**를 함께 설명한다.

> [!WARNING] 촬영 잠금
> 100110 → 실제 Pod 격리와 100111 → low → impossible은 새 TAKE에서 자동 실행되는
> 화면을 다시 확인한 뒤 사용한다. 사람 승인 WAF 차단과 동일 Payload 재공격 구간은
> 해당 Runtime PASS 전까지 성공 장면으로 읽지 않는다.

## 1. 이 영상에서 증명할 것

이 시연의 핵심 주장은 다음과 같다.

> 교육용 DVWA의 Command Injection을 통해 EC2 IMDS Credential endpoint에 접근한 징후를
> Wazuh가 조기에 탐지하고, 사전 승인된 자동 대응으로 공격을 처리한 Pod만 격리한다.
> 이후 CloudTrail에서 보호된 가짜 S3 Object의 실제 바이트 반환을 별도 Rule로 확인하고,
> DVWA의 기본 보안 수준을 low에서 impossible로 자동 배포한다. 마지막으로 관제자가
> 여러 Source의 Timeline을 조사해 최초 진입점에 좁은 WAF 차단을 적용하고, 같은 공격이
> Edge에서 끝나는지를 정상 기능과 수집 상태 대조군까지 포함해 검증한다.

영상에서 보여줄 흐름은 다음과 같다.

~~~text
정상 상태와 수집 경로 확인
→ 통제된 공격 실행
→ Rule 100110 조기탐지
→ 공격 Pod 자동 격리·보존
→ Rule 100111 S3 접근 성공 확인
→ DVWA low → impossible 자동 배포
→ 사람의 Incident Timeline 조사
→ 사람 승인 WAF 차단
→ 동일 Payload 재공격과 정상·수집 대조
~~~

### 주장 범위

- 실제 Capital One 사고의 SSRF를 그대로 복제한 것이 아니다.
- 교육용 DVWA Command Injection을 최초 진입점으로 사용한 승인된 Lab 시나리오다.
- S3 대상은 validation/capital-one-demo.csv라는 고정된 가짜 교육 데이터다.
- Rule 100110은 Credential 원문 탈취나 S3 접근 성공을 확정하지 않는다.
- Rule 100111은 고정 Object의 바이트 반환 성공을 확인하지만 대규모 외부 반출 전체를
  증명하지 않는다.
- Pod 격리는 이미 발급된 AWS 임시 Credential을 폐기하지 않는다.
- low → impossible은 DVWA 애플리케이션 완화이며 IAM 권한 회수나 Pod 격리가 아니다.
- WAF 조치는 동일 진입점의 재발을 줄이는 가상 패치이며 Root Cause 코드 수정은 아니다.

## 2. 촬영 표기와 진실성 규칙

이 대본은 각 장면을 다음 다섯 부분으로 나눈다.

- **화면**: 녹화에 실제로 남겨야 하는 화면
- **조작**: 발표자가 클릭하거나 실행할 순서
- **그대로 읽을 대사**: 발표자가 읽는 문장
- **증거**: 해당 장면이 성립했다고 판단할 값
- **중단 조건**: 만족하지 않으면 성공본으로 촬영하지 않는 조건

편집은 다음 원칙을 지킨다.

1. 원본 녹화는 보존한다.
2. CloudTrail 수집 대기 구간만 빨리감기할 수 있다.
3. 배속 전후에 같은 Dashboard, 같은 시간 범위, 같은 Rule Count를 남긴다.
4. 자막에 배속과 실제 대기 시간을 함께 표시한다.
5. 수집기 재시작, Event 재주입, Workflow 수동 호출로 대기 시간을 속이지 않는다.
6. 서로 다른 TAKE의 Alert·Execution·Commit을 하나의 Incident처럼 이어 붙이지 않는다.
7. 실패한 실행을 성공 장면으로 편집하지 않는다.

배속 자막 형식:

~~~text
8배속 — 실제 CloudTrail 자연 수집 대기 00분 00초
동일 TAKE / 동일 시간창 / Event 재주입·Workflow 수동 호출 없음
~~~

## SC-00 — 환경과 수집 상태 설명

**예상 길이:** 3~4분
**화면:** DVWA → Argo CD → Wazuh Dashboard → Rule 100102 원문

### 화면

1. DVWA Security level is currently: low
2. Argo CD의 정상 DVWA Pod와 현재 Revision
3. Wazuh 상단의 100102, 100110, 100111 Count
4. capital_one_rules.xml의 Rule 100102

### 조작

1. DVWA의 low를 3초간 보여준다.
2. Argo CD에서 정상 Pod가 Service 뒤에서 실행 중임을 보여준다.
3. Wazuh Dashboard 상단 세 Count의 시작값을 보여준다.
4. Rule 파일에서 100102의 네 조건을 한 줄씩 가리킨다.

### 화면에 띄울 Rule 100102 원문

~~~xml
<field name="transport" type="pcre2">^push$</field>
<field name="source" type="pcre2">^dvwa$</field>
<field name="payload.event_type" type="pcre2">^wazuh\.push\.validation$</field>
<field name="payload.training_marker" type="pcre2">^SAFE_VALIDATION_EVENT$</field>
~~~

### 그대로 읽을 대사

> 지금부터 교육용 은행 애플리케이션을 대상으로 공격의 조기탐지, 자동 대응, 사람의
> 후속 조치까지 하나의 흐름으로 시연하겠습니다.

> 공격 대상 DVWA는 AWS EKS에서 실행되고 있지만, Wazuh는 비용과 실습 환경의 제약 때문에
> 제 개인 노트북의 Docker 컨테이너에서 실행됩니다. 따라서 AWS의 로그를 로컬 Wazuh로
> 보내기 위해 인터넷에 Wazuh 수신 포트를 공개하는 방식은 사용하지 않았습니다.

> 대신 DVWA의 안전한 감사 Event가 CloudWatch Logs에 기록되면, Subscription Filter가
> 해당 Log Group의 Event를 Lambda로 전달합니다. Lambda는 Credential, Cookie, 원문
> Command와 응답을 제거하고 승인한 필드만 남긴 뒤 서울 리전의 SQS에 저장합니다.
> 로컬 Bridge는 이 Queue를 최대 20초 Long Poll로 읽어 Host의 JSONL 파일에 먼저 보존하고,
> 그 파일은 Docker의 Wazuh Manager에 읽기 전용으로 Mount됩니다. Wazuh는 이 JSON을
> 읽고 Rule을 평가합니다.

> 여기서 Subscription과 Lambda는 command.execution이나 GetObject 같은 공격 조건을
> 판정하지 않습니다. 승인된 DVWA Log Group의 Event를 운반하고 안전한 필드만 정규화하며,
> 위험 여부는 Wazuh에 도착한 뒤 Rule이 판단합니다. 즉 전달 조건과 탐지 조건을 분리했습니다.

> 이 구조에서 SQS는 탐지 제품이 아니라 Buffer입니다. 노트북이나 Wazuh가 잠시 꺼져도
> Event를 보관하고, Local Bridge가 다시 켜졌을 때 이어서 처리할 수 있게 합니다.
> Bridge는 AWS의 고정 Account와 Region, Reader Role, Event Schema를 검사하고, Host
> 파일에 기록한 메시지만 Queue에서 삭제합니다.

> 정확히 말하면 이 경로는 AWS가 Queue까지 Event를 밀어 넣는 Event-driven 전달과,
> 로컬 Bridge가 Queue를 Long Poll하는 소비 방식을 결합한 구조입니다. AWS에서 제
> 노트북으로 직접 연결하는 완전한 Inbound Push는 아닙니다.

> 이 Bridge를 구현할 때 AI를 코딩 보조 도구로 사용했습니다. 다만 운영 중에 AI가
> 로그를 판단하거나 전달하는 구조는 아닙니다. 실제 Runtime의 판단 주체는 고정된
> Allowlist, Schema 검증과 Wazuh Rule입니다. Bridge의 입력·출력과 실패 경계는 Source와
> 정적 Test로 고정했고, 정상 전달은 실제 Event로 확인했습니다.

> 먼저 상단의 Push Health는 공격 경고가 아닙니다. Rule 100102는 이 저지연 전달 경로가
> 현재 살아 있는지를 확인하기 위해 별도로 만든 무해한 상태 확인 Rule입니다.

> 상태 확인 스크립트는 실제 공격이나 DVWA 사용자의 행동을 만들지 않고, DVWA용
> CloudWatch Log Group에 wazuh.push.validation이라는 합성 Event를 기록합니다.
> 이 Event가 실제와 같은 CloudWatch Logs, Lambda, SQS, Local Bridge, Wazuh 입력을
> 통과하면 Rule 100102가 한 번 발생합니다.

> 첫 번째 조건인 transport가 push라는 것은 Wazuh가 기존 10분 Poll 입력이 아니라
> 방금 설명한 저지연 전달 Envelope를 읽었다는 뜻입니다. 두 번째 source가 dvwa라는
> 것은 Forwarder가 고정한 DVWA 전용 Source 채널이라는 뜻입니다. 이 검증 Event 자체를
> DVWA 애플리케이션이 생성했다는 뜻은 아닙니다.

> 세 번째 payload.event_type은 이 Event가 공격 로그가 아니라
> wazuh.push.validation이라는 상태 확인 Event임을 제한합니다. 마지막
> payload.training_marker는 SAFE_VALIDATION_EVENT라는 고정 문자열과 정확히
> 일치해야 합니다. 정규식의 앞뒤 ^와 $는 문자열 일부가 아니라 전체 값이 정확히
> 같아야 한다는 의미입니다.

> 따라서 Rule 100102의 Count 증가는 CloudWatch Log Group 이후부터 Wazuh Rule 평가까지의
> 전달 구간이 동작했다는 증거입니다. 반대로 이것만으로 모든 AWS Source가 정상 수집되거나,
> 실제 공격 탐지와 Shuffle 자동 대응까지 성공했다고 주장하지는 않습니다.

> 이 경로를 처음 검증했을 때는 무해 Event 세 건의 Event 발생부터 Wazuh Alert까지
> 6.439초, 3.427초, 3.761초가 걸렸고 누락은 0건이었습니다. 이 값은 과거 세 건의
> 측정 결과이며, 지금 화면의 최신 Health Event를 대신하는 현재 상태 증거로 사용하지는
> 않습니다.

> 다음 두 Count가 실제 공격 탐지입니다. Rule 100110은 DVWA가 IMDS Credential endpoint를
> 대상으로 실행한 명령에서 출력을 반환한 고위험 단계를 조기에 탐지합니다. Rule 100111은
> 뒤이어 고정된 가짜 S3 Object에서 실제 바이트가 반환된 CloudTrail Event를 확인합니다.
> 두 Rule은 각각 독립된 근거를 판정하고, 같은 공격 흐름이라는 연결은 뒤에서 Timeline으로
> 조사하겠습니다.

### 증거

- DVWA low
- 정상 DVWA Pod Ready
- Rule 100102 최신 Event와 Count
- Rule 100110/100111 시작 Count
- Rule 100102 네 필드가 화면에 보임

### 중단 조건

- DVWA가 low가 아님
- 이전 격리 Pod나 활성 Quarantine Request가 남아 있음
- 최근 Rule 100102 Event가 없음
- Wazuh·Bridge·필수 Dashboard 중 하나가 준비되지 않음

## SC-01 — 통제된 공격 실행

**예상 길이:** 1~2분
**화면:** PowerShell 7 → Wazuh의 최초 WAF ALLOW

### 조작

다음 명령을 미리 입력한 뒤 대사를 읽고 실행한다.

~~~powershell
Set-Location D:\terraform\aws_terraform_build_code

$attack = @{
  AwsProfile = 'terra-user'
  SkipAlarmWait = $true
  ConfirmRun = 'RUN CAPITAL ONE BASELINE'
}
.\observability\scenarios\Invoke-CapitalOneBaseline.ps1 @attack
~~~

### 그대로 읽을 대사

> 공격 Runner는 승인된 Lab 범위와 고정된 가짜 Object만 대상으로 한 번 실행합니다.
> 실제 Capital One 사고를 그대로 재현하는 것이 아니라, DVWA Command Injection을 통해
> 서버가 EC2 Instance Metadata Service에 접근할 수 있는 잘못된 구조를 교육용으로
> 재현합니다.

> 첫 번째 POST는 IMDS의 Role 이름 조회 endpoint를 호출합니다. 두 번째 POST는 확인된
> Role 아래의 Credential endpoint를 호출합니다. 이후 Runner는 이미 메모리에 받은 짧은
> 수명의 임시 Credential로 validation/capital-one-demo.csv라는 가짜 Object 하나만
> 읽습니다.

> Credential 값과 원문 Command, Cookie와 응답 본문은 출력하거나 Evidence에 저장하지
> 않습니다. 화면에는 단계, 성공 여부, TAKE ID와 Hash만 남깁니다.

**이 문장을 읽은 뒤 실행한다.**

> 지금 공격을 시작했습니다. 최초 요청은 AWS Managed WAF Rule에서
> EC2MetaDataSSRF_Body Label로 식별되지만, 현재는 관찰을 위한 COUNT 모드이므로 최종
> Action은 ALLOW입니다. 즉 WAF가 공격성 패턴을 보았지만 아직 차단하지 않아 요청이
> DVWA까지 도달한 상태입니다.

### 증거

- 새 TAKE_ID
- Runner가 IMDS role discovery와 credential acquisition 성공을 값 노출 없이 표시
- 가짜 S3 데이터의 Marker·행 수·SHA-256 확인
- WAF POST /vulnerabilities/exec/
- EC2MetaDataSSRF_Body
- 최종 Action ALLOW

### 중단 조건

- 승인된 Host·Path·Object 범위를 벗어남
- Credential·Cookie·CSRF Token·Command 원문이 화면에 노출됨
- 최초 WAF가 이미 BLOCK해 Baseline 공격이 진행되지 않음
- Runner가 오류로 끝남

## SC-02 — Rule 100110 조기탐지 원리

**예상 길이:** 3~4분
**화면:** Wazuh Panel 20, 21, 01 → Rule 100110 원문

### 조작

1. [CAPITAL-ONE] 20 Push 공격 단계의 두 행을 시간순으로 보여준다.
2. imds_role_discovery 행에는 Rule 100110이 없음을 보여준다.
3. imds_credential_fetch 행과 Rule 100110을 연결한다.
4. Rule 파일에서 100110의 조건을 네 묶음으로 가리킨다.

### 화면에 띄울 Rule 100110 원문

~~~xml
<field name="transport" type="pcre2">^push$</field>
<field name="source" type="pcre2">^dvwa$</field>
<field name="payload.event_type" type="pcre2">^command\.execution$</field>
<field name="payload.result" type="pcre2">^succeeded$</field>
<field name="payload.route" type="pcre2">^/vulnerabilities/exec/$</field>
<field name="payload.context.action" type="pcre2">^shell_command$</field>
<field name="payload.context.resource" type="pcre2">^ec2_imds$</field>
<field name="payload.context.security_level" type="pcre2">^low$</field>
<field name="payload.context.stage" type="pcre2">^imds_credential_fetch$</field>
<field name="payload.context.status" type="pcre2">^output_returned$</field>
~~~

### 그대로 읽을 대사

> DVWA는 공격 명령과 Credential 원문 대신, 서버 측 Audit 함수가 분류한 안전한
> 단계 정보를 남깁니다. 첫 번째 Event의 imds_role_discovery는 Role 이름을 조회한
> 단계이고, 두 번째 imds_credential_fetch는 그 Role의 Credential endpoint에 접근한
> 단계입니다. 이 Stage는 공격자가 보낸 임의 Header를 믿는 값이 아니라 서버가 실제
> Target을 검사해 만든 값입니다.

> Rule 100110을 만든 이유는 일반적인 IMDS 조회와 실제 Credential endpoint 접근을
> 구분하기 위해서입니다. Role 이름 조회만으로 격리를 시작하면 탐지 의미가 너무 넓어지고,
> 반대로 S3 로그가 도착할 때까지 기다리면 이미 다음 공격 단계가 끝날 수 있습니다.
> 그래서 Credential endpoint에서 출력이 반환된 순간을 조기대응 기준으로 정했습니다.

> Rule의 첫 묶음인 transport=push, source=dvwa는 이 Event가 DVWA 전용 저지연
> 전달 경로에서 왔음을 제한합니다.

> 두 번째 묶음인 payload.event_type=command.execution,
> payload.route=/vulnerabilities/exec/, context.action=shell_command는 DVWA의
> Command Injection 기능에서 Shell Command가 실행된 Event만 선택합니다.

> 세 번째 묶음인 context.resource=ec2_imds, context.security_level=low,
> context.stage=imds_credential_fetch는 대상이 EC2 Metadata Service이고,
> 취약한 low 상태에서 Role 이름 조회가 아닌 Credential endpoint 조회 단계였음을 뜻합니다.

> 마지막 payload.result=succeeded와 context.status=output_returned는 요청 시도만
> 있었던 것이 아니라 명령 실행이 성공했고 응답 출력까지 애플리케이션에 반환됐다는
> 조건입니다. 이 모든 값은 앞뒤가 고정된 정규식으로 정확히 일치해야 합니다.

> 따라서 첫 번째 imds_role_discovery Event에는 Rule 100110이 발생하지 않고, 두 번째
> imds_credential_fetch Event에만 Level 12 Alert가 발생합니다.

> 이 Alert는 Credential 문자열을 Wazuh에 저장했다는 뜻도, 공격자가 그 Credential을
> 외부로 반출했다는 뜻도 아닙니다. 다만 보호된 Cloud Resource 접근으로 이어질 수 있는
> 충분히 구체적인 고위험 단계이므로, 영향 범위를 고정한 자동 Workload 격리를 시작합니다.

### 화면에 3초 이상 남길 값

- rule.id=100110
- rule.level=12
- data.event_id
- data.payload.take_id
- stage=imds_credential_fetch
- status=output_returned
- result=succeeded
- Rule Description

### 증거

- Role 조회 Event의 100110은 0
- Credential endpoint Event와 100110은 일대일
- 100110 Count가 시작값보다 정확히 1 증가

### 중단 조건

- Role 조회 Event에도 100110이 발생함
- 같은 event_id로 Alert가 중복됨
- Rule 조건과 Dashboard 행이 일치하지 않음

## SC-03 — Alert에서 실제 Pod 격리까지

**예상 길이:** 4~5분
**화면:** Wazuh → Shuffle Execution → GitHub Actions → Argo CD → DVWA

### 조작

1. Rule 100110 Alert의 식별자와 시각을 보여준다.
2. 같은 Alert에 대응한 Shuffle Execution의 성공 상태를 보여준다.
3. GitHub Actions의 SOC Quarantine DVWA Pod Run을 보여준다.
4. Commit이 deploy/dvwa/values.yaml 한 파일만 변경했음을 보여준다.
5. Argo CD를 Refresh하고 다음 Resource를 차례로 연다.
   - 완료된 Quarantine Job
   - dvwa-quarantined-pod-deny-all NetworkPolicy
   - Orphaned Resources의 기존 공격 Pod
   - ReplicaSet 아래 새 정상 Pod
6. 기존 Pod의 soc.unoh.click/state=quarantined Label을 보여준다.
7. 격리 Pod의 Egress와 정상 Pod에서 격리 Pod로 향하는 Ingress를 실제로 시험한다.
8. 브라우저에서 unoh.click 정상 응답을 확인한다.

### 그대로 읽을 대사

> 이제 Alert가 실제 행동으로 이어지는 경로를 보겠습니다. Wazuh는 Level 12 이상의
> Rule 100110과 100111만 고정 Custom Integration에 전달하도록 설정돼 있습니다.
> Integrator는 전체 Alert를 그대로 외부로 보내지 않고, 먼저 로컬에서 Rule, Account,
> Region, Event Stage, Path, 발생 시각, Pod 이름과 UID를 다시 검증합니다.

> Rule 100110의 경우 Shuffle로 보내는 값은 Wazuh Alert ID와 Event 시각, TAKE ID,
> Kubernetes Downward API에서 생성된 Pod 이름과 UID, 그리고 원본 대신 사용하는
> SHA-256 Hash입니다. Credential, Command 원문과 응답 본문은 보내지 않습니다.

> 검증된 최소 Payload는 고정 Header로 인증된 HTTPS Webhook을 통해 Shuffle Cloud에
> 전달됩니다. Shuffle의 전용 App은 Schema, 고정 Account와 Region, Rule ID, Stage,
> Path, Hash와 Event freshness를 다시 검사합니다. 조건이 다르거나 오래된 Event,
> 예상하지 않은 필드가 있으면 GitHub 호출 전에 실패하도록 구성했습니다.

> 검증을 통과하면 Shuffle에 영구 저장한 Unoh03/Uns-DVWA 전용 fine-grained PAT로
> 고정 Repository의 soc-contain-dvwa.yml, main Branch만 Dispatch합니다. Shuffle이나
> Wazuh에는 Kubernetes 자격증명을 주지 않았습니다.

> GitHub Workflow는 임의 Command를 실행하는 것이 아니라 deploy/dvwa/values.yaml
> 한 파일에 Replica 수와 고정 Quarantine Request를 기록합니다. 이 변경이 Commit되면
> Argo CD가 선언된 Revision을 EKS에 Sync합니다.

> Argo는 정상 Replica를 먼저 두 개로 늘린 뒤, 제한된 Kubernetes Job을 실행합니다.
> Job은 Alert에서 온 Pod 이름만 믿지 않고 Pod UID, DVWA Label, ReplicaSet UID와
> Deployment 소유 관계를 다시 확인합니다. 모두 일치할 때만 JSON Patch의 test
> 연산과 함께 대상 Pod의 소유 관계를 제거하고 Service Selector에서 빠지는 Label로
> 바꿉니다.

> 여기 보이는 Orphaned Pod는 새로 만든 격리용 Pod가 아닙니다. 공격을 처리했던 원래
> Pod를 살아 있는 상태로 보존한 것입니다. ReplicaSet의 관리 대상과 Service Endpoint에서는
> 빠졌지만, 이름과 UID, Image, 생성 시각이 남아 있어 사건 증거로 조사할 수 있습니다.

> dvwa-quarantined-pod-deny-all NetworkPolicy는 soc.unoh.click/state=quarantined
> Label이 붙은 Pod의 Ingress와 Egress를 모두 차단합니다. ReplicaSet 아래의 새 정상
> Pod는 Service를 계속 제공하므로 전체 사이트를 중단하는 격리와 다릅니다.

> Argo에서 Orphaned Resource 경고가 보이는 것은 이 시연에서는 의도된 증거 보존
> 결과입니다. 다만 경고나 NetworkPolicy Resource가 존재한다는 사실만으로 격리 성공을
> 판단하지는 않습니다. 지금 실제 네트워크 요청이 timeout 되는지와 정상 서비스가
> 계속 응답하는지를 함께 확인하겠습니다.

### 실제 격리 확인

격리 Pod Terminal에서 Egress를 확인한다.

~~~sh
curl --connect-timeout 3 --max-time 5 \
  http://dvwa.dvwa.svc.cluster.local/login.php
~~~

예상 결과는 5초 이내 timeout이다. Argo Web Terminal 자체가 열리는 것은 격리 실패가
아니다. Terminal은 Kubernetes control-plane의 관리 경로이고, 판정 대상은 Pod의 Data
Plane 통신이다.

가능하면 새 정상 Pod Terminal에서 격리 Pod IP의 /login.php로 같은 유한 timeout 요청을
보내 Ingress 차단도 함께 보여준다. 공개 화면에는 내부 IP 전체를 마스킹한다.

### 증거

- Wazuh Alert ↔ Shuffle Execution ↔ GitHub Run 연결
- GitHub 변경 파일이 deploy/dvwa/values.yaml 하나
- 대상 Pod name·UID가 Source Event와 일치
- 기존 Pod: Running + Orphaned + quarantined
- 새 정상 Pod: ReplicaSet 아래 Ready
- 완료된 Quarantine Job
- deny-all NetworkPolicy
- 격리 Pod Egress timeout
- 정상 Pod에서 격리 Pod로 향하는 Ingress timeout
- unoh.click 정상 응답

### 중단 조건

- 사람이 Workflow를 수동 실행해야 했음
- Source Event와 다른 Pod가 대상이 됨
- 기존 공격 Pod가 삭제돼 증거가 보존되지 않음
- 격리 Pod의 Ingress 또는 Egress가 성공함
- 새 정상 Pod가 Ready가 아니거나 서비스가 중단됨
- 예상하지 않은 Repository·Branch·파일이 변경됨

## SC-04 — CloudTrail 수집 대기와 빨리감기

**예상 원본 길이:** 약 10분 이상 가능
**최종 영상:** 1~2분
**화면:** Wazuh Dashboard

### 그대로 읽을 대사

> 조기탐지와 Pod 격리는 이미 끝났지만, S3 접근 성공의 근거는 다른 Telemetry에서
> 확인합니다. 실제 S3 API 활동은 CloudTrail Data Event로 기록되고, 현재 Wazuh의 AWS
> 수집 모듈은 CloudTrail CloudWatch Log Group을 10분 주기로 읽습니다.

> 즉 Rule 100110의 DVWA Event는 CloudWatch Logs 구독과 SQS를 이용한 저지연 경로이고,
> Rule 100111의 CloudTrail Event는 현재 검증된 10분 예약 수집 경로입니다. 하나의
> Incident 안에서도 Source의 생성 방식과 전달 경로에 따라 도착 시각이 다를 수 있습니다.
> 이를 서로 다른 관제 시스템으로 보지 않고, 빠른 초기 신호와 뒤늦게 도착하는 확정 근거가
> 같은 Timeline을 보강하는 구조로 사용합니다.

> 이 대기 시간은 Wazuh의 Rule 처리 시간이 아니라 CloudTrail Event가 사용 가능해지는
> 시간과 10분 Poll 주기의 영향을 함께 받습니다. 수집 주기를 강제로 당기거나 Event를
> 다시 주입하지 않고, 같은 TAKE와 시간 범위를 유지한 채 Rule 100111이 도착할 때까지
> 기다리겠습니다. 이 구간만 실제 시간을 자막에 남기고 빨리감기하겠습니다.

### 빨리감기 시작 화면

- Dashboard Last 30 minutes
- Rule 100110 Count 증가 상태
- Rule 100111 시작 Count
- Dashboard 또는 화면 시각

### 빨리감기 중 허용 조작

- 20~30초마다 Dashboard Refresh
- 같은 시간 범위와 Filter 유지

다음은 하지 않는다.

- Wazuh·Bridge 재시작
- CloudTrail Event Replay
- 합성 Event 주입
- Shuffle 또는 GitHub Workflow 수동 실행

### 배속 종료 신호

Rule 100111 Count가 시작값보다 1 증가하면 2초 이상 정상 속도로 화면을 유지한다.

## SC-05 — Rule 100111과 자동 low → impossible

**예상 길이:** 4~5분
**화면:** Wazuh Panel 22, 02 → Rule 100111 원문 → Shuffle → GitHub → Argo → DVWA

### 조작

1. [CAPITAL-ONE] 22 Rule 100111 근거에서 CloudTrail Event를 연다.
2. Rule 파일의 100111 조건을 네 묶음으로 가리킨다.
3. 같은 Event의 Wazuh Alert와 Shuffle Execution을 보여준다.
4. GitHub Actions SOC Harden DVWA Security Level과 Commit Diff를 보여준다.
5. Argo CD exact Revision과 새 Pod를 보여준다.
6. 새 DVWA Session에서 Security level is currently: impossible을 보여준다.

### 화면에 띄울 Rule 100111 조건

아래는 공개 촬영용 표기다. 실제 Rule 파일에서는 Account, Role, Bucket 값이 정확한
Allowlist로 고정돼 있지만 공개 화면에서는 해당 값만 마스킹한다.

~~~text
eventSource = s3.amazonaws.com
eventName = GetObject
eventType = AwsApiCall
eventCategory = Data
managementEvent = false
readOnly = true
recipientAccountId = <고정 Lab Account exact>
awsRegion = ap-northeast-2
userIdentity.type = AssumedRole
sessionIssuer.userName = <고정 Primary Node Role exact>
bucketName = aws-topology-primary-<26 hex>
key = validation/capital-one-demo.csv
httpStatusCode = 200
bytesTransferredOut = positive integer
eventID = UUID
~~~

### 그대로 읽을 대사

> Rule 100111이 도착했습니다. 이 Rule을 만든 이유는 일반적인 S3 조회와 공격 시나리오의
> 실제 데이터 접근 성공을 구분하기 위해서입니다. 단순히 GetObject라는 이름 하나만
> 보고 침해로 판정하지 않고, 승인한 Lab의 Principal, 대상 Object와 성공 조건을 모두
> 만족해야 합니다.

> 첫 번째 묶음은 Event의 성격입니다. eventSource=s3.amazonaws.com,
> eventName=GetObject, eventType=AwsApiCall, eventCategory=Data는 S3 Object
> 읽기 API의 Data Event라는 뜻입니다. managementEvent=false와 readOnly=true는
> 관리 설정 변경이 아니라 실제 데이터 읽기 활동으로 범위를 좁힙니다.

> 두 번째 묶음은 실행 주체와 환경입니다. 고정된 Lab Account와 서울 Region,
> AssumedRole 유형, 그리고 공격 시나리오에서 예상한 Primary Node Role이 모두
> 일치해야 합니다. 공개 영상에서는 실제 Account와 전체 Resource 이름은 마스킹합니다.

> 세 번째 묶음은 대상입니다. Bucket은 이 Lab이 생성하는 고정 이름 패턴과 일치해야 하고,
> Key는 validation/capital-one-demo.csv 하나로 제한합니다. 다른 Bucket이나 Prefix,
> 정상 대조용 Object에는 이 Rule이 발생하지 않아야 합니다.

> 마지막 묶음은 성공 증거입니다. httpStatusCode=200이어야 하고,
> bytesTransferredOut은 0보다 커야 합니다. 즉 요청을 시도했거나 권한 오류가 난 것이
> 아니라 Object의 실제 바이트가 반환된 경우입니다. eventID는 UUID 형식이어야 하며
> 원본 Event 식별과 중복 억제의 기준으로 사용합니다.

> Wazuh Rule은 선택 필드인 errorCode의 부재 자체를 조건으로 삼지 않습니다. 대신
> HTTP 200과 양수 바이트를 직접 요구하고, Shuffle로 보내기 전 로컬 Integrator가
> errorCode가 비어 있는지도 한 번 더 검사합니다.

> 이 모든 조건을 만족하면 Level 14의 Rule 100111이 발생합니다. 이 Rule이 직접
> 증명하는 것은 고정된 가짜 Object의 바이트 반환 성공입니다. S3 전체가 유출됐다는
> 뜻은 아니며, Rule 100110이 원인이었다는 사실도 Rule 자체가 자동 계산한 것은 아닙니다.

> 두 Alert가 같은 공격 흐름이라는 판단은 Dashboard에서 실제 Event 시각, DVWA의
> TAKE와 Event ID, CloudTrail eventID, 같은 Role과 Object, WAF 요청 시각을 함께 본
> 관제자의 조사 결과입니다. 모든 Source를 관통하는 하나의 Trace ID가 있다고
> 과장하지 않습니다.

> 이제 두 번째 자동 대응을 보겠습니다. Rule 100111의 경우 Wazuh는 전체 CloudTrail
> 원문을 Shuffle에 보내지 않습니다. 로컬에서 전체 조건을 확인한 뒤 Rule ID, Event 시각,
> Wazuh Alert ID, CloudTrail eventID의 SHA-256, 원문 SHA-256만 전송합니다. Account,
> IAM Role, Bucket, Object 이름과 원문 Log는 Shuffle Payload에 포함하지 않습니다.

> Shuffle은 이 최소 Payload의 Schema, Rule ID, Hash와 최대 지연 범위를 검사한 뒤
> 고정된 soc-harden-dvwa.yml Workflow만 호출합니다. GitHub Workflow는
> deploy/dvwa/values.yaml의 defaultSecurityLevel 한 값을 low에서 impossible로
> 변경하고, 그 외 Byte가 바뀌면 실패합니다.

> Commit이 main에 Push되면 Argo CD가 정확한 Revision을 EKS에 배포합니다. 여기서
> 확인할 증거는 Workflow 성공 표시 하나가 아니라 한 줄 Diff, Commit SHA, Argo exact
> Revision, 새 Pod와 새 Session의 impossible Read-back입니다.

> 이 조치는 DVWA의 취약 기능을 더 강한 설정으로 완화한 것입니다. 이미 발급된 AWS
> Credential을 폐기하거나, 앞에서 보존한 공격 Pod의 NetworkPolicy 격리를 대신하는
> 조치는 아닙니다.

### Pod Rollout으로 로그인 화면이 나온 경우

> 보안 수준 변경으로 새 DVWA Pod가 배포되면서 기존 애플리케이션 Session이 종료됐습니다.
> 이는 자동 대응 실패가 아니라 새 Runtime으로 교체된 결과입니다. 준비된 시연 계정으로
> 한 번 다시 로그인한 뒤, 새 Session의 보안 수준을 확인하겠습니다.

Password는 녹화에서 마스킹하고, 로그인 뒤 security.php로 이동한다.

> 현재 새 DVWA Session의 보안 수준은 impossible입니다. 동일한 CloudTrail Event가
> 다시 수집되더라도 추가 Commit과 Rollout이 생기지 않는지도 별도로 확인합니다.

### 증거

- CloudTrail 원본 eventID ↔ Rule 100111 일대일
- rule.level=14
- 정확한 Principal·Object·HTTP 200·양수 바이트
- Wazuh Alert ↔ Shuffle Execution ↔ GitHub Run
- 변경 파일 하나, low → impossible 한 줄 Diff
- Commit SHA ↔ Argo exact Revision
- 새 Session의 impossible
- 동일 Event 재처리의 추가 Commit·Rollout 0

### 중단 조건

- 다른 Role·Object·실패 Event에도 100111이 발생함
- 원본 CloudTrail eventID와 Alert를 연결하지 못함
- 사람이 Workflow를 수동 실행해야 했음
- 예상하지 않은 Repository·Branch·파일이 변경됨
- Argo가 해당 Commit을 배포하지 않음
- 새 Session이 여전히 low

## SC-06 — Incident Timeline을 사람이 해석

**예상 길이:** 2~3분
**화면:** Capital One Incident Timeline v2

### 조작

다음 순서대로 같은 시간창의 행을 가리킨다.

1. WAF COUNT/ALLOW와 EC2MetaDataSSRF_Body
2. DVWA imds_role_discovery
3. DVWA imds_credential_fetch
4. Rule 100110
5. Shuffle·GitHub·Argo의 Pod 격리 결과
6. CloudTrail GetObject
7. Rule 100111
8. GitHub·Argo의 low → impossible

### 그대로 읽을 대사

> 전체 Incident를 시간순으로 정리하겠습니다. 최초 두 POST 요청은 WAF에서 IMDS 관련
> 패턴으로 식별됐지만 COUNT 모드였기 때문에 DVWA까지 전달됐습니다.

> DVWA의 서버 측 Audit는 Role 이름 조회와 Credential endpoint 조회를 서로 다른
> Event로 분류했습니다. 첫 단계는 관찰만 했고, 두 번째 단계에서 Rule 100110이 발생해
> 정확한 Source Pod를 자동 격리했습니다.

> 이미 메모리에 발급된 짧은 수명의 Credential로 수행된 가짜 S3 Object 읽기는
> CloudTrail Data Event에 기록됐습니다. 현재 10분 예약 수집 경로로 Wazuh에 도착한 뒤
> Rule 100111이 실제 바이트 반환 성공을 확인했고, DVWA의 기본 보안 수준은
> impossible로 자동 배포됐습니다.

> 이 Dashboard가 공격 원인을 AI로 자동 추론한 것은 아닙니다. WAF, DVWA, CloudTrail은
> 서로 다른 Source이고 공통 ID가 완전히 같지 않습니다. Dashboard는 고정 시간창과
> Rule ID, DVWA Event ID와 TAKE, CloudTrail eventID, Principal과 대상 Object를 한
> 화면에 배치해 사람이 사건을 조사할 수 있게 만든 도구입니다.

> 여기까지 자동화는 미리 승인한 두 반복 대응만 수행했습니다. 첫 번째는 공격을 처리한
> Workload의 네트워크 격리와 증거 보존이고, 두 번째는 DVWA 보안 수준 변경입니다.
> 이미 발급된 Credential의 회수와 Root Cause 코드 수정은 이 화면만으로 끝났다고
> 주장하지 않습니다.

> 관제자가 추가로 확인한 사실은 최초 진입점의 WAF가 동일한 공격 패턴을 이미 Label로
> 식별했다는 점입니다. 따라서 다음 단계에서는 전체 Managed Rule Set을 무작정 차단하는
> 대신, 실제 공격에서 확인한 Label, POST Method와 정확한 Path만 결합한 좁은 WAF
> 가상 패치를 사람이 승인합니다.

### 증거

- 하나의 Incident 시간창
- WAF → DVWA → 100110 → 격리 → CloudTrail → 100111 → hardening 순서
- 각 Source의 실제 Event 시각과 Wazuh Alert 시각 구분
- 자동 조치와 사람 조치 구분

### 중단 조건

- 다른 TAKE나 날짜의 Event가 섞임
- Dashboard가 자동 인과분석을 했다고 설명해야 함
- Push 표 하나만으로 WAF·CloudTrail·대응 전체를 설명함

## SC-07 — 사람 승인 WAF 조치

> [!DANGER] 현재 촬영 잠금
> 고정 IaC Diff, Apply 명령, Rule ID, Rollback과 Runtime Read-back이 PASS하기 전에는
> 아래 대사를 성공 장면으로 사용하지 않는다.

**예상 길이:** 2~3분
**화면:** Incident Timeline → WAF IaC Diff → 승인 → Apply → Read-back

### 조작 계약

1. 사전 준비된 WAF Diff를 연다.
2. 조건이 다음 세 항목의 AND인지 확인한다.
   - Managed Label EC2MetaDataSSRF_Body
   - HTTP Method POST
   - URI /vulnerabilities/exec/
3. 전체 AWSManagedRulesCommonRuleSet이 일괄 BLOCK으로 바뀌지 않음을 보여준다.
4. 사람 승인을 기록한 뒤 고정 Apply 경로를 실행한다.
5. WAF Rule ID, Priority, Action과 적용 시각을 Read-back한다.

### Runtime PASS 뒤 그대로 읽을 대사

> 자동 격리와 애플리케이션 완화 뒤, 같은 진입점의 재발을 막기 위한 추가 조치를
> 사람이 승인하겠습니다.

> 전체 Managed Rule을 BLOCK으로 바꾸면 정상 요청까지 영향을 받을 수 있습니다.
> 그래서 실제 Incident에서 확인한 EC2MetaDataSSRF_Body Label, POST Method와
> /vulnerabilities/exec/ Path를 모두 만족하는 요청만 BLOCK하도록 범위를 좁혔습니다.

> 이 변경은 Console에서 임시로 만든 Rule이 아니라 재현과 Rollback이 가능한 IaC
> 변경입니다. 지금 적용 결과의 Rule ID와 Action을 다시 읽어 실제 상태를 확인하겠습니다.

### 증거

- 승인된 한정 Diff
- Apply 성공
- WAF Rule ID·Priority·Action Read-back
- Rollback 경로

### 중단 조건

- Console에서 출처 불명의 임시 Rule을 직접 만듦
- 전체 Managed Rule Set을 일괄 BLOCK함
- 정상 Numeric IP Ping까지 차단하는 넓은 조건임
- Apply 결과를 Read-back하지 못함

## SC-08 — 동일 Payload 재공격과 대조군

> [!DANGER] 현재 촬영 잠금
> 전용 Reattack Runner의 실제 인자, WAF terminating Rule, downstream 조회 Adapter와
> Health 대조가 Runtime PASS하기 전에는 아래 성공 대사를 사용하지 않는다.

**예상 길이:** 3~4분
**화면:** Reattack Runner → WAF BLOCK → Wazuh/Source 0 → 정상 DVWA → Rule 100102

### 조작 계약

1. 새 REATTACK_ID와 시작 UTC를 기록한다.
2. 최초 공격과 동일한 IMDS role-discovery Payload임을 안전한 Hash로 확인한다.
3. 전용 Reattack Runner를 한 번 실행한다.
4. HTTP 403, WAF action=BLOCK, 사람 승인 terminating Rule을 함께 확인한다.
5. 고정 관찰 시간창에서 다음 신규 건수가 0인지 확인한다.
   - ALB 공격 요청
   - DVWA command.execution
   - 저지연 전달 경로의 공격 Event
   - Rule 100110
   - 보호 Object GetObject
   - Rule 100111
   - 추가 Shuffle Execution·GitHub Commit·Argo Rollout
6. 정상 로그인·홈·안전한 Numeric IP Ping을 확인한다.
7. 새 무해 Health Event를 보내 Rule 100102가 증가하는지 확인한다.

### Runtime PASS 뒤 그대로 읽을 대사

> 사람 승인 WAF Rule이 적용된 뒤, 최초 공격과 같은 Payload를 다시 전송했습니다.
> 이번에는 응답이 403이고, WAF Event의 Action은 BLOCK이며, terminating Rule도 방금
> 적용한 고정 Rule과 일치합니다.

> 403만으로 WAF 차단을 확정하지는 않습니다. 동일 요청이 ALB와 DVWA까지 내려가지
> 않았고, 신규 command.execution과 Rule 100110, 보호 Object의 GetObject와
> Rule 100111이 모두 0인지 같은 관찰 시간창에서 확인합니다.

> 신규 Alert가 없다는 사실만으로도 성공을 선언하지 않습니다. 정상 로그인과 홈,
> 공격과 무관한 안전한 Numeric IP Ping은 계속 성공합니다. 또한 별도의 무해한 상태
> 확인 Event가 같은 CloudWatch Logs, Lambda, SQS, Local Bridge를 거쳐 Rule 100102를
> 새로 발생시켰습니다.

> 따라서 신규 공격 Alert 0은 수집 파이프라인이 멈춘 결과가 아니라, 공격 요청이
> WAF Edge에서 먼저 차단돼 애플리케이션과 Cloud Resource까지 도달하지 않은 결과입니다.

### 증거

- 새 REATTACK_ID
- 같은 Payload Hash
- HTTP 403
- WAF BLOCK과 정확한 terminating Rule
- downstream 신규 Event·Rule·자동 행동 0
- 정상 기능 PASS
- 재공격 뒤 Rule 100102 Health PASS

### 중단 조건

- 403만 있고 WAF terminating Rule을 확인하지 못함
- 최초 공격과 Payload가 다름
- downstream Event나 추가 자동 행동이 하나라도 발생함
- 정상 기능이 실패함
- Health Event가 Wazuh에 도착하지 않음

## SC-09 — 결론과 현재 구조의 한계

> [!DANGER] 사용 조건
> SC-07과 SC-08의 WAF 적용·재공격 Runtime이 실제로 PASS한 촬영에서만 이 결론 전체를
> 읽는다. 그 전에는 WAF 차단 성공 문장을 삭제하거나 미래 계획으로 명확히 바꾼다.

**예상 길이:** 2분
**화면:** 최종 Timeline → Argo 격리 결과 → DVWA impossible → WAF BLOCK 요약

### 그대로 읽을 대사

> 이번 시연에서는 실제 Event 하나를 끝까지 추적했습니다. DVWA의 Credential endpoint
> 접근 징후를 Rule 100110이 조기에 탐지했고, Wazuh Alert는 인증과 Schema 검증을 거쳐
> Shuffle과 고정 GitHub Workflow로 전달됐습니다. 그 결과 공격을 처리한 Pod만
> 네트워크에서 격리하면서 증거로 보존했고, 새 정상 Pod가 서비스를 이어갔습니다.

> 뒤이어 CloudTrail에서 고정된 가짜 S3 Object의 실제 바이트 반환을 Rule 100111이
> 별도로 확인했습니다. 두 번째 자동 대응은 GitOps를 통해 DVWA의 기본 보안 수준 한
> 값을 low에서 impossible로 배포했습니다.

> 자동화는 사전에 승인한 좁고 반복 가능한 조치만 수행했습니다. 사람은 여러 Source의
> Timeline을 해석해 최초 진입점에 적용할 추가 방어의 위치와 범위를 결정했습니다.
> 같은 공격은 WAF Edge에서 차단됐고, 정상 기능과 수집 Health를 함께 확인했습니다.

> 현재 저지연 Event-driven 전달을 Runtime으로 적용한 Source는 DVWA입니다. WAF,
> CloudTrail, ALB와 CloudFront는 Source와 Telemetry 특성에 따라 기존 수집 경로와
> 도착 지연이 다릅니다. 특히 이번 Rule 100111은 현재 검증된 10분 예약 수집 경로를
> 사용합니다.

> 후속 검토에서는 각 Source에 적합한 Event-driven Telemetry로 저지연 수집을 넓히고,
> 기존 Poll과 Archive는 원본 보존, 누락 보완과 재분석 경로로 남기는 구조를 개선
> 후보로 정리했습니다. 다만 구현만 바꾸고 충분히 검증하지 않은 상태를 최종 결과에
> 섞지 않고, 이번 영상은 실제 Runtime으로 확인한 As-built 범위만 증명합니다.

### 최종 자막

~~~text
Rule 100110 early detection
→ automatic workload isolation

Rule 100111 confirmed protected GetObject
→ automatic DVWA low → impossible

Human investigation
→ narrow WAF mitigation
→ same-payload reattack blocked at Edge

Normal service / telemetry health maintained
~~~

## 5. 촬영 중 즉시 중단할 조건

- 새 TAKE 시작 시 DVWA가 low가 아님
- Rule 100102 Health가 없어 수집 상태를 증명할 수 없음
- Rule 100110이 Role 조회 단계에서 발생함
- 같은 Source Event에 100110이 중복 발생함
- 격리 대상 Pod name·UID가 Source Event와 다름
- 공격 Pod가 보존되지 않거나 새 정상 Pod가 Ready가 아님
- 격리 Pod의 실제 Ingress 또는 Egress가 성공함
- 서로 다른 TAKE의 100110/100111을 하나의 사건으로 설명해야 함
- Rule 100111 원본 eventID와 성공 조건을 확인할 수 없음
- 자동 대응에 사람이 Workflow를 직접 실행해야 했음
- 예상하지 않은 Repository·Branch·파일이 변경됨
- DVWA 새 Session이 impossible이 아님
- WAF·재공격 구간이 Runtime PASS 전임
- Secret·Credential·Cookie·Token·원문 Command가 화면에 노출됨

실패한 TAKE를 부분 편집으로 성공본처럼 만들지 않는다. 원인을 수정하고 Reset한 뒤 새
TAKE로 다시 촬영한다.
