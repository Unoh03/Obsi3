> **AWS 클라우드 환경**

# EKS 컨테이너 침투 기반 모의해킹 및 위협 탐지 분석 프로젝트

취약한 파드 → 컨테이너 탈출 → IRSA 오설정 악용 → AWS 리소스 확산 시나리오

## 프로젝트 제안 보고서

AWS 클라우드 보안 엔지니어링 과정 팀 프로젝트

모의해킹팀 · 데이터분석팀 통합

# 1. 프로젝트 개요

## 1.1 배경

클라우드 침해사고의 상당수는 AWS 자체의 취약점이 아니라 IAM 오설정, 컨테이너 환경의 권한 관리 미흡 등 사용자 책임 영역에서 발생한다. 특히 쿠버네티스(EKS)와 같은 컨테이너 오케스트레이션 환경은 파드(Pod) 단위의 취약점이 클러스터 내부를 넘어 AWS 계정 전체로 확산될 수 있는 구조적 위험을 가지고 있다.

본 프로젝트는 AWS 클라우드 보안 엔지니어링 과정에서 학습한 Terraform 기반 인프라 자동화 및 쿠버네티스(EKS) 운영 지식을 바탕으로, 실제 공격자의 관점에서 컨테이너 환경 침투가 AWS 클라우드 전체 침해로 확산되는 과정을 재현하고, 이를 로그 기반으로 탐지·분석하는 것을 목표로 한다.

## 1.2 목적

- EKS(Kubernetes) 환경에서 발생 가능한 대표적 취약점을 실제 인프라에 재현하고 공격 시나리오를 검증한다.
- 컨테이너 탈출 및 IRSA(IAM Roles for Service Accounts) 오설정을 악용한 권한 확산 경로를 규명한다.

- 공격 과정에서 생성되는 로그(CloudTrail, EKS 컨트롤플레인 로그 등)를 분석하여 탐지 지표와 대시보드를 구축한다.
- 모의해킹(공격 재현)과 데이터분석(탐지·시각화)을 하나의 팀 프로젝트로 통합하여, 레드팀-블루팀 협업 구조를 학습한다.

## 1.3 프로젝트 범위 (Scope)

본 프로젝트는 AWS 책임 공유 모델(Shared Responsibility Model)상 고객 책임 영역에 한정하여 진행한다. AWS의 물리적 인프라, 하이퍼바이저 등 AWS 자체 관리 영역은 대상에서 제외하며, 온프레미스 환경 역시 프로젝트 범위에 포함하지 않는다.

| **구분**            | **포함 범위**                                     | **비고**            |
|---------------------|---------------------------------------------------|---------------------|
| 진단/공격 대상 환경 | AWS 클라우드 (EKS 클러스터, IAM, EC2, S3 등)      | 고객 책임 영역      |
| OS/컨테이너 레벨    | 취약한 컨테이너 이미지 및 파드 설정 (진입점 역할) | 최소 범위로 한정    |
| AWS 서비스 레벨     | IAM(IRSA), EKS, S3, CloudTrail 등                 | 핵심 진단·공격 대상 |
| 제외 범위           | 온프레미스 인프라, AWS 자체 물리 인프라           | \-                  |

# 2. 공격 시나리오 (Kill Chain)

본 프로젝트의 공격 시나리오는 컨테이너 레벨의 취약점에서 시작하여 AWS 계정 전체로 확산되는 4단계 킬체인으로 구성한다. 각 단계는 실제 클라우드 침해사고에서 빈번히 관찰되는 공격 패턴을 기반으로 설계하였다.

| **단계**               | **공격 행위**            | **설명**                                                                                                                     |
|------------------------|--------------------------|------------------------------------------------------------------------------------------------------------------------------|
| 1단계 (초기 침투)      | 취약한 파드 진입         | 취약한 컨테이너 이미지 또는 오설정된 파드(과도한 권한, 불필요하게 열린 서비스 등)를 통해 파드 내부로 침투                    |
| 2단계 (권한 확인)      | 서비스어카운트 토큰 탈취 | 파드 내부에 마운트된 쿠버네티스 서비스어카운트(ServiceAccount) 토큰을 탈취하여 클러스터 내 권한 확인                         |
| 3단계 (권한 확산)      | IRSA 오설정 악용         | IAM Roles for Service Accounts(IRSA) 설정 오류를 악용해 파드에 연결된 AWS IAM Role의 자격증명을 탈취, AWS API 접근 권한 획득 |
| 4단계 (최종 목표 달성) | AWS 리소스 접근/유출     | 탈취한 IAM Role 권한으로 EKS 클러스터 외부의 AWS 리소스(S3, RDS 등)에 접근하여 최종 침해 시연                                |

## 2.1 공격 흐름도

취약한 파드 진입 → 서비스어카운트 토큰 탈취 → IRSA 오설정 악용 → IAM Role 자격증명 획득 → AWS 리소스(S3/RDS) 접근

*※ 각 단계는 실제 침투 재현 전, 팀 내부 승인 및 격리된 테스트 계정 환경에서만 수행한다.*

# 3. 시스템 아키텍처

## 3.1 인프라 구성

- VPC / Subnet: 테스트 전용 VPC 구성, 퍼블릭/프라이빗 서브넷 분리
- EKS 클러스터: 취약점 재현을 위한 파드 오설정, 일부 노드에 과도한 권한의 IRSA 연결

- IAM: 파드-역할 간 신뢰관계(Trust Policy)를 의도적으로 과도하게 설정한 Role 구성
- S3 / RDS: 공격의 최종 목표가 되는 리소스, 민감 데이터(더미 데이터) 저장

- 로깅: CloudTrail(전 리전), EKS 컨트롤플레인 로그(kube-apiserver, audit), VPC Flow Logs 활성화

## 3.2 인프라 자동화

전체 인프라는 Terraform으로 코드화(Infrastructure as Code)하여 구성한다. 모듈 단위(network, iam, eks, s3, logging)로 분리하여 재사용성과 가독성을 확보하고, 원격 상태 관리를 위해 S3 백엔드와 DynamoDB 락을 사용한다.

# 6. 데이터 분석 파트 상세

데이터분석팀은 공격 시나리오 수행 중 생성되는 로그를 수집하여, 공격 탐지 관점의 분석을 수행한다. 이는 실제 기업의 보안관제(SOC) 업무와 유사한 구조로, 공격 발생 시점과 탐지 시점의 차이를 정량적으로 분석하는 데 초점을 둔다.

- 로그 소스: CloudTrail(IAM/S3 API 호출), EKS Audit Log(kube-apiserver 요청), VPC Flow Logs
- 분석 목표: 정상 트래픽과 공격 트래픽의 패턴 차이 도출, 이상탐지(Anomaly Detection) 모델 적용

- 핵심 지표: MTTD(평균 탐지 소요 시간), 공격 단계별 로그 발생 시점 매핑
- 산출물: 공격 타임라인 대시보드, 탐지 룰(Rule) 제안서

# 9. 유의사항

- 모든 취약 환경 구축 및 공격 시연은 팀 전용 테스트 AWS 계정에서만 수행하며, 운영 계정과 완전히 분리한다.
- AWS 비용 관리를 위해 예산 알림(Budget Alert)을 설정하고, 사용하지 않는 리소스는 즉시 destroy 처리한다.

- 본 프로젝트에서 다루는 공격 기법은 학습 목적에 한하며, 팀 소유 계정 외 어떠한 시스템에도 적용하지 않는다.
