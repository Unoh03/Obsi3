# 멘토 질문 리스트

> [!note] 이 문서의 목적
> 멘토에게 주제를 대신 정해 달라고 요청하는 것이 아니라, **4주 안에 보안 프로젝트로 인정받을 기준과 우선순위**를 확인한다.
> 아래의 프로젝트 방향은 아직 팀에서 확정되지 않은 후보이며, 멘토의 실제 답변과 구분한다.

## 질문 전 전달할 현재 상황

- 최종 프로젝트 기간은 4주이며, 팀은 3~4명으로 구성될 예정이다.
- 현재 후보 중 하나는 Terraform과 Kubernetes로 환경을 구성하고, 다른 교육생이 만든 웹 애플리케이션인 VOLT를 적용하는 방향이다.
- 아직 주제, 역할, 필수 산출물은 확정되지 않았다.
- 2차 프로젝트에서는 KISA 기준 온프레미스·AWS 취약점 진단, 조치, 재점검과 일부 웹 취약점 재현을 수행했다.
- 이번에는 기술을 많이 사용했다는 사실보다 **무슨 보안 문제를 어떻게 검증했는지**가 드러나야 한다고 생각한다.

## 질문 목적과 우선순위

| 우선순위 | 확인할 판단 기준 | 질문 번호 |
|---:|---|---|
| 1 | 클라우드 구축과 클라우드 보안 프로젝트의 경계 | Q1, Q2 |
| 2 | 4주 프로젝트의 적정 깊이와 범위 | Q3 |
| 3 | Kubernetes·컨테이너에서 달라지는 보안 관점 | Q4 |
| 4 | 취약점 진단과 모의해킹 직무의 경계 및 신입 기대 수준 | Q5, Q6 |
| 5 | 지난 상담에서 답하지 못한 SQL Injection 질문 보완 | Q7 |

## 내일 반드시 확인할 질문

### Q1. 무엇이 클라우드 **구축**이 아니라 클라우드 **보안** 프로젝트를 만드는가?

> 저희는 Terraform과 Kubernetes로 클라우드 환경을 구축하고 웹 애플리케이션을 적용하는 방향을 검토하고 있습니다. 이때 단순한 인프라 구축 프로젝트와 클라우드 보안 프로젝트를 가르는 핵심 기준은 무엇인가요?  
> 예를 들어 IAM·RBAC·Secrets·NetworkPolicy 같은 설정 진단, 실제 공격, 로그 탐지, 조치와 재점검 중 무엇이 반드시 포함돼야 하나요?

**얻고 싶은 것:** 사용 기술 목록이 아니라 보안 문제·검증·산출물을 정하는 기준.

### Q2. 웹 공격을 하면 일반 웹 모의해킹이 되는데, 무엇이 있어야 **클라우드 보안**이 되는가?

> 지난 상담에서 실제 웹 공격을 수행하고 그 공격이 클라우드 환경 어디에서 탐지되는지 확인해 보라고 하셨습니다.  
> 웹 취약점 재현에 WAF나 로그만 붙이면 클라우드 보안 프로젝트가 되는 것은 아닐 것 같은데, 공격 경로·IAM 권한·컨테이너·데이터·탐지와 대응 가운데 어떤 연결을 보여줘야 클라우드 환경을 이해한 프로젝트로 보시나요?

**얻고 싶은 것:** 2차 프로젝트의 단순 반복과 클라우드 기술 전시를 동시에 피할 기준.

### Q3. 4주·3~4명이라면 넓은 환경과 깊은 시나리오 중 무엇을 우선해야 하는가?

> Terraform, Kubernetes, 애플리케이션, 스캐너, 로그 수집까지 넓게 구성하는 방법과, 보안 시나리오 한두 개를 공격 → 증적 확인 → 원인 분석 → 조치 → 재점검까지 깊게 수행하는 방법 중 신입 프로젝트에서는 어느 쪽이 더 좋은 증거가 되나요?  
> 둘을 함께 한다면 어느 수준에서 범위를 끊는 것이 현실적인가요?

**얻고 싶은 것:** 4주 동안 완성도 있게 끝낼 최소 범위와 포기할 범위.

### Q4. Kubernetes·컨테이너 환경에서는 진단의 대상과 증적이 어떻게 달라지는가?

> 기존에는 OS·네트워크·DB·웹 애플리케이션을 중심으로 취약점을 봤습니다. Kubernetes와 컨테이너 환경에서는 자산, 신뢰 경계, 권한, 공격 경로와 증적이 어떻게 달라지나요?  
> 신입이 4주 동안 다룬다면 이미지 취약점, RBAC, Secrets, NetworkPolicy, Pod Security, 공급망 중 무엇부터 보는 것이 좋을까요?

**얻고 싶은 것:** “컨테이너 버전의 2차 프로젝트”를 넘어서는 핵심 변화와 학습 순서.

### Q5. 실무에서 취약점 진단과 모의해킹은 어디까지 겹치고 어디서 갈라지는가?

> 채용 공고에서는 취약점 진단과 모의해킹이 한 직무에 함께 적힌 경우가 있습니다. 실제 신입 업무에서는 두 업무가 어느 정도 겹치며, 결과물·판단 방식·요구 기술은 어디서 달라지나요?

**얻고 싶은 것:** 명칭보다 실제 업무를 기준으로 관심 직무를 좁힐 근거.

### Q6. 신입에게 기대하는 최소 증거는 무엇인가?

> 저는 KISA 기준 진단과 조치·재점검, SQL Injection 재현, 자동 판정의 오탐과 `Manual` 원인 분석을 경험했습니다.  
> 취약점 진단 직무와 모의해킹 직무 각각에서, 이 경험 중 실제 강점으로 인정될 부분과 아직 반드시 보완해야 할 증거는 무엇인가요?

**얻고 싶은 것:** 현재 경험을 과대평가하거나 과소평가하지 않고 다음 학습을 정할 기준.

## 지난 상담 후속 질문

### Q7. 지난번 SQL Injection 질문에서는 무엇을 확인하려 하셨나요?

> 지난번에 SQL Injection을 어떻게 공격했는지 질문해 주셨는데 제대로 답하지 못했습니다.  
> 당시에는 로그인과 게시글 검색 입력에 참·거짓 조건과 오류 유도 값을 넣어 인증 우회 가능성, 응답 차이, 오류 노출을 확인했습니다. 멘토님이 그 질문을 통해 확인하려 했던 것은 공격 유형의 구분, 실제 수행 과정, 성공 판정 근거 중 어느 부분이었나요? 제 검증에서 부족했던 부분도 듣고 싶습니다.

**얻고 싶은 것:** 외운 공격명보다 입력 지점·가설·성공 조건·증적을 설명하는 법.

## 시간이 남으면 물을 꼬리질문

- 다른 팀이 만든 애플리케이션을 가져와도, 분석 범위와 공격 가설·증적·조치 기여가 명확하면 보안 프로젝트의 유효한 기반이 될 수 있나요?
- 자동 스캐너 결과와 수동 검증을 비교할 때 신입이 보여줘야 할 핵심은 탐지 개수인가요, 오탐 제거와 판정 근거인가요?
- 공격이 WAF·애플리케이션 로그에는 남지만 CloudTrail이나 GuardDuty에는 남지 않는다면, “탐지 실패”가 아니라 각 로그의 관측 범위를 구분한 결과로 설명해도 되나요?
- 팀원들이 인프라 구축에 집중하고 제가 취약점 검증을 맡을 경우, 개인 기여가 분리되어 보이면서도 하나의 보안 스토리로 연결되려면 어떤 산출물을 남겨야 하나요?
