# 멘토 상담 후 보고서·발표 반영

> [!IMPORTANT]
> 이 문서는 보고서와 발표에 실제로 옮길 문구의 정본이다.  
> As-built, Runtime Verified, Target Candidate를 섞지 않는다.

## 1. 현재 검증 범위

현재 체크포인트를 Gate 단위로 쓴다.

```text
DVWA→Wazuh 하위 경로 Runtime
- 무해 Event 3건
- Rule 100102 Alert 3건
- 총지연 6.439 / 3.427 / 3.761초
- 누락 0건
- Shuffle은 포함하지 않음

G0~G2
- Shuffle Workflow / Webhook 구조 검증
- 정상 Header 합성 Payload 왕복
- wrong / missing Header 거절
- 인증 실패 요청의 신규 Execution 0건

G3
- Rule 100103 대상 Wazuh Integrator·Rule·Sanitizer·Secret 경계
- Manager 적용 및 strict Runtime PASS

G4
- 실제 Rule 100103 Alert ↔ Shuffle Execution 일대일 Evidence
- 현재 미완료
```

따라서 G4 완료 전 보고서의 `현재 검증 범위`는 다음처럼 쓴다.

> DVWA에서 Wazuh까지의 저지연 하위 경로는 무해 Rule `100102` Event 3건으로 Runtime 검증했으며, Rule `100103`을 대상으로 한 Wazuh Integrator·Rule·Sanitizer 설정은 G3 strict Runtime PASS를 확보하였다. Shuffle Webhook의 구조·인증·합성 Payload 왕복도 검증하였다. 다만 실제 Rule `100103` Alert와 Shuffle Execution을 일대일로 연결하는 G4 Evidence는 아직 완료되지 않았으므로, 실제 사건 기반 Wazuh→Shuffle E2E 완료로 표기하지 않았다.

G4 완료 뒤에는 Evidence 경로와 SHA-256을 붙여 다음으로 승격한다.

> 실제 Rule `100103` Alert N건과 Shuffle terminal Execution N건의 전단사 관계를 Runtime Evidence로 확인하였다.

## 2. 보고서에서 설명할 개선 발견

### 후속 검토에서 발견한 한계

> 초기 설계에서는 AWS 서비스를 대표 로그 Source 단위로 구분하여 수집 경로를 구성하였다. 이후 Runtime 검증과 현업 멘토 상담, AWS 공식 문서 재검토를 통해 동일한 서비스에서도 Logging mechanism에 따라 Telemetry 사용 가능 지연, 전달 목적지, 비용, Sampling, 보존 특성이 크게 달라질 수 있음을 확인하였다. 예를 들어 ALB Legacy S3 Access Logs와 Vended Logs, CloudFront Standard Logging과 Real-time Access Logging은 동일 Resource의 Log Telemetry이지만 관제 용도와 운영 특성이 다르다.

### 현재 As-built

```text
DVWA 저지연 Event-driven Push
→ Wazuh 초기 탐지 Trigger

기존 5-Source Poll / Query / Archive
→ 후행 조사·Confirmation·Evidence
```

### Target Candidate

```text
각 Resource에 적합한 Logging mechanism
→ Event-driven AWS-native Destination
→ Buffer / Retry / DLQ
→ Wazuh 중앙 분석·Correlation

기존 Poll / Archive
→ 원본 보존
→ Replay
→ 누락 보완
→ Historical Investigation
```

이 구조를 `최선`으로 단정하지 않는다.

권장 표현:

- 공식 문서 검토상 더 적합한 개선 후보
- Target Architecture Candidate
- 후속 Runtime 비교 대상
- 저지연 관제에 유리한 Telemetry mechanism

## 3. 왜 이번 최종 구현에 반영하지 않았는가

### 보고서용 문구

> 프로젝트 후반 현업 피드백과 공식 문서를 추가 검토하면서 일부 AWS Resource에는 기존 Polling 경로보다 저지연 관제에 유리할 가능성이 있는 별도 Logging mechanism과 Event-driven Delivery 경로가 존재함을 확인하였다. 그러나 해당 변경은 단순 로그 설정 변경에 그치지 않고 Terraform 구성, Delivery Destination, Wazuh Input·Decoder·Rule, Source 간 Correlation, 중복·누락·장애 복구와 기존 Runtime Evidence 전체를 다시 검증해야 하는 구조 변경이다. 따라서 미검증 신규 구조를 최종 결과에 포함하기보다 실제 Runtime Evidence가 확보된 현재 Baseline을 유지하고, 개선안은 Target Candidate와 후속 검증 항목으로 분리하였다.

핵심 한 문장:

> **구현만 바꾼 뒤 충분히 검증되지 않은 상태를 완료 결과로 제시하기보다, 검증된 범위를 동결하고 개선안을 후속 Runtime 검증 대상으로 남겼다.**

### 기술적 최적성과 일정 판단을 분리

`프로젝트 남은 일정`은 최적 Route의 기술 평가 기준에 포함하지 않는다.

```text
기술적 평가
→ latency, 신뢰성, Buffer, 보안 경계, 비용, 운영 복잡도, 정보 가치

프로젝트 Scope 결정
→ 변경 후 동일 수준의 Runtime 재검증을 완료할 수 있는가
```

따라서:

```text
시간이 없어서 기존 구조가 기술적으로 최적이다.  X

공식 문서상 개선 후보를 확인했지만,
변경 후 충분한 Runtime 검증을 완료할 수 없어
As-built와 Target Candidate를 분리했다.  O
```

## 4. 발표 슬라이드 구성

### 추천 제목

```text
Runtime 검증 이후 확인한 로그 수집 구조 개선점
```

또는:

```text
검증된 As-built와 후속 Target Architecture
```

### 슬라이드 1장 구성

#### 현재 Runtime 검증

```text
DVWA → Wazuh Rule 100102 무해 하위 경로 N=3
Rule 100103 Wazuh Integrator / Sanitizer G3 strict PASS
Shuffle 인증·합성 Payload 왕복 G0~G2 PASS
5-Source Evidence 조사

실제 Rule 100103 Alert ↔ Shuffle Execution G4
→ 완료 후 Evidence로 별도 표시
```

#### 후속 검토에서 확인

```text
서비스 ≠ 단일 로그 방식

ALB
Legacy S3 Access Logging
↔ Vended Logs Target Candidate

CloudFront
Standard Logging
↔ Real-time Access Logging
```

#### 결정

```text
미검증 구조를 막판에 완료로 포함하지 않음
→ Runtime Baseline 동결
→ Source별 Logging mechanism 전환은 Future Work
```

## 5. 발표 대본

> 초기에는 각 AWS 서비스를 대표 로그 기준으로 수집했습니다. 그러나 실제 Runtime 검증과 현업자 상담 이후 공식 문서를 다시 확인하면서, 같은 서비스에서도 Logging mechanism에 따라 Telemetry가 사용 가능해지는 시간과 전달 구조가 크게 다르다는 점을 확인했습니다. 예를 들어 ALB Legacy S3 Access Log는 5분 단위 파일 특성이 있지만 Vended Logs라는 별도 후보가 있고, CloudFront에는 Standard Logging과 수초 단위의 Real-time Access Logging이 있습니다. 다만 Real-time이 항상 완벽한 상위호환은 아닙니다. 비용, Sampling, Kinesis Consumer 운영, Archive 목적이 다르기 때문입니다. 따라서 장기적으로는 Source별 요구에 맞는 mechanism을 Event-driven 방식으로 Wazuh에 연계하는 구조를 Target Candidate로 두었습니다. 이번 결과에서는 구현만 바꾸고 검증되지 않은 상태를 제시하지 않기 위해 기존 Runtime Baseline을 유지했습니다.

G4가 아직 미완료인 시점의 발표라면 다음을 추가한다.

> DVWA→Wazuh 하위 경로는 Rule `100102` 무해 Event 3건으로 검증했고, Rule `100103` Integrator·Sanitizer 설정은 G3 strict PASS입니다. Shuffle Webhook의 구조·인증·합성 Payload 왕복도 확인했습니다. 다만 실제 Rule `100103` Alert와 Shuffle Execution의 일대일 Evidence는 아직 최종 G4로 남아 있어 완료 처리하지 않았습니다.

G4 완료 후에는 위 문장을 Evidence 결과로 교체한다.

## 6. Q&A

### `시간이 없어서 못 한 것 아닌가요?`

> 네. 프로젝트 후반에 확인한 개선안이라 전체 구조를 변경하고 기존과 같은 수준으로 다시 검증하기에는 남은 범위가 충분하지 않았습니다. 다만 구현 시간보다 더 중요한 문제는 변경 후 수집, Rule, Correlation, 중복·누락, 장애 복구 Evidence를 다시 확보해야 한다는 점이었습니다. 그래서 미검증 신규 구조를 완료로 포함하지 않고, 현재 검증된 Baseline과 Target Candidate를 분리했습니다.

### `그러면 기존 구조가 잘못된 것인가요?`

> 기존 구조는 경로별로 실제 Runtime 동작과 Evidence가 확인된 As-built입니다. 다만 모든 Source의 주 탐지 Route로 영구 최적이라고 보지는 않습니다. 후속 검토에서 더 저지연일 가능성이 있는 mechanism을 발견했으며, 실제 우월성은 latency·비용·누락·운영 복잡도를 Runtime으로 비교해야 확정할 수 있습니다.

### `왜 모든 Source를 즉시 Push하지 않았나요?`

> Event-driven 전달로 Poll 대기는 줄일 수 있지만, Source가 Record를 생성하고 AWS Destination에 제공하는 A+B 지연까지 항상 없앨 수 있는 것은 아닙니다. 또한 각 서비스의 Logging mechanism과 Destination이 다르므로 동일한 하나의 Transport를 강제하기보다 Source별 적합한 경로를 Wazuh의 하나의 Incident 흐름에서 연계하는 방향을 선택했습니다.

### `Real-time Logs가 Standard보다 무조건 좋은가요?`

> 아닙니다. Real-time은 수초 단위 탐지에 유리하지만 CloudFront 추가 요금과 Kinesis 비용, Sampling, Consumer 운영, best-effort 전달을 고려해야 합니다. Standard는 느리지만 Archive, Historical analysis, S3·Parquet·Athena 같은 장기 분석에 유리합니다. 목적에 따라 병행하거나 역할을 분리해야 합니다.

### `GetObject가 안 보이면 공격 실패인가요?`

> 바로 실패로 판정하지 않습니다. Data Event Selector, 대상 Prefix, 시간 창, Delivery 완료와 Telemetry Coverage가 정상인지 먼저 확인합니다. 성공 Evidence가 있으면 CONFIRMED, 정상 Coverage와 명시적 실패 Evidence가 있으면 REJECTED, 로그 부재나 Coverage 불확실이면 INCONCLUSIVE로 둡니다.

## 7. Microsoft Sentinel 비교 문구

> Microsoft Sentinel도 NRT 분석 규칙으로 빠른 신호를 탐지하고, Scheduled 분석 규칙과 추가 Alert로 같은 Incident의 문맥을 보강하며, Incident 생성·갱신 시 Automation Rule과 Playbook을 실행할 수 있습니다. 저희도 이와 유사하게 초기 고신뢰 신호로 제한적 대응을 시작하고, 이후 여러 Source의 Evidence로 사건을 확인하도록 설계했습니다.

주의:

```text
동일한 구현이다.  X
유사한 운영 패턴을 지원한다.  O
```

## 9. 권장 표현

```text
후속 공식 검토에서 개선 가능한 Logging mechanism과 Route를 확인했다.
현재 구현은 Runtime으로 검증된 As-built다.
개선안은 공식 문서 기반 Target Candidate다.
적용하려면 기존 수준의 Runtime 재검증이 필요하다.
따라서 현재 Baseline을 동결하고 Future Work로 분리했다.
미검증 항목은 완료 처리하지 않았다.
```

## 10. 프로젝트 스토리

```text
초기 설계
→ 구현
→ Runtime에서 latency 문제 확인
→ DVWA 저지연 Push 추가
→ 현업 멘토 피드백
→ 빠른/느린 관제 개념 재검토
→ NIST / AWS / Sentinel 공식 자료 교차검증
→ Telemetry availability latency와 Transport latency 분리
→ Resource × Logging mechanism × Route로 재평가
→ 현재 Baseline과 Target Candidate 분리
→ 실제 Alert ↔ Execution Gate는 Evidence가 생길 때만 완료
```

처음부터 완벽했다고 포장하기보다, **구현과 검증을 통해 초기 가정을 수정하고 미검증 변경은 완료로 주장하지 않았다는 과정**을 프로젝트의 공학적 성과로 설명한다.
