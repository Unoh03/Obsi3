## 발표와 포트폴리오에 반영할 것

멘토 피드백 중 가장 직접적으로 프로젝트 발표에 적용할 수 있는 부분.

단순히 아래처럼 말하면 구현의 깊이가 잘 드러나지 않음.

```text
Wazuh를 사용했다.
Shuffle을 연동했다.
```

대신 실제 사건 한두 건을 끝까지 연결해 보여줘야 함.

```text
실제 Event
→ 어떤 Wazuh Rule이 탐지했는가
→ 어떤 Alert가 발생했는가
→ 그 Alert가 Shuffle에 어떻게 전달됐는가
→ 어떤 Workflow/Action이 실행됐는가
→ 실제 결과가 무엇이었는가
```

즉 발표에서 중요한 건 제품 이름을 많이 보여주는 것이 아니라, **어떤 Rule을 왜 만들었고 그 Rule이 실제 Runtime에서 무엇을 일으켰는지 증명하는 것**.

현재 진행 중인 `Rule 100103 Alert → Wazuh Integrator → custom-shuffle-soc → Shuffle Webhook → Execution`의 실제 일대일 Runtime Evidence 검증은 이 피드백과 잘 맞음.

또한 최종 발표에서는 다음 상태를 섞지 말 것.

```text
설계됨
구현됨(Source 존재)
설정/정적 검증됨
실제 Runtime 검증됨
```

`연동 완료`, `자동 대응 완료` 같은 표현은 어느 단계까지 Evidence가 있는지에 맞춰 사용.

## 그래서 보고서, 발표엔 어떻게 넣어야하는가!

핵심은 **`시간이 없어서 못 했다`를 결과의 중심 이유로 쓰지 않는 것**이다.

실제 상황은 다음에 더 가깝다.

```text
초기 설계
→ 실제 구현·Runtime 검증
→ 현업 멘토 피드백
→ 공식 문서 재검토
→ 서비스 × Telemetry × Route 관점의 더 나은 개선 후보 발견
→ 변경 시 수집·탐지·상관분석·Evidence 전체 재검증 필요
→ 검증된 Baseline은 동결
→ 개선안은 Target Architecture / Future Work로 분리
```

즉 **구현할 시간이 부족했다**보다 **변경한 구조를 충분히 재검증할 수 없는 상태에서 미검증 구현을 최종 결과에 섞지 않았다**가 더 정확한 설명이다.

### 보고서에는 어떻게 넣을까

보고서의 `한계 및 향후 개선`, `고찰`, `향후 과제` 계열 섹션에 넣는 것이 가장 자연스럽다.

#### 1. 현재 검증된 범위

먼저 As-built와 Runtime으로 확인한 범위를 사실대로 고정한다.

```text
DVWA→Wazuh 하위 경로 Runtime
- 무해 Event 3건
- Rule 100102 Alert 3건
- 총지연 6.439 / 3.427 / 3.761초
- 누락 0건
- Shuffle은 포함하지 않음

G0~G2
- Shuffle Workflow / Webhook 구조 검증
- 정상 Header 합성 Payload 왕복
- wrong / missing Header 거절
- 인증 실패 요청의 신규 Execution 0건

G3
- Rule 100103 대상 Wazuh Integrator·Rule·Sanitizer·Secret 경계
- Manager 적용 및 strict Runtime PASS

G4
- 실제 Rule 100103 Alert ↔ Shuffle Execution 일대일 Evidence
- 현재 미완료
```

완료하지 않은 Target을 현재 구현처럼 쓰지 않는다.

#### 2. 후속 검토에서 발견한 한계

단순히 `Polling이 느렸다`에서 끝내지 않고, 왜 기존 판단이 불완전했는지 설명한다.

> 초기 설계에서는 AWS 서비스를 대표 로그 Source 단위로 구분하여 수집 경로를 구성하였다. 이후 현업자 피드백과 AWS 공식 문서를 재검토하면서 동일한 서비스에서도 Telemetry 종류에 따라 지연 특성과 전달 방식이 크게 달라질 수 있음을 확인하였다. 예를 들어 ALB의 Legacy S3 Access Logs와 Vended Logs, CloudFront의 Standard Logs와 Real-time Logs는 동일 서비스의 로그이지만 관제 관점에서 서로 다른 latency와 전달 특성을 가진다.

#### 3. 개선 후보

```text
현재
DVWA 저지연 Event-driven
+ 일부 Source 10분 Poll

개선 Target
각 Source에 적합한 Telemetry 선택
→ Event-driven AWS-native Destination
→ Buffer / Retry / DLQ
→ Wazuh 중앙 분석·Correlation

기존 Poll / Archive
→ 원본 보존
→ Replay
→ 누락 보완
→ Historical Investigation
```

여기서 `이 구조가 최선이다`라고 단정하지 않는다.

사용할 표현:

- `공식 문서 검토상 더 적합한 개선 후보`
- `Target Architecture`
- `후속 Runtime 검증 대상`
- `저지연 관제에 유리한 Telemetry 후보`

#### 4. 왜 이번 최종 구현에는 반영하지 않았는가

보고서에 그대로 사용할 수 있는 문구:

> 프로젝트 후반 현업 피드백과 공식 문서를 추가 검토하면서, 일부 AWS Source는 기존 Polling 방식보다 저지연의 Event-driven Telemetry 및 전달 경로를 사용할 수 있음을 확인하였다. 그러나 해당 변경은 단순한 로그 설정 변경에 그치지 않고 Terraform 구성, 로그 전달 경로, Wazuh 입력 및 Rule, Source 간 상관분석, 중복·누락·장애 복구와 기존 Runtime Evidence를 다시 검증해야 하는 구조 변경이다. 따라서 검증되지 않은 신규 구조를 최종 결과에 포함하기보다, 실제 Runtime Evidence가 확보된 현재 Baseline을 유지하고 개선 구조는 후속 Target Architecture로 분리하였다.

한 문장으로 줄이면:

> **구현만 변경한 뒤 충분히 검증되지 않은 상태를 완료 결과로 제시하기보다, 검증된 범위를 동결하고 개선안을 후속 검증 대상으로 남겼다.**

#### 기술적 최적성과 프로젝트 Scope 결정은 분리한다

```text
기술적 Route 평가
→ A+B/C 지연, 신뢰성, Buffer, 보안 경계, 비용, 운영 복잡도, 정보 가치

프로젝트 Scope 결정
→ 구조 변경 뒤 기존과 같은 수준의 Runtime 재검증을 완료할 수 있는가
```

따라서 `시간이 없으므로 기존 Route가 기술적으로 최적이다`라고 말하지 않는다. 공식 문서상 개선 후보를 확인했지만 변경 후 충분한 Runtime 검증을 완료하지 못하므로 As-built와 Target Candidate를 분리했다고 설명한다.

이게 보고서에서 가장 중요한 문장.

### 발표 자료에는 어떻게 넣을까

발표에서는 긴 변명처럼 설명하지 않는다.

슬라이드 한 장 또는 기존 관제 아키텍처 슬라이드의 `한계 및 개선 방향` 영역이면 충분하다.

#### 추천 슬라이드 제목

```text
후속 검토에서 확인한 한계와 Target Architecture
```

또는

```text
Runtime 검증 이후 확인한 로그 수집 구조 개선점
```

#### 슬라이드 내용 예시

**현재 Runtime 검증**

```text
DVWA → Wazuh Rule 100102 무해 하위 경로 N=3
Rule 100103 Wazuh Integrator / Sanitizer G3 strict PASS
Shuffle 인증·합성 Payload 왕복 G0~G2 PASS
5-Source Evidence 조사

실제 Rule 100103 Alert ↔ Shuffle Execution G4
→ 현재 미완료
```

**후속 검토에서 확인**

```text
서비스 ≠ 단일 로그 Source

ALB
Legacy S3 Access Logs ↔ Vended Logs

CloudFront
Standard Logs ↔ Real-time Logs
```

**판단**

```text
미검증 구조를 막판에 교체하지 않음
→ 현재 Runtime Baseline 유지
→ Source별 최적 Telemetry 전환은 Future Work
```

#### 발표 대본 예시

> 초기에는 각 AWS 서비스를 대표 로그 기준으로 수집했습니다. 하지만 Runtime 검증과 현업자 상담 이후 공식 문서를 다시 확인하면서, 같은 서비스에서도 Telemetry 종류에 따라 지연 특성이 크게 다르다는 점을 확인했습니다. 예를 들어 ALB에는 기존 S3 Access Log 외에 Vended Logs가 있고, CloudFront에는 Standard Logs 외에 수초 단위의 Real-time Logs가 있습니다. 따라서 장기적으로는 Source별 가장 적합한 Telemetry를 Event-driven 방식으로 Wazuh에 통합하는 구조가 개선 후보입니다. 다만 이 변경은 기존 수집뿐 아니라 Rule, 상관분석, 중복·누락 및 장애 복구까지 다시 Runtime 검증해야 하므로, 이번 결과에서는 검증된 Baseline을 유지했습니다. 현재 Wazuh Integrator와 Shuffle Webhook의 구조·인증·합성 Payload 왕복은 검증했지만, 실제 Rule `100103` Alert와 Shuffle Execution의 일대일 Evidence는 G4로 남아 있어 완료 처리하지 않았습니다.

마지막에 강조할 한 문장:

> **구현만 바꾸고 검증되지 않은 상태를 최종 결과로 제시하지 않는 쪽을 선택했습니다.**

### 발표 Q&A에서 `시간이 없어서 못 한 거 아닌가요?`라고 물으면

시간 부족 자체를 숨길 필요는 없음.

다만 이렇게 답한다.

> 네. 프로젝트 후반에 확인한 개선안이라 전체 구조를 변경하고 다시 검증하기에는 남은 시간이 충분하지 않았습니다. 다만 구현 자체보다 더 큰 문제는 변경 후 기존과 같은 수준의 Runtime Evidence를 다시 확보해야 한다는 점이었습니다. 그래서 미검증 신규 구조를 완료로 포함하지 않고, 현재 검증된 범위를 최종 결과로 고정한 뒤 개선안을 후속 과제로 분리했습니다.

즉:

```text
시간 부족
→ 사실

시간 부족해서 그냥 포기
→ 아님

구조 변경 + 재검증 비용을 판단
→ 검증된 Baseline 동결
→ 개선안은 명시적으로 문서화
```

### 쓰지 않는 표현

```text
시간이 없어서 못 했습니다.
나중에 더 좋은 방법을 알았습니다.
이 구조가 무조건 최선입니다.
원래 구조는 잘못된 구조였습니다.
ALB는 원래 느립니다.
CloudFront는 원래 느립니다.
```

이런 표현은 각각 변명, 과장, 또는 Telemetry 차이를 지워버리는 문제가 있음.

### 권장 표현

```text
후속 검토에서 개선 가능한 Telemetry와 Route를 확인했다.
현재 구현은 Runtime으로 검증된 As-built다.
개선안은 공식 문서 기반 Target Architecture다.
적용하려면 기존 수준의 Runtime 재검증이 필요하다.
따라서 현재 Baseline을 동결하고 Future Work로 분리했다.
```

### 이 내용을 프로젝트 스토리로 쓰는 법

이 과정 자체도 결과의 일부로 볼 수 있음.

```text
초기 설계
→ 구현
→ 실제 Runtime에서 latency 문제 확인
→ 저지연 DVWA Push 추가
→ 현업 멘토 피드백
→ 빠른/느린 관제라는 개념 재검토
→ 공식 NIST/AWS/Sentinel 자료 교차검증
→ Telemetry 사용 가능 지연(A+B)과 SIEM Transport 지연(C) 구분
→ 서비스 × Telemetry × Route 기준으로 재평가
→ 현재 Baseline과 Target Architecture 분리
```

단순히 `처음부터 완벽한 설계를 했다`고 포장하는 것보다, **구현과 검증을 통해 초기 가정을 수정하고 더 나은 후속 설계를 도출했다**고 설명하는 편이 이 프로젝트에서 실제로 한 일을 더 정확히 보여준다.
