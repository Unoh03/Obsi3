# 멘토 상담용 인프라 이해와 설명 준비 계획

> [!summary] 계획 판정
> Chat과 Codex의 두 통합안은 실행 순서와 핵심 원칙이 충분히 일치한다. 추가 AI 토론은 중단하고 이 문서를 기준 계획으로 사용한다. 다만 `Current Runtime Preflight`는 **실시간 시연이 있을 때만 필수**로 하고, 멘토 상담 전 새로 완성할 도식은 **D1·D2 두 개**로 제한한다.

## 1. 목적

멘토가 약 5분 안에 다음을 이해하고, 프로젝트의 다음 방향을 구체적으로 판단할 수 있게 한다.

1. 무엇을 보호하고 실험하는 환경인가
2. 사용자 요청은 실제로 어디를 지나가는가
3. 코드 변경은 어떻게 BANK DVWA Pod까지 배포되는가
4. 공격·이상행위의 흔적은 어느 계층에 남는가
5. 매일 Runtime을 삭제하면서 무엇을 보존하는가
6. 무엇을 실제로 검증했고 무엇은 아직 미검증인가

### 중심 설명

> **Terraform으로 재현되는 EKS 기반 은행형 취약 웹서비스에서, 공격이 어느 계층까지 도달했는지 로그로 추적하고 조치 전후의 통제 효과를 검증하는 보안 실험환경입니다.**

그림·표·Screenshot·설명은 이 문장을 이해시키거나 증명하는 데 필요한 것만 사용한다.

## 2. 범위 고정

### 본편 기준

- `minimal` Runtime Profile
- Primary Region
- 현재 BANK DVWA
- 현재 As-built 구조
- 실제 검증 이력과 보존 Evidence

### 선택 기능·부록

- `dr-test`, `full`
- DR 상세 구조
- Valkey, EFS
- Subnet CIDR, 세부 Security Group, IAM Role 전체 목록
- Karpenter 세부 정책과 Terraform Resource 전체 목록

### 이번 계획에서 하지 않는 것

- 새로운 AWS Resource Apply·Destroy
- Terraform·GitOps·Application Source 수정
- Git staging·commit·push와 GitHub Workflow 실행
- 기존 프로젝트 문서를 발표 내용에 맞추기 위한 광범위한 재작성
- 모든 AWS 서비스 노트 완성
- 제출용 상세 네트워크 도식 전면 재작성
- 아직 검증하지 않은 기능을 완료 상태로 표현
- 표현 취향만을 이유로 Chat과 Codex 사이에서 반복 수정

### Read-only 경계

```text
작업 순서·범위·Gate의 기준 = 이 계획서
인프라 사실의 기준        = 현재 Source·State·보존 Runtime Evidence
```

이번 작업에서 AWS, Terraform Source, GitOps·Application Source, Git 상태와 기존 MOC는 Read-only로 취급한다. 새로 만들거나 수정하는 것은 멘토 준비용 Ledger, D1·D2, 설명 자료와 이 계획서처럼 **이번 산출물 자체인 프로젝트 노트**로 제한한다.

## 3. 사실의 원본: Architecture Truth & Evidence Ledger

그림과 발표문보다 먼저, 발표에서 주장할 **사실 단위**를 하나의 장부에 고정한다. 별도의 Truth 장부와 Evidence 장부를 중복 운영하지 않는다.

Ledger는 D1·D2와 멘토용 세 부분에서 실제로 사용할 핵심 Claim만 담는다. Terraform Resource 전체 목록이나 AWS 서비스 백과사전으로 확장하지 않는다. 근거가 부족한 항목은 추정하지 않고 `Open·미검증`으로 남긴다.

### 권장 열

| ID | Flow | 주장 | 쉬운 설명 | Source | Runtime Evidence·날짜 | 현재 활성 | Profile·수명주기 | 한계 | 발표 |
|---|---|---|---|---|---|---|---|---|---|
| `REQ-01` | Request | Route 53 Alias가 CloudFront를 가리킨다 | Route 53은 요청을 전달하는 Proxy가 아니라 목적지를 알려준다 | 확인 예정 | 확인 예정 | 당일 확인 | External | DNS 조회와 HTTP 요청은 별개 | L1 |

### Claim ID

- `REQ-xx`: Request
- `DEP-xx`: Deployment
- `OBS-xx`: Observability·Detection·Evidence
- `LIF-xx`: Lifecycle
- `IAM-xx`: Identity·Authorization
- `DR-xx`: Optional DR

### 반드시 분리할 상태

```text
Source에 존재
Runtime에서 동작한 검증 이력
현재 이 순간 활성
Evidence가 보존됨
계획만 존재
```

`Source 존재`만으로 `Runtime 검증 완료`라고 표현하지 않는다. 과거 성공은 검증 이력이지 현재 시연 가능 상태가 아니다.

### 근거 우선순위

```text
현재 Runtime 출력·화면
→ 현재 Repository Source·State·Diff
→ 보존된 Runtime Evidence
→ 현재 프로젝트 결정·상태 문서
→ 공식 문서
→ AI 설명
```

Chat과 Codex가 같은 말을 해도 그 자체는 증거가 아니다.

## 4. 네 개의 Canonical Flow

서비스를 사전식으로 나열하지 않고, 다음 네 흐름으로 프로젝트를 이해한다.

### A. Request Flow

```text
DNS 조회
Client ⇢ Route 53 ⇢ CloudFront 주소 확인

실제 요청
Client
→ CloudFront
  [연결된 WAF Web ACL로 Viewer Request 평가]
→ Primary ALB
→ Target Group (ip)
→ BANK DVWA Pod IP
→ RDS
```

제어 관계는 실제 요청 경로와 분리한다.

```text
Kubernetes Service
        +
TargetGroupBinding
        +
AWS Load Balancer Controller
        ↓
Target Group에 Pod IP 등록·조정
```

확인할 핵심:

- Route 53은 Traffic Proxy가 아니다.
- WAF는 CloudFront 뒤의 독립 Server Hop이 아니라 연결된 검사 정책이다.
- ALB가 `ip` Target Group을 사용할 때 실제 Target은 Pod IP다.
- Service·TargetGroupBinding·Controller는 Target 등록과 조정을 담당한다.

### B. Deployment Flow

```text
Developer Push
→ GitHub Actions
→ GitHub OIDC / IAM
  ├→ ECR에 immutable Image Push
  └→ Helm values 변경
      → GitOps Commit
      → Argo CD
      → Kubernetes Desired State 반영

Pod → ECR Image Pull·실행
```

확인할 핵심:

- ECR은 Image Artifact 저장소다.
- Git Repository의 선언이 GitOps Desired State다.
- Argo CD는 ECR을 감시하는 것이 아니라 Git 선언을 조정한다.
- OIDC는 장기 AWS Access Key 없이 Workflow가 제한된 IAM Role을 사용하게 한다.

### C. Security·Observability·Evidence Flow

#### Traffic 사후 분석

```text
CloudFront · ALB · VPC REJECT
→ Persistent Security S3
→ Athena
→ Grafana·조사
```

#### 근실시간 Log 분석

```text
WAF · EKS Audit · BANK Application Audit · CloudTrail
→ CloudWatch Logs
├→ Logs Insights
├→ Live Tail·Viewer
└→ Grafana
```

#### 탐지·알림

```text
BANK Login Audit
→ Metric Filter
→ CloudWatch Alarm
→ SNS

GuardDuty
→ Finding
→ EventBridge
├→ CloudWatch Logs
└→ SNS
```

#### Evidence

```text
S3 · CloudWatch · Athena · Runtime Output
→ Evidence Collector
→ Local Evidence Bundle
```

분석, 탐지, 알림, Evidence를 하나의 선형 Pipeline처럼 그리지 않는다.

### D. Lifecycle Flow

```text
External Persistent
└─ Route 53 Hosted Zone

Persistent Foundation
├─ ACM
├─ ECR
├─ GitHub OIDC / IAM
├─ Security Log S3 / CloudWatch
├─ CloudTrail
└─ GuardDuty / EventBridge / SNS

Daily Runtime
├─ CloudFront / WAF / ALB
├─ VPC / NAT / Bastion
├─ EKS / Nodes / Add-ons
├─ BANK DVWA
└─ RDS
```

```text
daily-up
→ 환경 재현
→ 검증·실험
→ Evidence 수집
→ daily-down
→ 과금 Runtime 제거
→ Image·설정·Security Evidence 보존
```

`minimal`, `dr-test`, `full` Profile과 Valkey·EFS 같은 선택 Toggle은 기본 As-built와 섞지 않는다.

## 5. 멘토 전 핵심 학습 범위

모든 구성요소 노트를 완성하지 않는다. D1·D2와 5분 설명에 필요한 다음 여섯 묶음만 먼저 이해한다.

| 핵심 묶음 | 설명 합격 기준 |
|---|---|
| Route 53·CloudFront·WAF | DNS, 실제 Request Endpoint, 연결된 Web ACL의 차이 |
| ALB·Target Group·TargetGroupBinding·Pod | `ip target`과 제어 관계의 차이 |
| GitHub Actions·OIDC·ECR·GitOps·Argo CD | Image Artifact Flow와 Desired-state Flow 분리 |
| EKS | 단일 Server가 아니라 Workload를 실행·조정하는 Cluster 경계임을 설명 |
| S3·Athena vs CloudWatch | 사후 Traffic 분석과 근실시간 Log 분석의 차이 |
| Foundation vs Daily·Profile | 무엇을 왜 남기고 무엇을 왜 지우는지 설명 |

Pod Identity는 Deployment Flow에 넣지 않는다. 다음 Identity Flow로 별도 설명한다.

```text
Kubernetes Workload
→ ServiceAccount
→ Pod Identity Association
→ IAM Role
→ AWS API
```

## 8. 멘토용 본편 구성

반드시 PPT 세 장일 필요는 없지만, 정보 단위는 세 부분으로 고정한다.

### 1. 무엇을 만들었고 어떻게 동작하는가

- 보호·실험 대상: BANK DVWA
- Request Flow
- Deployment Flow
- Foundation·Daily Runtime

### 2. 공격이 발생하면 무엇을 볼 수 있는가

```text
행위
→ 흔적 생성
→ 보존
→ 조회·분석
→ 탐지·판정
→ Evidence
```

| 관측점 | 답할 수 있는 질문 |
|---|---|
| WAF | 어떤 Web Attack Rule이 Match했는가 |
| CloudFront | 외부에서 어떤 Path로 요청했는가 |
| ALB | Origin까지 요청이 전달됐는가 |
| VPC Flow | 어떤 Network 연결이 거부됐는가 |
| Application Audit | 어떤 계정 행동이 성공·실패했는가 |
| EKS Audit | 누가 Kubernetes API를 사용했는가 |
| CloudTrail | 누가 AWS Control Plane을 변경했는가 |

### 3. 무엇을 증명했고 무엇을 아직 못 했는가

| 항목 | Source | Runtime 검증 | 현재 활성 | Evidence | 다음 조치 |
|---|---:|---:|---:|---:|---|
| 작성 대상 | 확인 | 확인 | 조건부 확인 | 확인 | 명시 |

현재 상태값은 기존 문서에서 복사해 단정하지 않고 Truth Ledger와 당일 조건에 맞춰 채운다.

## 9. 작업 순서와 Gate

```text
① Scope Freeze
→ ② Architecture Truth & Evidence Ledger
→ ③ 네 Flow Claim 확정
→ ④ P1·P2 Architecture 검토
→ Architecture Freeze
→ ⑤ 핵심 여섯 묶음 학습
→ ⑥ D1·D2 기술 초안 작성
→ ⑦ Chat 이해·표현 검토
→ ⑧ 멘토 본편 세 부분·5분 설명문 작성
→ ⑨ Codex 최종 P1/P2 검토
→ Presentation Freeze
→ ⑩ 필요할 때만 Current Runtime Preflight
→ ⑪ 멘토 상담과 결정 질문
```

> [!important] Hard Gate
> Ledger의 핵심 Claim과 네 Flow에서 P1 사실 오류와 P2 조건·상태 누락이 해소되기 전에는 D1·D2를 확정하지 않는다. D1·D2의 모든 핵심 화살표는 Ledger Claim에 대응해야 한다.

### Phase별 완료 조건

| Phase | 완료 조건 |
|---|---|
| Scope | 본편과 Optional 범위가 섞이지 않음 |
| Ledger | D1·D2의 모든 화살표에 Claim ID와 근거가 있음 |
| 학습 | 핵심 여섯 묶음을 사용자 말로 설명 가능 |
| D1·D2 | P1 사실 오류와 P2 상태·조건 누락이 없음 |
| 본편 | 멘토가 5분 뒤 구체적인 설계 판단을 내릴 수 있음 |
| Preflight | 시연 대상만 현재 활성 상태로 재확인 |

## 10. Chat ↔ Codex 검토 규칙

### Chat 역할

- 쉬운 정신 모델
- 발표 문장과 흐름
- 정보 압축

### Codex 역할

- 현재 Source·State·Runtime Evidence 대조
- 화살표와 소유권 검증
- 조건·한계·현재 상태 누락 확인
- 잘못된 완료 표현 검출

### 이번 Goal에서의 작성·검증 분리

Codex가 Ledger와 D1·D2의 **기술 초안**을 만들 수는 있지만, 그것만으로 교차검증이 끝난 것은 아니다.

```text
Codex 기술 초안
→ Chat의 쉬운 설명·이해 가능성 검토
→ Codex의 Source·Evidence 기반 최종 P1/P2 검토
→ Freeze
```

Chat 피드백 전 산출물은 `기술 초안`이며 최종 교차검증 완료로 표시하지 않는다.

### 피드백 등급

```text
P1 — 사실 오류: 반드시 수정
P2 — 조건·한계·상태 누락: 반드시 수정
P3 — 표현·취향: 선택
```

P1·P2가 0이면 Freeze한다. P3만 남은 상태에서 추가 왕복하지 않는다.

|---:|---|---|
| 0:00–0:30 | 프로젝트 목적 | 왜 만들었는가 |

## 12. Current Runtime Preflight

### 실시간 시연을 하는 경우

상담 직전에만 다음을 확인하고 `현재 활성` 열을 갱신한다.

- Runtime Profile
- Application URL과 CloudFront 응답
- Argo CD `Synced / Healthy`
- BANK DVWA Pod Ready와 실행 Image
- ALB Target Health
- WAF Log 유입
- Grafana·Athena 시연 가능 여부
- Evidence 위치

### 실시간 시연을 하지 않는 경우

- Preflight와 Daily Apply를 필수로 하지 않는다.
- 실제 Down Evidence가 있으면 `Daily Down·비활성 — 비용 통제를 위한 정상 운영 상태`로 표시한다.
- State만 존재하거나 AWS 실재를 확인하지 않았다면 `현재 활성 미확인`으로 표시한다. Terraform State 존재는 현재 Runtime 활성의 증거가 아니다.
- 날짜가 있는 과거 Runtime Evidence로 검증 이력을 설명한다.
- 과거 성공을 현재 활성으로 표현하지 않는다.

이미 Runtime이 실행 중이라면 필요한 범위의 Read-only 확인은 가능하다. Runtime이 꺼져 있거나 실재 여부가 불명확하면 이 Goal을 위해 새로 올리지 않는다.

## 13. 멘토에게 받을 결정

## 14. 완료 판정

다음을 모두 충족하면 멘토 상담 준비를 Freeze한다.

- [ ] 네 Flow의 중요 Claim이 Ledger에 기록됨
- [ ] D1·D2의 모든 주요 화살표가 Claim과 연결됨
- [ ] 실제 Network, DNS, Control, Deployment, Log Flow가 구분됨
- [ ] 완료로 표시한 항목에 Source 또는 Runtime Evidence가 있음
- [ ] 현재 활성과 과거 검증 이력이 분리됨
- [ ] 미검증·Optional·한계가 숨겨지지 않음
- [ ] 사용자가 핵심 여섯 묶음과 네 Flow를 자기 말로 설명할 수 있음
- [ ] 멘토가 답할 결정 질문이 고정됨
- [ ] Chat의 이해·표현 검토 결과가 반영됨
- [ ] Chat 반영 뒤 Codex 최종 P1·P2 검토를 통과함
- [ ] P1·P2가 0임
- [ ] 실시간 시연을 할 경우에만 Preflight가 통과함
