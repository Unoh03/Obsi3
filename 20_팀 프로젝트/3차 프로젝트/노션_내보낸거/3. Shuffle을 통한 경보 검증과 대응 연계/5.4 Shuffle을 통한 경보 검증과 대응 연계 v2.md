# 5.4 Shuffle을 통한 경보 검증과 대응 연계

> **Shuffle은 Wazuh Alert를 그대로 실행하지 않는다. Wazuh에서 정제한 Alert가 사전에 정의된 입력 계약을 통과한 경우에만 Rule별 고정 GitHub Workflow를 호출한다.**

## 5.4.1 Wazuh에서 Shuffle로 전달되는 정보

Wazuh Integration은 원문 Alert를 외부로 그대로 전송하지 않고, Rule별 허용 조건을 로컬에서 다시 검증한 뒤 대응에 필요한 최소 정보만 전달한다.

| Rule | Wazuh 로컬 검증 | Shuffle 전달 정보 |
|---|---|---|
| `100110` | Rule·Level·Source·Account·Region·Push Transport·IMDS 단계·실행 결과 | Alert ID, Event 시각, Event 해시, `take_id`, Pod 이름·UID, 허용된 Event 상태 |
| `100111` | CloudTrail의 Account·Region·Role·Bucket·Object·`GetObject`·HTTP `200`·반환 바이트 | Rule ID, Event 시각, Wazuh Alert ID, CloudTrail Event ID SHA-256, 원문 SHA-256 |

Credential, Cookie, 명령 원문과 응답, Account의 상세 자원명 및 CloudTrail 원문은 Shuffle Payload에 포함하지 않는다.

## 5.4.2 Shuffle의 Rule별 분기

Shuffle의 고정 Action은 인증 Webhook으로 Alert를 수신하고 다음 항목을 검증한다.

- 허용된 Rule ID
- Rule별 exact Schema와 필수 필드
- Event 시각의 신선도
- Event ID 및 원문 SHA-256 형식
- 사전에 지정한 GitHub Repository·Branch·Workflow
- Rule `100110`의 Pod 이름과 Kubernetes UID 형식

| 검증 결과 | 연결되는 대응 | 결과 |
|---|---|---|
| Rule `100110` 정상 입력 | `soc-contain-dvwa.yml` | UID가 검증된 침해 Pod 격리 요청 |
| Rule `100111` 정상 입력 | `soc-harden-dvwa.yml` | DVWA 방어 프로필 전환 요청 |
| 허용되지 않은 Rule·Schema·대상 | 없음 | GitHub Workflow 호출 전 거부 |

## 5.4.3 Rule 100110 — 침해 Pod 격리·보존

1. Shuffle이 검증된 `pod_name`, `pod_uid`와 Event 해시를 고정 GitHub Workflow로 전달한다.
2. Workflow가 `main`, `CAPITAL-ONE`, Rule `100110`, Pod 이름·UID 형식을 확인한다.
3. GitOps 값에는 해당 격리 요청만 기록하며 예상하지 못한 파일 변경이 있으면 중단한다.
4. Argo CD가 새 Git Revision을 EKS에 동기화한다.
5. Kubernetes 격리 Job이 실제 Pod UID, DVWA Label, ReplicaSet 및 Deployment 소유 관계를 다시 검증한다.
6. 검증된 Pod만 Deployment의 소유 관계에서 분리하고 `quarantined` Label과 NetworkPolicy를 적용해 보존한다.
7. Deployment는 정상 서비스를 위한 대체 DVWA Pod를 유지한다.

따라서 Alert가 임의의 Namespace나 Workload를 직접 격리할 수 없다. 대상 정보는 Alert에서 전달되지만, 고정된 DVWA 범위에서 실제 UID와 소유 관계가 일치하는 Pod만 조치한다.

## 5.4.4 Rule 100111 — 사전 승인된 방어 프로필 배포

1. Wazuh가 CloudTrail 원문을 로컬에서 검증하고 승인된 해시 필드만 Shuffle로 전송한다.
2. Shuffle이 Rule `100111`, Event 시각 및 해시 형식을 확인한다.
3. 고정된 `soc-harden-dvwa.yml`만 호출한다.
4. Workflow가 GitOps 설정의 `defaultSecurityLevel: low`를 `impossible`로 전환한다.
5. 예상하지 못한 Repository·Branch·파일·설정값이면 실행을 거부한다.
6. Git Commit이 `main`에 반영되면 Argo CD가 해당 Revision을 EKS에 배포한다.
7. 새 DVWA Pod와 Session에서 `security=impossible` 상태를 확인한다.

이 절에서는 대응의 **실행 경로**만 설명한다. DVWA의 `impossible` 기능을 선택한 이유와 운영환경 적용 한계는 5.5에서 다룬다.

## 5.4.5 자동 대응 안전장치와 증적

| 통제 | 적용 내용 |
|---|---|
| 입력 최소화 | 원문 Credential·Cookie·Command·응답을 외부로 전송하지 않음 |
| 대상 제한 | 고정 Repository·Branch·Workflow와 DVWA 범위만 허용 |
| 변경 제한 | Rule별 지정 GitOps 값 외의 Diff가 발생하면 중단 |
| 충돌 방지 | Workflow `concurrency`와 상태 기반 멱등 처리 적용 |
| 사후 추적 | Wazuh Alert ID·Event 해시·Workflow Run·Commit SHA·Argo Revision 기록 |
| 복구 | Reset Workflow로 격리 요청과 DVWA 방어 프로필을 기준선으로 복구 |

현재 구현은 범용 Event Dedupe 시스템이 아니다. 동일한 GitOps 상태에 대한 불필요한 변경을 피하고 서로 다른 활성 요청의 충돌을 거부하는 **상태 기반 멱등 처리와 동시 실행 제한**으로 설명하는 것이 정확하다.
