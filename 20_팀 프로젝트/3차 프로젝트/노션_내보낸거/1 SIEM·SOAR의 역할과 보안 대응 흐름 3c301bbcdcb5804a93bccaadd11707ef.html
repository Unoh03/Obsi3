SIEM·SOAR의 역할과 보안 대응 흐름

클라우드 환경에서는 애플리케이션, Kubernetes, AWS API, S3 등 여러 위치에서 보안 로그가 생성된다. 본 프로젝트는 Wazuh(SIEM)로 로그를 수집·분석하고, Shuffle(SOAR)로 검증된 경보를 안전한 대응 절차와 연결한다.

🔵 SIEM — Wazuh

Wazuh AWS 모듈은 보안 로그 S3의 ALB 로그와 CloudWatch Logs의 CloudTrail·WAF·DVWA·CloudFront 로그를 5분 주기로 Polling한다. DVWA 감사 로그는 별도로 Lambda·SQS·Local Bridge Push 경로를 통해 저지연 전달받는다.

Rule 100110과 100111, Timeline Dashboard를 통해 IMDS 접근 징후와 S3 객체 반환 사실을 분석한다.

🟣 SOAR — Shuffle

탐지된 경보가 대응 가능한 사건인지 검증하고, 사전 승인된 조치와 연결한다.

인증 Webhook, exact Schema·allowlist, Timestamp 및 eventID·원문 SHA-256 검증을 적용한다.

🟢 통제 계층 — GitHub Actions·Argo CD·EKS

Rule별 고정 조건과 안전 검증을 통과한 사건에 한해 제한된 격리와 DVWA 보안 수준 변경을 수행한다.

Rule 100110·100111 자동 대응은 Wazuh Integration, Shuffle Validator·Dispatcher, 고정 GitHub Workflow 및 Argo CD 자동 동기화로 연결되어 있다.

로그 원천 → Wazuh 탐지·분석 → Shuffle 검증 → GitHub Actions·Argo CD·EKS 통제 → 재검증·증적 보관

상세 설명

클라우드 환경에서는 애플리케이션 요청, Kubernetes Pod 동작, AWS API 호출, S3 객체 접근처럼 서로 다른 위치에서 보안 관련 기록이 생성된다.

개별 로그만으로는 공격 여부와 영향 범위를 판단하기 어렵기 때문에, 본 프로젝트는 SIEM을 통해 로그와 경보를 수집·분석하고, SOAR를 통해 검증된 경보를 안전한 대응 절차와 연결하는 구조를 구성한다.

SIEM은 여러 로그를 한곳에서 조회하고 상관분석하여 이상 행위를 탐지하는 역할을 수행한다.

본 환경에서 Wazuh AWS 모듈은 보안 로그 S3의 ALB 로그와 CloudWatch Logs의 CloudTrail·WAF·DVWA·CloudFront 로그를 5분 주기로 Polling한다. DVWA 감사 로그는 CloudWatch Logs에서 Lambda·SQS·Local Bridge를 거치는 Push 방식으로도 Wazuh에 저지연 전달된다. CloudTrail의 S3 사본은 장기 보관과 증적 재분석에 사용한다. Rule 100110은 IMDS 자격증명 엔드포인트 관련 실행 징후를 조기에 탐지하고, Rule 100111은 CloudTrail S3 Data Event를 통해 검증용 객체의 실제 바이트 반환 성공을 탐지한다. 두 Alert의 관계는 관제자가 Timeline Dashboard에서 시간과 이벤트 식별자를 비교하여 판단한다.

SOAR는 SIEM에서 생성된 경보를 즉시 차단하는 도구가 아니라, 대응 가능한 사건인지 검증하고 사전에 허용된 조치를 연결하는 역할을 수행한다.

본 프로젝트의 Shuffle 연계는 인증 Webhook, 입력 Schema, allowlist, Timestamp와 SHA-256 무결성 검증을 통과한 Rule 100110·100111만 고정된 대응 Workflow로 전달한다. Rule 100110은 고정 DVWA Workload 격리 Workflow를, Rule 100111은 GitOps 기반 low → impossible Workflow를 실행한다.

구분역할본 프로젝트의 구성 요소
로그 원천보안 이벤트와 실행 흔적 생성DVWA, Kubernetes Pod, WAF, CloudFront, ALB, CloudTrail
SIEM로그 수집, 탐지 규칙 적용, Alert 생성, Timeline 조사 지원Wazuh
SOAR입력 계약·무결성 검증, 승인된 대응 절차 연계Shuffle
통제 계층격리 설정과 DVWA 보안 수준 변경 및 배포GitHub Actions·Argo CD·EKS·NetworkPolicy·DVWA 설정

전체 흐름은 다음과 같다.

로그 원천 → Wazuh(SIEM) 수집·탐지·분석 → Shuffle(SOAR) 검증·대응 요청 → GitHub Actions·Argo CD·EKS 통제 → 재검증 및 증적 보관

Wazuh의 Alert는 각기 다른 보안 사실을 알리는 조사 근거이다. Rule 100110은 IMDS 관련 실행 징후를, Rule 100111은 S3 객체의 실제 바이트 반환 성공을 독립적으로 탐지한다.

Rule 100110과 100111은 각각 Wazuh에서 Shuffle로 전달되어 서로 다른 고정 대응 절차를 실행한다. 관제자는 Timeline Dashboard에서 두 Alert와 원본 로그의 시간·이벤트 식별자·Role·Object를 비교하여 동일한 공격 흐름인지 사후 분석한다.

본 프로젝트의 현재 범위에서 Wazuh는 Rule 100110·100111을 독립적으로 탐지하고, Shuffle은 입력 계약을 검증해 각 Rule에 고정된 GitHub Workflow만 호출한다. GitHub Actions가 제한된 Git 설정을 변경하면 Argo CD가 해당 Revision을 EKS에 자동 반영한다. 관제자의 Timeline 분석은 이 자동 대응과 별도로 두 Alert의 인과관계를 설명하는 조사 절차이다.

자동 대응을 구현하는 핵심 코드

observability/wazuh/integrations/custom-shuffle-soc — Wazuh Alert를 Rule allowlist로 제한하고 승인 필드만 Shuffle에 전달한다.

if rule_id == EXPECTED_WORKLOAD_RULE_ID:
    sanitized = build_sanitized_workload_alert(alert)
elif rule_id == EXPECTED_CONFIRMED_S3_RULE_ID:
    sanitized = build_sanitized_confirmed_s3_alert(alert)
else:
    raise ContractError("rule.id is not allowlisted")

send_to_shuffle(sanitized, webhook_url, header_key)

observability/shuffle/apps/aws-topology-soc-rule100110-auto-containment/1.0.1/src/autocontainment.py — Rule별 입력 계약을 검증하고 호출 가능한 GitHub Workflow를 고정한다.

if rule_id == "100110":
    inputs = validate_rule_100110_payload(parsed, now=now)
    dispatch_url = DISPATCH_URL

    inputs = validate_rule_100111_payload(parsed, now=now)
    dispatch_url = HARDEN_DISPATCH_URL
else:
    raise ContractError("rule_id")
