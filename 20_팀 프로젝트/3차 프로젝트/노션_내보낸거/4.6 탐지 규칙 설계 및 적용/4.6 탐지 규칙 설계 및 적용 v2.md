# 4.6 탐지 규칙 설계 및 적용 v2

## 1. 탐지 체계 설계 원칙

Capital One 공격 시나리오는 하나의 행위가 아니라 다음과 같이 서로 다른 단계의 행위와 증거로 구성된다.

1. DVWA의 Command Injection 취약점을 통해 EC2 IMDS의 Role 및 Credential endpoint에 접근한다.
2. 반환된 임시 자격 증명을 이용해 보호된 S3 Object를 조회한다.
3. DVWA 서버 Audit Event와 AWS CloudTrail Data Event가 서로 다른 수집 경로를 통해 Wazuh에 도착한다.

따라서 모든 행위를 하나의 Rule로 뭉뚱그리지 않고, DVWA에서 IMDS Credential endpoint의 출력 반환을 탐지하는 Rule `100110`과 CloudTrail에서 보호된 S3 Object의 실제 바이트 반환을 탐지하는 Rule `100111`로 분리했다.

두 Rule의 분리는 **공격을 진행 중에 반드시 차단했다는 의미가 아니다.** 실제 시연에서는 공격 스크립트가 끝까지 실행된 뒤 Rule `100110` Count가 증가했다. Rule `100110`의 저지연성은 공격 스크립트 완료 전 차단을 보장한다는 뜻이 아니라, 5분 주기의 수집 경로를 사용하는 Rule `100111`보다 먼저 경보와 대응을 시작할 수 있다는 의미다.

즉, Rule `100110`은 공격 흐름상 앞선 단계의 증거를 저지연 경로로 관제에 제공하고, Rule `100111`은 이후 CloudTrail에서 실제 S3 데이터 반환을 독립적으로 확인한다. 두 Rule을 분리함으로써 관제자는 **IMDS Credential endpoint 접근**과 **해당 권한을 이용한 S3 데이터 접근**을 구분해 조사할 수 있다.

## 2. Rule 100110 — IMDS Credential endpoint 출력 반환 탐지

Rule `100110`의 입력은 DVWA 서버가 Command 실행 결과를 검사해 생성한 Audit Event다. 클라이언트가 임의로 지정한 문자열이 아니라 서버 측 분류값을 사용한다.

주요 조건은 다음과 같다.

| 필드 | 조건 | 의미 |
|---|---|---|
| `transport` | `push` | CloudWatch Logs·Lambda·SQS·Local Bridge로 구성한 저지연 전달 경로를 통해 수집됨 |
| `source` | `dvwa` | DVWA 서버 Audit Event |
| `payload.event_type` | `command.execution` | Command 실행 Event |
| `payload.result` | `succeeded` | 서버 측 Command 실행 처리 성공 |
| `payload.route` | `/vulnerabilities/exec/` | DVWA Command Injection 실습 경로 |
| `payload.context.resource` | `ec2_imds` | 명령 대상이 EC2 IMDS임 |
| `payload.context.security_level` | `low` | 취약한 DVWA 보안 수준에서 발생함 |
| `payload.context.stage` | `imds_credential_fetch` | Role 목록 조회가 아니라 특정 Role의 Credential endpoint를 조회함 |
| `payload.context.status` | `output_returned` | 대상 명령에서 출력이 반환됨 |

`imds_role_discovery`는 IMDS에서 Role 이름을 확인한 단계이므로 Rule `100110`의 조건에 포함되지 않는다. 특정 Role의 Credential endpoint를 조회한 `imds_credential_fetch` 단계에서 출력까지 반환되어야 Rule `100110`이 발생한다.

Rule Description은 다음과 같다.

> AWS-SOC: DVWA command returned output from the EC2 IMDS credential endpoint.

이 Rule이 직접 증명하는 범위는 **DVWA가 IMDS Credential endpoint를 대상으로 명령을 실행했고 출력이 반환됐다는 사실**이다. Credential 원문이 실제로 외부에 탈취됐다는 사실이나, 뒤이은 S3 접근을 공격 도중 차단했다는 사실까지 Rule `100110` 하나만으로 증명하지는 않는다.

## 3. Rule 100111 — 보호된 S3 Object 바이트 반환 탐지

Rule `100111`의 입력은 CloudTrail의 S3 Data Event다. 다음 조건을 모두 만족해야 발생한다.

| 구분 | 조건 |
|---|---|
| Event Source | `s3.amazonaws.com` |
| Event Name | `GetObject` |
| Event Category | `Data` |
| Account·Region | 승인된 실습 Account와 `ap-northeast-2` |
| 호출 주체 | `aws-topology-primary-karpenter-node` Assumed Role |
| 대상 | 실습용 고정 Bucket 패턴과 `validation/capital-one-demo.csv` |
| 응답 | `httpStatusCode=200` |
| 데이터 반환 | `bytesTransferredOut>0` |

Rule Description은 다음과 같다.

> CAPITAL-ONE: Protected S3 object bytes were returned through the compromised node role.

이 Rule은 고정된 S3 Object의 실제 바이트가 해당 Node Role을 통해 반환됐다는 사실을 직접 탐지한다. 다만 Rule `100110`과 Rule `100111`을 하나의 사건으로 자동 상관분석하지는 않는다. 관제자가 Incident Timeline에서 발생 시각과 Event 식별자를 비교해 동일한 공격 흐름인지 조사한다.

## 4. 왜 두 개의 Rule로 분리했는가

| 구분 | Rule 100110 | Rule 100111 |
|---|---|---|
| 공격 단계 | IMDS Credential endpoint 조회 | 보호된 S3 Object 조회 |
| 증거 출처 | DVWA 서버 Audit Event | CloudTrail S3 Data Event |
| 수집 특성 | 저지연 전달 경로 | 5분 주기 수집 경로 |
| 탐지 의미 | Credential endpoint 대상 명령에서 출력이 반환됐음을 먼저 관제에 알림 | 보호된 S3 Object의 실제 바이트 반환을 확인 |
| 시간 해석 | 공격 스크립트 종료 전에 차단했다는 의미가 아니라, Rule `100111`보다 먼저 관제·대응을 시작할 수 있다는 의미 | CloudTrail Event가 수집된 뒤 실제 S3 데이터 접근을 독립적으로 확인 |
| 자동 대응 | 경보에 포함된 Pod 정보를 검증한 뒤 침해 Pod 격리·보존 | GitOps를 통해 DVWA 보안 수준을 `low`에서 `impossible`로 변경 |

두 Rule은 서로 다른 계층에서 생성된 독립 증거다. Rule `100110`은 저지연 경로로 먼저 도착해 후속 공격이나 반복 실행에 대한 대응을 시작하게 하고, Rule `100111`은 정기 수집된 CloudTrail Event를 통해 실제 S3 데이터 반환을 확인한다.

## 5. Rule 100110 자동 격리의 실제 경계

Rule `100110`이 발생하면 Wazuh Integration은 원문 Alert를 그대로 외부로 전달하지 않는다. 고정 Account·Region·Rule·Event 조건을 로컬에서 검증하고, 승인된 필드와 해시만 포함한 Sanitized Payload를 Shuffle로 전송한다.

Sanitized Payload에는 `take_id`, `pod_name`, `pod_uid`가 포함된다. 따라서 격리 대상이 Rule Payload와 무관한 정적 Pod로 고정되는 구조는 아니다. 대신 다음과 같은 제한을 연속적으로 적용한다.

1. Wazuh Integration이 Rule `100110`, DVWA Source, Push Transport, 고정 Account·Region 및 Event 조건을 검증한다.
2. Shuffle이 정해진 GitHub Repository와 격리 Workflow만 호출한다.
3. GitHub Workflow가 `main`, `CAPITAL-ONE`, Rule `100110`, Pod 이름 및 UID 형식을 검증한다.
4. Kubernetes 격리 Job이 실제 Pod UID, DVWA Label, ReplicaSet 및 Deployment 소유 관계를 다시 확인한다.
5. 검증을 통과한 Pod만 `quarantined` 상태로 표시하고 기존 Deployment의 소유 관계에서 분리해 보존한다.
6. 격리 Pod에는 별도 NetworkPolicy를 적용하고, 정상 서비스를 담당할 대체 DVWA Pod는 Deployment가 유지한다.

즉, **대상 정보는 Alert에서 전달되지만 임의의 Namespace나 Workload를 그대로 신뢰하지 않고, 고정된 DVWA 범위 안에서 UID와 소유 관계가 일치하는 Pod만 격리한다.**

## 6. Rule 100111 자동 강화의 실제 경계

Rule `100111`이 발생하면 Wazuh가 CloudTrail 원문을 로컬에서 검증한다. 외부로는 Rule ID, 발생 시각, Wazuh Alert ID, CloudTrail Event ID의 SHA-256, 원문 SHA-256 등 승인된 최소 정보만 전송한다.

Shuffle은 고정된 GitHub Workflow를 호출하고, Workflow는 DVWA의 기본 보안 수준을 `low`에서 `impossible`로 변경한다. 변경 사항이 `main`에 반영되면 Argo CD가 해당 Git Revision을 EKS에 동기화하고 새 DVWA Pod와 Session에서 `security=impossible` 상태를 제공한다.

이 대응은 S3 접근 자체를 되돌리는 복구가 아니라, 확인된 공격 경로가 같은 DVWA 취약점을 통해 다시 실행되지 않도록 애플리케이션 보안 수준을 강화하는 조치다.

## 7. 중복 Event와 멱등 처리

기존 문서의 “동일 Event의 실제 조치는 Dedupe 로직으로 정확히 1회만 실행된다”는 표현은 현재 구현보다 강하다.

현재 Workflow는 `concurrency`로 같은 종류의 상태 변경을 직렬화하고, 이미 같은 GitOps 상태가 반영된 경우 추가 변경 없이 종료한다. Rule `100110` 격리 Workflow는 다른 격리 요청이 활성화된 상태에서 새 대상이 들어오면 이를 거부한다. Rule `100111` 강화 Workflow도 이미 `impossible` 상태라면 같은 변경을 다시 Commit하지 않는다.

따라서 현재 구현은 **상태 기반 멱등 처리와 충돌 방지**로 설명하는 것이 정확하다. 모든 재수집 Event를 영구 저장소에서 비교해 정확히 한 번만 처리하는 범용 Event Dedupe 시스템으로 표현해서는 안 된다.

## 8. 성공 판정과 현재 증거의 구분

자동 대응의 성공 기준과 현재 확보한 실행 증거를 구분해 기록한다.

### 코드상 성공 기준

- Rule `100110`: 요청 Contract 검증, 대상 Pod UID·Label·Owner 검증, 격리 상태 및 소유 관계 분리 Read-back
- Rule `100111`: 고정 Workflow 실행, Git Commit 생성 또는 기존 상태 확인, Argo CD의 해당 Revision 동기화, DVWA `impossible` 상태 반영

### 시연에서 확인할 실행 증거

- Wazuh Dashboard의 Rule `100110`, `100111` Count 및 근거 Event
- Shuffle Workflow 실행 결과
- GitHub Actions Run과 Commit SHA
- Argo CD Revision 및 동기화 결과
- Rule `100110` 대응 후 격리·보존된 Pod와 정상 대체 Pod
- Rule `100111` 대응 후 새 Session의 DVWA `security=impossible`

Egress 차단, Health 경로 유지, 다른 Namespace 및 비대상 Workload에 대한 영향 없음은 중요한 검증 항목이지만, 실제 실행 증거를 확보한 범위까지만 결과로 표현한다. 코드에 존재하는 검증 기준과 촬영에서 확인한 Runtime 결과를 같은 수준의 완료 증거로 합치지 않는다.
