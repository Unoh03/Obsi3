# 5.0 보안관제 구현 결과

> **결론적으로 본 프로젝트는 AWS·EKS에서 발생한 보안 로그를 Wazuh로 수집·탐지하고, 검증된 Alert만 Shuffle과 GitOps를 통해 실제 자동 대응으로 연결하였다. Rule `100110` 발생 후 침해 Pod를 격리·보존하면서 정상 대체 Pod로 서비스를 유지했고, Rule `100111` 발생 후 DVWA 보안 수준을 `low`에서 `impossible`로 변경하였다.**

## 구현한 관제 흐름

**보안 로그 수집 → Wazuh Rule 탐지 → Shuffle 입력 검증 → GitHub Actions 대응 → Argo CD 배포 → Runtime 결과 확인·복구**

| 탐지 | 확인한 보안 사실 | 자동 대응 | Runtime 결과 |
|---|---|---|---|
| Rule `100110` | DVWA의 IMDS Credential endpoint 대상 명령에서 출력 반환 | Pod 이름·UID·소유 관계를 검증한 뒤 침해 Pod 격리·보존 | 격리 Pod와 정상 대체 Pod 확인 |
| Rule `100111` | 보호 S3 Object의 `GetObject`가 성공하고 실제 바이트 반환 | 고정 Workflow로 DVWA `low → impossible` 변경 | GitHub Actions 성공 및 Argo CD 배포 확인 |

## 핵심 성과

- **수집:** CloudWatch Logs와 보안 로그 S3를 5분 주기로 수집하고, DVWA Audit Event에는 별도의 저지연 전달 경로를 구성하였다.
- **탐지:** IMDS Credential endpoint 접근과 실제 S3 데이터 반환을 서로 다른 Rule과 독립 증거로 구분하였다.
- **검증:** Shuffle이 Rule·Schema·Timestamp·해시·대응 대상을 검증한 뒤 허용된 Workflow만 호출하도록 제한하였다.
- **대응:** 침해 Pod 격리와 `low → impossible` 변경을 Git Commit·Workflow Run·Argo CD Revision으로 추적 가능하게 구현하였다.
- **복구:** Reset Workflow를 통해 격리 상태와 DVWA 보안 수준을 촬영·재검증 가능한 기준선으로 복구하였다.

## 결과 해석

Rule `100110`은 공격 스크립트가 끝나기 전에 차단했다는 뜻이 아니라, 5분 주기로 수집되는 Rule `100111`보다 먼저 관제와 대응을 시작하게 하는 저지연 경보다. Rule `100111`은 이후 CloudTrail에서 보호 S3 Object의 실제 바이트 반환을 확인한다. 두 Alert의 관계는 관제자가 Timeline의 시각과 식별자를 비교해 동일 사건인지 조사한다.

본 구현은 임의의 공격과 Workload에 대응하는 범용 SOC가 아니라, 고정된 Capital One 시나리오에서 **수집·탐지·검증·자동 대응·배포·복구가 실제로 연결됨을 검증한 관제 체계**다.
