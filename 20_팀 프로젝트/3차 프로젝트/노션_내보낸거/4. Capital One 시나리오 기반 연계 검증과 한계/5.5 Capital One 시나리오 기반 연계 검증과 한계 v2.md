# 5.5 Capital One 시나리오 기반 연계 검증과 한계

> **Capital One 시나리오를 통해 웹 애플리케이션 공격, IMDS 접근 탐지, 침해 Pod 격리, S3 데이터 반환 확인, 사전 승인된 방어 프로필 배포와 기준선 복구까지의 관제 흐름을 검증하였다. 다만 `low → impossible`은 우리가 작성한 소스 패치가 아니라 자동 대응 경로를 검증하기 위해 선택한 제한적 완화 조치다.**

## 5.5.1 DVWA와 검증 시나리오

DVWA(Damn Vulnerable Web Application)는 취약한 코드와 보안 조치가 적용된 코드를 비교·실습하도록 제작된 교육용 웹 애플리케이션이다. 본 프로젝트는 개인정보나 운영 데이터 대신 고정된 검증용 S3 Object를 사용해 다음 흐름을 재현하였다.

**DVWA Command Injection → EC2 IMDS Node Role Credential endpoint 접근 → 검증용 S3 Object `GetObject` → Wazuh 탐지 → Shuffle 검증 → GitOps 자동 대응**

임시 자격증명은 공격 검증 과정에서만 사용하며 Wazuh Push Payload, Shuffle Payload 및 보고서 증적에는 저장하지 않는다.

## 5.5.2 시나리오 검증 결과

| 단계 | 확인 내용 | 결과 |
|---|---|---|
| DVWA 공격 | `/vulnerabilities/exec/`에서 IMDS Credential endpoint 대상 명령 실행 | Audit Event 생성 확인 |
| Rule `100110` | 명령의 출력 반환 Event 탐지 | Runtime Alert 확인 |
| 침해 Pod 대응 | Pod 이름·UID·소유 관계 검증 후 격리·보존 | 격리 Pod와 정상 대체 Pod 확인 기록 |
| Rule `100111` | CloudTrail에서 고정 S3 Object의 `GetObject`, HTTP `200`, 실제 바이트 반환 탐지 | Runtime Alert 확인 |
| 방어 프로필 배포 | 고정 Workflow로 DVWA `low → impossible` 전환 | Run `32637113392` 성공 기록 |
| Argo CD 반영 | Git Commit Revision을 EKS에 자동 배포 | `Synced`, `Healthy`, `impossible` 확인 |
| 기준선 복구 | 격리 상태 정리 및 DVWA `low` 복구 | Reset Run `32643206492` 성공 기록 |

Rule `100110`과 Rule `100111`은 서로 독립적으로 발생한다. 두 Alert가 같은 사건에 속하는지는 관제자가 Timeline의 발생 시각, `take_id`, Pod 정보, IAM Role 및 S3 Object를 비교해 조사한다.

## 5.5.3 `low → impossible`을 선택한 이유

DVWA의 `low`와 `impossible`은 단순한 화면 표시가 아니라 서로 다른 요청 처리 코드를 사용한다.

- Command Injection의 `low` 구현은 사용자 입력을 직접 `shell_exec()`에 연결한다.
- `impossible` 구현은 Anti-CSRF Token을 검사하고 입력을 IPv4 형식으로 Allowlist 검증한 뒤에만 제한된 `ping` 명령을 실행한다.
- DVWA는 `impossible`을 취약한 코드와 방어 코드의 비교를 위한 보안 수준으로 제공한다.

따라서 `low → impossible` 전환은 실제 공격 경로의 동작을 변경한다. 그러나 방어 코드는 DVWA에 이미 존재하며, 본 프로젝트가 새로 개발한 Source Patch는 아니다.

본 프로젝트가 이 조치를 선택한 이유는 SOAR가 Alert를 근거로 임의의 소스코드를 생성·수정하도록 만드는 대신, 다음 조건을 만족하는 사전 승인 Playbook을 사용하기 위해서다.

- 변경 대상과 결과가 고정돼 있음
- Git Diff와 배포 Revision을 검증할 수 있음
- 자동 실행의 영향 범위가 제한됨
- 동일한 실험을 반복할 수 있음
- Reset Workflow로 기준선 복구가 가능함

즉, “프로젝트의 핵심이 아니어서 기존 기능을 대충 사용했다”가 아니라, **탐지에서 GitOps 배포까지의 자동 대응 경로를 안전하고 재현 가능하게 검증하기 위해 고정·가역적인 완화 조치를 의도적으로 선택했다.**

## 5.5.4 운영환경에서의 대응과 차이

실제 운영환경에서는 보안 수준 설정을 전환하는 것으로 대응이 끝나지 않는다. 일반적으로 다음과 같은 후속 조치가 필요하다.

- 취약한 소스코드 수정과 Code Review
- 검증된 새 Container Image Build·배포
- 탈취된 IAM Session 및 임시 자격증명 무효화
- Node Role 권한 축소
- 침해 Node 격리·교체
- S3 Bucket Policy 또는 IAM Policy를 이용한 접근 차단
- 재공격과 정상 기능에 대한 회귀 검증

따라서 본 프로젝트의 `low → impossible` 전환은 운영환경의 Source Patch를 대신했다고 주장하는 조치가 아니다. **사전에 검토된 보안 설정 또는 Patch Image를 배포하는 운영 Playbook을 교육용 환경에서 축소해 표현한 것**이다.

## 5.5.5 한계와 향후 개선 방향

- Rule `100110`은 공격 스크립트 완료 전에 차단했음을 보장하지 않는다.
- Pod 격리는 이미 외부로 유출된 Node Role 자격증명을 폐기하지 못한다.
- 현재 시나리오는 EKS Pod Identity가 아니라 EC2 IMDS Node Role 접근을 대상으로 한다.
- Rule `100110`과 Rule `100111`의 관계는 관제자가 조사하며 자동 상관분석하지 않는다.
- 고정된 Capital One 실습 시나리오에 최적화돼 있어 범용 Workload 대응 플랫폼은 아니다.
- MTTD·MTTR과 반복 실험에 따른 통계적 탐지 성능은 측정하지 않았다.

향후에는 EKS Pod Identity와 Workload 전용 최소권한 Role, 침해 IAM Session 무효화, Node 격리, Patch Image 자동 배포, Rule 간 상관분석 및 반복 실험 기반 MTTD·MTTR 측정을 추가할 수 있다.
