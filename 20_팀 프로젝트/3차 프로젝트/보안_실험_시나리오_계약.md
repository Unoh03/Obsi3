# 보안 관측 검증 후보 시나리오

> [!important] 현재 역할
> 아래 두 항목은 **우리 조가 확정한 공격·실습 프로젝트가 아니다.** 현재 로그 수집·Query·Evidence Pipeline이 서로 다른 계층에서도 작동하는지 확인하기 위해 이 작업에서 제안한 관측 검증 후보다. 팀·멘토 결정에 따라 교체하거나 제외할 수 있으며, 그전에는 본편 시나리오나 프로젝트 확정안으로 표현하지 않는다.

## 1. 검증 후보

| ID | 계층 | 대표 질문 | 현재 상태 |
|---|---|---|---|
| WEB-01 | Edge·Application | 반복 로그인 실패를 어디서 관찰하고, 제한 조치 뒤 같은 요청이 어디서 차단되는가 | 20회×3단계 Runtime 완료. Application 20건씩, WAF `COUNT` 2건, `BLOCK` 0건으로 차단 미검증 |
| IAM-01 | Kubernetes·AWS IAM·S3 | 특정 ServiceAccount에 잠재된 S3 권한을 Pod가 사용할 수 있으며, 최소 권한 조치 뒤 같은 접근이 실패하는가 | 허용·조치·동일 조건 거부와 S3 Data Event 검증 완료 |

두 후보를 둔 이유는 같은 웹 공격의 변형만으로 관측 구조를 시험하지 않기 위해서다. WEB-01은 사용자 요청과 애플리케이션 인증 Event를, IAM-01은 Pod 내부 실행을 전제로 한 AWS 권한 오용을 다룬다. 이 구분 자체가 팀의 공격 주제 선정을 의미하지는 않는다.

## 2. 후보 승인 후 적용할 공통 실행 규칙

```text
정상 Baseline
→ 조치 전 행위
→ 차단·통과 지점 확인
→ 관련 로그 수집과 Query
→ 원인 판정
→ 최소 조치
→ 같은 입력·조건으로 재실행
→ 결과 차이 확인
→ Evidence Bundle 생성
```

- 사용자 소유의 격리된 BANK DVWA와 AWS Account만 대상으로 한다.
- 실험 ID와 UTC 시작·종료 시각을 먼저 고정한다.
- 실제 Password·Cookie·Session·Authorization·AWS Credential은 명령, 로그, Screenshot, Vault에 남기지 않는다.
- 조치 전·후에는 같은 Source, 요청 수, 간격, 경로, Manifest와 명령을 사용한다. 달라진 변수를 Manifest와 Evidence Manifest에 기록한다.
- 필수 로그가 누락되면 공격 성공 여부와 관계없이 해당 시나리오는 완료가 아니다.
- WAF Block 전환, 공격·Misconfiguration 실행, S3 Data Event 추가 Apply는 사용자 승인 Gate다.

## 3. WEB-01 — 반복 로그인 실패의 탐지와 제한

### 3.1 보호 자산과 가설

- 보호 자산: BANK 계정 인증, 로그인 Endpoint 가용성, 인증 실패 Audit Trail
- 정상 Baseline: 통제된 테스트 계정의 정상 로그인 1회와 의도적 실패 1회
- 조치 전 가설: 현재 WAF는 AWS Managed Common Rule을 `COUNT`로 관찰할 뿐 로그인 실패 횟수를 제한하지 않는다. 반복 실패 요청은 Application까지 도달하고 `auth.login.failed` Event가 누적될 가능성이 높다.
- 조치 후 가설: 로그인 경로에 한정한 Rate-based WAF Rule 또는 Application 인증 제한을 적용하면 같은 입력이 정해진 경계에서 제한된다.

현재 Terraform에는 `/login.php` POST만 집계하는 Rate-based Rule이 있으며 기본값은 `disabled`다. 승인된 실험에서만 같은 Rule Instance를 `count` 또는 `block`으로 전환한다. AWS WAF Rate 제한은 정밀한 요청 횟수 제한이 아니라 근사치이며, 완화 시작은 보통 30~50초 지연되고 더 길어질 수도 있다.

### 3.2 통제된 행위

1. 테스트 계정과 존재하지 않는 비밀번호를 사용한다. 실제 비밀번호 값은 Evidence에 저장하지 않는다.
2. 정상 Baseline과 조치 전·후에 동일한 요청 수와 간격을 사용한다.
3. 서비스 장애를 만들지 않는 낮은 요청량으로 제한한다.
4. CloudFront 공개 Endpoint만 사용하며 ALB 직접 접근이나 외부 대상은 공격하지 않는다.
5. `count`·`block`은 Web ACL 변경 뒤 기본 90초를 기다리고, 승인된 요청을 최소 50초 동안 보낸다. 다음 재검증 제안은 단계별 60회·1초 간격이며 실행 전 다시 승인받는다.

### 3.3 필요한 증거

| 계층 | 확인할 사실 | Source·Query |
|---|---|---|
| CloudFront | Viewer 요청이 Edge에 도착했는가 | Standard Access Log, `03_cloudfront_request_trace.sql` |
| WAF | Rule Match와 최종 `COUNT`·`BLOCK` Action은 무엇인가 | WAF Log, `02_waf_count_matches.cwli`, `06_waf_login_rate_limit.cwli` |
| ALB | Edge를 통과한 요청과 Target 응답은 무엇인가 | ALB Access Log, `01_alb_4xx_5xx_by_source.sql`, `04_alb_trace_id_correlation.sql` |
| BANK Application | 실패 Event가 실제 인증 코드까지 도달했는가 | `auth.login.failed`, `01_repeated_login_failures.cwli` |

정확한 Join은 ALB `trace_id`와 BANK `request_id`를 우선 사용한다. CloudFront·WAF와의 연결은 Runtime에서 공통 Request ID가 확인되기 전까지 실험 시간, Source IP, Method, Path를 이용한 상관관계로 표시한다.

최소 조기 경보 Source는 Primary BANK Log Group의 `data.event_type="auth.login.failed"`를 건당 1로 변환하고, 5분 합계가 5건 이상이면 SNS Topic으로 상태 변화를 전달한다. Source IP별 판정은 기존 Logs Insights Query가 담당하며 Metric에 IP Dimension을 만들지 않는다. 이는 고카디널리티 비용을 피하는 대신 여러 사용자의 실패가 합산될 수 있으므로, Alarm은 공격 확정이 아니라 조사 시작 신호다. `2026-08-02` Foundation Apply로 세 리소스를 생성했고 AWS API에서 Filter·5분/5건 Alarm·SNS Action을 확인했다. 최신 Runtime에서는 로그인 실패로 `OK → ALARM`, 이후 Data 감소로 `ALARM → OK`를 확인했다. SNS Subscription은 0건이므로 실제 수신자 전달은 미검증이다.

### 3.4 Runtime 결과

- `before`, `count`, `block`에서 로그인 실패를 각각 20회 실행했고 BANK Audit Log는 각 단계 20건을 기록했다.
- 세 단계의 Client 응답은 모두 HTTP 200이었다.
- `count`는 마지막 2건만 `bank-login-rate`에 Match했고, `block`은 WAF Match 0건·HTTP 403 0건이었다.
- `count`·`block`은 Web ACL 변경 후 90초를 기다리고 약 57초 동안 실행했다. 이전의 짧은 실행시간만으로 현재 결과를 설명할 수 없다.
- 현재 판정은 **관측 성공·차단 미검증**이다. 실험 뒤 WAF Mode는 기본값 `disabled`로 복구했다.

### 3.5 판정 기준

조치 전 통과:

- 동일 Source의 반복 요청이 CloudFront·ALB를 거쳐 Application에 도착한다.
- BANK Log에 `auth.login.failed`가 요청 수와 설명 가능한 범위로 증가한다.
- 현재 WAF가 Match하지 않거나 `COUNT`만 했음을 구분할 수 있다.

조치 후 제한:

- 동일 입력이 선택한 통제에서 제한된다.
- WAF 조치라면 `BLOCK` Event가 발생하고, 제한 이후 요청은 ALB·Application Event로 이어지지 않는다.
- Application 조치라면 WAF·ALB 도달 뒤 Application에서 제한 Event와 응답을 확인한다.

### 3.6 최소 조치와 재검증

- 우선 조치 후보: `/login.php`에만 적용하는 낮은 범위의 Rate-based WAF Rule을 `COUNT`로 검증한 뒤 별도 승인으로 `BLOCK` 전환
- 보완 후보: Application의 계정·IP 기반 지연 또는 잠금. NAT 공유와 계정 잠금 악용 위험을 별도로 평가
- 재검증: 동일한 테스트 계정, Source, 요청 수, 간격, URL을 사용
- 판정 경계: Threshold를 넘었다는 사실만으로 즉시 차단을 기대하지 않는다. WAF Log·Managed Key·후단 ALB·Application Event로 실제 제한 시작을 확인한다.

### 3.7 중단·복구

- 예상보다 넓은 경로가 차단되거나 정상 로그인에 영향이 생기면 즉시 실험을 중단한다.
- WAF 변경은 Terraform Diff와 Rule 단위 Rollback 경로를 준비한 뒤 수행한다.
- 과도한 요청, 실제 계정 대입, 외부 계정·서비스 대상 Credential 공격은 금지한다.

## 4. IAM-01 — EKS Pod Identity S3 권한 오용

### 4.1 보호 자산과 실제 Source 경계

- 보호 자산: S3 테스트 Bucket의 `web/` Prefix, EKS Workload Identity, IAM Role
- Terraform은 승인된 IAM-01 조치 전 상태에서만 `dvwa/web-app` ServiceAccount용 EKS Pod Identity Association과 전용 Role·Policy를 생성할 수 있다.
- 조치 전 연결 Role은 Bucket 조회와 `web/*`의 Get·Put·Delete를 허용했다.
- 현재 BANK Deployment는 `web-app`을 사용하지 않고, Application 코드에서도 S3 사용 경로가 확인되지 않았다.

따라서 조치 전 상태는 **Dormant Association**이었고 실제 BANK 업무 요구가 확인되지 않았다. 2026-08-02 검증 뒤 Association·Role·Policy를 제거하고 `enable_web_s3_pod_identity=false`를 기본값으로 유지한다.

### 4.2 정상 Baseline과 통제된 행위

정상 Baseline:

- 기본 ServiceAccount Pod에는 `web-app` Association 자격 증명이 주입되지 않는다.
- 전용 Canary 객체 외에는 읽거나 변경하지 않는다.

조치 전 행위:

1. `dvwa/web-app` ServiceAccount와 이를 사용하는 임시 AWS CLI 검증 Pod를 생성한다.
2. `kubectl exec`로 진입하고 `aws sts get-caller-identity`로 Role ARN만 확인한다.
3. `web/experiment-<id>/canary.txt`에 한정해 Put·Get·Delete를 실행한다.
4. 임시 Credential 값과 Token은 출력하지 않는다.

### 4.3 필요한 증거

| 단계 | 확인할 사실 | Source·Query |
|---|---|---|
| Pod 진입 | 누가 어느 Pod에서 `exec`를 수행했는가 | EKS Audit Log, `03_kubectl_exec_and_secret_access.cwli` |
| Role 제공 | 어떤 Association이 임시 Role을 제공했는가 | CloudTrail `AssumeRoleForPodIdentity`, `07_pod_identity_and_s3_activity.cwli` |
| 객체 작업 | 어떤 Role이 Canary에 Get·Put·Delete를 수행했는가 | S3 Data Event, 같은 Query의 Data Event 구간 |
| 구성 조치 | Association·IAM Policy가 어떻게 바뀌었는가 | Terraform Plan·Targeted Diff |
| 재검증 | 같은 요청이 거부됐는가 | CLI `AccessDenied`와 조치 후 CloudTrail |

Foundation CloudTrail에는 Management Event를 유지하면서 프로젝트 Primary·DR Bucket 이름 Prefix의 `GetObject`·`PutObject`·`DeleteObject`만 수집하는 Advanced Event Selector를 적용했다. 조치 전 Canary의 Put·Get·Delete와 관련 Data Event를 확인했고, 조치 후에는 Credential이 없어 S3 Object API Event가 0건이었다.

### 4.4 판정 기준

조치 전 성공:

- 임시 Pod가 예상한 Role ARN을 사용한다.
- Canary Put·Get·Delete 결과와 CloudTrail Data Event가 서로 일치한다.
- EKS `pods/exec`, Pod Identity Role 제공, S3 객체 작업을 시간·Role·Namespace·ServiceAccount·객체 경로로 연결한다.

조치 후 차단:

- BANK에 S3 기능이 불필요하면 Association과 Role을 제거하고 동일 Manifest·명령이 자격 증명 부재 또는 `AccessDenied`로 실패한다.
- S3 기능이 필요하면 필요한 Action·Prefix만 남기고 허용 범위 안과 밖을 각각 재검증한다.

### 4.5 최소 조치

1. 팀에 BANK의 S3 업무 요구가 있는지 확인한다.
2. 요구가 없으면 `primary_web_s3`·`dr_web_s3` Association과 전용 Role·Policy를 제거한다.
3. 요구가 있으면 ServiceAccount를 실제 Workload에 명시하고 Action·Bucket·Prefix를 최소화한다.
4. 필요하면 EKS Pod Identity Session Tag 또는 Association Policy로 추가 제한한다.

### 4.6 중단·복구

- Canary Prefix 밖의 객체가 보이거나 수정될 가능성이 있으면 즉시 중단한다.
- `DeleteBucket`, IAM 변경, 실제 사용자 Data 접근은 실험 명령에 포함하지 않는다.
- 임시 Pod·ServiceAccount·Canary는 Evidence 수집 후 삭제하되, 삭제도 승인된 실험 절차에 포함한다.
