> [!important] 문서의 역할

### 1.2 보조 근거

- Codex 평가: 원본 계획과 AWS 공식 문서를 대조한 평가
- Claude 평가: 사용자가 제공한 외부 AI 평가
- AWS·HashiCorp 공식 문서: IRSA, EKS Pod Identity, EKS Audit Log, CloudTrail S3 Data Event, RDS IAM 인증, Terraform S3 backend

AI 평가 간의 동의 자체는 증거로 사용하지 않는다. 원본 계획이나 공식 문서에서 확인된 주장만 유지한다.

## 2. 평가 기준

평가 우선순위는 다음과 같다.

1. 핵심 보안 질문이 명확한가
2. 공격 경로와 기술적 인과가 맞는가
3. 무엇을 증명하고 무엇을 증명하지 못하는지 구분하는가
4. 공격·증적·조치·동일 조건 재검증이 연결되는가
5. `퍼블릭 클라우드 기반 보안 운영`이라는 상위 주제에 맞는가
6. 결과물을 면접과 포트폴리오에서 설명할 수 있는가
7. 4주·3~4명 실행 가능성

실행 가능성은 평가에서 제외하지 않지만 가장 낮은 우선순위로 둔다.

## 3. 종합 결론

| 관점 | 순위 | 의미 |
|---|---|---|
| 문서와 검증 계획의 논리적 완성도 | 운호 > 우수현 > 타조 | 범위 제한, 증적, 조치·재검증 기준 |
| 원본 주제의 넓은 항목 커버리지 | 우수현 > 타조 ≈ 운호 | 다루는 보안 영역의 폭 |
| 클라우드 네이티브 보안 집중도 | 운호 > 타조 > 우수현 | AWS IAM·EKS·CloudTrail이 문제의 중심인지 |
| 실제 웹 취약점 재현의 구체성 | 우수현 > 타조 > 운호 | IDOR·SQLi·세션·자동화 공격의 구체성 |
| 공격 서사의 발표 흡인력 | 타조 > 우수현 > 운호 | 침투와 확산을 보여주는 이야기 구조 |
| 실행 리스크가 낮은 순서 | 운호 > 타조 > 우수현 | 참고용 최하위 지표 |

> [!warning] 자기평가 편향
> 운호안은 Codex가 앞선 대화에서 중요하다고 판단한 `범위 통제·증적·재검증·과장 방지` 기준에 맞춰 작성했다.
> 이후 Codex가 같은 기준으로 다시 평가했으므로 자기평가 편향 가능성이 있다.
> Claude도 원본 문서에서 같은 구조적 강점을 찾았지만, 두 AI의 동의만으로 객관적 우위를 확정하지 않는다.

## 4. 계획별 평가

### 4.1 운호안

#### 판정

**하나의 가설을 증거로 검증하는 계획으로는 세 안 중 가장 완결돼 있다.**

#### 강점

- 핵심 질문이 하나로 닫혀 있다.
- 최초 침투를 `kubectl exec`로 가정했다고 명시하여 실제 RCE 성공으로 과장하지 않는다.
- 공격 단계별 확인할 사실과 EKS Audit Log·CloudTrail 증적이 연결돼 있다.
- S3 `GetObject` Data Event를 별도로 활성화해야 한다는 조건을 알고 있다.
- IAM 최소 권한 조치 후 같은 조건으로 재검증한다.
- P0·P1, 주차별 통과 조건, 실패 시 EC2·ECS 축소안이 있다.
- Secret·개인정보·임시 자격증명을 증적에 남기지 않는 경계가 있다.

#### 약점과 보정

- 최초 침투를 가정하므로 실제 웹 모의해킹 능력을 직접 증명하지 않는다.
- 의도적으로 과도한 권한을 부여한 뒤 예상된 S3 접근을 확인하는 데 그치면 실험이 단순해질 수 있다.
- 현재 핵심 공격은 허가된 ServiceAccount가 과도한 Permissions Policy를 사용하는 경우다. 이때 Trust Policy의 `sub` 제한은 핵심 조치가 아니다.
- Trust Policy 오설정은 다른 namespace·ServiceAccount가 Role을 사용할 수 있는 별도 P1 시나리오로 분리하는 편이 정확하다.
- SDK credential cache 때문에 재실행마다 `AssumeRoleWithWebIdentity`가 새로 발생하지 않을 수 있다. 새 Pod 또는 새 SDK session으로 증적 조건을 고정해야 한다.
- AWS는 가능하면 EKS Pod Identity 사용을 권장한다. IRSA를 교체할 필요는 없지만, OIDC Trust Policy와 `AssumeRoleWithWebIdentity` 경로를 학습·검증하기 위해 IRSA를 선택했다는 이유가 필요하다.

#### 정체성

완전한 모의해킹보다 다음 표현이 정확하다.

> Assumed Breach 기반 EKS workload IAM 권한 통제 검증

### 4.2 타조안

#### 판정

**공격 서사와 레드·블루 협업 구조는 강하지만, 현재 문서는 공격 용어와 실제 기술 경로가 섞여 있다.**

#### 강점

- Pod 침해에서 AWS 리소스 접근까지 이어지는 발표 서사가 직관적이다.
- EKS, IAM, CloudTrail, EKS Audit Log를 하나의 흐름으로 연결한다.
- 모의해킹팀과 데이터분석팀의 역할 분리가 명확하다.
- Terraform 기반 재현 환경과 비용 관리·destroy를 고려한다.
- 원본 주제의 위협 탐지·조사 영역을 적극적으로 다룬다.

#### 약점과 보정

- 제목과 서두의 `컨테이너 탈출`은 실제 킬체인에 존재하지 않는다. 현재 내용은 host escape가 아니라 Pod 침해 후 workload credential 사용이다.
- IRSA는 Node가 아니라 Kubernetes ServiceAccount에 IAM Role을 연결한다. `일부 노드에 과도한 권한의 IRSA 연결` 표현은 수정해야 한다.
- 자기 Pod에 연결된 Role 사용을 `IRSA를 뚫었다`고 표현하면 안 된다. 핵심 문제는 workload에 과도한 AWS 권한을 준 최소 권한 위반이다.
- RDS API 권한과 실제 SQL 데이터 접근은 다르다. 데이터 접근을 주장하려면 RDS IAM DB 인증 활성화와 DB 사용자 매핑 등 별도 조건이 필요하다.
- 공격과 로그 분석은 있지만 최소 권한 조치와 동일 공격 재검증이 빠져 있다.
- `scikit-learn 이상탐지`, QuickSight, MTTD는 정상 데이터, 탐지 규칙, 경보 발생 시각이 정의되지 않아 현재는 과장 가능성이 있다.
- 새 Terraform 구성에서 DynamoDB state lock을 채택할 이유를 재검토해야 한다. 현재 S3 backend는 `use_lockfile`을 지원하고 DynamoDB locking은 deprecated 상태다.

#### 정체성

`컨테이너 탈출`을 제거하고 조치·재검증을 추가하면 다음과 같이 정리할 수 있다.

> 침해된 EKS Pod의 workload IAM 권한 오용 및 로그 기반 위협 탐지

### 4.3 우수현안

#### 판정

**웹 취약점·로그 분석·재검증 흐름은 가장 풍부하지만, 여러 개의 독립 프로젝트가 한 문서에 결합돼 있다.**

#### 강점

- IDOR, Rate Limit 미비, 세션 관리, 제한적 SQL Injection의 테스트 조건이 구체적이다.
- WAF·Web·Application·DB 로그와 조치 후 결과가 연결된다.
- 공통 로그 스키마와 민감정보 제외 기준이 구체적이다.
- 서버·방화벽·컨테이너·Kubernetes 보안까지 폭넓게 다룬다.
- 세 계획 중 웹 취약점과 통합 보안 운영 흐름의 설명력이 가장 높다.

#### 약점과 보정

- 온프레미스/AWS 비교, 자체 웹앱, 웹 모의해킹, 서버 진단, WAF, SIEM식 로그 정규화, Kubernetes 보안이 동시에 존재하여 핵심 질문이 분산된다.
- 양쪽 환경을 Kubernetes로 운영한다고 했지만 AWS 구조도에는 `EC2 기반 Web Application`만 표시돼 있어 아키텍처가 불일치한다.
- WAF·ALB·Application·DB 로그가 같은 `request_id`로 자동 연결되는 것은 아니다. ID 생성·전달·기록 방식을 직접 설계해야 한다.
- Trivy·kube-bench 결과는 assessment artifact이고 WAF·Application 로그는 runtime telemetry다. 같은 저장소에 넣더라도 성격을 구분해야 한다.
- AWS가 주요 환경인데 IAM, Resource Policy, 계정·권한 경계가 약하다.
- Terraform·CloudFormation 등 IaC가 없어 원본의 자동화·코드형 인프라 항목을 충족하지 못한다.
- 온프레미스와 AWS를 직접 연결하지 않으므로 하이브리드 사설망 항목을 충족한다고 볼 수 없다.

#### 정체성

현재 계획은 다음 성격에 가장 가깝다.

> 온프레미스·AWS 웹 AppSec 및 통합 로그 분석·재검증

## 5. 원본 3차 주제 충족도

원본은 첫 줄을 포함하면 18줄이고, 첫 줄을 제목으로 보면 17개 세부 항목이다. 첫 줄의 역할은 원문만으로 확정할 수 없다.

아래 숫자는 성적이 아니라 `직접 충족 / 부분 충족 / 미포함`을 기계적으로 분류한 참고치다.

| 계획 | 직접 충족 | 부분 충족 | 미포함 | 해석 |
|---|---:|---:|---:|---|
| 운호 | 8 | 4 | 6 | 표면적은 좁지만 IAM·로그·조치 항목은 깊다 |
| 타조 | 7 | 6 | 5 | EKS·IAM·탐지는 강하지만 조치·데이터 보호가 약하다 |
| 우수현 | 9 | 4 | 5 | 웹·네트워크·로그·재검증을 가장 넓게 다룬다 |

이 공통 공백을 무조건 추가해야 한다는 뜻은 아니다. 원본의 모든 항목이 필수인지 선택 가능한 상위 영역인지 먼저 확인해야 한다.

## 6. Claude 평가 교차검증

### 유지한 판단

- 타조안의 `컨테이너 탈출`과 실제 시나리오가 불일치한다.
- 타조안의 RDS 데이터 접근 주장은 조건이 빠져 있다.
- 타조안은 조치 후 재검증이 누락됐다.
- 우수현안은 IaC가 빠졌고 범위가 가장 넓다.
- 운호안은 자기 과장 방지, 통과 조건, 증적 설계가 가장 명시적이다.
- EKS Pod Identity를 비교 대상으로 검토할 가치가 있다.

### 보정하거나 기각한 판단

- 우수현안이 운호·타조안의 `상위 집합`이라는 평가는 기각한다. Kubernetes RBAC를 다루지만 IRSA·AWS workload IAM 공격 경로는 다루지 않는다.
- EKS Pod Identity 미사용을 운호안의 결함으로 보지는 않는다. IRSA를 선택한 이유가 있으면 된다.
- 타조안의 자동화·보안 설계를 `부분 충족`으로만 보는 것은 과소평가다. Terraform 모듈화를 명시했으므로 해당 항목은 강하다.
- 출처 확인일 누락은 문서 품질 보완 사항이지만 계획 우열을 바꾸는 핵심 결함은 아니다.

## 7. 실행 가능성 참고

이 항목은 종합 평가에서 가장 낮은 가중치를 가진다.

- 운호안: 가장 작게 닫혀 있고 P0·P1과 축소안이 있다.
- 타조안: 문서 자체가 8주 일정이며, 분석 도구와 공격 범위를 줄일 필요가 있다.
- 우수현안: 구축·웹앱·진단·로그 파이프라인·Kubernetes를 모두 수행하므로 범위 확장 위험이 가장 크다.

## 8. 현재 확정할 수 있는 것

1. 운호안은 `범위 통제·증적·조치 후 재검증` 기준에서 가장 완결돼 있다.
2. 이 판정은 모의해킹 기술의 난도나 공격 깊이가 가장 높다는 뜻이 아니다.
3. 우수현안은 원본 주제를 가장 넓게 수용하지만 핵심 질문과 클라우드 고유 보안이 약해질 수 있다.
4. 타조안은 공격 서사가 가장 강하지만 용어·권한 경로·재검증을 먼저 교정해야 한다.
5. 세 계획을 모두 합치면 장점이 합쳐지는 것이 아니라 범위가 다시 통제 불가능해질 가능성이 높다.
