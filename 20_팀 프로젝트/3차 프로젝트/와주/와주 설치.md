# Wazuh 설치

## 설치 목표

프로젝트의 AWS 로그를 한곳에서 검색·분석하고 탐지 규칙을 적용하기 위해 로컬 Docker 환경에 Wazuh 중앙 구성요소를 설치한다.

이번 단계에서는 고가용성 구성이 아닌 **Single-node stack**을 사용한다. 한 대의 Docker 호스트에서 다음 세 구성요소를 각각의 컨테이너로 실행하는 방식이다.

- **Wazuh Manager**: 수집된 이벤트를 분석하고 탐지 규칙을 적용한다.
- **Wazuh Indexer**: 이벤트와 Alert를 저장하고 검색할 수 있게 색인한다.
- **Wazuh Dashboard**: 검색·분석·시각화를 제공하는 웹 화면이다.

AWS 로그 연결과 Shuffle SOAR 연동은 Wazuh 자체의 기동과 데이터 보존을 먼저 확인한 뒤 진행한다.

## 1. 공식 설치 방식 선택

Wazuh 설치 페이지에서 `Installation guide`로 이동했다.

![[Pasted image 20260812164915.png]]

`Installation alternatives → Deployment on Docker → Wazuh Docker deployment`를 선택했다. 프로젝트용 로컬 검증 환경이므로 여러 서버에 구성요소를 분산하는 Multi-node가 아니라, 한 호스트에서 중앙 구성요소 세 개를 실행하는 Single-node 절차를 따랐다.

![[Pasted image 20260812165046.png]]

## 2. 공식 Docker 구성 다운로드

```bash
git clone https://github.com/wazuh/wazuh-docker.git -b v4.14.7
```

- 설치 위치: `D:\Wazuh\wazuh-docker`
- 고정 버전: `v4.14.7`
- 확인된 체크아웃 커밋: `adcc5b5`

버전 태그를 직접 체크아웃했기 때문에 나타나는 `detached HEAD`는 정상이다. 애플리케이션 소스를 개발하려는 것이 아니라 동일한 Wazuh 구성을 재현하기 위해 특정 버전에 고정한 상태다.

출력 중 `refs/tags/v4.14.7 ... is not a commit` 경고가 있었지만, Git이 태그를 실제 공식 릴리스 커밋 `adcc5b5`로 해석하여 체크아웃을 완료했으므로 clone 실패로 판정하지 않았다.

## 3. 내부 통신용 인증서 생성

`single-node` 디렉터리에서 다음 명령을 실행했다.

```bash
cd wazuh-docker/single-node
docker compose -f generate-indexer-certs.yml run --rm generator
```

명령의 의미는 다음과 같다.

- `-f generate-indexer-certs.yml`: 기본 Compose 파일 대신 인증서 생성 전용 설정을 사용한다.
- `run generator`: 인증서 생성 서비스를 일회성으로 실행한다.
- `--rm`: 작업이 끝난 임시 컨테이너만 삭제한다. 호스트 폴더에 생성된 인증서는 남는다.

![[Pasted image 20260812171713.png]]

생성기는 Manager·Indexer·Dashboard 및 Filebeat가 서로 TLS로 통신할 때 사용할 인증서를 만들었다.

![[Pasted image 20260812171726.png]]

### 인증서 생성 결과 판정

출력에 `/wazuh-certs-tool.sh: line 636: find: command not found`가 표시됐다. 그러나 다음 경로에 인증서와 키 12개가 실제로 생성된 것을 확인했다.

```text
D:\Wazuh\wazuh-docker\single-node\config\wazuh_indexer_ssl_certs\
```

이후 세 중앙 구성요소가 해당 인증서를 사용해 정상 기동하고 Dashboard HTTPS 접속까지 성공했다. 따라서 이번 실행에서는 인증서 생성 결과를 유효한 것으로 판정하되, 재현 시 참고할 수 있도록 경고 문구는 기록으로 남긴다.

## 4. Wazuh Single-node 기동

```bash
docker compose up -d
```

Docker Compose가 Wazuh Manager·Indexer·Dashboard `v4.14.7` 이미지를 내려받고, 구성에 필요한 Network·영속 Volume·컨테이너를 생성한 뒤 백그라운드에서 실행했다.

![[Pasted image 20260812175513.png]]

이 명령은 공식 `docker-compose.yml`에 정의된 포트, 환경변수, 인증서 Mount, Network, Volume과 구성요소 간 연결 관계를 한꺼번에 적용한다. 개별 이미지를 Docker Desktop에서 따로 실행하지 않은 이유는 이 관계를 GUI에서 모두 수동으로 재현하면 누락 가능성이 커지기 때문이다.

## 5. Docker Desktop에서 실행 상태 확인

Docker Desktop의 `Containers` 화면에서 세 구성요소가 `single-node` Compose 애플리케이션으로 묶여 실행되는 것을 확인했다.

![[Pasted image 20260812180130.png]]

그룹을 펼쳐 Manager·Indexer·Dashboard의 실행 상태와 통합 로그를 확인했다. Indexer 로그에서는 Cluster Health가 `YELLOW`에서 `GREEN`으로 전환됐다.

![[Pasted image 20260812180843.png]]

초기 로그에는 구성요소 시작 순서로 인한 `ECONNREFUSED`와 이미 생성된 Index를 다시 만들면서 발생한 `resource_already_exists_exception`이 보였다. 그러나 이후 다음 근거가 연속으로 확인됐으므로 이번 실행의 치명적인 기동 실패로 판정하지 않았다.

- 세 컨테이너가 모두 계속 `Up` 상태를 유지했다.
- Indexer Cluster Health가 `GREEN`으로 전환됐다.
- Dashboard가 `https://0.0.0.0:5601`에서 실행됐다는 로그가 남았다.
- 브라우저에서 실제 로그인과 Dashboard 접속에 성공했다.

각 컨테이너의 호스트 포트 연결도 확인했다.

- **Indexer**: `9200:9200`
- **Manager**: `1514`, `1515`, `514/UDP`, `55000`
- **Dashboard**: 호스트 `443` → 컨테이너 `5601`

![[Pasted image 20260812181607.png]]

## 6. HTTPS 접속과 로그인

Docker Desktop의 포트 링크는 `http://localhost:443`으로 열려 `ERR_EMPTY_RESPONSE`가 발생했다. Dashboard 장애가 아니라 HTTPS 서비스에 HTTP로 접근한 것이 원인이었다.

다음 주소를 직접 입력해 로그인 화면에 접속했다.

```text
https://localhost
```

Wazuh가 생성한 자체 서명 인증서를 사용하므로 브라우저에 인증서 경고가 표시된다. 로컬 검증 환경임을 확인한 뒤 접속을 계속했다.

![[Pasted image 20260812182212.png]]

최초 로그인에는 공식 Docker 구성의 기본 관리자 계정을 사용했다.

- 초기 사용자: `admin`
- 초기 비밀번호: 공식 Docker 기본값 사용

> [!warning]
> 기본 비밀번호는 최초 접속을 위한 값이다. 외부에 노출되는 운영 환경에서는 공식 절차에 따라 변경해야 하며, 변경한 실제 비밀번호는 Obsidian·Git·스크린샷에 기록하지 않는다.

## 7. Dashboard 접속 확인

로그인 후 Wazuh Overview 화면에 접근했다. 이를 통해 Docker에서 실행된 Dashboard가 HTTPS 요청에 정상 응답하고, Dashboard·Indexer·Manager 간 연결이 실제 웹 UI 사용까지 이어지는 것을 확인했다.

![[Pasted image 20260812182642.png]]

화면에 `This instance has no agents registered`가 표시되는 것은 현재 단계에서 정상이다. 이번 프로젝트는 먼저 Wazuh Agent를 PC에 배포하는 것이 아니라, Wazuh Manager가 AWS 로그 원본을 읽도록 연결할 계획이다.

또한 초기 화면의 Alert 개수와 `Amazon Web Services` 메뉴는 Wazuh의 기본 화면 및 기능을 보여줄 뿐이다. **아직 프로젝트의 AWS 로그가 수집됐다는 증거는 아니다.** AWS 연동 완료 판정은 CloudTrail 등 실제 프로젝트 이벤트가 Wazuh에서 검색되고 원본 이벤트까지 추적되는지를 별도로 검증한 뒤 내린다.

## 8. AWS 로그 읽기용 최소 권한 Policy 작성

AWS Console의 `IAM → Policies → Create policy → JSON`에서 로컬 Wazuh 전용 Reader가 사용할 고객 관리형 Policy `aws-topology-wazuh-local-reader-policy`를 생성했다.

이 Policy의 의미는 다음과 같다.

- 프로젝트 Security Log S3 Bucket 전체가 아니라 **CloudTrail Prefix만** 목록 조회·Object 읽기를 허용한다.
- CloudWatch Logs는 **WAF와 Primary DVWA Log Group만** 조회할 수 있다.
- 로그 쓰기·수정·삭제와 다른 AWS Resource 접근은 허용하지 않는다.
- 첫 Runtime 검증에서는 CloudTrail만 연결하고, WAF·DVWA 권한은 이후 수집 범위를 확장할 때 사용한다.

> [!code]- 적용한 IAM Policy JSON 전문
> ```json
> {
>   "Version": "2012-10-17",
>   "Statement": [
>     {
>       "Sid": "ListCloudTrailPrefix",
>       "Effect": "Allow",
>       "Action": "s3:ListBucket",
>       "Resource": "arn:aws:s3:::aws-topology-security-logs-e10b7e4f152e9420159dba755d",
>       "Condition": {
>         "StringLike": {
>           "s3:prefix": [
>             "AWSLogs/433048100798/CloudTrail",
>             "AWSLogs/433048100798/CloudTrail/*"
>           ]
>         }
>       }
>     },
>     {
>       "Sid": "ReadCloudTrailObjects",
>       "Effect": "Allow",
>       "Action": "s3:GetObject",
>       "Resource": "arn:aws:s3:::aws-topology-security-logs-e10b7e4f152e9420159dba755d/AWSLogs/433048100798/CloudTrail/*"
>     },
>     {
>       "Sid": "DescribeApprovedLogStreams",
>       "Effect": "Allow",
>       "Action": "logs:DescribeLogStreams",
>       "Resource": [
>         "arn:aws:logs:us-east-1:433048100798:log-group:aws-waf-logs-aws-topology-edge:*",
>         "arn:aws:logs:ap-northeast-2:433048100798:log-group:/aws/eks/aws-topology-primary/dvwa:*"
>       ]
>     },
>     {
>       "Sid": "ReadApprovedLogEvents",
>       "Effect": "Allow",
>       "Action": "logs:GetLogEvents",
>       "Resource": [
>         "arn:aws:logs:us-east-1:433048100798:log-group:aws-waf-logs-aws-topology-edge:log-stream:*",
>         "arn:aws:logs:ap-northeast-2:433048100798:log-group:/aws/eks/aws-topology-primary/dvwa:log-stream:*"
>       ]
>     }
>   ]
> }
> ```

생성 결과 화면에서 허용 서비스가 CloudWatch Logs와 S3 두 개이며, 액세스 수준이 나열·읽기로 제한된 것을 확인했다.

### 장기 Credential Profile 인증 확인

로컬 Docker Wazuh가 반복적인 STS Session 갱신 없이 AWS 로그를 읽도록 전용 IAM User의 Access Key를 생성했다. 실제 Access Key와 Secret Access Key는 Obsidian·Git·Screenshot에 기록하지 않고, Git 밖의 전용 AWS Credential 파일에 `wazuh-reader` Profile로 저장했다.

> [!warning]
> 장기 Access Key 사용은 로컬 실습 편의를 위한 프로젝트 한정 절충안이다. `terra-user` Credential을 재사용하지 않고 읽기 권한만 가진 전용 User로 범위를 제한했으며, 프로젝트 종료 후 Access Key를 비활성화·삭제한다.

`aws sts get-caller-identity` 결과가 전용 IAM User ARN을 반환해 `wazuh-reader` Profile의 인증을 확인했다.

![[Pasted image 20260812202500.png]]

### 실제 CloudTrail Object 읽기 검증

첫 검증에서는 S3 Prefix와 동일한 0바이트 폴더 표시용 Object를 선택했다. 이 결과는 목록 조회와 해당 빈 Object 접근만 증명하므로 실제 CloudTrail 로그 읽기의 최종 Evidence로 사용하지 않았다.

> [!note]- 처음 수행한 0바이트 Object 검증
> 반환된 Key가 `AWSLogs/433048100798/CloudTrail/`에서 끝나고 `Size`가 `0`이므로 실제 CloudTrail 로그 파일이 아니다.
>
> ![[Pasted image 20260812203005.png]]

검증 대상을 `ap-northeast-2` 경로의 최신 `*.json.gz` 파일로 보정했다. 실제 CloudTrail Object Key가 출력됐고 `head-object`가 `Size: 6837`을 반환했다. 이를 통해 전용 Reader의 CloudTrail Prefix `ListBucket`과 실제 Object `GetObject` 권한이 Runtime에서 모두 작동함을 확인했다. Object 내용은 내려받거나 수정하지 않았다.

![[Pasted image 20260812203308.png]]

### Credential 파일을 Wazuh Manager에 Read-only로 연결

Git 밖에 저장한 `wazuh-reader` Credential 파일을 Wazuh Manager의 `/root/.aws/credentials`에 Bind Mount하도록 `docker-compose.yml`의 `wazuh.manager.volumes`에 설정을 추가했다. `read_only: true`로 Container의 쓰기를 막고, `create_host_path: false`로 Host 파일이 없을 때 Docker가 같은 이름의 디렉터리를 자동 생성하지 않게 했다.

![[Pasted image 20260812204207.png]]

변경 사항을 적용하기 위해 전체 Stack이 아니라 Wazuh Manager 하나만 재생성했다. `--no-deps`로 Indexer·Dashboard 재생성을 막았으며 기존 Named Volume은 삭제하지 않았다.

```powershell
docker compose up -d --no-deps --force-recreate wazuh.manager
```

![[Pasted image 20260812204438.png]]

Manager 재생성 뒤 `docker inspect`로 실제 Container Mount를 확인했다. 출력의 `RW=false`와 `Type=bind`는 Credential 파일이 Bind Mount로 연결됐고 Container에서 쓸 수 없음을 의미한다. 이어서 파일 내용을 출력하지 않고 `wazuh-reader` Profile Header가 읽히는지만 확인했다.

![[Pasted image 20260812204718.png]]
![[Pasted image 20260813101246.png]]

3. 수집된 이벤트가 있는 상태에서 Docker를 정지·시작해 Credential Mount와 Wazuh 데이터가 유지되는지 검증한다.

> [!danger]
> Docker Desktop의 정지·시작은 컨테이너와 Volume을 삭제하지 않는다. 반면 `docker compose down -v` 또는 Volume 삭제는 Wazuh의 저장 데이터를 제거할 수 있으므로 초기화를 의도한 경우가 아니면 사용하지 않는다.
