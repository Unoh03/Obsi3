# 작업 설계 스킬 회고

2026-11-25~26에 [[00_index/투두 리스트|투두 리스트]]의 **핸드오프 회고 및 AI 플랜 기능 확장 개발 계획**을 진행했다. [[20_팀 프로젝트/Agent Handoff/HANDOFF_SKILL_DRAFT_v0.2|Agent Handoff v0.2 초안]]을 다시 읽고, 그때 정리한 질문을 작업 설계에도 적용할 수 있는지 검토했다. 그 결과 Codex에서 쓸 `work-design` 스킬을 만들었다.

## 핸드오프에서 가져온 원칙

플랜은 앞으로 할 일을 정할 때 쓰고, 핸드오프는 다른 세션이나 에이전트가 작업 상태를 복원해야 할 때 쓴다. 메이플 계산기에서는 인수인계문을 받은 뒤 계산 기준을 정하고 플랜을 세웠다. 두 작업은 쓰이는 계기가 다르고, 다음 판단에 필요한 목표·결정·근거를 선별하는 방법을 공유한다.

- **목적과 결정의 이유를 보존한다.** 사용자에게 어떤 결과가 필요한지는 `INTENT`에, 그 결과를 위해 특정 방법을 선택한 이유는 `DECISIONS`에 담는다. 사용자 확정 사항과 AI 제안도 구분한다.
- **작업 범위, 도구 가용성, 실행 권한을 따로 확인한다.** 적합한 도구를 찾았더라도 대상 환경에서 쓸 수 있는지와 설치·사용 권한이 있는지는 별도 판단이다.
- **진행 상태와 확인 수준을 구분한다.** 구현 상태, 관찰한 결과, 추론은 각각 다른 정보다. `EVIDENCE`는 관찰한 근거와 확인 예정인 근거를 담고, `DONE`은 어떤 결과를 보면 완료인지 정한다. `FIRST ACTION`은 현재 상태에서 실제로 시작할 행동을 가리킨다.

설계 질문은 선행 결정부터 다루고, 자료를 읽어 확인할 수 있는 사실은 에이전트가 먼저 찾는다. 플랜의 구성과 단계가 실행 성과에 영향을 줄 수 있고, 작은 변경에 과도한 명세가 붙으면 검토 비용이 늘어날 수 있다는 조사 결과도 참고했다. ## 육하원칙과 10개 필드

| 질문 | 작업을 설계할 때 확인할 내용 | 연결되는 필드 |
|---|---|---|
| 무엇을 | 사용자에게 필요한 결과와 산출물, 바꿀 대상은 무엇인가? | `INTENT`, `SCOPE` |
| 왜 | 이 결과가 어디에 필요하고, 중요한 방법을 고른 이유는 무엇인가? | `INTENT`, `DECISIONS` |
| 누가 | 누가 결정하고 실행하는가? 사용자 판단이나 별도 승인이 필요한가? | `DECISIONS`, `CONSTRAINTS`, 필요할 때 `HOW` |
| 어디서 | 기준 자료는 어디에 있고, 어떤 환경에서 접근하고 실행할 수 있는가? | `INPUTS & ASSETS`, `CURRENT STATE` |
| 언제 | 현재 어디까지 왔고, 어떤 선행조건이 갖춰져야 시작하거나 다음 단계로 넘어가는가? | `CURRENT STATE`, `FIRST ACTION`, `HOW` |
| 어떻게 | 문제를 어떤 방식과 도구로 풀고, 어떤 결과를 확인해 완료로 판단하는가? | `HOW`, `FIRST ACTION`, `EVIDENCE`, `DONE` |

육하원칙은 빠진 판단을 찾는 질문으로 쓴다. `work-design`은 결과에서 v0.2의 10개 필드 이름과 순서를 사용한다. ‘누가’의 일부는 현재 `DECISIONS`와 `CONSTRAINTS`에 들어 있다. 실행 담당자나 검증 담당자가 실제로 갈리는 작업에서는 그 역할까지 적을 가치가 있다.

**도구 선택의 예**로, 메이플 아티팩트 계산기에서는 AP 예산과 크리스탈 옵션을 정수 제약 최적화로 표현했다. 입력·모델·출력은 Python이 맡고, 최적 배치 탐색은 OR-Tools의 CP-SAT이 맡았다. 이 사례에서 `HOW`가 담아야 할 것은 언어와 도구 이름, 각 도구의 역할이다. `DECISIONS`에는 그 엔진이 조건과 우선순위를 처리하기에 적합한 이유를 남긴다. ## 구현 선택과 서비스별 적용

처음에는 `/plan`의 출력 형식을 사용자 `AGENTS.md`에 추가하는 안을 검토했다. 사용자는 상시 지침의 토큰 비용을 지적하고, 연구한 필드로 작업을 설계하는 스킬이 목적이라고 범위를 바로잡았다. **스킬을 사용하는 요청에서** 일반 대화와 Plan Mode에 같은 설계 절차를 적용하도록 구현했다. 중간 질문은 대화로 이어가고, 설계 결과를 제시할 때 10행 표를 한 번 넣는다. `HOW`에는 구현 언어와 핵심 도구·엔진의 역할을 명시하며, 미정이면 선택 기준을 적는다.

| 서비스 | 2026-11-25에 검토한 적용 형태 | 작업 상태 |
|---|---|---|
| Codex | 사용자 스킬로 일반 대화와 `/plan`에서 사용. 저장소에서 공유할 때는 `.agents/skills/` 경로를 사용할 수 있다. | 로컬 `work-design`과 Work 등록용 ZIP을 제작했다. [Codex Plan Mode](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex) · [스킬 경로](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills) |
| Claude Code | Plan Mode의 탐색·검토 과정에 프로젝트의 `.claude/skills/` 지침을 결합하는 안. | 공식 문서로 적용 후보를 확인했다. [Plan Mode](https://code.claude.com/docs/en/permission-modes#analyze-before-you-edit-with-plan-mode) · [스킬](https://code.claude.com/docs/en/skills) |
| Google Antigravity | `.agents/skills/`에서 공통 지침을 불러오고 `/plan`의 `Implementation Plan`을 작성할 때 적용하는 안. | 공식 문서로 적용 후보를 확인했다. [플랜](https://antigravity.google/docs/plan/) · [스킬](https://antigravity.google/docs/skills) |

첫 구현은 지침과 표시 이름만 담은 스킬로 충분했다. 플러그인은 여러 스킬을 묶어 배포하거나 외부 도구를 연결할 필요가 생길 때 검토할 형태로 남겼다. Work Cloud는 지원 계정에서 ZIP을 따로 올릴 수 있고, Codex Cloud는 연결된 저장소에 들어 있는 스킬을 사용할 수 있다. ## 확인 범위와 이후 관찰

- **확인한 결과** — 로컬 `~/.codex/skills/work-design/`에 `SKILL.md`와 `agents/openai.yaml`을 만들었다. 필드 순서와 출력 규칙을 파일에서 대조했고, 다운로드 폴더의 `work-design.zip`에 두 파일이 원본과 같은 SHA-256으로 들어 있는 것을 확인했다.
- **남은 확인** — 스킬을 실제로 호출했을 때의 설계 품질, 표 출력, Work 업로드·활성화, Claude Code·Antigravity에서의 조합 동작은 미검증이다. 비교 실험은 이번 범위에서 보류하기로 했고, 실제 다른 투두에서 스킬을 사용하며 확인하기로 했다.
- **실사용에서 볼 것** — 사소한 요청에 스킬이 실제로 자동 선택됐는지, 선택한 도구의 이유가 문제 조건으로 설명되는지 본다. Codex의 자동 선택은 기본적으로 허용된다. CP-SAT 예시가 다른 문제에서도 선택을 끌어당긴다는 건 아직 가설이다. [Codex 호출 정책](https://learn.chatgpt.com/docs/build-skills#optional-metadata)

Claude 교차 검토 때는 GitHub 클론에 CP-SAT 사례가 없고 로컬 미커밋 연구 로그에만 있는 상태였다. 회고·육하원칙 대응·3사 검토 결과도 대화에 흩어져 있었다. 이 기록은 볼트에서 그 결정과 확인 범위를 다시 찾기 위해 남긴다.
