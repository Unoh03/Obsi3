# Agent Handoff 연구 로그

## 2026-09-20 — Handoff 개념 학습 및 10-field Schema 1차 공격

### 1. 현재까지의 핵심 정의

현재 연구 단계에서 Agent handoff는 단순한 대화 요약이 아니라 다음과 같이 본다.

> **다른 세션 또는 Agent가 진행 중인 작업을 올바른 상태에서 이어받을 수 있도록 현재 실행 상태를 외부화하여 전달하는 state transfer.**

핵심은 과거 설명이 아니라 **continuation 가능성**이다.

정신 모델:

Producer Agent → serialize → Handoff State → deserialize → Receiving Agent → correct execution state에서 재개

따라서 HANDOFF는 Markdown 문서 자체보다 **Agent-to-Agent interface / task-state interchange format**에 가깝게 본다.

---

### 2. 인접 개념과의 현재 구분

#### Summary
- 질문: 지금까지 무슨 일이 있었는가?
- 과거 설명 중심.
- 좋은 summary라도 다음 실행 상태가 복원된다는 보장은 없음.

#### Compaction
- 같은 작업 context를 줄여 계속 사용하기 위한 압축.
- Handoff는 fresh agent/session이 이어받는 것을 전제로 함.

#### Checkpoint
- 현재 상태 snapshot.
- branch, HEAD, test status, phase 등은 보존하지만 의도·결정 이유·다음 행동이 부족할 수 있음.
- 현재 가설: checkpoint는 handoff의 일부가 될 수 있지만 둘은 동일하지 않음.

#### Task Brief
- 작업 시작 전 objective, scope, requirements, constraints, acceptance criteria를 정의.
- Handoff는 작업 진행 중 새로 생긴 실제 상태·결정·blocker까지 포함.

#### Runbook
- 반복 가능한 일반 절차.
- Handoff는 특정 작업 instance의 현재 상태.
- HANDOFF는 필요한 runbook을 참조할 수 있지만 복제해서는 안 됨.

#### Memory / AGENTS.md
- 장기적으로 재사용할 지속 정보·규칙.
- Handoff는 현재 특정 task의 일시적 실행 상태.
- HANDOFF가 persistent policy를 복제하지 않도록 역할 분리가 필요.

### 3. 현재 발견한 최소 상태 범주 후보

10개 section보다 한 단계 추상적인 상태 종류로 다음 5개가 보인다.

1. Intent State — 왜 하는가 / 무엇을 달성하려는가
2. Execution State — 지금 어디까지 왔는가 / 무엇이 존재하는가
3. Decision State — 무엇을 왜 결정했는가 / 무엇을 버렸는가
4. Verification State — 무엇이 실제로 검증됐는가 / 무엇이 아직 주장·가정인가
5. Continuation State — 다음 Agent가 어디서 어떻게 시작해야 하는가

현재 10-field schema를 이 관점으로 재배치하면:

- Intent → WHY, GOAL
- Execution → CURRENT STATE, SCOPE, INPUTS & ASSETS, HOW, CONSTRAINTS
- Verification → EVIDENCE, DONE
- Continuation → FIRST ACTION

여기서 **Decision State가 기존 top-level 10개에는 명시적으로 없다**는 점을 발견했다.

---

### 4. DECISIONS 개선 후보 — 강하게 채택

사용자도 DECISIONS의 중요성에 전적으로 동의.

현재 개선 후보:

- DECISIONS를 더 강하게 승격하여 취급.
- 최소한 중요한 결정에 대해 selected approach / rejected alternative / why selected / why rejected를 보존.
- 단순 HOW보다 결정 이유가 더 복구하기 어려운 정보일 수 있음.

이유:

HOW 자체는 후속 Agent가 source를 보고 다시 계산할 수 있을 수 있지만, 다음과 같은 과거 판단 맥락은 원래 대화가 사라지면 복구가 어렵다.

- 왜 특정 scraping 방식을 버렸는가
- 왜 Push와 Poll을 공존시켰는가
- 왜 특정 자동화 경로를 제한했는가

향후 공격 대상:

> DECISIONS를 top-level로 승격할 것인가, 아니면 CURRENT STATE/HOW 아래 강제 subsection으로 둘 것인가?

아직 최종 결정하지 않음.

### 5. HOW에 대한 새 관찰 — Tool / Plugin Acquisition Authority

사용자는 Maple script 작업 중 다음과 같은 추가 지시를 별도로 준 경험이 있음.

> 필요한 경우 Tool이나 Plugin을 적극적으로 설치하거나 요청해도 된다.

이 기억은 HOW가 단순한 실행 절차만으로 충분하지 않을 수 있음을 시사한다.

현재 가능한 해석 후보:

#### 후보 A — HOW 내부
- preferred tools
- allowed acquisition of missing tools/plugins
- execution strategy

#### 후보 B — CONSTRAINTS / AUTHORITY
- may install local tools
- may request plugin connection
- may not change external state without approval

#### 후보 C — INPUTS & ASSETS / CAPABILITIES
- currently available tools
- may obtain additional tools if needed

현재 판단:

- 어떤 툴을 쓸 것인가는 HOW에 가깝다.
- 없는 툴을 설치/요청할 권한이 있는가는 HOW라기보다 **authority/capability boundary**에 더 가까울 가능성이 있다.
- 아직 새 top-level field를 추가하지 않는다.
- 이후 공개 handoff 패턴에서 tool availability, permissions, authority가 어떻게 모델링되는지 조사한다.

이 항목은 **사용자 경험에서 나온 실제 failure/overhead 사례**이므로 향후 schema 검증에서 우선순위를 높인다.

### 6. 기존 10개 필드 1차 공격 결과

| Field | Current assessment | Main question |
|---|---|---|
| WHY | Strong keep candidate | Small tasks may overlap with GOAL |
| GOAL | Strong keep candidate | Boundary with WHY needs sharper definition |
| CURRENT STATE | Core | Needs epistemic typing |
| SCOPE | Strong keep candidate | Strong task-brief characteristic |
| INPUTS & ASSETS | Useful | May need Source of Truth vs Dependencies distinction |
| HOW | Re-evaluate | Too rigid may reduce Agent adaptability; tool authority issue emerged |
| CONSTRAINTS | Near-core | Avoid duplication with AGENTS.md; may need authority semantics |
| EVIDENCE | Strong candidate | May be optional for trivial tasks |
| DONE | Strong candidate | Relationship with acceptance criteria needs review |
| FIRST ACTION | Useful but under attack | Could potentially merge into NEXT / CURRENT STATE |
| DECISIONS | Missing/underrepresented | Strong candidate for promotion |

Important distinction:

> The concepts may all be useful even if they do not all deserve top-level fields.

### 7. WHY the original 10-field draft looked strong

The original schema covered the full continuation loop rather than only task description.

- WHY → intent
- GOAL → target result
- CURRENT STATE → current position
- SCOPE → task boundary
- INPUTS & ASSETS → starting material / search-space reduction
- HOW → selected execution strategy
- CONSTRAINTS → forbidden or protected action space
- EVIDENCE → observations required for judgment
- DONE → acceptance predicate over evidence
- FIRST ACTION → resume point

This creates a nearly closed chain: **Intent → Execution → Verification → Continuation**.

The strong points were not that 10 is a good number, but explicit intent preservation, state checkpointing, scope control, source/search-space narrowing, rationale-aware execution, safety/authority boundaries, evidence-based verification, explicit acceptance conditions, and low resume latency.

Additional strong rules:

- preserve WHAT + WHY
- separate FACT / VERIFIED or OBSERVED / ASSUMPTION / PLAN

These turn the schema from a formatting template into a possible state-transfer protocol.

### 8. Versioning Policy for the Draft

현재 연구 단계의 결정:

#### Preserve the current baseline
- HANDOFF_SKILL_DRAFT.md는 deeper study 이전에 만든 원본 baseline으로 그대로 보존한다.

#### Use Git history for fine-grained change tracking
- commit/diff는 개별 수정의 권위 있는 변경 이력으로 사용한다.

#### Use explicit versioned copies for meaningful design revisions
- schema 또는 설계 철학이 의미 있게 바뀔 때만 HANDOFF_SKILL_DRAFT_v0.2.md, v0.3.md 같은 복사본을 만든다.
- 단순 문구 수정마다 새 버전을 만들지는 않는다.

목적:

- Git은 '어느 줄이 어떻게 변했는가?'에 강하다.
- versioned draft는 '중요 시점의 설계안들이 어떻게 달랐는가?'를 나란히 비교하기 쉽다.

위험:

- 중복 문서가 stale해질 수 있음.
- 어느 것이 현재 후보인지 혼동될 수 있음.
- 버전이 너무 많으면 noise가 됨.

완화:

- MOC에서 baseline / current candidate를 명확히 표시한다.
- 의미 있는 설계 변경에만 버전을 만든다.
- 연구가 안정되면 HANDOFF_SKILL_SPEC.md 같은 별도 canonical final spec을 만든다.

이 방식은 Git과 일부러 중복된다. 목적이 revision recovery가 아니라 **human conceptual comparison**이기 때문이다.

### 9. Current Research Questions Added Today

- Is DECISIONS important enough to become a top-level field?
- Should HOW describe an execution plan, preferred strategy, or merely known decisions?
- Where should tool/plugin installation or acquisition authority live?
- Should AUTHORITY / CAPABILITIES be explicit?
- Should trivial tasks be allowed to omit EVIDENCE or other low-value sections while preserving a stable schema?
- Is FIRST ACTION truly distinct from NEXT STEP?
- What information is hardest to reconstruct after session loss, and should schema priority be based on reconstruction cost?
- Can the schema be evaluated by actual continuation cost rather than document completeness?
